# 05 工具系统与文件修改

Agent 的价值在于改变工作区，而不是只生成建议。Codex 将命令、文件修改、搜索和外部服务都建模为工具，并通过统一的审批、执行和结果回传流程控制它们。

## 工具调用闭环

```text
模型提出 tool call
  -> 解析参数与目标资源
  -> 执行策略 / 审批判断
  -> 沙箱内运行
  -> 收集 stdout、stderr、文件变化
  -> 截断并结构化
  -> 回传模型继续决策
```

## Shell 与统一执行

`codex-rs/exec` 提供非交互执行入口，`core/src/exec.rs` 负责在 Agent 循环中组织执行，`exec-server` 将进程启动、PTY、退出码和流式输出封装为服务。命令需要考虑 shell 类型、工作目录、环境变量、信号、超时和平台差异。

## apply_patch

`apply_patch` 不是简单的字符串替换。它解析文件路径、上下文和增删块，检查目标文件是否符合预期，再以可审查的 diff 形式应用。失败时应报告上下文不匹配，而不是静默覆盖用户修改。

## 输出治理

测试日志可能远超上下文预算，因此工具结果需要按字节和行数截断，保留退出码、错误尾部和关键匹配。长 diff 应支持摘要和定位；敏感环境变量、token 和密钥不得进入模型上下文或日志。

## 源码入口

- `codex-rs/core/src/tools`：工具定义和调用
- `codex-rs/core/src/apply_patch.rs`：补丁解析与应用
- `codex-rs/exec`：exec CLI
- `codex-rs/exec-server`：进程执行服务
- `codex-rs/file-search`、`file-system`：文件能力

## 6. 工具 schema 如何影响模型行为

工具描述不仅是类型声明，也是模型的操作边界。名称应表达动作，参数要有明确的必填和枚举约束，描述中要说明路径基准、破坏性和返回值。过于宽泛的 `run_command(command: string)` 会让模型难以判断风险，也让审批界面无法展示影响范围。

## 7. Shell 执行的工程细节

执行器必须固定 cwd，明确是否继承环境变量，区分 shell 内建命令和可执行文件，并设置 stdout/stderr 上限。长时间命令需要发送取消信号并回收子进程；Windows、Unix 和 WSL 的引号、路径和信号语义不同，不能只在 Linux 上拼接字符串测试。

## 8. Patch 的安全性

补丁应用前应检查路径是否位于允许根目录、目标文件版本是否匹配、是否出现二进制或符号链接边界。应用后最好重新读取变更文件并生成 diff，确保模型看到的结果与磁盘事实一致。冲突时保留用户修改优先于“尽力合并”。

## 9. 结果如何反馈

工具结果至少包含工具名、退出码、是否超时、工作目录、输出摘要和错误分类。模型需要知道命令是失败、被拒绝还是被取消；用户需要知道是否真的写入了文件。将这三类状态混成一段文本会导致错误修复。

## 10. 新增工具的检查清单

- 明确 schema、权限范围和是否需要审批。
- 为成功、参数错误、超时、取消和外部服务失败定义结果。
- 限制输出大小并脱敏敏感字段。
- 覆盖 Unix、Windows 或远程执行环境的差异。
- 测试模型拒绝、用户拒绝、工具失败和重复调用。
