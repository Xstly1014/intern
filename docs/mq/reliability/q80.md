# Q80 消息重复根因

Kafka 消息重复的根因在于分布式系统中"至少一次送达"的默认语义——网络不可靠、进程可能随时宕机、ACK 可能丢失，导致 Producer 或 Broker 在不确定消息是否成功时选择重试，而 Consumer 在 offset 提交失败时只能重新消费。完全避免重复需要分布式事务，代价极高，因此业务幂等是性价比最高的解法。

## 四种避免重复的代码分层

### Layer 1 — 幂等生产者配置（解决 Producer 侧重试重复）

```java
// KafkaProducer 配置 — 启用幂等生产者
// enable.idempotence=true 会自动设置 acks=all, retries=MAX_INT, max.in.flight.requests.per.connection<=5
@Configuration
public class KafkaProducerConfig {
    @Bean
    public ProducerFactory<String, OrderEvent> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, JsonSerializer.class);

        // 核心配置：启用幂等生产者
        // Producer 会为每条消息分配 <PID, sequence number>，
        // Broker 按 sequence number 去重，保证同一 PID 下消息不重复
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

        // 幂等生产者隐式设置 acks=all，确保 ISR 全部确认
        // 幂等生产者隐式设置 max.in.flight.requests.per.connection=5，保证顺序
        return new DefaultKafkaProducerFactory<>(props);
    }
}
```

`enable.idempotence=true` 是 Producer 侧消除重复的第一道防线——Broker 根据 Producer ID + sequence number 自动去重，零业务侵入。但它只覆盖 Producer 到 Broker 这一段，无法解决 Consumer 侧重复。

### Layer 2 — 业务幂等实现（解决 Consumer 侧重消费重复）

```java
// 方案 A: 数据库唯一键去重 — INSERT IGNORE
// 适合 MySQL/PG，利用数据库唯一约束天然去重
@Service
public class OrderDeduplicationService {

    @Transactional
    public void processOrder(OrderEvent event) {
        // INSERT IGNORE: 唯一键冲突时静默跳过，返回 affected rows=0
        // 无需额外查询，性能最优
        jdbcTemplate.update(
            "INSERT IGNORE INTO order_processed (order_id, event_id, processed_at) VALUES (?, ?, NOW())",
            event.getOrderId(), event.getEventId()
        );
        // 只有首次插入成功才执行业务逻辑
        // 实际可用 affected rows 判断，为0则跳过
    }
}

// 方案 B: Redis SETNX — 分布式去重
// 适合高并发、无需持久化的场景
@Component
public class RedisDedupFilter {
    @Autowired
    private StringRedisTemplate redis;

    public boolean isDuplicate(String eventId, long ttlSeconds) {
        // SETNX 原子操作：key 不存在则设置并返回 true，存在则返回 false
        Boolean success = redis.opsForValue()
            .setIfAbsent("dedup:" + eventId, "1", Duration.ofSeconds(ttlSeconds));
        return !Boolean.TRUE.equals(success); // true=重复
    }
}

// 方案 C: 乐观锁 — 状态机判断
// 适合订单/工作流等有明确状态流转的场景
@Service
public class OrderStateMachine {
    @Transactional
    public void pay(OrderEvent event) {
        // UPDATE 带版本号或状态条件，WHERE 条件不满足时 affected rows=0
        int rows = jdbcTemplate.update(
            "UPDATE orders SET status='PAID', version=version+1 " +
            "WHERE order_id=? AND status='PENDING'",
            event.getOrderId()
        );
        if (rows == 0) {
            // 状态已变更，重复消息直接丢弃
            log.warn("Duplicate or invalid state transition: {}", event.getOrderId());
        }
    }
}
```

业务幂等是解决重复问题最根本的手段。它覆盖全部四种根因场景，不依赖 Kafka 内部机制。DB 唯一键适合持久化场景，Redis SETNX 适合高吞吐临时去重，乐观锁适合有状态流转的业务。

### Layer 3 — 事务消费（消费 + 处理 + offset 提交原子化）

```java
// Kafka 事务消费：将消息处理与 offset 提交绑定在同一个事务中
// 适用场景：消费 Kafka → 写入 DB，然后提交 offset 必须原子化
@Configuration
public class TransactionalConsumerConfig {

    @Bean
    public KafkaListenerContainerFactory<?> transactionalFactory(
            ConsumerFactory<String, String> consumerFactory,
            KafkaTemplate<String, String> kafkaTemplate) {

        ConcurrentKafkaListenerContainerFactory<String, String> factory =
            new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(consumerFactory);

        // 核心：设置事务隔离级别为 read_committed
        // Consumer 只消费已 commit 的事务消息，跳过未 commit 的
        factory.getContainerProperties().setSubBatchPerRecordWithPartition(true);

        return factory;
    }
}

@Component
public class TransactionalOrderConsumer {

    @Autowired
    private JdbcTemplate jdbc;

    @Transactional  // Spring 管理事务
    @KafkaListener(topics = "order-topic", groupId = "order-group")
    public void consume(ConsumerRecord<String, OrderEvent> record,
                        Acknowledgment ack) {
        // ① 处理业务：写入 DB
        jdbc.update("INSERT INTO orders (order_id, amount) VALUES (?, ?)",
            record.value().getOrderId(), record.value().getAmount());

        // ② 处理成功 → 手动确认 offset
        // 如果此处抛异常，Spring 回滚 DB + offset 不提交 → 消息重新投递
        ack.acknowledge();

        // ③ 若步骤①成功但步骤②前宕机 → offset 未提交 → 重启后重新消费
        //    此时需要 Layer 2 的业务幂等兜底 (INSERT IGNORE)
    }
}
```

事务消费将"处理 + 提交 offset"包裹在同一事务中，大幅缩小重复窗口。但仍然无法覆盖"DB 写入成功但 offset 提交前宕机"的极端情况——这正是 Layer 2 业务幂等兜底的价值。

### Layer 4 — Rebalance 优化配置（减少 Rebalance 触发频率）

```java
// Consumer 配置 — 减少不必要的 Rebalance
@Bean
public Map<String, Object> consumerConfigs() {
    Map<String, Object> props = new HashMap<>();
    props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
    props.put(ConsumerConfig.GROUP_ID_CONFIG, "order-group");

    // ① session.timeout.ms: Consumer 与 Coordinator 之间的心跳超时
    //    默认 45s，适当调大避免短暂网络问题触发 Rebalance
    props.put(ConsumerConfig.SESSION_TIMEOUT_MS_CONFIG, 30000); // 30s

    // ② heartbeat.interval.ms: 心跳发送间隔
    //    建议设为 session.timeout.ms 的 1/3
    props.put(ConsumerConfig.HEARTBEAT_INTERVAL_MS_CONFIG, 10000); // 10s

    // ③ max.poll.interval.ms: 两次 poll 之间的最大间隔
    //    如果消息处理时间超过此值，Consumer 被认为"卡死"并触发 Rebalance
    //    根据业务最长处理时间调大
    props.put(ConsumerConfig.MAX_POLL_INTERVAL_MS_CONFIG, 600000); // 10min

    // ④ max.poll.records: 每次 poll 拉取的最大消息数
    //    减小批次大小，让 poll 更频繁，避免处理时间过长
    props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 100);

    // ⑤ enable.auto.commit: 关闭自动提交，改为手动提交
    props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);

    return props;
}
```

合理配置 Consumer 参数可以显著减少 Rebalance 频率，从而降低因分区重新分配导致的重复消费。这是辅助手段，不能替代业务幂等。

## 四种避免重复方案对比

| 方案 | 作用机制 | 覆盖的重复场景 | 业务侵入性 | 性能代价 | 推荐度 |
|---|---|---|---|---|---|
| 业务幂等 (DB唯一键) | INSERT IGNORE / 状态机 / 乐观锁，重复消息被业务逻辑静默忽略 | Producer重试 / Offset提交 / Rebalance / 网络抖动 — 全部四类 | 中 (需设计去重键或状态字段) | 低 (一次索引查询) | 最优先 |
| 业务幂等 (Redis SETNX) | 分布式锁/去重标记，首次处理设置标记 | 全部四类 | 低 (加一层 Filter) | 极低 (内存操作) | 高并发首选 |
| 幂等生产者 enable.idempotence | Broker 按 <PID, seq> 去重 | 仅 Producer 重试导致的重复 | 零 (配置文件改一行) | 极低 (内存比对) | 必开 |
| 事务消息 | 消费→处理→offset提交原子化，read_committed 隔离 | Offset 提交问题 (缩小窗口) / Producer 重复 | 中 (事务 API 改造) | 中等 (事务日志开销) | 业务事务场景 |
| Rebalance 参数调优 | 减少不必要的 Group 重平衡 | Rebalance 触发频率降低 (不根除) | 零 | 零 | 辅助 |

## 一句话总结

**消息重复无法 100% 避免，因为分布式系统中"不确定"是常态——真正可靠的方案不是阻止重复发生，而是让系统对重复消息免疫：幂等生产者挡 Producer 侧，业务幂等兜 Consumer 侧，前者零成本必开，后者是最终防线。**
