# Q74 min.insync.replicas

min.insync.replicas 定义了 Producer 设置 acks=all 时，一条消息必须被多少个 ISR（In-Sync Replica）副本成功写入才算提交成功。它是在 TP 可靠性核心三角（replication.factor + min.insync.replicas + acks=all）中保证"至少 N 个副本落地"的那把锁。

## min.insync.replicas 代码实践

### Layer 1 — min.insync.replicas 配置

```java
// ============ Topic 级别配置（推荐，精确控制） ============
// --- 方式一：创建 Topic 时指定 ---
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders \
  --partitions 3 \
  --replication-factor 3 \
  --config min.insync.replicas=2

// --- 方式二：动态修改已有 Topic ---
kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic orders \
  --config min.insync.replicas=2

// --- 查看 Topic 配置 ---
kafka-configs.sh --bootstrap-server localhost:9092 \
  --describe --topic orders --all | grep min.insync


// ============ Broker 级别配置（全局默认） ============
// server.properties
min.insync.replicas=2     // 全局默认值，Topic 级覆盖
```
Topic 级配置优先级高于 Broker 级。核心 Topic 建议显式指定，避免受全局默认值变更影响。

### Layer 2 — acks=all + min.insync.replicas=2 组合配置

```java
// ============ Spring Kafka Producer 配置 ============
@Configuration
public class KafkaProducerConfig {

    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

        // 核心三步组合
        props.put(ProducerConfig.ACKS_CONFIG, "all");                    // (1) 等待所有 ISR 确认
        props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);     // (2) 无限重试（配合 delivery.timeout.ms）
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);       // (3) 开启幂等（Kafka 0.11+ 精确一次语义前提）

        // delivery.timeout.ms 控制总超时（含重试），默认 120000ms
        // request.timeout.ms 控制单次请求超时，默认 30000ms
        return new DefaultKafkaProducerFactory<>(props);
    }
}
```
acks=all 保证消息被所有 ISR 副本确认后才返回成功，与 min.insync.replicas=2 配合确保至少 Leader+1 Follower 写入。`enable.idempotence=true` 开启幂等生产者，防止重试导致消息重复。

### Layer 3 — NotEnoughReplicasException 异常处理

```java
// ============ 异步发送 + Callback 捕获异常 ============
@Service
public class OrderProducer {

    private final KafkaTemplate<String, String> kafkaTemplate;

    public OrderProducer(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public void sendOrder(String orderJson) {
        ProducerRecord<String, String> record =
            new ProducerRecord<>("orders", orderJson);

        kafkaTemplate.send(record).addCallback(
            result -> {
                // 发送成功
                RecordMetadata meta = result.getRecordMetadata();
                log.info("消息发送成功: topic={}, partition={}, offset={}",
                    meta.topic(), meta.partition(), meta.offset());
            },
            ex -> {
                // 发送失败 — 关键判断
                if (ex instanceof NotEnoughReplicasException) {
                    // ISR 数量不足 — 可靠性优先场景下应告警并持久化到死信存储
                    log.error("ISR 副本不足，写入拒绝: {}", ex.getMessage());
                    saveToDeadLetterQueue(orderJson);   // 落到 DB/本地文件，人工介入
                    alertOps("Kafka ISR 不足，Topic=orders");
                } else if (ex instanceof TimeoutException) {
                    // 超时 — 可能网络抖动 or Broker 压力大
                    log.warn("发送超时，将重试: {}", ex.getMessage());
                    // 配置了 retries 会自动重试，此处做降级
                } else {
                    log.error("发送失败: ", ex);
                    saveToDeadLetterQueue(orderJson);
                }
            }
        );
    }

    private void saveToDeadLetterQueue(String message) {
        // 写入数据库 / Redis / 本地文件，保证不丢消息
        jdbcTemplate.update("INSERT INTO kafka_dlq (topic, payload, create_time) VALUES (?,?,NOW())",
            "orders", message);
    }

    private void alertOps(String msg) {
        // 触发监控告警（Prometheus / Grafana / 钉钉 / 飞书）
    }
}
```
NotEnoughReplicasException 是 min.insync.replicas 的"防线"生效信号：当 ISR 数量不足时 Producer 直接收到异常，此时你有两个选择 — 让消息落入死信队列（可靠性优先）或降级到 acks=1（可用性优先）。

### Layer 4 — 故障演练：模拟 Follower 宕机

```bash
# ============ Step 1: 创建 Topic（replication.factor=3, min.insync.replicas=2）============
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic test-mir \
  --partitions 1 --replication-factor 3 \
  --config min.insync.replicas=2

# ============ Step 2: 查看 ISR 状态 ============
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic test-mir
# 输出示例：ISR: 0,1,2   （三个副本都在 ISR）

# ============ Step 3: 正常发送一条消息 ============
echo '{"id":1,"msg":"正常消息"}' | kafka-console-producer.sh \
  --bootstrap-server localhost:9092 \
  --topic test-mir \
  --producer-property acks=all
# → 发送成功 ✓

# ============ Step 4: 停掉 2 个 Follower Broker ============
# 先找出 Follower 所在的 Broker，然后逐个停掉
kafka-server-stop.sh   # 停 Broker 1 (Follower)
kafka-server-stop.sh   # 停 Broker 2 (Follower)

# ============ Step 5: 再次查看 ISR — 只剩 Leader ============
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic test-mir
# 输出：ISR: 0   （只有 Leader 在 ISR 中）

# ============ Step 6: 尝试发送消息 — 预期失败 ============
echo '{"id":2,"msg":"故障中消息"}' | kafka-console-producer.sh \
  --bootstrap-server localhost:9092 \
  --topic test-mir \
  --producer-property acks=all
# → ✗ NotEnoughReplicasException: Number of alive brokers '1' does not meet
#   the required replication factor '3' for the offsets topic ...

# ============ Step 7: 恢复 1 个 Follower，ISR=[L,F1]=2 — 恢复写入 ============
kafka-server-start.sh config/server1.properties
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic test-mir
# ISR: 0,1  → 满足 min.insync.replicas=2
echo '{"id":3,"msg":"恢复后消息"}' | kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic test-mir --producer-property acks=all
# → 发送成功 ✓
```
这个演练验证了 min.insync.replicas=2 的核心行为：容忍 1 个副本故障，故障超过 1 个时拒绝写入但不丢数据。生产环境中这个演练在故障演练平台（如 Chaos Mesh）上定期执行。

| 维度 | = 1 | = 2（推荐） | = 3 |
|---|---|---|---|
| 最少 ISR 要求 | 仅 Leader | Leader + 1 Follower | 全部 3 个副本 |
| 数据可靠性 | 低（退化为 acks=1） | 高（至少 2 副本落地） | 最高（3 副本全部落地） |
| 容忍故障数 | 2 个 Follower 故障仍可写 | 1 个 Follower 故障仍可写 | 0 — 任何故障都拒绝写入 |
| 写入失败条件 | ISR 为空（极罕见） | ISR 数量 < 2 | ISR 数量 < 3 |
| 典型异常 | 无（几乎不抛异常） | NotEnoughReplicasException | NotEnoughReplicasException |
| CAP 倾向 | AP（可用性优先） | CP（一致性优先，兼顾可用性） | 强 CP（一致性极致） |
| 适用场景 | 日志采集等容忍丢失 | 订单、支付等核心业务 | 极高一致性要求（极少见） |
| 与 acks=all 组合 | 有歧义 — 名义 all 实际 1 | 黄金组合 | 过度约束，可用性极差 |

## 一句话总结

**min.insync.replicas 是 acks=all 的"质量门槛" — 设为 1 是假可靠，设为 3 是过度保守，设为 2 是在"宁可不可用也不丢数据"与"容忍单点故障"之间找到的那个工业级平衡点。**
