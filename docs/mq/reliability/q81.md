# Q81 消息顺序性

Kafka 单 Partition 内消息天然有序（写入顺序即 offset 顺序，消费按 offset 递增），但多 Partition 之间无全局顺序。推荐方案是按业务 key（如订单 ID）哈希分区，使同一实体的消息路由到同一 Partition 从而保证局部有序，不同实体间可并行消费，兼顾顺序性与吞吐。

从上图可以清晰看到两种顺序保证策略的架构差异：左侧将所有消息塞入一个 Partition 实现全局有序但牺牲了并行度，右侧按业务 key 分区在保证同实体有序的同时最大化并行能力。下面通过代码分层展示具体实现。

## 顺序消费代码分层

### Layer 1 — 单 Partition 全局有序配置（Producer + Consumer）

```java
// 方案一: 单 Partition 全局有序 — 仅适用于极低吞吐场景
// Producer 侧配置
@Configuration
public class SinglePartitionProducerConfig {

    @Bean
    public KafkaTemplate<String, OrderEvent> singlePartitionTemplate(
            ProducerFactory<String, OrderEvent> pf) {
        // 单 Partition Topic: 创建时指定 partitions=1
        // $ kafka-topics --bootstrap-server localhost:9092 --create \
        //     --topic order-global --partitions 1 --replication-factor 3
        return new KafkaTemplate<>(pf);
    }
}

// Consumer 侧 — 全局有序但吞吐极低
@Component
public class GlobalOrderConsumer {

    // concurrency=1 保证单线程消费
    @KafkaListener(
        topics = "order-global",
        groupId = "order-group",
        concurrency = "1"  // 关键：单线程保证消费顺序
    )
    public void consumeInOrder(List<ConsumerRecord<String, OrderEvent>> records,
                                Acknowledgment ack) {
        for (ConsumerRecord<String, OrderEvent> record : records) {
            // 按 offset 顺序逐条处理
            processOrder(record.value());
        }
        ack.acknowledge();
    }

    private void processOrder(OrderEvent event) {
        // 业务处理：所有订单排队串行 — 吞吐受限于单线程
    }
}
```

单 Partition 方案虽然实现了严格的全局有序，但并行度为 1，Consumer Group 中只有一个实例能消费该 Partition，无法水平扩展。仅在吞吐量极低（每秒几十条）且对全局顺序有硬性要求的场景适用。

### Layer 2 — 按 Key 分区局部有序（推荐方案）

```java
// 方案二: 按业务 key 分区 — 推荐方案
// 相同 orderId 的消息路由到同一 Partition，保证该实体消息有序
// 不同 orderId 分布在不同 Partition，可并行消费

@Service
public class KeyBasedOrderProducer {

    @Autowired
    private KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public void sendOrderEvent(String orderId, OrderEvent event) {
        // ProducerRecord 指定 key = orderId
        // Kafka 对 key 做 hash 取模，同一 orderId 路由到同一 Partition
        ProducerRecord<String, OrderEvent> record =
            new ProducerRecord<>("order-events", orderId, event);

        kafkaTemplate.send(record).addCallback(
            success -> {
                RecordMetadata meta = success.getRecordMetadata();
                log.info("Sent to partition={}, offset={}, key={}",
                    meta.partition(), meta.offset(), orderId);
            },
            failure -> log.error("Send failed for key={}", orderId, failure)
        );
    }
}

// 验证：命令行查看消息分布
// $ kafka-console-consumer --bootstrap-server localhost:9092 \
//     --topic order-events --property print.partition=true --property print.key=true
// 输出示例:
// Partition:0  order-001  {status:CREATED}
// Partition:0  order-001  {status:PAID}      ← 同一订单在同一 Partition
// Partition:1  order-002  {status:CREATED}
// Partition:0  order-001  {status:SHIPPED}   ← 三条消息都在 P0，保持有序
```

按 key 分区是 Kafka 实现顺序性的核心机制。同一个 key 的消息永远落在同一 Partition，而每个 Partition 内消息按 offset 严格有序。只要业务合理设计 key（如订单 ID、用户 ID），就能在保证关键实体有序的同时充分利用多 Partition 并行能力。

### Layer 3 — Consumer 单线程消费保证顺序

```java
// Consumer 侧 — 保证 Partition 内顺序的关键配置
@EnableKafka
@Configuration
public class OrderedConsumerConfig {

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, OrderEvent> orderedFactory(
            ConsumerFactory<String, OrderEvent> consumerFactory) {

        ConcurrentKafkaListenerContainerFactory<String, OrderEvent> factory =
            new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(consumerFactory);

        // 关键①: 单线程处理同一 Partition 的消息
        // concurrency 决定消费线程数，每个线程分配若干 Partition
        // 同 Partition 只被一个线程消费 → 保证顺序
        factory.setConcurrency(3); // 3 个 Partition → 3 个线程，每个保序

        // 关键②: 关闭自动提交，手动确认
        factory.getContainerProperties().setAckMode(
            ContainerProperties.AckMode.MANUAL_IMMEDIATE);

        // 关键③: 每次 poll 只取少量消息，避免批次过大
        factory.getContainerProperties().setMaxPollRecords(50);

        return factory;
    }
}

@Component
public class OrderedConsumer {

    // 使用 MANUAL_IMMEDIATE 模式，处理完一条立即提交一条的 offset
    // 注意：不能使用多线程 ExecutorService 并行处理同 Partition 的消息
    @KafkaListener(topics = "order-events", groupId = "order-group")
    public void consume(ConsumerRecord<String, OrderEvent> record,
                        Acknowledgment ack) {
        try {
            // 逐条处理 — 不可以用线程池或异步
            processSingle(record.value());
            ack.acknowledge(); // 处理成功才提交
        } catch (Exception e) {
            // 失败不提交 offset → 消息会被重新消费
            // 注意：不可跳过坏消息，否则破坏顺序
            log.error("Process failed, will retry: {}", record.key(), e);
            throw e; // 抛出异常触发重试
        }
    }

    private void processSingle(OrderEvent event) {
        // 必须是同步、单线程处理
    }
}
```

Consumer 侧的顺序保证依赖于三个关键点：concurrency 线程数不超过分区数确保每线程独占分区、MANUAL_IMMEDIATE 确认模式避免自动提交乱序、禁止线程池并行处理同一分区的消息。这三个约束缺一不可。

### Layer 4 — 顺序消费 + 失败处理策略

```java
// 顺序消费下的失败处理 — 最棘手的场景
// 坏消息：不能跳过（破坏顺序），不能死循环重试（阻塞后续消息）
// 推荐策略：暂停 Partition + 异步重试 + 死信队列

@Component
public class OrderedFailureHandler {

    @Autowired
    private KafkaListenerEndpointRegistry registry;

    @Autowired
    private KafkaTemplate<String, OrderEvent> dlqTemplate;

    private static final int MAX_RETRIES = 5;

    @KafkaListener(topics = "order-events", groupId = "order-group")
    public void consumeWithFailureHandling(
            ConsumerRecord<String, OrderEvent> record,
            Acknowledgment ack,
            @Header(KafkaHeaders.RECEIVED_PARTITION_ID) int partition) {

        try {
            processWithRetry(record.value());
            ack.acknowledge();
        } catch (NonRetryableException e) {
            // 不可重试异常 → 直接投递死信队列，然后确认跳过
            dlqTemplate.send("order-dlq", record.key(), record.value());
            ack.acknowledge();
            log.warn("Sent to DLQ: key={}", record.key());
        } catch (RetryableException e) {
            // 可重试异常 → 暂停该 Partition 消费，等待人工介入
            MessageListenerContainer container =
                registry.getListenerContainer("order-group");
            if (container != null) {
                // 暂停当前 Partition，不阻塞其他 Partition
                container.pausePartition(
                    new TopicPartition("order-events", partition));
                log.warn("Paused partition={} for key={}, retry exceeded",
                    partition, record.key());
            }
            // 不确认 offset → 消息保留在 Broker
            // 需要外部监控告警，人工排查后 resume
        }
    }

    private void processWithRetry(OrderEvent event) {
        for (int i = 0; i < MAX_RETRIES; i++) {
            try {
                doBusinessLogic(event);
                return;
            } catch (RetryableException e) {
                if (i == MAX_RETRIES - 1) throw e;
                Thread.sleep(1000L * (i + 1)); // 退避重试
            }
        }
    }

    private void doBusinessLogic(OrderEvent event) {
        // 实际业务逻辑
    }
}
```

顺序消费的失败处理是所有消息系统中最具挑战性的问题。核心策略是：不可重试的异常投递死信队列后继续，可重试的异常暂停当前 Partition 并等待人工排查，绝不跳过任何一条消息。这是因为在顺序语义下，跳过一条消息意味着其后续所有消息都失去了上下文。

## 三种顺序保证方案对比

| 维度 | 1个Partition 全局有序 | 按 Key 分区局部有序 (推荐) | 多Partition无序并行 |
|---|---|---|---|
| 有序范围 | 全局所有消息 | 同一 Key 的消息 | 无 |
| 并行度 | 1 (单线程) | N (Partition 数 × Consumer 数) | N (最大并行) |
| 水平扩展 | 不可扩展 | 可扩展 (增加 Partition) | 可扩展 |
| 吞吐量 | 低 (~1-5k msg/s) | 高 (~N × 10k msg/s) | 最高 |
| 失败处理 | 暂停整个消费 | 暂停当前 Partition | 跳过/重试/死信 |
| 适用场景 | 极低吞吐全局有序 | 订单/支付/IM消息 (推荐) | 日志/埋点/统计 |
| 实现复杂度 | 低 | 低 (选对 Key 即可) | 最低 |

## 一句话总结

**Kafka 的顺序性本质是一条权衡曲线——全局有序与高吞吐不可兼得，但按业务 Key 分区在二者之间找到了最佳平衡点：同一实体消息局部有序满足业务诉求，不同实体间并行消费释放吞吐潜力，这是目前工业界证明最高效的顺序保证方案。**
