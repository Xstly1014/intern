# Q76 消费者不丢消息

消费者不丢消息的核心策略是"先消费后提交 + 幂等去重"：关闭自动提交（enable.auto.commit=false），业务处理成功后再手动 commitSync()；即使处理中途宕机，offset 未提交导致重启后重复消费，通过唯一键或状态检查实现幂等，确保重复消费不产生副作用。

## 消费者不丢消息代码实践

### Layer 1 — 手动提交配置

```java
// ============ Spring Kafka Consumer 手动提交配置 ============
@Configuration
@EnableKafka
public class KafkaConsumerConfig {

    @Bean
    public ConsumerFactory<String, String> consumerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "order-consumer-group");

        // 核心三步：关自动提交 + 手动模式 + 从最早开始（首次消费）
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);              // (1) 关自动提交
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");          // (2) 新 Group 从最早开始
        props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 10);                   // (3) 每次 poll 最多 10 条

        return new DefaultKafkaConsumerFactory<>(props);
    }

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, String> kafkaListenerContainerFactory() {
        ConcurrentKafkaListenerContainerFactory<String, String> factory =
            new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(consumerFactory());
        // 设置手动提交模式
        factory.getContainerProperties().setAckMode(ContainerProperties.AckMode.MANUAL);
        return factory;
    }
}
```
关键配置 `enable.auto.commit=false` + `AckMode.MANUAL`，将提交控制权完全交给业务代码。`MAX_POLL_RECORDS=10` 限制每次拉取数量，避免单次处理时间过长导致 Session 超时。

### Layer 2 — commitSync 同步提交

```java
// ============ 手动提交：处理完再 commitSync() ============
@Service
@Slf4j
public class OrderConsumer {

    @Autowired
    private OrderService orderService;

    @KafkaListener(topics = "orders", groupId = "order-consumer-group")
    public void consume(ConsumerRecord<String, String> record, Acknowledgment ack) {
        try {
            String orderJson = record.value();
            log.info("收到消息: offset={}, partition={}, key={}",
                record.offset(), record.partition(), record.key());

            // 1. 处理业务逻辑
            orderService.processOrder(orderJson);

            // 2. 业务处理成功后，手动提交 offset
            ack.acknowledge();  // commitSync() 语义，阻塞等待 Broker 确认
            log.info("offset={} 提交成功", record.offset());

        } catch (Exception e) {
            log.error("处理消息失败: offset={}, error={}", record.offset(), e.getMessage());

            // 3. 不提交 offset！让消息重新被消费
            // nack() 或抛异常触发重试（需要工厂配置 SeekUtils）
            throw e;
        }
    }
}
```
acknowledge() 内部调用 commitSync()，是阻塞同步提交。如果 Broker 确认失败（如 Coordinator 不可用），会抛异常导致提交失败，消息不会被跳过。只有业务处理成功 + Broker 确认成功后，offset 才真正前进。

### Layer 3 — 幂等消费实现

```java
// ============ 幂等消费：唯一键去重 + 数据库状态判断 ============
@Service
@Slf4j
public class IdempotentOrderConsumer {

    @Autowired
    private OrderService orderService;
    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private JdbcTemplate jdbcTemplate;

    // 幂等键格式：{topic}:{partition}:{offset} 或业务唯一 ID
    private static final String IDEMPOTENT_KEY_PREFIX = "kafka:idempotent:";

    @KafkaListener(topics = "orders", groupId = "order-consumer-group")
    public void consume(ConsumerRecord<String, String> record, Acknowledgment ack) {
        OrderMessage msg = JSON.parseObject(record.value(), OrderMessage.class);
        String idempotentKey = IDEMPOTENT_KEY_PREFIX + msg.getOrderId();
        String kafkaOffsetKey = String.format("orders:%d:%d", record.partition(), record.offset());

        try {
            // --- 策略1：Redis 唯一键去重（幂等键 = 订单 ID）---
            Boolean isFirstTime = redisTemplate.opsForValue()
                .setIfAbsent(idempotentKey, "1", Duration.ofHours(24));

            if (Boolean.FALSE.equals(isFirstTime)) {
                // 已处理过 → 幂等跳过，但仍提交 offset
                log.info("重复消费，幂等跳过: orderId={}, offset={}", msg.getOrderId(), record.offset());
                ack.acknowledge();
                return;
            }

            // --- 策略2：数据库状态判断（互补方案）---
            String status = jdbcTemplate.queryForObject(
                "SELECT status FROM orders WHERE order_id = ?",
                String.class, msg.getOrderId()
            );
            if ("PROCESSED".equals(status) || "PAID".equals(status)) {
                // 数据库已有终态 → 跳过
                log.info("订单已处理，跳过: orderId={}, status={}", msg.getOrderId(), status);
                ack.acknowledge();
                return;
            }

            // --- 最终处理：幂等键已存 + 状态不是终态 → 安全处理 ---
            orderService.processOrder(msg);
            ack.acknowledge();
            log.info("订单处理成功: orderId={}, offset={}", msg.getOrderId(), record.offset());

        } catch (Exception e) {
            log.error("处理失败: orderId={}, offset={}", msg.getOrderId(), record.offset(), e);
            // 删除幂等键，让消息可以重试
            redisTemplate.delete(idempotentKey);
            throw e; // 不提交 → 重新消费
        }
    }
}
```
两层幂等保护：Redis setIfAbsent（快速判断，TTL 24h 覆盖最大重试窗口）+ 数据库状态检查（终极兜底，面向持久化状态）。处理失败时删除 Redis 幂等键，确保下次重试不被误判为"已处理"。

### Layer 4 — 消费失败重试 + 死信队列

```java
// ============ 消费失败：重试 3 次 → 死信队列（DLQ）============
@Configuration
@EnableKafka
public class RetryAndDLQConfig {

    // --- 主 Topic 的 Listener 工厂（无自动重试，手动控制）---
    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, String> retryContainerFactory(
            ConsumerFactory<String, String> consumerFactory) {
        ConcurrentKafkaListenerContainerFactory<String, String> factory =
            new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(consumerFactory);
        factory.getContainerProperties().setAckMode(ContainerProperties.AckMode.MANUAL);

        // 使用 SeekToCurrentErrorHandler：失败后暂停 1s，重新 seek 当前 offset
        // 配合自定义 retry count 实现有限重试
        factory.setCommonErrorHandler(new DefaultErrorHandler(
            (record, exception) -> {
                // 重试耗尽后 → 发送到 DLQ Topic
                deadLetterPublishingRecoverer(record);
            },
            new FixedBackOff(1000L, 3L)  // 间隔 1s，最多重试 3 次
        ));

        return factory;
    }

    private void deadLetterPublishingRecoverer(ConsumerRecord<?, ?> record) {
        // 将失败消息发送到 DLQ Topic
        try (KafkaProducer<String, String> dlqProducer = createDlqProducer()) {
            ProducerRecord<String, String> dlqRecord = new ProducerRecord<>(
                "orders.DLQ",                           // DLQ Topic
                (String) record.key(),
                (String) record.value()
            );
            // 在 Headers 中记录原始 Topic 和失败原因
            dlqRecord.headers().add("original-topic", record.topic().getBytes());
            dlqRecord.headers().add("original-offset",
                String.valueOf(record.offset()).getBytes());
            dlqRecord.headers().add("retry-exhausted", "true".getBytes());

            dlqProducer.send(dlqRecord).get();
            log.warn("消息进入死信队列: topic={}, offset={}",
                record.topic(), record.offset());
        }
    }

    // --- DLQ 消费者：人工处理或告警 ---
    @KafkaListener(topics = "orders.DLQ", groupId = "dlq-processor")
    public void processDLQ(ConsumerRecord<String, String> record, Acknowledgment ack) {
        String originalTopic = new String(
            record.headers().lastHeader("original-topic").value());
        String originalOffset = new String(
            record.headers().lastHeader("original-offset").value());

        log.error("DLQ 消息: 原始 Topic={}, offset={}, 消息内容={}",
            originalTopic, originalOffset, record.value());

        // 写入数据库待人工处理表
        jdbcTemplate.update(
            "INSERT INTO kafka_dlq_records (topic, offset, payload, create_time) VALUES (?,?,?,NOW())",
            originalTopic, originalOffset, record.value()
        );

        // 提交 DLQ offset（消息已持久化到 DB）
        ack.acknowledge();

        // 触发告警通知
        alertOps(String.format("Kafka DLQ 有新消息: %s offset=%s", originalTopic, originalOffset));
    }
}
```
错误处理使用 `DefaultErrorHandler` + `FixedBackOff(1s, 3次)` 实现紧耦合重试，重试耗尽后消息进入 `orders.DLQ` 死信 Topic。DLQ 消费者将消息持久化到数据库并触发告警，等待人工复核后决定重放或丢弃。这里的重试由 Kafka Consumer 框架在内存中完成，不依赖外部重试队列。

| 方案 | 自动提交 | 手动提交 + 无幂等 | 手动提交 + 幂等（推荐） |
|---|---|---|---|
| 消息丢失风险 | 高（处理前自动提交，宕机即丢） | 极低 | 极低 |
| 消息重复风险 | 低（但丢了更严重） | 高（网络抖动导致重复消费） | 无（幂等去重） |
| offset 提交时机 | auto.commit.interval.ms 定时 | 业务处理成功后手动 commitSync() | 业务处理成功后手动 commitSync() |
| 故障恢复行为 | 从已提交 offset 继续 → 丢失未处理消息 | 从未提交 offset 重新消费 → 可能重复 | 从未提交 offset 重新消费 → 幂等跳过已处理 |
| 一致性保证 | At-Most-Once（最多一次） | At-Least-Once（至少一次） | At-Least-Once + 业务层 Exactly-Once |
| 实现复杂度 | 零配置（默认开箱即用） | 低（改配置 + 添加 ack） | 中（需增幂等键存储 + 状态判断） |
| 适用场景 | 无（生产环境禁用） | 对重复不敏感的场景（如日志） | 订单、支付、库存等所有核心业务 |
| 核心风险 | 宕机丢消息 — 灾难性 | 重复扣款/重复发货 — 业务 BUG | 幂等键的 TTL 需覆盖最大重试窗口 |

## 一句话总结

**"消费者不丢消息"不是靠 Kafka 保证的，而是靠两条铁律自己构建的：offset 是你说"我消化完了"的承诺而非"我收到了"的回执，幂等是你消化两次也不会中毒的免疫系统 — 手动提交给 Kafka 画分割线，幂等去重给自己上保险。**
