# Q79 事务消息流程

Kafka 事务消息流程本质上是两阶段提交的变体：Producer 先向 TransactionCoordinator 注册获得 PID+epoch，然后在事务内发送消息和提交 offset，最后 Coordinator 通过 PREPARE_COMMIT -> COMMIT -> COMPLETE_COMMIT 三阶段确保所有涉及的 Partition 原子性地可见或回滚，消费者通过 read_committed 只读已提交消息。

Kafka 事务流程以 TransactionCoordinator 为协调中枢，Producer 和 Broker 都与之交互。Coordinator 通过 `__transaction_state` 持久化事务状态，即使 Producer 崩溃或 Coordinator 重启，也能通过这个内部 Topic 恢复未完成事务。两阶段提交的核心是：先确保状态持久化（PREPARE_COMMIT），再原子标记所有 Partition（COMMIT），最后清理状态（COMPLETE_COMMIT）。

## 代码：Spring Kafka 事务分层实现

### Layer 1 — 事务 Producer 配置

```java
// ============ Layer 1: 事务 Producer 配置 ============
// transactional.id 是事务 Producer 的唯一身份标识
@Configuration
@EnableTransactionManagement
public class KafkaTransactionConfig {

    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        // 事务强制要求幂等（自动开启）
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        // 核心：唯一事务标识，跨重启保持身份
        props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG,
                "payment-service-tx-v1");
        // ProducerFactory 必须设置 transactionIdPrefix 或
        // 每个 Producer 设置独立的 transactional.id
        return new DefaultKafkaProducerFactory<>(props);
    }

    @Bean
    public KafkaTransactionManager<String, String> transactionManager(
            ProducerFactory<String, String> producerFactory) {
        // KafkaTransactionManager 将 Kafka 事务纳入 Spring 事务管理
        // @Transactional 注解可直接驱动 Kafka 事务
        return new KafkaTransactionManager<>(producerFactory);
    }

    @Bean
    public KafkaTemplate<String, String> kafkaTemplate(
            ProducerFactory<String, String> producerFactory) {
        return new KafkaTemplate<>(producerFactory);
    }
}
// 关键: transactional.id 对应 Coordinator 中 __transaction_state
// 的记录键，Coordinator 据此恢复或分配 (PID, epoch)
```

`transactional.id` 是整个事务体系的根基：Coordinator 将其作为 `__transaction_state` 的 Key，记录 `(PID, epoch, 状态, 涉及Partition列表)` 等元数据，即使 Producer 崩溃也能从持久化状态中恢复。

### Layer 2 — 事务消息发送

```java
// ============ Layer 2: 事务消息发送 ============
// Spring @Transactional 驱动 Kafka 事务
@Service
public class OrderTransactionalService {

    private final KafkaTemplate<String, String> kafkaTemplate;

    public OrderTransactionalService(
            KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    // 方案A: @Transactional 驱动 Kafka 事务
    @Transactional  // Spring 事务管理 → KafkaTransactionManager → Kafka 事务
    public void createOrderWithTransaction(Order order) {
        // beginTransaction() 由 KafkaTransactionManager 自动调用

        // 1. 发送订单创建消息到 order-topic
        kafkaTemplate.send("order-topic", order.getId(), order.toJson());
        // 底层: Producer.sendOffsetsToTransaction() 包装消息带事务标记

        // 2. 发送扣减库存消息到 inventory-topic（同一事务）
        kafkaTemplate.send("inventory-topic", order.getSku(),
                String.valueOf(order.getQuantity()));

        // 3. 发送通知消息到 notification-topic
        kafkaTemplate.send("notification-topic", order.getUserId(),
                "Order " + order.getId() + " created");

        // commitTransaction() 由 KafkaTransactionManager 自动调用
        // 以上三条消息要么全部 COMMIT（原子可见），要么全部 ABORT
    }

    // 方案B: KafkaTemplate.executeInTransaction 手动控制
    public void createOrderManualTx(Order order) {
        kafkaTemplate.executeInTransaction(operations -> {
            // 回调内自动 beginTransaction()
            operations.send("order-topic", order.getId(), order.toJson());
            operations.send("inventory-topic", order.getSku(),
                    String.valueOf(order.getQuantity()));

            if (order.getAmount() <= 0) {
                // 抛异常自动触发 abortTransaction()
                throw new IllegalArgumentException("Invalid amount");
            }
            // 正常返回自动 commitTransaction()
            return true;
        });
    }
}
// 核心价值：跨 Topic 跨 Partition 原子写入 —
// 三条消息要么全部成功，要么全部回滚，绝不出现部分可见
```

两种方式各有所长：`@Transactional` 融入 Spring 声明式事务体系，与 `@Transactional(rollbackFor=...)`、事务传播行为无缝配合；`executeInTransaction` 提供更精细的手动控制，适合不需要 Spring 事务管理的轻量场景。

### Layer 3 — Consumer offset 纳入事务

```java
// ============ Layer 3: Consumer offset 纳入事务 ============
// 消费-处理-生产模式的 Exactly-Once 关键步骤
@Service
public class ConsumeProcessProduceService {

    private final KafkaTemplate<String, String> kafkaTemplate;

    @KafkaListener(topics = "source-topic", groupId = "eos-group")
    @Transactional  // Kafka 事务 + offset 提交原子化
    public void consumeAndProduce(
            ConsumerRecord<String, String> record,
            Acknowledgment ack) {

        try {
            // 1. 处理消息
            String processed = processMessage(record.value());

            // 2. 输出到下游 Topic
            kafkaTemplate.send("sink-topic", record.key(), processed);

            // 3. sendOffsetsToTransaction — 将 offset 提交纳入当前事务
            // Spring Kafka 在事务模式下自动调用此方法：
            // KafkaMessageListenerContainer 检测到 @Transactional
            // → 自动将 Consumer offset 作为事务的一部分
            // → commitTransaction() 时一起提交 offset

            // 4. 确认消息已处理
            ack.acknowledge();

        } catch (Exception e) {
            // 异常触发 abortTransaction()
            // → 消息回滚到 source-topic（可重试）
            // → sink-topic 的写入也回滚
            throw e;
        }
    }
}
// 关键：Spring Kafka 事务模式下，
// Consumer offset 提交自动纳入 Producer 事务，
// 确保"处理+输出"的原子性
```

这是 Kafka Streams EOS 的底层原理：将 Consumer offset 提交纳入同一个 Producer 事务，确保"读完这条消息 + 产出下游消息"要么一起成功、要么一起回滚，杜绝了"offset 已提交但产出未成功"或"产出已成功但 offset 未提交"的不一致。

### Layer 4 — 事务提交/回滚 与 故障恢复

```java
// ============ Layer 4: 事务提交/回滚 + 故障恢复 ============
// initTransactions 是故障恢复的关键入口
@Component
public class TransactionRecoveryService {

    private final KafkaTemplate<String, String> kafkaTemplate;

    public TransactionRecoveryService(
            KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    /**
     * 事务 Producer 初始化时必须调用 initTransactions()
     * 这是故障恢复的入口点
     */
    @PostConstruct
    public void initProducer() {
        // 内部流程：
        // 1. 找到 transactional.id 对应的 TransactionCoordinator
        // 2. 发送 InitProducerIdRequest(transactional.id="payment-service-tx-v1")
        // 3. Coordinator 查找 __transaction_state:
        //    - 无记录 → 分配新 PID，epoch=0
        //    - 有记录 → 恢复 PID，epoch+1，检查上次事务状态
        //      - PREPARE_COMMIT/ONGOING → 自动 abortTransaction()
        //      - COMMIT → 补写 COMPLETE_COMMIT 清理
        //      - COMPLETE_COMMIT → 正常恢复
        // 4. 返回 (PID, epoch) 给 Producer
        kafkaTemplate.executeInTransaction(ops -> {
            // 初始化即完成故障恢复
            return true;
        });
    }

    /**
     * 模拟事务中途崩溃 → 重启后自动恢复
     */
    public void simulateCrashRecovery() {
        try {
            kafkaTemplate.executeInTransaction(ops -> {
                ops.send("topic-a", "key1", "msg1");
                ops.send("topic-b", "key2", "msg2");

                // 模拟崩溃：在 commitTransaction() 之前宕机
                // → __transaction_state 记录停留在 ONGOING 状态
                throw new RuntimeException("Simulated crash before commit");
            });
        } catch (Exception e) {
            // Producer 重启后再次 initTransactions()
            // → Coordinator 发现该 transactional.id 的
            //   __transaction_state 为 ONGOING
            // → 自动执行 abortTransaction()
            // → 之前发送的 msg1、msg2 全部标记为 ABORT
            // → Consumer(read_committed) 自动跳过这些消息
            System.out.println("Transaction aborted, messages rolled back");
        }
    }

    /**
     * 正常提交流程
     */
    @Transactional
    public void normalCommit(String key, String value) {
        kafkaTemplate.send("output-topic", key, value);
        // 方法结束时自动 commitTransaction():
        // Phase 1: Coordinator 写 __transaction_state = PREPARE_COMMIT
        // Phase 2: Coordinator 向所有涉及 Partition 写 COMMIT 标记
        // Phase 3: Coordinator 写 __transaction_state = COMPLETE_COMMIT
        // → Consumer(read_committed) 现在可以读到消息
    }
}
// initTransactions 是 Kafka 事务故障恢复的精髓：
// 无论上次事务停留在哪个阶段，重启后都能自动恢复到一致状态
```

`initTransactions` 是事务故障恢复的总开关。Coordinator 内部维护 `__transaction_state` 的状态机 —— `Empty -> Ongoing -> PrepareCommit -> CompleteCommit -> Empty` —— 每次 `initTransactions` 都会检查状态，自动推进到下一个合法状态，确保没有"卡住"的事务。

## Kafka 事务 API 一览

| API | 作用 | 调用时机 |
|---|---|---|
| `initTransactions()` | 向 Coordinator 注册 transactional.id，分配/恢复 (PID, epoch)，自动清理未完成事务 | Producer 初始化时（必须首先调用，阻塞等待 Coordinator 响应） |
| `beginTransaction()` | 标记事务开始，后续 send 纳入事务上下文 | 开始一个新事务时（Spring 由 @Transactional 自动管理） |
| `send()` | 发送消息并携事事务标记（消息在 COMMIT 前对 read_committed 不可见） | 事务内发送任何消息 |
| `sendOffsetsToTransaction()` | 将 Consumer offset 提交纳入当前事务，确保消费进度与产出原子化 | 消费-处理-生产模式的 offset 提交环节 |
| `commitTransaction()` | 两阶段提交：PREPARE_COMMIT -> COMMIT -> COMPLETE_COMMIT，消息变为可见 | 事务所有操作成功后（Spring 自动调用） |
| `abortTransaction()` | 回滚事务：写 ABORT 标记到所有涉及 Partition，read_committed 自动跳过 | 异常时或业务判定失败时（Spring 自动调用） |
| `KafkaTemplate.executeInTransaction()` | Spring 封装的事务执行器，自动管理 begin/commit/abort | 直接在方法内手动控制事务边界 |

## 一句话总结

**Kafka 事务消息流程是一场由 Coordinator 指挥的两阶段提交交响乐：Producer 发消息只是"排练"，commitTransaction 才是"正式演出" —— PREPARE_COMMIT 确认全员就位，COMMIT 让观众可见，COMPLETE_COMMIT 谢幕退场，而 initTransactions 是所有乐手的集合号。**
