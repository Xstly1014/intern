# Q82 分布式事务消息

分布式事务消息解决"本地事务与消息发送"的原子性难题。RocketMQ 的事务消息面向业务事务（DB + MQ 原子化），通过半消息 + 本地事务 + 回查机制实现；Kafka 的事务消息面向流处理（Kafka-to-Kafka 原子化），通过事务协调器保证同一事务内跨 Topic 写入的原子性。两者定位不同，不可互换。

## 分布式事务消息代码分层

### Layer 1 — RocketMQ 事务消息（DB + MQ 原子化）

```java
// RocketMQ 事务消息: 解决"下单写DB"与"扣库存发消息"的原子性问题
// 核心接口: TransactionListener — 实现 executeLocalTransaction + checkLocalTransaction

@RocketMQTransactionListener(txProducerGroup = "order-tx-group")
public class OrderTransactionListener implements RocketMQLocalTransactionListener {

    @Autowired
    private OrderService orderService;

    @Autowired
    private JdbcTemplate jdbc;

    // Step 1 & 2: 发送 Half Message 后，执行本地事务
    @Override
    public RocketMQLocalTransactionState executeLocalTransaction(
            org.apache.rocketmq.common.message.Message msg, Object arg) {

        OrderEvent event = parseOrderEvent(msg);
        try {
            // 本地事务: 写 DB (INSERT order)
            orderService.createOrder(event);
            // 本地事务成功 → Commit 半消息，Consumer 可见
            return RocketMQLocalTransactionState.COMMIT;
        } catch (Exception e) {
            // 本地事务失败 → Rollback 半消息，消息删除
            return RocketMQLocalTransactionState.ROLLBACK;
        }
        // 注意: 如果此处进程宕机，Broker 收不到 Commit/Rollback → 触发回查
    }

    // Step 4: Broker 回查 — Producer 宕机后 Broker 定时回调
    @Override
    public RocketMQLocalTransactionState checkLocalTransaction(
            org.apache.rocketmq.common.message.MessageExt msg) {

        String orderId = msg.getKeys();
        // 查询 DB: 订单是否已创建?
        Order order = jdbc.queryForObject(
            "SELECT status FROM orders WHERE order_id=?",
            Order.class, orderId);

        if (order != null && "CREATED".equals(order.getStatus())) {
            // DB 中有订单 → 上次 DB 写入成功但 Commit 丢失 → 补 Commit
            return RocketMQLocalTransactionState.COMMIT;
        } else {
            // DB 中无订单 → 本地事务未执行或已回滚 → Rollback
            return RocketMQLocalTransactionState.ROLLBACK;
        }
    }
}

// Producer 发送事务消息
@Service
public class OrderTxProducer {
    @Autowired
    private RocketMQTemplate rocketMQTemplate;

    public void sendOrderEvent(OrderEvent event) {
        // sendMessageInTransaction: 发送半消息 + 执行本地事务
        // 三个参数: topic, destination, 消息体, 附加参数
        TransactionSendResult result = rocketMQTemplate.sendMessageInTransaction(
            "order-tx-group",
            "order-topic",
            MessageBuilder.withPayload(event)
                .setHeader("orderId", event.getOrderId())
                .build(),
            null  // arg, 传给 executeLocalTransaction
        );
        log.info("Tx result: {}, msgId: {}", result.getSendStatus(), result.getMsgId());
    }
}
```

RocketMQ 事务消息的精髓在于半消息 + 回查机制。半消息暂存在 Broker 但对 Consumer 不可见，只有在本地事务成功 Commit 后才变为可见。如果 Producer 在 Commit/Rollback 之前宕机，Broker 会定时回查 `checkLocalTransaction`，通过查询 DB 状态来补交或回滚——这是 DB + MQ 原子性的兜底保障。

### Layer 2 — Kafka 事务消息（Kafka → Kafka 原子化）

```java
// Kafka 事务消息: 跨 Topic 原子写入
// 典型场景: 从 Topic-A 消费 → 处理 → 同时写入 Topic-B 和 Topic-C
// 注意: Kafka 事务只保证 Kafka 内部的原子性，不涉及外部系统

@Configuration
public class KafkaTransactionalConfig {

    @Bean
    public ProducerFactory<String, String> transactionalProducerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

        // ① 启用幂等生产者 (事务的前提)
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

        // ② 设置事务 ID (每个 Producer 实例唯一)
        //    对应 __transaction_state 中的键
        props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-tx-producer-1");

        DefaultKafkaProducerFactory<String, String> factory =
            new DefaultKafkaProducerFactory<>(props);

        // ③ 开启事务支持
        factory.setTransactionIdPrefix("tx-");

        return factory;
    }

    @Bean
    public KafkaTemplate<String, String> transactionalTemplate(
            ProducerFactory<String, String> pf) {
        return new KafkaTemplate<>(pf);
    }
}

// 事务消费 + 处理 + 生产
@Component
public class KafkaTransactionalProcessor {

    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    // Kafka 事务: consume → transform → produce (全部在一个事务内)
    @Transactional  // Spring + KafkaTransactionManager
    @KafkaListener(topics = "order-raw", groupId = "order-tx-group")
    public void processAndProduce(String rawMessage) {

        // ① 从 order-raw 消费 (offset 会在事务 commit 时提交)

        // ② 业务处理: 拆分为订单事件和支付事件
        OrderEvent orderEvent = parseOrder(rawMessage);
        PaymentEvent paymentEvent = parsePayment(rawMessage);

        // ③ 同时写入两个 Topic — 在同一个事务内原子化
        kafkaTemplate.send("order-events",
            orderEvent.getOrderId(), toJson(orderEvent));

        kafkaTemplate.send("payment-events",
            paymentEvent.getPaymentId(), toJson(paymentEvent));

        // ④ 事务提交: offset + 两条消息 同时 commit
        //    如果任意一步失败 → 全部回滚，Consumer 不消费到中间状态

        // isolation.level=read_committed 的 Consumer:
        //   只有事务 commit 后才看到这两条消息
    }
}

// 命令行验证事务
// $ kafka-console-consumer --bootstrap-server localhost:9092 \
//     --topic order-events --isolation-level read_committed
```

Kafka 事务消息的核心边界是"仅保证 Kafka 内部的原子性"。`initTransactions` 向 Transaction Coordinator 注册，`beginTransaction` 开始事务，所有 `send` 和 offset 提交操作在事务内暂存，`commitTransaction` 时 Coordinator 统一写入 `__transaction_state` 标记事务完成。Consumer 设置 `isolation.level=read_committed` 后只能读取已提交事务的消息。

### Layer 3 — "本地 DB + Kafka" 的变通方案（Outbox Pattern + CDC）

```sql
-- ============================================================
-- Outbox Pattern: 解决 Kafka 无法直接支持"DB + MQ"事务的问题
-- 核心思想: 在同一个 DB 事务中同时写入业务表和 outbox 表，
--          然后用 CDC (Change Data Capture) 工具读取 outbox 表
--          将消息投递到 Kafka，投递成功后删除 outbox 记录
-- ============================================================

-- Step 1: 创建 outbox 表 (与业务表在同一 DB)
CREATE TABLE order_outbox (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    aggregate_id VARCHAR(64) NOT NULL,       -- 业务主键 (order_id)
    event_type VARCHAR(64) NOT NULL,          -- 事件类型 (OrderCreated)
    payload JSON NOT NULL,                    -- 消息体
    created_at TIMESTAMP DEFAULT NOW(),
    INDEX idx_created (created_at)
);

-- Step 2: 在同一个 DB 事务中写入业务表 + outbox 表
-- 以下的 SQL 在同一个 @Transactional 方法中执行:
-- (用 Spring @Transactional 包裹)

-- 写入业务表
INSERT INTO orders (order_id, user_id, amount, status, created_at)
VALUES ('ORD-001', 'U-123', 99.00, 'CREATED', NOW());

-- 写入 outbox 表 (同一事务)
INSERT INTO order_outbox (aggregate_id, event_type, payload)
VALUES ('ORD-001', 'OrderCreated', '{"orderId":"ORD-001","amount":99.00}');

-- 事务提交: 两条 INSERT 同时成功或同时失败
-- 不会出现"订单写了但 outbox 没写"的情况

-- Step 3: Debezium CDC 监听 MySQL binlog，读取 outbox 变更
-- Debezium 配置 (connector config JSON):
-- {
--   "connector.class": "io.debezium.connector.mysql.MySqlConnector",
--   "database.hostname": "localhost",
--   "table.include.list": "mydb.order_outbox",
--   "transforms": "outbox",
--   "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
--   "transforms.outbox.route.topic.replacement": "${routedByValue}"
-- }

-- Debezium 流程:
-- 1. 监听 order_outbox 的 INSERT 事件 (binlog)
-- 2. EventRouter 转换: 提取 payload 作为消息体
-- 3. 发送到 Kafka topic (如 order-events)
-- 4. 发送成功后，可定期清理 outbox 中的旧记录
--    DELETE FROM order_outbox WHERE created_at < NOW() - INTERVAL 7 DAY;
```

Outbox Pattern 是 Kafka 生态中实现"DB + MQ"事务原子性的最佳实践。它的核心洞察是：既然 Kafka 事务不能跨越外部 DB，那就在 DB 内部多加一张 outbox 表，利用 DB 自身的事务能力保证业务数据和消息数据的原子写入，然后用 Debezium 这种 CDC 工具将 outbox 记录"搬运"到 Kafka。投递至少一次，结合幂等消费去重。

### Layer 4 — Kafka Streams 事务流处理（消费 + 处理 + 生产原子化）

```java
// Kafka Streams 事务流处理: 消费 → 聚合/转换 → 生产，端到端精确一次
// 适用场景: 实时流计算 — 统计/聚合/join 后写入结果 Topic
@Configuration
public class KafkaStreamsExactlyOnceConfig {

    @Bean
    public KStream<String, OrderEvent> orderStream(StreamsBuilder builder) {
        Properties props = new Properties();
        props.put(StreamsConfig.APPLICATION_ID_CONFIG, "order-streams-app");
        props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");

        // ① 启用精确一次语义 (Kafka Streams 2.6+)
        //    内部自动使用事务 API: initTransactions → begin → consume → produce → commit
        props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG,
            StreamsConfig.EXACTLY_ONCE_V2);

        // ② 自动管理事务边界: 每条记录的处理 + offset提交 + 结果写入 在同一事务中
        KStream<String, OrderEvent> stream =
            builder.stream("order-events",
                Consumed.with(Serdes.String(), orderEventSerde));

        // ③ 按订单状态聚合统计
        KTable<String, Long> statusCounts = stream
            .groupBy((key, event) -> event.getStatus(),
                Grouped.with(Serdes.String(), orderEventSerde))
            .count(Materialized.as("order-status-counts"));

        // ④ 结果流式写入下游 Topic — 全部在事务中原子化
        statusCounts.toStream().to("order-status-stats",
            Produced.with(Serdes.String(), Serdes.Long()));

        return stream;
    }
}

// 说明: Kafka Streams 的 EXACTLY_ONCE_V2 在内部:
// 1. consumer.poll() → 读取消息 (记录 offset)
// 2. process() → 流处理逻辑
// 3. producer.send() → 写入结果 Topic
// 4. producer.sendOffsetsToTransaction(offsets) → 提交消费 offset
// 5. producer.commitTransaction() → 整个事务提交
// 任何一步失败 → abortTransaction() → 全部回滚
// Consumer (read_committed) 只看到已提交的结果
```

Kafka Streams 的 `EXACTLY_ONCE_V2` 是 Kafka 事务消息的最高级封装，它将"消费 offset + 处理 + 生产结果"全部包裹在同一个事务中，对外表现为端到端精确一次语义。这适合 Kafka 内部的流处理管道，但不涉及外部系统（DB、Redis、第三方 API）。

## RocketMQ 事务消息 vs Kafka 事务消息 对比

| 维度 | RocketMQ 事务消息 | Kafka 事务消息 |
|---|---|---|
| 设计目标 | 业务事务: DB 写入 + MQ 发送原子化 | 流处理事务: consume → process → produce 原子化 |
| 事务边界 | 跨越外部系统 (DB/Redis + MQ) | 仅限 Kafka 内部 (多 Topic 间) |
| 核心机制 | Half Message + 本地事务 + 回查 | Transaction Coordinator + __transaction_state |
| 半消息 | 支持 — 暂存 Broker，对 Consumer 不可见 | 不支持半消息概念 |
| 回查机制 | 有 — Producer 宕机后 Broker 定时回查 DB 状态 | 无 — 依赖 Producer 主动 abort (超时自动 abort) |
| 外部系统参与 | 是 — 回查时查询 DB 判断事务状态 | 否 — 不涉及任何外部系统 |
| 典型场景 | 下单发消息扣库存 / 支付后发通知 | Kafka Streams 聚合 / 多 Topic 级联写入 |
| 实现复杂度 | 中等 (需实现 TransactionListener 两个方法) | 低 (配置 + @Transactional 注解) |
| 精确一次语义 | 业务层面 (消息 + DB 状态一致) | 流处理层面 (consume + produce 精确一次) |
| DB + Kafka 事务 | 原生支持 | 不支持 — 需 Outbox Pattern + CDC 变通 |

## 一句话总结

**RocketMQ 事务解决"DB 写了消息没发"的业务灾难，Kafka 事务解决"流处理中间状态泄漏"的数据一致性问题——两者名字里都有"事务"，但解决的问题域完全不同，选型时必须先看清事务边界在哪里。**
