# Q77 Exactly-Once 语义

Kafka Exactly-Once 语义（EOS）通过"幂等生产者 + 事务 + 事务消费者"三件套实现 Kafka 流处理场景内的端到端精确一次，但不保证 Kafka 到外部系统的 Exactly-Once —— 那需要消费端自行幂等。

EOS 三件套各司其职：幂等 Produer 确保单 Partition 不重复，事务 Producer 保证跨 Partition 原子提交，事务 Consumer 只读已提交结果。但三件套的效力止步于 Kafka 边界 —— 一旦消息写出到外部系统，必须回到消费端幂等。

## 代码：Spring Kafka EOS 分层配置

### Layer 1 — 幂等生产者配置

```java
// ============ Layer 1: 幂等生产者 ============
// enable.idempotence=true 是 EOS 的基础，Kafka 3.0+ 默认开启
@Configuration
public class IdempotentProducerConfig {

    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
                StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
                StringSerializer.class);

        // 幂等核心配置 — Kafka 3.0+ 默认 true
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        // 幂等要求 acks=all，自动强制设置
        // 幂等要求 max.in.flight.requests.per.connection <= 5
        // 幂等要求 retries > 0

        return new DefaultKafkaProducerFactory<>(props);
    }
}
// 关键：Producer 启动时从 Broker 获取唯一 PID，
// 每条消息带 (PID, Partition, seqNum)，Broker 端按 maxSeq 去重
```

配置 `enable.idempotence=true` 后，Producer 会自动获取 PID 并为每个 Partition 维护递增 seq，Broker 端按 `(PID, Partition)` 维度维护 maxSeq 去重。

### Layer 2 — 事务生产者配置

```java
// ============ Layer 2: 事务生产者 ============
// transactional.id 让 Producer 跨 Session 保持事务身份
@Configuration
@EnableTransactionManagement  // 启用 Spring 事务管理
public class TransactionalProducerConfig {

    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);   // 事务强制要求幂等
        // 事务核心：唯一标识事务 Producer，跨重启保持 PID+epoch
        props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "tx-app-01");
        // 事务超时（默认 60s）
        props.put(ProducerConfig.TRANSACTION_TIMEOUT_CONFIG, 60000);
        return new DefaultKafkaProducerFactory<>(props);
    }

    @Bean
    public KafkaTransactionManager<String, String> transactionManager(
            ProducerFactory<String, String> producerFactory) {
        // 将 Kafka 事务纳入 Spring 事务管理体系
        return new KafkaTransactionManager<>(producerFactory);
    }

    @Bean
    public KafkaTemplate<String, String> kafkaTemplate(
            ProducerFactory<String, String> producerFactory) {
        return new KafkaTemplate<>(producerFactory);
    }
}
// transactional.id 将 Producer 标识为事务型 —
// 同一 transactional.id 的 Producer 重启后恢复 PID 和未完成事务
```

`transactional.id` 是关键：它让 Producer 在重启后保持事务身份，Coordinator 按 `transactional.id` 恢复或分配 `(PID, epoch)`，epoch 递增用于隔离僵尸 Producer。

### Layer 3 — 事务消费者配置

```java
// ============ Layer 3: 事务消费者 ============
// isolation.level=read_committed 过滤未提交事务的消息
@Configuration
public class TransactionalConsumerConfig {

    @Bean
    public ConsumerFactory<String, String> consumerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "tx-consumer-group");
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG,
                StringDeserializer.class);
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
                StringDeserializer.class);

        // 事务消费核心：只读已提交事务的消息
        props.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG,
                "read_committed");
        // read_uncommitted（默认）：能读到未提交/已回滚的消息
        // read_committed：只读到 COMMIT 标记后的消息，保障事务原子性

        return new DefaultKafkaConsumerFactory<>(props);
    }
}
// 消费者开启 read_committed 后，遇到未提交事务会等待（事务超时前）
// 遇到 ABORT 标记直接跳过，保证只消费已成功提交的原子消息
```

`isolation.level=read_committed` 是事务消费者的必修课 —— 它过滤掉所有未提交和已回滚的消息，与事务生产者的原子提交形成闭环。

### Layer 4 — Kafka Streams EOS 配置

```java
// ============ Layer 4: Kafka Streams EOS ============
// 一行配置启动 Kafka Streams 端到端 Exactly-Once
@Configuration
public class KafkaStreamsEosConfig {

    @Bean
    public KStream<String, String> eosStream(StreamsBuilder builder) {
        KStream<String, String> source = builder.stream("source-topic");

        KStream<String, String> processed = source
                .mapValues(value -> value.toUpperCase())    // 转换逻辑
                .filter((key, value) -> value.length() > 0);

        processed.to("sink-topic");
        return processed;
    }

    @Bean
    public KafkaStreams kafkaStreams() {
        Properties props = new Properties();
        props.put(StreamsConfig.APPLICATION_ID_CONFIG, "eos-app-01");
        props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");

        // Kafka Streams EOS 一行搞定！
        props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG,
                "exactly_once_v2");  // Kafka 2.6+ 推荐
        // exactly_once_v2 比 exactly_once 性能更好
        // 底层自动配置幂等+事务+read_committed+事务 offset 提交

        return new KafkaStreams(new Topology(), props);
    }
}
// EOS 的最佳实践场景：无外部副作用的 Kafka→Kafka 流处理
// 一旦涉及外部系统写入，必须回退到 At Least Once + 业务幂等
```

Kafka Streams 的 `exactly_once_v2` 是 EOS 的最终形态 —— 一行配置自动集成三件套，但适用范围严格限定在 Kafka 内部流处理。

## 三种交付语义对比

| 维度 | At Most Once | At Least Once | Exactly-Once |
|---|---|---|---|
| 语义 | 消息最多消费一次，可能丢失 | 消息最少消费一次，可能重复 | 消息精确消费一次，不丢不重 |
| 可靠性 | 低（丢消息） | 高（不丢） | 最高（不丢不重） |
| 实现方式 | auto-commit 立即提交 offset | 手动提交 offset + 重试 | 幂等 Producer + 事务 + read_committed |
| 性能开销 | 最低 | 中等 | 高（吞吐降 20%+，事务协调开销） |
| 适用场景 | 监控日志、非关键指标 | 通用业务（订单、支付） | Kafka Streams 流处理 |
| 外部系统保证 | 无 | 需要消费端幂等 | 需要消费端幂等（同 At Least Once） |
| 重试策略 | 不重试 | 重试 + 去重 | 事务回滚后重试 |
| 典型配置 | enable.auto.commit=true | enable.auto.commit=false | transactional.id + read_committed |

## 一句话总结

**Kafka Exactly-Once 是一场"Kafka 内部的魔法"：三件套让流处理精确一次，但消息一旦离开 Kafka 边界就变回 At Least Once —— 业务幂等才是终极答案。**
