# Q72 acks 三个级别

acks 控制 Producer 等待多少副本确认后才认为发送成功：0 不等待（最快但可能丢），1 等 Leader 确认（默认，Leader 宕机可能丢），all/-1 等所有 ISR 副本确认（最可靠但延迟最高）——这是一个吞吐与可靠性的经典权衡。

三个级别的核心差异在于"确认等待范围"：acks=0 发完不管，acks=1 等 Leader 刷盘，acks=all 等全体 ISR 同步。但 acks=all 不等于绝对安全——ISR 缩容时必须靠 min.insync.replicas 兜底。

## 分层代码实现

### Layer 1 — acks=0 配置（Fire and Forget，吞吐优先）

```java
// FireAndForgetProducer.java — 发完即走，不关心结果
@Configuration
public class FireAndForgetProducer {

    @Bean
    public ProducerFactory<String, String> acks0ProducerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker1:9092,broker2:9092,broker3:9092");

        // acks=0: 不等待任何确认，最高吞吐
        props.put(ProducerConfig.ACKS_CONFIG, "0");
        props.put(ProducerConfig.RETRIES_CONFIG, 0);           // 不重试
        props.put(ProducerConfig.LINGER_MS_CONFIG, 5);          // 微批量优化
        props.put(ProducerConfig.BATCH_SIZE_CONFIG, 65536);     // 64KB 批量

        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

        return new DefaultKafkaProducerFactory<>(props);
    }
}
```

```bash
# 命令行等价测试 — acks=0 发送
kafka-console-producer.sh --broker-list localhost:9092 --topic logs-topic \
  --producer-property acks=0 \
  --producer-property batch.size=65536 \
  --producer-property linger.ms=5
```

> **关键点：** acks=0 时 Producer 不等待任何响应，因此 `retries` 配置无意义。消息可能在 Producer 的发送缓冲区满时被丢弃，也可能在网络层丢失——Producer 完全无感知。仅适合日志、埋点、指标等允许少量丢失的海量数据场景。

### Layer 2 — acks=1 配置（默认，Leader 确认）

```java
// AtLeastOnceProducer.java — Leader 写入确认，Kafka 默认行为
@Configuration
public class AtLeastOnceProducer {

    @Bean
    public ProducerFactory<String, String> acks1ProducerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker1:9092,broker2:9092,broker3:9092");

        // acks=1: Leader 写入成功即返回（Kafka 默认）
        props.put(ProducerConfig.ACKS_CONFIG, "1");
        props.put(ProducerConfig.RETRIES_CONFIG, 3);            // 有限重试
        props.put(ProducerConfig.REQUEST_TIMEOUT_MS_CONFIG, 10000);

        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

        return new DefaultKafkaProducerFactory<>(props);
    }
}
```

```bash
# 命令行等价测试 — acks=1 发送
kafka-console-producer.sh --broker-list localhost:9092 --topic biz-topic \
  --producer-property acks=1 \
  --producer-property retries=3
```

> **关键点：** acks=1 是 Kafka 的默认值。Leader 写入本地日志后立即返回 ACK，Follower 异步拉取同步。隐患：Leader 返回 ACK 后、Follower 同步前宕机，该消息丢失——因为新 Leader（原 Follower）没有这条消息。

### Layer 3 — acks=all 配置（ISR 全部确认，可靠性优先）

```java
// FullyReliableProducer.java — ISR 全部副本确认才返回
@Configuration
public class FullyReliableProducer {

    @Bean
    public ProducerFactory<String, String> acksAllProducerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker1:9092,broker2:9092,broker3:9092");

        // acks=all: 所有 ISR 副本写入成功才返回
        props.put(ProducerConfig.ACKS_CONFIG, "all");            // 等价于 "-1"
        props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        props.put(ProducerConfig.DELIVERY_TIMEOUT_MS_CONFIG, 120000);

        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

        return new DefaultKafkaProducerFactory<>(props);
    }
}
```

```bash
# 命令行等价测试 — acks=all 发送
kafka-console-producer.sh --broker-list localhost:9092 --topic payment-topic \
  --producer-property acks=all \
  --producer-property enable.idempotence=true
```

> **关键点：** `acks=all` 的 "all" 不是指所有配置的副本（`replication.factor`），而是 ISR 中的全部副本。如果 ISR 当前只有 Leader（其他 Follower 都掉线了），`acks=all` 退化为 `acks=1`。这是最常见的理解误区。

### Layer 4 — acks=all + min.insync.replicas 组合使用

```bash
# === Broker 端配置（server.properties 或动态配置） ===

# 创建 topic 时指定 min.insync.replicas=2, replication.factor=3
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic critical-topic \
  --partitions 3 --replication-factor 3 \
  --config min.insync.replicas=2
# 效果: 消息必须被 Leader + 至少 1 个 Follower 确认后才返回

# === 验证 ISR 状态 ===
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic critical-topic
# 输出示例:
# Topic: critical-topic  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
#                                                              ^^^^^^^^ ISR 全部在线

# === 模拟 Follower 掉线：ISR 缩减，acks=all 仍能写入 ===
# kill Broker 3 (Follower)
# Isr 变为 1,2 — 仍有 2 个副本满足 min.insync.replicas=2
# Producer acks=all 正常写入

# === 再 kill Broker 2 (最后一个 Follower) ===
# Isr 变为 1 — 不满足 min.insync.replicas=2
# Producer 发送直接报错: NOT_ENOUGH_REPLICAS
# 宁可不可用，也不能丢消息！
```

> **关键点：** `acks=all` + `min.insync.replicas=2` 的组合是生产环境标配。`acks=all` 解决"写几个副本"的问题，`min.insync.replicas` 解决"最少几个 ISR 在线才接受写入"的问题。两者配合才能避免 ISR 收缩时的退化风险。推荐 `replication.factor=3, min.insync.replicas=2`。

## acks 三个级别核心对比

| 维度 | acks=0 | acks=1（默认） | acks=all / -1 |
|---|---|---|---|
| 确认范围 | 不等待任何确认 | Leader 写入本地日志 | 所有 ISR 副本写入 |
| 吞吐量 | 最高（~200w msg/s） | 高（~80w msg/s） | 中高（~50w msg/s） |
| 端到端延迟 | <1ms | ~2-5ms | ~5-10ms |
| 持久性保证 | 无（发送缓冲区满即丢） | Leader 写入（Follower 未同步前 Leader 宕机则丢） | ISR 全写入（仅 ISR 全宕才丢） |
| 重试意义 | 无（不等响应，不知道失败） | 有意义（可补发 Leader 未确认的消息） | 有意义（配合幂等防止重复） |
| 丢消息条件 | Producer 缓冲区满、网络丢包 | Leader 宕机且 Follower 未同步 | 所有 ISR 副本同时宕机且磁盘损坏 |
| 推荐 min.insync.replicas | 不适用 | >=1（无额外保障） | >=2（防止 ISR 缩容退化） |
| 适用场景 | 日志采集、点击流、监控指标 | 普通业务消息、通知推送 | 订单、支付、账户变动等关键消息 |
| 风险等级 | 高 | 中 | 低（需配 min.insync.replicas） |

## 一句话总结

**acks 的选择本质是"确认范围越大越安全但越慢"的权衡——acks=0 追求极致速度但放弃可靠性，acks=1 在速度和安全间取折中（也是默认值），acks=all 以更高延迟换取最强持久性，但必须搭配 min.insync.replicas 才能真正闭环。**
