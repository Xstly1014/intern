# Q73 Broker 端不丢消息

Broker 不丢消息依赖四层保障：副本机制（多 Broker 冗余）、ISR 最小确认（acks=all + min.insync.replicas）、禁止 unclean 选举（落后副本不能当 Leader）、日志持久化（磁盘恢复）——四层叠加后，只有所有副本同时物理损毁才可能丢数据。

Broker 故障转移的核心链路是：Controller 监听 ZooKeeper 感知宕机 → 从 ISR 中选新 Leader → Producer/Consumer 通过 Metadata 刷新自动切换。整个过程由 Kafka 自动完成，业务代码无需任何修改。

## 分层代码实现

### Layer 1 — Broker 副本与容灾配置

```bash
# === Broker 端 server.properties 核心参数 ===

# 1. 副本机制：每个 Partition 至少 3 个副本
default.replication.factor=3

# 2. ISR 最小确认：至少 2 个 ISR 副本确认才接受写入
min.insync.replicas=2

# 3. 禁止 unclean Leader 选举（数据落后的副本不能当 Leader）
unclean.leader.election.enable=false

# 4. 日志持久化：确保写入磁盘
log.flush.interval.messages=10000      # 每 10000 条消息刷盘
log.flush.interval.ms=1000             # 或每 1 秒刷盘
log.segment.bytes=1073741824           # 1GB 一个日志段

# 5. Controller 相关
auto.leader.rebalance.enable=true      # 自动 Leader 再平衡

# === 创建 Topic 时显式指定（推荐） ===
kafka-topics.sh --bootstrap-server broker1:9092,broker2:9092,broker3:9092 \
  --create --topic order-topic \
  --partitions 6 \
  --replication-factor 3 \
  --config min.insync.replicas=2 \
  --config unclean.leader.election.enable=false

# 验证 Topic 配置
kafka-topics.sh --bootstrap-server broker1:9092 \
  --describe --topic order-topic
# Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
# Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
# ... Leader 均匀分布在 3 个 Broker 上
```

> **关键点：** `replication.factor=3` 意味着每个 Partition 有 3 份副本分布在 3 个不同 Broker。`min.insync.replicas=2` 配合 Producer 的 `acks=all`，确保至少 2 个副本写入成功才返回——容忍 1 个 Broker 宕机而不丢数据。

### Layer 2 — 模拟 Broker 宕机与 Leader 切换

```bash
# === 模拟测试步骤 ===

# Step 1: 查看当前集群状态
kafka-broker-api-versions.sh --bootstrap-server broker1:9092 | head -5
# 正常输出: broker1:9092 (id: 1 rack: null) -> ...

# Step 2: 查看 order-topic 的 Leader 分布
kafka-topics.sh --bootstrap-server broker1:9092 --describe --topic order-topic
# Partition: 0  Leader: 1  Isr: 1,2,3  ← P0 Leader 在 Broker 1

# Step 3: 发送消息并观察
kafka-console-producer.sh --broker-list broker1:9092,broker2:9092,broker3:9092 \
  --topic order-topic --producer-property acks=all
# 输入: msg-001, msg-002, msg-003

# Step 4: Kill Broker 1 (P0 的 Leader)
kill -9 $(cat /tmp/kafka-broker-1.pid)

# Step 5: 立即查看 Leader 变化（Controller 秒级完成选举）
sleep 3
kafka-topics.sh --bootstrap-server broker2:9092 --describe --topic order-topic
# Partition: 0  Leader: 2  Isr: 2,3  ← Leader 自动切换到 Broker 2!
#                               ^ P0 Leader 变为 2，数据在 ISR 中完好

# Step 6: Producer 继续发送（自动发现新 Leader）
# 输入: msg-004, msg-005  ← 仍然可以发送，acks=all 下延迟有轻微增加

# Step 7: Consumer 验证数据完整性
kafka-console-consumer.sh --bootstrap-server broker2:9092,broker3:9092 \
  --topic order-topic --from-beginning
# msg-001, msg-002, msg-003, msg-004, msg-005  ← 全部在，一条不丢！

# Step 8: 恢复 Broker 1
# 启动 Broker 1，重新加入 ISR
# Isr: 2,3 → Isr: 1,2,3，集群恢复健康
```

> **关键点：** 整个切换过程对 Producer 和 Consumer 完全透明。Producer 通过 Metadata 请求发现新 Leader，Consumer 自动从新 Leader 拉取。因为所有 ISR 副本数据一致，Consumer 不会读到重复或丢失的消息。这个切换通常只需几秒钟。

### Layer 3 — 跨机房部署方案（跨 AZ Broker 分布 + Rack Awareness）

```bash
# === Broker 端：启用 Rack Awareness ===
# 每个 Broker 的 server.properties 中指定所属机架/可用区

# Broker 1 — 位于 AZ-A（可用区 A）
# server-1.properties:
broker.id=1
broker.rack=az-a
listeners=PLAINTEXT://broker1-az-a:9092

# Broker 2 — 位于 AZ-B（可用区 B）
# server-2.properties:
broker.id=2
broker.rack=az-b
listeners=PLAINTEXT://broker2-az-b:9092

# Broker 3 — 位于 AZ-C（可用区 C）
# server-3.properties:
broker.id=3
broker.rack=az-c
listeners=PLAINTEXT://broker3-az-c:9092

# === 创建 Topic 时 Kafka 自动跨 AZ 分布副本 ===
kafka-topics.sh --bootstrap-server broker1-az-a:9092,broker2-az-b:9092,broker3-az-c:9092 \
  --create --topic global-topic \
  --partitions 3 \
  --replication-factor 3 \
  --config min.insync.replicas=2
# 效果: 每个 Partition 的 3 个副本分布在 az-a, az-b, az-c

# === 验证跨 AZ 分布 ===
kafka-topics.sh --bootstrap-server broker1-az-a:9092 --describe --topic global-topic
# Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
# Broker 1 (az-a), Broker 2 (az-b), Broker 3 (az-c) — 完美分布!

# === 模拟整个 AZ 宕机 ===
# Kill Broker 1 (az-a 全部宕机)
# Isr 变为 2,3 — 仍在 az-b 和 az-c
# acks=all + min.insync.replicas=2 继续正常工作
# 数据不丢！服务不中断！
```

> **关键点：** 跨 AZ 部署是防范机房级故障的核心手段。`broker.rack` 配置启用后，Kafka 自动确保同一 Partition 的副本分布在不同机架/AZ。一个 AZ 整体宕机时，其他 AZ 的 ISR 副本仍能满足 `min.insync.replicas` 的要求。

### Layer 4 — 极端故障演练与恢复

```bash
# === 极端场景：所有 Broker 同时宕机 ===

# 场景: 整个集群断电
# 同时 kill 所有 Broker:
kill -9 $(cat /tmp/kafka-broker-1.pid)
kill -9 $(cat /tmp/kafka-broker-2.pid)
kill -9 $(cat /tmp/kafka-broker-3.pid)

# 恢复步骤:
# 1. 按顺序启动 Broker（先启动 Controller 所在 Broker）
# 2. 检查日志恢复状态
ls -la /var/lib/kafka/data/order-topic-0/
# 00000000000000000000.log  ← 所有日志段文件完好
# 00000000000000000000.index
# 3. 启动后 Kafka 自动从日志文件恢复状态
# 4. 检查 ISR 是否全部恢复
kafka-topics.sh --bootstrap-server broker1:9092 --describe --topic order-topic
# Isr: 1,2,3  ← 全部恢复!

# === 极端恢复：单 Broker 磁盘损坏 ===
# 1. 从其他 Broker 的副本复制数据目录
rsync -av broker2:/var/lib/kafka/data/order-topic-0/ broker1:/var/lib/kafka/data/order-topic-0/
# 2. 启动 Broker 1，自动加入 ISR
# 3. 等待副本同步完成

# === 极端场景下的数据安全边界 ===
echo "最坏情况概率分析:"
echo "  单 Broker 磁盘损坏概率: ~1%/年 (企业级 SSD)"
echo "  3 个 Broker 同时损坏概率: (0.01)^3 = 0.0001% ≈ 百万分之一"
echo "  跨 3 个 AZ 部署后同时损坏概率: 趋近于 0"
```

> **关键点：** Kafka 的 WAL 日志文件就是最终的数据安全保障。只要日志段（`.log`）文件在磁盘上没有物理损坏，重启后数据就能完整恢复。跨 AZ 部署进一步将"所有副本同时物理损毁"的概率降到统计学上可以忽略不计的水平。

## Broker 可靠性保障层级

| 层级 | 机制 | 防护场景 | 局限 |
|---|---|---|---|
| L1: 副本冗余 | replication.factor >= 3，Partition 副本分布在不同 Broker | 单 Broker 宕机/磁盘故障 | 更多副本 = 更多磁盘和网络开销 |
| L2: ISR 最小确认 | acks=all + min.insync.replicas=2，消息至少写入 2 个 ISR 副本 | Leader 宕机后 Follower 无数据 | ISR 数量不足时拒绝写入（可用性 vs 一致性权衡） |
| L3: 禁止 Unclean 选举 | unclean.leader.election.enable=false | 数据落后的 OSR 副本不能当选 Leader 导致数据回退 | ISR 全宕时 Partition 彻底不可用（宁可不可用也不丢数据） |
| L4: 日志持久化 | 消息写入 `.log` 文件，OS 缓存 + 定时刷盘策略 | 进程重启、OS 崩溃 | 未刷盘的 OS 缓存数据在断电时可能丢失（默认异步刷盘） |
| L4+: 跨 AZ 部署 | broker.rack 启用机架感知，副本跨可用区分布 | 整个 AZ（机房）宕机 | 跨 AZ 网络延迟增加 1-5ms |
| 极限兜底 | 跨 Region 异步复制（MirrorMaker 2） | 整个 Region 故障 | 异步复制有延迟，可能丢最后几秒的数据 |

## 一句话总结

**Broker 端不丢消息不是某一个配置的作用，而是"多副本冗余 + ISR 同步确认 + 禁止落后副本当选 + 磁盘持久化"四层防御环环相扣的结果——其中 unclean.leader.election.enable=false 是最容易被忽略但最致命的一环，它决定了故障时是"丢数据"还是"暂不可用"。**
