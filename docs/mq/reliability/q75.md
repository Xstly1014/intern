# Q75 unclean leader election

unclean.leader.election.enable 控制当 ISR（In-Sync Replica）集合为空时，是否允许从非 ISR 副本（OSR）中选举 Leader。设为 false 是 Kafka 自 0.11 版本以来的默认值，选 CP 一致性强；设为 true 则选 AP 可用性高，但以丢失未同步消息为代价。

## unclean.leader.election.enable 代码实践

### Layer 1 — unclean.leader.election.enable 配置

```bash
# ============ Broker 级别配置（全局生效）============
# server.properties（所有 Broker 统一配置）
unclean.leader.election.enable=false    # Kafka 0.11+ 默认值，强烈推荐

# ============ 验证配置 ============
kafka-configs.sh --bootstrap-server localhost:9092 \
  --broker 0 --describe --all | grep unclean
# 输出：unclean.leader.election.enable=false sensitive=false synonyms={STATIC_BROKER_CONFIG:unclean.leader.election.enable=false}
```
unclean.leader.election.enable 是 Broker 级全局配置，集群所有 Broker 应保持一致，不允许 Topic 级覆盖。

### Layer 2 — 查看 ISR 状态与 Leader 选举

```bash
# ============ 查看 Topic 的 Partition 分布与 ISR ============
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic orders
# 示例输出：
# Topic: orders  PartitionCount: 1  ReplicationFactor: 3
#   Partition: 0  Leader: 0  Replicas: 0,1,2  Isr: 0,1,2
#                                                   ^^^^^^^ ISR 列表

# ============ 监控 ISR 收缩（shrink）============
# 推荐使用 kafka-metadata.sh 或 JMX 指标实时监控：
# kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions
# 该指标 > 0 表示有 Partition 的 ISR 不足（未达到 replication factor）

# 查看未完全同步的 Partition
kafka-topics.sh --bootstrap-server localhost:9092 --describe --under-replicated-partitions

# 查看没有 Leader 的 Partition（ISR 为空时的极端情况）
kafka-topics.sh --bootstrap-server localhost:9092 --describe --unavailable-partitions
```
`--under-replicated-partitions` 显示副本数不足的 Partition，是 ISR 收缩的前兆。`--unavailable-partitions` 显示无法选举 Leader 的 Partition（即 ISR=[] 且 unclean=false 时的状态）。

### Layer 3 — 故障演练：模拟 ISR 全挂

```bash
# ============ Step 1: 创建测试 Topic ============
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic test-unclean \
  --partitions 1 --replication-factor 3

# ============ Step 2: 确认配置 ============
kafka-configs.sh --bootstrap-server localhost:9092 \
  --broker 0 --describe --all | grep unclean
# 预期：unclean.leader.election.enable=false

# ============ Step 3: 写入一批消息 ============
for i in $(seq 1 200); do
  echo "msg-$i" | kafka-console-producer.sh \
    --bootstrap-server localhost:9092 --topic test-unclean
done
echo "写入 200 条消息完成"

# ============ Step 4: 停掉所有 ISR 中的 Broker（模拟 ISR=[]）============
# 先确认 ISR 中有哪些 Broker
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic test-unclean
# 逐个停掉 ISR 中的 Broker
kafka-server-stop.sh   # Broker 0
kafka-server-stop.sh   # Broker 1
kafka-server-stop.sh   # Broker 2

# ============ Step 5: 检查 Partition 状态 — 预期不可用 ============
kafka-topics.sh --bootstrap-server localhost:9091 --describe --topic test-unclean 2>&1
# 预期：Leader: -1（没有 Leader）
# 或：Leader: none   Isr: （空）
# Consumer 读取会报错：LEADER_NOT_AVAILABLE

# ============ Step 6: 恢复 Broker — 从 ISR 选举 ============
kafka-server-start.sh config/server0.properties
# 等待 Broker 恢复后重新查看
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic test-unclean
# 预期：Leader 重新选举，数据完整（msg 1-200 都在）

# ============ 对比：如果 unclean=true，非 ISR 副本可能被选为 Leader ============
# 某些场景下存在一个落后副本 B2（不在 ISR），B2 数据只到 msg-100
# unclean=true 时 B2 被选为 Leader → msg 101-200 永久丢失
```
演练的核心结论是：unclean=false 时 ISR 为空会导致 Partition 不可用，但这是"安全不可用"，数据不会丢。恢复任意一个 ISR Broker 后数据完整复原。

### Layer 4 — 生产环境监控与告警

```java
// ============ 监控 ISR 收缩，在 ISR=[] 前提前告警 ============
@Component
public class KafkaHealthMonitor {

    // 基于 JMX 指标：UnderReplicatedPartitions
    // 或通过 AdminClient 定期检查 ISR 状态

    @Scheduled(fixedDelay = 30_000) // 每 30 秒检查一次
    public void checkISRHealth() {
        try (AdminClient admin = AdminClient.create(props)) {
            // 获取所有 Topic 的元数据
            DescribeTopicsResult result = admin.describeTopics(
                admin.listTopics().names().get()
            );
            Map<String, TopicDescription> topics = result.allTopicNames().get();

            int underReplicatedCount = 0;
            List<String> warnings = new ArrayList<>();

            for (TopicDescription td : topics.values()) {
                for (TopicPartitionInfo pInfo : td.partitions()) {
                    int isrSize = pInfo.isr().size();
                    int replicaSize = pInfo.replicas().size();

                    if (isrSize < replicaSize) {
                        underReplicatedCount++;
                    }
                    // 危险：ISR 只剩 1 个（Leader 自己）
                    if (isrSize <= 1 && replicasBefore > 1) {
                        warnings.add(String.format(
                            "CRITICAL: %s-%d ISR=%d/%d (只剩 Leader 在 ISR！)",
                            td.name(), pInfo.partition(), isrSize, replicaSize
                        ));
                    }
                    // 极端危险：ISR 为空
                    if (isrSize == 0) {
                        warnings.add(String.format(
                            "EMERGENCY: %s-%d ISR 为空，Partition 即将不可用！",
                            td.name(), pInfo.partition()
                        ));
                    }
                }
            }

            // 上报到 Prometheus / Grafana
            gaugeUnderReplicated.set(underReplicatedCount);

            // 告警通知
            if (!warnings.isEmpty()) {
                String alertMsg = String.join("\n", warnings);
                sendAlert(alertMsg);
            }
        } catch (Exception e) {
            log.error("ISR 健康检查失败", e);
        }
    }

    private void sendAlert(String msg) {
        // 接入飞书/钉钉/企业微信/邮件告警
        // ISR 收缩到 1 时必须触发 P2 告警
        // ISR 为空时必须触发 P0 告警
    }
}
```
监控是 unclean leader election 策略的"前线哨兵"。当 ISR 收缩到 1（只剩 Leader）时触发 P2 告警，必须在 ISR 变为空之前介入处理。ISR 为空时触发 P0 告警，此时 Partition 已经不可用。

| 维度 | false（推荐，Kafka 0.11+ 默认） | true |
|---|---|---|
| Leader 选举范围 | 仅限 ISR 中的副本 | ISR 为空时可从非 ISR 副本选 |
| ISR=[] 时行为 | Partition 不可用（LEADER_NOT_AVAILABLE） | 立即恢复可用（牺牲一致性） |
| 数据丢失风险 | 无 — 只在 ISR 内选举 | 有 — 非 ISR 副本可能落后任意数量消息 |
| 可用性 | 低（ISR=[] 时不可用） | 高（ISR=[] 时仍可恢复） |
| 一致性保证 | 强 — 选出的 Leader 一定有最新数据 | 弱 — 选出 Leader 可能落后 |
| CAP 倾向 | CP（一致性强） | AP（可用性高） |
| 故障恢复后 | 自动恢复，数据完整 | 可能已丢数据，无法回滚 |
| 适用场景 | 订单、支付等所有核心业务（适合 99% 场景） | 日志采集等完全容忍丢失的极端场景（几乎不存在） |

## 一句话总结

**unclean.leader.election.enable 是 Kafka 中最不该动的一票否决红线 — 设为 false 用短暂不可用换取数据零丢失（CP），设为 true 用永久丢数据换取即时恢复（AP），而生产系统中丢消息的代价永远是短暂不可用的无数倍。**
