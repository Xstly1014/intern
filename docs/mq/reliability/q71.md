# Q71 生产者不丢消息

生产者不丢消息依赖五重保障层层递进：acks=all 确保多副本写入，retries 兜底网络抖动，enable.idempotence 消除重试产生的重复，callback 感知失败并落库补偿，本地缓存作为最终兜底——缺一环都不够。

五层保障环环相扣：每一层解决上一层的遗留问题。acks=all 保证写入可靠，retries 兜底网络瞬时故障，幂等消除重试副作用，callback 让业务方有感知，本地落库是最后的保险丝。

## 分层代码实现

### Layer 1 — 核心配置：acks=all + retries + 幂等

```java
// KafkaProducerConfig.java — 核心可靠性配置
@Configuration
public class KafkaProducerConfig {

    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker1:9092,broker2:9092,broker3:9092");

        // === 五重保障核心参数 ===
        props.put(ProducerConfig.ACKS_CONFIG, "all");                    // L1: 所有 ISR 副本确认
        props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);     // L2: 无限重试
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);       // L3: 幂等生产者
        props.put(ProducerConfig.DELIVERY_TIMEOUT_MS_CONFIG, 120000);    //    总超时 2 分钟
        props.put(ProducerConfig.REQUEST_TIMEOUT_MS_CONFIG, 30000);      //    单次请求超时 30s

        // 序列化 & 压缩
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "snappy");

        return new DefaultKafkaProducerFactory<>(props);
    }
}
```

> **关键点：** `enable.idempotence=true` 会自动设置 `acks=all`, `retries=MAX_VALUE`, `max.in.flight.requests.per.connection=5`，所以不必重复配置前三项——但显式写出来能让意图更清晰。

### Layer 2 — 幂等生产者实现

```java
// IdempotentOrderProducer.java — 确保重试不产生重复订单消息
@Service
public class IdempotentOrderProducer {

    private final KafkaTemplate<String, String> kafkaTemplate;

    public IdempotentOrderProducer(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    /**
     * 发送订单消息（幂等保证）
     * Broker 用 ProducerId + SequenceNumber 判定重复
     */
    public void sendOrder(String orderId, String payload) {
        ProducerRecord<String, String> record =
            new ProducerRecord<>("order-topic", orderId, payload);

        // 幂等模式下重试自动去重
        kafkaTemplate.send(record);
    }

    // === 如需 Exactly-Once 语义（跨分区事务） ===
    // 配合 @Transactional + transactional.id 使用
    // @Transactional("kafkaTransactionManager")
    // public void sendBatchWithTransaction(List<Order> orders) { ... }
}
```

> **关键点：** 幂等生产者去重依赖 `ProducerId`（Broker 分配）和 `SequenceNumber`（Producer 自增）。Broker 对每个 `TopicPartition` 维护最近 5 个 `SequenceNumber` 用于去重。重启后 ProducerId 变化，但业务逻辑无需感知。

### Layer 3 — 回调处理失败 + 本地 SQLite 落库兜底

```java
// ReliableOrderProducer.java — callback 感知 + SQLite 兜底
@Service
public class ReliableOrderProducer {

    private final KafkaTemplate<String, String> kafkaTemplate;
    private final FailedMessageRepository failedRepo;  // SQLite 本地存储
    private final ScheduledExecutorService retryExecutor;

    public ReliableOrderProducer(KafkaTemplate<String, String> kafkaTemplate,
                                  FailedMessageRepository failedRepo) {
        this.kafkaTemplate = kafkaTemplate;
        this.failedRepo = failedRepo;
        this.retryExecutor = Executors.newSingleThreadScheduledExecutor();

        // 启动后台重试线程
        this.retryExecutor.scheduleWithFixedDelay(
            this::retryFailedMessages, 10, 10, TimeUnit.SECONDS);
    }

    /**
     * 带回调的可靠发送：失败落库，后台异步重发
     */
    public void sendReliably(String topic, String key, String payload) {
        ProducerRecord<String, String> record =
            new ProducerRecord<>(topic, key, payload);

        ListenableFuture<SendResult<String, String>> future =
            kafkaTemplate.send(record);

        future.addCallback(
            result -> {
                // 发送成功：记录 offset
                log.info("Sent OK: topic={}, partition={}, offset={}",
                    result.getRecordMetadata().topic(),
                    result.getRecordMetadata().partition(),
                    result.getRecordMetadata().offset());
            },
            ex -> {
                // 发送失败：落库兜底
                log.error("Send FAILED: topic={}, key={}", topic, key, ex);
                failedRepo.save(new FailedMessage(topic, key, payload, System.currentTimeMillis()));
            }
        );
    }

    /**
     * 后台线程：从 SQLite 读取失败消息并重发
     */
    private void retryFailedMessages() {
        List<FailedMessage> messages = failedRepo.findPending(100);
        for (FailedMessage msg : messages) {
            try {
                kafkaTemplate.send(msg.getTopic(), msg.getKey(), msg.getPayload()).get(5, TimeUnit.SECONDS);
                failedRepo.markSuccess(msg.getId());
            } catch (Exception e) {
                failedRepo.incrementRetry(msg.getId());
                log.warn("Retry failed: id={}, retries={}", msg.getId(), msg.getRetryCount());
            }
        }
    }
}
```

> **关键点：** 回调里不要做重试逻辑——重试交给 Producer 内置的 `retries`。回调只做"记录失败事实"这一件事：写日志、落库、发告警。后台异步重发线程是"最终保障"，处理内置重试耗尽后的残留消息。

### Layer 4 — 端到端可靠性验证（控制变量测试）

```bash
# === 测试 1: 正常场景 — 预期全部 delivered ===
kafka-console-producer.sh --broker-list localhost:9092 --topic test-reliable --producer-property acks=all
# 输入 100 条消息，观察 Consumer 侧全部收到

# === 测试 2: acks=0 丢消息验证 — 预期有 dropped ===
# 先模拟 Broker 突然 kill
kill -9 $(cat /tmp/kafka-broker-1.pid)
# 此时 acks=0 的 Producer 不感知，消息丢失
kafka-console-producer.sh --broker-list localhost:9092 --topic test-reliable --producer-property acks=0

# === 测试 3: acks=all + retries — 预期重试后 delivered ===
# Broker 短暂不可用 5s 后恢复
kafka-console-producer.sh --broker-list localhost:9092 --topic test-reliable \
  --producer-property acks=all \
  --producer-property retries=10 \
  --producer-property request.timeout.ms=3000

# === 测试 4: 幂等验证 — 预期无重复 ===
# Consumer 侧统计 key 去重数量
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic test-reliable \
  --property print.key=true | awk '{print $1}' | sort | uniq -c | grep -v "^ *1 "
# 幂等生产者保证：每个 key 只出现一次
```

## 可靠性等级对比

| 维度 | Fire and Forget | At Least Once | 幂等 At Least Once | Exactly Once (事务) |
|---|---|---|---|---|
| acks 配置 | acks=0 | acks=1 | acks=all | acks=all |
| 重试机制 | 无 | retries>0 | retries=MAX_VALUE | retries=MAX_VALUE |
| 幂等保证 | 无 | 无 | enable.idempotence=true | transactional.id |
| 消息语义 | 可能丢 | 至少一次（可能重复） | 至少一次（无重复） | 精确一次 |
| 吞吐量 | 最高 (~200w msg/s) | 高 (~80w msg/s) | 中高 (~50w msg/s) | 中 (~30w msg/s) |
| 延迟 | <1ms | ~2-5ms | ~5-10ms | ~10-20ms |
| 使用场景 | 日志/指标采集 | 普通业务消息 | 订单/支付消息 | 跨分区/跨 Topic 原子写入 |
| 丢消息风险 | 高 | 中（Leader 宕机） | 极低（ISR 全宕） | 极低（ISR 全宕） |

## 一句话总结

**生产者不丢消息的本质不是单个配置项的开关，而是一套从 Broker 端副本确认（acks=all）到网络重试（retries）到去重（idempotence）再到业务兜底（callback+本地缓存）的纵深防御体系——任何一环单独使用都可能失败，五层叠加才能做到真正可靠。**
