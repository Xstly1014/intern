# Q78 幂等生产者

Kafka 幂等生产者通过 PID（Producer ID）+ Sequence Number 机制保证单 Partition 内消息不重复：每条消息携带 (PID, Partition, seqNum)，Broker 端按 (PID, Partition) 维度维护 maxSeq 去重 —— seq == maxSeq+1 接受，seq <= maxSeq 丢弃，seq > maxSeq+1 报错。Kafka 3.0+ 默认开启。

幂等生产者的核心是 Broker 端的 maxSeq 状态表：每当收到一条消息，Broker 检查 seq 与 maxSeq 的关系 —— 连续递增则接收并更新 maxSeq，小于等于则丢弃重复，跳跃过大则报错。这套机制简单有效，但仅限单 Session 单 Partition。

## 代码：幂等生产者分层解析

### Layer 1 — enable.idempotence 配置（Kafka 3.0+ 默认开启）

```java
// ============ Layer 1: 幂等生产者基本配置 ============
// Kafka 3.0+ 中 enable.idempotence 默认为 true，无需显式设置
@Configuration
public class KafkaProducerConfig {

    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");

        // Kafka 3.0+ 默认 true，显式写出更清晰
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

        // 幂等要求这三项自动强制：
        // - acks=all（等所有 ISR 确认）
        // - retries > 0（默认 Integer.MAX_VALUE）
        // - max.in.flight.requests.per.connection <= 5

        return new DefaultKafkaProducerFactory<>(props);
    }

    @Bean
    public KafkaTemplate<String, String> kafkaTemplate(
            ProducerFactory<String, String> pf) {
        return new KafkaTemplate<>(pf);
    }
}
// 开启幂等后，Producer 首次连接 Broker 时自动获取 PID
// 底层通过 InitProducerIdRequest 获取全局唯一的 PID
```

开启 `enable.idempotence=true` 后，Producer 启动时通过 `InitProducerIdRequest` 向 Broker 申请唯一 PID，之后所有消息都自动附带 (PID, Partition, seqNum)，对业务代码完全透明。

### Layer 2 — PID 和 seq 的工作原理（代码模拟）

```java
// ============ Layer 2: PID 分配与 seq 递增原理 ============
// 以下为 Kafka 内部逻辑的概念性模拟，展示去重核心机制
public class IdempotentProducerInternals {

    // --- Producer 端 ---
    // 每个 Producer 实例拥有全局唯一的 PID（由 Broker 分配）
    private long pid;                         // e.g., 100
    // 按 Partition 维度维护 sequence number
    private Map<Integer, Integer> seqByPartition = new ConcurrentHashMap<>();

    public void send(String topic, int partition, String message) {
        // 1. 获取当前 Partition 的下一个 seq（从 0 递增）
        int seq = seqByPartition.merge(partition, 0,
                (old, init) -> old + 1);

        // 2. 构造 ProduceRequest，携带 (PID, Partition, seq)
        ProduceRequest request = ProduceRequest.builder()
                .pid(pid)              // PID=100
                .partition(partition)  // Partition=0
                .sequenceNumber(seq)   // seq=0,1,2,3...
                .message(message)
                .build();

        // 3. 发送到 Broker
        broker.handle(request);
    }

    // --- Broker 端 ---
    // Broker 为每个 (PID, Partition) 维护最后成功写入的 seq
    private Map<String, Integer> maxSeqMap = new ConcurrentHashMap<>();
    // Key = "PID-Partition", e.g., "100-0"

    public void handle(ProduceRequest request) {
        String key = request.pid + "-" + request.partition;
        int currentSeq = request.sequenceNumber;
        int maxSeq = maxSeqMap.getOrDefault(key, -1);  // 初始 -1

        if (currentSeq == maxSeq + 1) {
            // 情况1: 正常递增 → 接受消息，更新 maxSeq
            appendToLog(request);
            maxSeqMap.put(key, currentSeq);
            // maxSeq: -1→0→1→2→3...

        } else if (currentSeq <= maxSeq) {
            // 情况2: seq 小于等于 maxSeq → 重复消息，丢弃
            // 例如：重试导致 seq=2 再次到达，而 maxSeq 已经是 3
            // → 直接返回成功但不写入，Producer 收到确认
            return;  // 丢弃但返回成功，不抛异常

        } else {
            // 情况3: seq > maxSeq+1 → 乱序，数据丢失
            // 例如：maxSeq=2，收到 seq=10 → 中间消息丢失
            throw new OutOfOrderSequenceException(
                "Invalid sequence number: expected " + (maxSeq + 1)
                + " but got " + currentSeq);
        }
    }
}
// 核心精髓：Broker 端 maxSeq 状态表是幂等唯一真相源，
// seq 必须连续递增，任何跳跃都视为异常
```

Broker 端的 maxSeq 状态表是整个幂等机制的核心：它不存储每条消息的 seq，只记住每个 (PID, Partition) 的最大值，通过简单的大小比较即可判断接受、丢弃还是报错。

### Layer 3 — 跨 Session 问题：重启后 PID 变化导致重复

```java
// ============ Layer 3: 跨 Session 问题 ============
// Producer 重启后 PID 重新分配，Broker 认为是新 Producer
// 旧 Session 的重试消息可能变成"新消息"
public class CrossSessionProblem {

    public void demonstrateCrossSessionIssue() {
        // Session 1: PID=100, Partition-0, seq=0,1,2 已成功
        // Broker maxSeq[100-0] = 2

        // --- Producer 重启 ---
        // Session 2: 新 PID=200, Partition-0, seq 重新从 0 开始
        // Broker 为新 PID 创建 maxSeq[200-0] = -1
        // 旧 PID=100 的重试消息 seq=2 可能仍在网络链路中...

        // 问题: 旧 PID=100 的消息 seq=2 到达 Broker
        // → Broker 检查 maxSeq[100-0]=2, seq=2 <= 2, 正常丢弃
        // → 但新 PID=200 的 seq=0,1,2 消息可能与旧消息重叠
        // → 如果旧 PID 未过期就收到新 PID 消息，可能导致乱序

        // Kafka 的防护: PID epoch 机制
        // 同一个 transactional.id 每次重启 epoch 递增
        // 旧 epoch 的消息到达时，Broker 直接拒绝
        // 但 enable.idempotence 不涉及 epoch ——
        // 这是幂等生产者的本质限制！
    }
}
// 结论：幂等生产者无法解决跨 Session 重复，
// 需要 transactional.id 启用事务 Producer（见 Layer 4）
```

跨 Session 问题是幂等生产者最关键的面试考点：Producer 重启后获取新 PID，Broker 为新 PID 创建新的 maxSeq 条目，但旧 PID 的重试消息仍在网络中，新旧消息可能交叠。解决之道是 `transactional.id`。

### Layer 4 — transactional.id 解决跨 Session 幂等

```java
// ============ Layer 4: transactional.id 跨 Session 幂等 ============
// transactional.id 让 Producer 跨重启保持事务身份
// Coordinator 维护 (transactional.id → PID, epoch) 映射
@Configuration
@EnableTransactionManagement
public class TransactionalIdConfig {

    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

        // transactional.id 解决跨 Session 问题
        props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-service-v1");
        // Producer 重启后:
        // 1. initTransactions() 向 Coordinator 发送
        //    InitProducerIdRequest(transactional.id="order-service-v1")
        // 2. Coordinator 查找该 transactional.id 的上一次 (PID, epoch)
        // 3. 返回原 PID + epoch+1（而非分配新 PID）
        // 4. 旧 epoch 的消息被自动拒绝（FencedException）

        return new DefaultKafkaProducerFactory<>(props);
    }
}
// transactional.id 的本质作用：
// 将 Producer 的"身份"从 PID（随 Session 变化）
// 升级为 transactional.id（持久化在 Coordinator 端）
// 配合 epoch 递增隔离僵尸 Producer
```

`transactional.id` 将 Producer 身份从易变的 PID 提升为持久化的逻辑标识，配合 epoch 递增机制，Coordinator 能精确识别并拒绝旧 Session 的过期消息，从而解决跨 Session 重复问题。

## 普通 vs 幂等 vs 事务 Producer 对比

| 维度 | 普通 Producer | 幂等 Producer | 事务 Producer |
|---|---|---|---|
| 配置方式 | 默认（无特殊配置） | enable.idempotence=true | transactional.id + 幂等 |
| 去重保证 | 无（retries 可能重复） | 单 Partition 单 Session | 跨 Partition 跨 Session |
| acks 要求 | 0/1/all 均可 | 强制 all | 强制 all |
| PID 机制 | 无 | 自动获取，重启后变化 | transactional.id 绑定，重启恢复 |
| 性能开销 | 最低 | 中等（acks=all） | 高（+事务协调开销） |
| 典型场景 | 日志收集、指标上报 | 一般业务消息 | Kafka Streams 流处理 |
| Kafka 3.0+ 默认 | 否（需显式关闭） | 是 | 否（需显式开启） |

## 一句话总结

**幂等生产者本质上是 Broker 端的一张 (PID, Partition) -> maxSeq 状态表：seq 连续递增就接收，不连续就拒绝——简单、高效，但跨 Session 的那一刻，你需要 transactional.id 来接管身份。**
