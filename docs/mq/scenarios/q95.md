# Q95 日志收集系统

百万级日志/秒的收集架构采用三级流水线：Filebeat 采集层部署于各业务服务器 → Kafka 缓冲层按业务分 Topic（access/error/business），30 Partition + 3 副本 → Logstash/Flink 消费层分别清洗富化写入 ES（实时搜索）和 HDFS（离线分析），全程通过 Lag 监控告警保证管道健康。

日志收集三级流水线是典型的生产者-消费者分离架构——Filebeat 作为轻量级采集器只负责"搬运"日志文件到 Kafka，Kafka 按业务维度拆分 Topic 并行缓冲，Logstash 和 Flink 各自以独立 Consumer Group 订阅消费，互不阻塞。整个管道容忍少量日志丢失（acks=1），优先保证吞吐量，并通过 lz4 压缩节省跨机房带宽。

## 端到端配置与代码实现

### Layer 1 — Filebeat 配置（采集日志发 Kafka）

```yaml
# filebeat.yml — 部署在每台业务服务器上
filebeat.inputs:
  - type: log
    enabled: true
    paths:
      - /var/log/app/access.log
    fields:
      topic: access
      server_id: ${SERVER_ID}
    multiline:
      pattern: '^\d{4}-\d{2}-\d{2}'
      negate: true
      match: after

  - type: log
    enabled: true
    paths:
      - /var/log/app/error.log
    fields:
      topic: error
      server_id: ${SERVER_ID}

  - type: log
    enabled: true
    paths:
      - /var/log/app/business.log
    fields:
      topic: business
      server_id: ${SERVER_ID}

# 输出到 Kafka
output.kafka:
  hosts: ["kafka-broker-1:9092", "kafka-broker-2:9092", "kafka-broker-3:9092"]
  topic: '%{[fields.topic]}'        # 按字段路由到不同 Topic
  partition.round_robin:
    reachable_only: true
  required_acks: 1                   # 容忍少量丢失，优先吞吐
  compression: lz4                   # 压缩节省带宽
  max_message_bytes: 1000000
  client_id: filebeat-${SERVER_ID}

# 日志处理
processors:
  - add_host_metadata: ~
  - add_cloud_metadata: ~
  - drop_fields:
      fields: ["agent.ephemeral_id"]
```

### Layer 2 — Kafka Topic 创建与分区规划（30 Partition, 3 副本, 7 天保留）

```bash
# 创建 3 个 Topic，每个 30 Partition, 3 副本, 7 天保留
kafka-topics.sh --bootstrap-server kafka-broker-1:9092 \
  --create --topic access \
  --partitions 30 --replication-factor 3 \
  --config retention.ms=604800000 \
  --config compression.type=lz4 \
  --config segment.bytes=1073741824 \
  --config max.message.bytes=1000000

kafka-topics.sh --bootstrap-server kafka-broker-1:9092 \
  --create --topic error \
  --partitions 30 --replication-factor 3 \
  --config retention.ms=604800000 \
  --config compression.type=lz4

kafka-topics.sh --bootstrap-server kafka-broker-1:9092 \
  --create --topic business \
  --partitions 30 --replication-factor 3 \
  --config retention.ms=604800000 \
  --config compression.type=lz4

# Producer 优化配置 (server.properties or topic-level)
# batch.size=65536            (64KB 批量发送)
# linger.ms=10                (最多等 10ms 凑批)
# compression.type=lz4        (lz4 在速度和压缩比之间最佳平衡)
# acks=1                      (Leader 确认即可，日志场景容忍少量丢失)
# buffer.memory=67108864      (64MB 发送缓冲区)
```

### Layer 3 — Logstash 消费 Kafka → ES（清洗 / 过滤 / 富化）

```
# logstash.conf — 消费 Kafka 三个 Topic，清洗后写入 ES
input {
  kafka {
    bootstrap_servers => "kafka-broker-1:9092,kafka-broker-2:9092,kafka-broker-3:9092"
    topics_pattern => "access|error|business"
    group_id => "logstash-group"
    consumer_threads => 10          # 30 Partition 配 10 线程并发消费
    auto_offset_reset => "latest"
    max_poll_records => 500
    decorate_events => true
    codec => "json"
  }
}

filter {
  # 解析 access 日志格式
  if [kafka][topic] == "access" {
    grok {
      match => {
        "message" => '%{IP:client_ip} - - \[%{HTTPDATE:timestamp}\] "%{WORD:method} %{URIPATHPARAM:request} HTTP/%{NUMBER:http_version}" %{NUMBER:status} %{NUMBER:bytes}'
      }
    }
    # 添加地理位置信息
    geoip { source => "client_ip" }
  }

  # error 日志不需要 grok，保持原始 message
  if [kafka][topic] == "error" {
    mutate {
      add_tag => ["error"]
      add_field => { "severity" => "ERROR" }
    }
  }

  # business 日志：JSON 解析 + 字段标准化
  if [kafka][topic] == "business" {
    json { source => "message" }
    mutate {
      rename => { "userId" => "user_id" }
      rename => { "orderAmount" => "order_amount" }
    }
  }

  # 移除不需要的字段
  mutate {
    remove_field => ["@version", "message", "[event][original]"]
  }
}

output {
  # 按 Topic 路由到不同 ES 索引
  if [kafka][topic] == "access" {
    elasticsearch {
      hosts => ["es-node-1:9200", "es-node-2:9200"]
      index => "access-logs-%{+YYYY.MM.dd}"
      template => "/etc/logstash/templates/access-template.json"
      template_name => "access-logs"
    }
  } else if [kafka][topic] == "error" {
    elasticsearch {
      hosts => ["es-node-1:9200", "es-node-2:9200"]
      index => "error-logs-%{+YYYY.MM.dd}"
    }
  } else {
    elasticsearch {
      hosts => ["es-node-1:9200", "es-node-2:9200"]
      index => "business-logs-%{+YYYY.MM.dd}"
    }
  }
}
```

### Layer 4 — Flink 消费 → HDFS（窗口聚合 + 离线分析）

```java
public class LogAnalysisJob {

    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env =
            StreamExecutionEnvironment.getExecutionEnvironment();
        env.enableCheckpointing(60000); // 每分钟一次 Checkpoint

        // Kafka Source：独立 Consumer Group，不影响 Logstash
        KafkaSource<LogEvent> source = KafkaSource.<LogEvent>builder()
            .setBootstrapServers("kafka-broker-1:9092,kafka-broker-2:9092")
            .setTopics("access", "error", "business")
            .setGroupId("flink-group")
            .setStartingOffsets(OffsetsInitializer.latest())
            .setDeserializer(new LogEventDeserializer())
            // 自动发现新增 Partition
            .setProperty("partition.discovery.interval.ms", "30000")
            .build();

        DataStream<LogEvent> stream = env
            .fromSource(source, WatermarkStrategy.noWatermarks(), "Kafka Source");

        // 按 Topic 分流处理
        stream.process(new ProcessFunction<LogEvent, Object>() {
            @Override
            public void processElement(LogEvent event, Context ctx,
                                       Collector<Object> out) {
                switch (event.getTopic()) {
                    case "access":
                        // 按 URL 聚合 PV/UV（5 分钟滚动窗口）
                        stream.filter(e -> "access".equals(e.getTopic()))
                            .keyBy(LogEvent::getUrl)
                            .window(TumblingProcessingTimeWindows.of(Time.minutes(5)))
                            .aggregate(new PvUvAggregator())
                            .addSink(parquetSink("hdfs://namenode/logs/access_pv/"));
                        break;
                    case "error":
                        // 错误日志按类型统计
                        stream.filter(e -> "error".equals(e.getTopic()))
                            .keyBy(LogEvent::getErrorType)
                            .window(TumblingProcessingTimeWindows.of(Time.minutes(1)))
                            .aggregate(new ErrorCountAggregator())
                            .addSink(parquetSink("hdfs://namenode/logs/error_stats/"));
                        break;
                    case "business":
                        // 业务日志：订单量、GMV 等实时大盘
                        stream.filter(e -> "business".equals(e.getTopic()))
                            .keyBy(LogEvent::getEventType)
                            .window(TumblingProcessingTimeWindows.of(Time.minutes(1)))
                            .aggregate(new BusinessMetricsAggregator())
                            .addSink(parquetSink("hdfs://namenode/logs/business_metrics/"));
                        break;
                }
            }
        });

        env.execute("Log Analysis Pipeline");
    }

    // Parquet 列存 Sink（HDFS）
    private static FileSink<Object> parquetSink(String path) {
        return FileSink.forBulkFormat(new Path(path),
            ParquetAvroWriters.forReflectRecord(Object.class))
            .withRollingPolicy(
                OnCheckpointRollingPolicy.build())
            .build();
    }
}
```

## 日志收集方案对比

| 维度 | Filebeat + Kafka + ES | Fluentd + Kafka + HDFS |
|------|----------------------|------------------------|
| **采集器** | Filebeat (Go)，极轻量，CPU < 5%，内存 < 50MB | Fluentd (C/Ruby)，资源消耗稍高，插件丰富 |
| **缓冲层** | Kafka，磁盘持久化，多副本，积压能力几乎无限 | 同 Kafka |
| **消费层** | Logstash → ES，grok 解析能力强，适合实时搜索 | Flink → HDFS/Parquet，流批一体，适合离线分析 |
| **搜索能力** | ES + Kibana，全文搜索 + 可视化强 | HDFS 需 Hive/Spark/Impala 查询，延迟高 |
| **存储成本** | ES 索引占用磁盘大，按天 Rollover 需运维 | HDFS 三副本 + Parquet 列存压缩，成本低 |
| **实时性** | 端到端延迟 < 5 秒 | 分钟级窗口，准实时 |
| **数据丢失容忍** | acks=1 可能丢少量日志 | 同 Kafka acks 配置，Checkpoint 保证精确一次语义 |
| **监控** | ES 自带 + Kafka Lag Exporter | Flink Metrics + Kafka Lag Exporter |
| **适用场景** | 实时排障、全文本日志搜索、运维监控 | 离线日志分析、用户行为分析、数据仓库 ETL |

## 一句话总结

**百万级日志收集系统通过 Filebeat（轻量采集）→ Kafka（按业务分 Topic，30 Partition 并行 + lz4 压缩）→ Logstash/Flink（各自独立 Consumer Group 消费，同一份数据写入 ES 实时搜索和 HDFS 离线分析）三级流水线架构，以 acks=1 容忍少量丢失换取极致吞吐，用 Lag 监控全程保障管道健康。**
