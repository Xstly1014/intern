# Q93 订单异步处理

订单服务通过消息队列（RabbitMQ Topic Exchange 或 Kafka Topic）发布订单创建事件，库存扣减、积分发放、短信通知、物流创建等下游服务各自独立消费，实现服务解耦与异步协作。可靠性依赖事务消息 + 手动 ACK + 幂等消费 + 死信队列四重保障。

订单异步处理的核心思想是将订单创建这一核心事件广播给所有关心的下游服务。Kafka 的多 Consumer Group 机制天然适合这种一对多广播场景——每个下游服务拥有独立的 Consumer Group，各自维护 offset，消费速度互不影响。同时通过 orderId 取模路由到同一 Partition，保证了同一订单的处理顺序。

## 端到端代码实现

### Layer 1 — 订单服务发消息（KafkaTemplate + 本地消息表）

```java
@Service
public class OrderEventPublisher {

    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    @Autowired
    private LocalMessageTableMapper messageTableMapper;

    @Transactional
    public void createOrder(OrderRequest request) {
        // 1. 订单入库
        Order order = orderMapper.insert(buildOrder(request));

        // 2. 写入本地消息表（同一事务，保证原子性）
        OrderEventMessage msg = new OrderEventMessage();
        msg.setOrderId(order.getId());
        msg.setPayload(JSON.toJSONString(buildEventPayload(order)));
        msg.setStatus("PENDING");
        msg.setCreateTime(new Date());
        messageTableMapper.insert(msg);

        // 3. 提交事务后立即发送（也可用定时任务补偿）
        sendMessage(msg);
    }

    @Async
    public void sendMessage(OrderEventMessage msg) {
        try {
            ListenableFuture<SendResult<String, String>> future =
                kafkaTemplate.send("order-events",
                    String.valueOf(msg.getOrderId()), msg.getPayload());
            future.addCallback(
                result -> messageTableMapper.updateStatus(msg.getId(), "SENT"),
                ex -> {
                    log.error("发送失败, orderId={}", msg.getOrderId(), ex);
                    // 定时任务会扫描 PENDING 状态补偿重发
                }
            );
        } catch (Exception e) {
            log.error("发送异常", e);
        }
    }
}
```

### Layer 2 — 库存扣减消费者（幂等去重 + 失败重试 3 次 → DLQ）

```java
@Component
public class InventoryDeductConsumer {

    @Autowired
    private InventoryService inventoryService;
    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private KafkaTemplate<String, String> dlqTemplate;

    private static final int MAX_RETRY = 3;

    @KafkaListener(topics = "order-events", groupId = "inventory-group")
    public void onMessage(ConsumerRecord<String, String> record, Acknowledgment ack) {
        String orderId = record.key();
        OrderEvent event = JSON.parseObject(record.value(), OrderEvent.class);

        // 1. 幂等校验：Redis SETNX 防止重复消费
        String idempotentKey = "order:deduct:" + orderId;
        Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(idempotentKey, "1", Duration.ofHours(24));
        if (Boolean.FALSE.equals(locked)) {
            log.info("重复消费, 直接 ACK, orderId={}", orderId);
            ack.acknowledge();
            return;
        }

        // 2. 业务处理 + 本地重试
        int retryCount = getRetryCount(record);
        try {
            inventoryService.deduct(event.getItems());
            ack.acknowledge();
            log.info("库存扣减成功, orderId={}", orderId);
        } catch (Exception e) {
            log.error("库存扣减失败, orderId={}, retry={}", orderId, retryCount, e);
            if (retryCount < MAX_RETRY) {
                // 短暂休眠后重新抛出异常，触发 Kafka 重试
                Thread.sleep(1000L * (retryCount + 1));
                throw new RetryableException("重试中", e);
            } else {
                // 超过最大重试次数，投递到死信队列
                sendToDLQ(record);
                ack.acknowledge(); // 确认原消息，避免无限重试
            }
        }
    }

    private void sendToDLQ(ConsumerRecord<String, String> record) {
        dlqTemplate.send("order-events-dlq", record.key(), record.value());
    }
}
```

### Layer 3 — 积分/短信/物流消费者（独立 Consumer Group 各自消费，互不阻塞）

@Component
public class PointsAwardConsumer {

### Layer 4 — 新增下游消费者（只需加 Listener，订单服务零改动）

```java
// 新增"实时数据看板"消费者——不改动任何已有代码
@Component
public class DashboardConsumer {

    @KafkaListener(topics = "order-events", groupId = "dashboard-group")
    public void onMessage(ConsumerRecord<String, String> record, Acknowledgment ack) {
        OrderEvent event = JSON.parseObject(record.value(), OrderEvent.class);
        // 更新实时 GMV、订单量、热销商品等
        dashboardService.updateRealtimeMetrics(event);
        ack.acknowledge();
    }
}
// 无需改动 OrderService、无需修改 Kafka Topic 配置
// 只需新增一个带唯一 groupId 的 @KafkaListener 即可
```

## 方案对比

| 维度 | 直接 RPC 调用 | 消息队列异步 |
|------|-------------|------------|
| **耦合度** | 订单服务需感知所有下游接口，新增下游需改代码并重新上线 | 订单服务只发消息，下游独立消费，新增下游零改动 |
| **可靠性** | 任一 RPC 失败就需重试逻辑，故障易级联放大 | 各消费者独立 ACK，失败不影响其他消费者，DLQ 兜底 |
| **性能** | 串行等待所有 RPC 返回，RT = sum(各接口耗时) | 消息一发即返回，RT 与下游数量无关，仅取决于写 MQ 耗时 |
| **一致性** | 分布式事务（Seata/TCC），实现复杂 | 最终一致性 + 本地消息表补偿，相对简单 |
| **流量削峰** | 无缓冲，下游直接承受峰值 | MQ 缓冲，下游按自身能力消费 |
| **运维复杂度** | 服务少时简单 | 引入 MQ 集群运维、消息堆积监控 |
| **适用场景** | 强一致性要求、低延迟、下游数量少 | 异步解耦、下游数量多、容忍最终一致性 |

## 一句话总结

**订单异步处理通过 Kafka 的多 Consumer Group 实现一对多广播解耦，以事务消息保证生产端原子性，以手动 ACK + 幂等校验 + 死信队列保证消费端可靠性，新增下游只需加一个 Listener 即可零侵入接入。**
