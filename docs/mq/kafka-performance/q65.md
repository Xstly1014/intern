# Q65 索引文件

.index 文件采用稀疏索引（Sparse Index）设计，不是每条消息都有索引项，而是每隔 `index.interval.bytes`（默认 4KB）记录一个 `(offset, position)` 映射对。这样既能快速定位消息，又能将索引文件控制在极小体积内，整个索引可完全驻留在 Page Cache 中。

稀疏索引的核心思想是"用空间换时间的平衡艺术"：Kafka 不做每条消息的精确索引，而是每隔 4KB 打一个锚点，查找时先二分定位到最近的锚点，再顺序扫描最多 4KB 范围。因为 Kafka 主要是顺序读写场景，这种设计既保证了定位效率，又将索引体积控制在极小的范围内。

### Layer 1 — 索引配置与原理

// server.properties
log.index.interval.bytes = 4096  // 默认 4KB，每隔这些字节写入一条索引项

// 核心类：OffsetIndex（稀疏索引实现）

### Layer 3 — 消息查找过程模拟（二分 + 顺序扫描）

```java
/**
 * 模拟 Kafka 稀疏索引的消息查找过程
 * 1. 根据 offset 在 .index 中二分查找最近的索引项
 * 2. 从索引项的 position 开始在 .log 中顺序扫描
 */
public class SparseIndexLookup {
    static class IndexEntry {
        long offset;
        long position;
        IndexEntry(long offset, long position) {
            this.offset = offset;
            this.position = position;
        }
    }

    // 稀疏索引（每隔 indexIntervalBytes 一个条目）
    static final List<IndexEntry> sparseIndex = Arrays.asList(
        new IndexEntry(0,    0),
        new IndexEntry(156,  4096),
        new IndexEntry(312,  8192),
        new IndexEntry(468,  12288),
        new IndexEntry(624,  16384)
    );

    /**
     * Step 2: 在稀疏索引中二分查找 ≤ targetOffset 的最近索引项
     */
    static IndexEntry binarySearchIndex(List<IndexEntry> index, long targetOffset) {
        int lo = 0, hi = index.size() - 1;
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (index.get(mid).offset <= targetOffset) {
                lo = mid + 1;
            } else {
                hi = mid - 1;
            }
        }
        return index.get(Math.max(0, hi)); // 返回 ≤ target 的最近项
    }

    public static void main(String[] args) {
        long targetOffset = 500;
        IndexEntry entry = binarySearchIndex(sparseIndex, targetOffset);
        System.out.println("找到最近索引项: offset=" + entry.offset
            + ", position=" + entry.position);
        // 输出: 找到最近索引项: offset=468, position=12288

        // Step 3: 从 position=12288 开始顺序扫描 .log
        // 最坏情况扫描 4KB（index.interval.bytes）范围
        System.out.println("从 position=" + entry.position
            + " 开始顺序扫描，最多扫描 4KB");
    }
}
```

### Layer 4 — 稀疏索引 vs 稠密索引 存储开销对比

```java
/**
 * 存储开销对比计算
 * 场景：1GB 日志文件，每条消息平均 1KB，共约 100 万条消息
 */
public class IndexStorageComparison {
    static final long SEGMENT_SIZE     = 1_073_741_824L;  // 1GB
    static final long INDEX_INTERVAL   = 4_096L;          // 4KB
    static final int  ENTRY_SIZE       = 8;               // 每个索引项 8 字节
    static final long MSG_COUNT        = 1_000_000L;      // 100 万条消息

    public static void main(String[] args) {
        // 稀疏索引：每 4KB 一个索引项
        long sparseEntries = SEGMENT_SIZE / INDEX_INTERVAL;
        long sparseSize = sparseEntries * ENTRY_SIZE;
        System.out.printf("稀疏索引: %d 个索引项, 文件大小 %s%n",
            sparseEntries, formatBytes(sparseSize));
        // 输出: 稀疏索引: 262144 个索引项, 文件大小 2.0 MB

        // 稠密索引：每条消息一个索引项
        long denseSize = MSG_COUNT * ENTRY_SIZE;
        System.out.printf("稠密索引: %d 个索引项, 文件大小 %s%n",
            MSG_COUNT, formatBytes(denseSize));
        // 输出: 稠密索引: 1000000 个索引项, 文件大小 7.6 MB

        double ratio = (double) denseSize / sparseSize;
        System.out.printf("稠密索引是稀疏索引的 %.1f 倍%n", ratio);
        // 输出: 稠密索引是稀疏索引的 3.8 倍
    }

    static String formatBytes(long bytes) {
        if (bytes < 1024) return bytes + " B";
        if (bytes < 1048576) return String.format("%.1f KB", bytes / 1024.0);
        return String.format("%.1f MB", bytes / 1048576.0);
    }
}
```

## 对比表格

| 维度 | 稀疏索引（Kafka 实际方案） | 稠密索引（理论对照） |
|---|---|---|
| 索引粒度 | 每 `index.interval.bytes`（默认 4KB）一个条目 | 每条消息一个条目 |
| 索引条目数 | ≈ Log 字节数 / 4096 | = 消息总数 |
| 索引文件大小 | 极小（通常几 MB，可全放 Page Cache） | 巨大（与消息数成正比，无法全缓存） |
| 查找复杂度 | O(log N_index) + 顺序扫描最多 4KB | O(log N_msg)，但索引可能不在内存 |
| 实际 IO | 二分查找在内存完成 + 一次顺序 IO（≤ 4KB） | 二分查找可能需要多次磁盘 IO |
| 顺序消费场景 | 完美适配，几乎零额外开销 | 过度设计，浪费存储和内存 |
| 随机消费场景 | 每次查找扫描 ≤ 4KB，可接受 | 理论上更快，但索引大小抵消优势 |
| Page Cache 命中率 | 接近 100%（文件小，可完整缓存） | 低（文件大，频繁换入换出） |
| 适用场景 | 写入密集型、顺序消费为主的日志系统 | 大量随机读取的数据库场景 |

## 一句话总结

**稀疏索引是 Kafka 在"定位速度"与"存储效率"之间的精妙平衡：每 4KB 一个锚点，二分定位后顺序扫描，用 O(log N) 的复杂度实现毫秒级查找，同时让索引小到可以完全驻留在 Page Cache 中。**
