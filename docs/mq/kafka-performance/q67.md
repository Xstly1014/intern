# Q67 消费者组并行度

消费者组的并行度由公式 `并行度 = min(Partition 数, 消费者数)` 决定，消费者数量不能超过 Partition 数，多余的消费者会处于闲置状态。提高消费速度的核心思路是围绕这个约束，从扩展性、处理模型、批量化和逻辑优化四个维度入手。

四种策略各有适用场景，没有银弹。实际生产环境中通常是组合使用：先优化消费逻辑消除瓶颈（策略4），再通过批量处理减少开销（策略3），如果仍不够，最后考虑水平扩展（策略1）。策略2（多线程）应作为最后手段且需要极其谨慎地处理 offset 提交。

## 代码：四种提速策略实现

### Layer 1 — 增加 Partition + Consumer 扩容（推荐方案）

```java
// ===== Broker 端：增加 Topic Partition（不可逆操作） =====
// 命令行方式
kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic order-topic \
  --partitions 10

// ===== Consumer 端：Spring Kafka 水平扩展 =====
// application.yml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    consumer:
      group-id: order-processor-group
      enable-auto-commit: false
      max-poll-records: 500
    listener:
      concurrency: 5   // ← 启动 5 个 Consumer 线程

// 或者通过 @KafkaListener 注解指定
@KafkaListener(
    topics = "order-topic",
    concurrency = "5",       // 5 个 Consumer 实例
    groupId = "order-processor-group"
)
public void onMessage(ConsumerRecord<String, String> record) {
    processOrder(record.value());
}

// 关键：concurrency 必须 ≤ Partition 数
// Partition=10, concurrency=5 → 每个 Consumer 分配 2 个 Partition
// Partition=10, concurrency=12 → 只有 10 个 Consumer 工作，2 个闲置
```

### Layer 2 — 单消费者多线程处理（高风险方案）

```java
/**
 * 策略2：单 Consumer 内多线程处理
 * 严重风险：消息乱序 + offset 提交难以保证
 * 仅在"消息处理无顺序要求 + 可容忍重复消费"时使用
 */
@Component
public class MultiThreadConsumer {
    private final ExecutorService executor =
        Executors.newFixedThreadPool(8);

    @KafkaListener(topics = "order-topic", groupId = "risk-group")
    public void onMessage(List<ConsumerRecord<String, String>> records,
                          Acknowledgment ack) {
        // 并发处理所有消息 → 顺序被打乱
        List<CompletableFuture<Void>> futures = records.stream()
            .map(record -> CompletableFuture.runAsync(() -> {
                processMessage(record.value());
            }, executor))
            .collect(Collectors.toList());

        // 等待所有任务完成后再提交 offset
        CompletableFuture.allOf(
            futures.toArray(new CompletableFuture[0])
        ).join();

        ack.acknowledge(); // 所有处理完才提交

        // ⚠ 风险：如果某个任务失败但 offset 已提交，消息丢失
        // ⚠ 风险：如果 offset 提交前崩溃，所有消息重复消费
    }

    private void processMessage(String value) {
        // 业务处理逻辑
    }
}
```

### Layer 3 — 批量处理配置

```java
// ===== application.yml =====
spring:
  kafka:
    consumer:
      max-poll-records: 500          // 每次 poll 最多拉 500 条
      fetch-min-bytes: 1048576        // 至少拉取 1MB 才返回
      fetch-max-wait-ms: 500          // 最多等 500ms

// ===== Spring Kafka Batch Listener =====
@KafkaListener(
    topics = "order-topic",
    groupId = "batch-group",
    concurrency = "1"
)
public void onBatchMessage(
        List<ConsumerRecord<String, String>> records,
        Acknowledgment ack) {

    // 批量提取数据
    List<Order> orders = records.stream()
        .map(r -> parseOrder(r.value()))
        .collect(Collectors.toList());

    // 批量写入数据库（一次 SQL 处理 500 条）
    orderRepository.batchInsert(orders);

    // 批量处理完一次性提交 offset
    ack.acknowledge();
}

// ===== 注意超时配置 =====
// max.poll.interval.ms 必须 > 批量处理总耗时
// 否则 Consumer 会被踢出消费者组触发 Rebalance
spring:
  kafka:
    consumer:
      properties:
        max.poll.interval.ms: 600000   // 10 分钟，根据批量处理耗时调整
```

### Layer 4 — 优化消费逻辑（异步化 + 幂等）

```java
/**
 * 策略4：优化消费逻辑本身
 * 核心思路：减少单条消息处理时间 + 去重 + 缓存
 */
@Component
public class OptimizedConsumer {

    // 幂等性：通过消息 key 去重
    private final Cache<String, Boolean> processedCache =
        Caffeine.newBuilder()
            .expireAfterWrite(1, TimeUnit.HOURS)
            .maximumSize(100_000)
            .build();

    // 本地缓存：减少外部调用
    private final Cache<String, ProductInfo> productCache =
        Caffeine.newBuilder()
            .expireAfterWrite(5, TimeUnit.MINUTES)
            .maximumSize(10_000)
            .build();

    @KafkaListener(topics = "order-topic", groupId = "optimized-group")
    public void onMessage(ConsumerRecord<String, String> record,
                          Acknowledgment ack) {
        String msgKey = record.key();

        // 1. 幂等去重：避免重复处理
        if (processedCache.getIfPresent(msgKey) != null) {
            ack.acknowledge();
            return;
        }

        // 2. 本地缓存命中，减少 DB/RPC 调用
        String orderJson = record.value();
        Order order = parseOrder(orderJson);

        ProductInfo product = productCache.get(order.getProductId(),
            this::loadProductFromDB); // 缓存未命中的回源函数

        // 3. 批量累积后异步写 DB（配合策略3）
        orderRepository.asyncInsert(order);

        processedCache.put(msgKey, true);
        ack.acknowledge();
    }

    private ProductInfo loadProductFromDB(String productId) {
        return productRepository.findById(productId);
    }
}
```

## 对比表格

| 维度 | 增加 Partition + Consumer | 单 Consumer 多线程 | 批量处理 | 优化消费逻辑 |
|---|---|---|---|---|
| 提速原理 | 水平扩展并行度 | 单 Partition 内多核并行 | 减少单次 IO/网络开销 | 减少单条消息耗时 |
| 架构改动 | 大（需修改 Topic 配置） | 中（修改 Consumer 代码） | 小（仅改配置） | 小（仅改业务代码） |
| 顺序性保证 | 完全保证（单 Partition 顺序消费） | 严重破坏，消息乱序 | 保证（同批内顺序处理） | 保证（不改处理模型） |
| offset 提交 | 简单，各 Consumer 独立提交 | 极难正确实现 | 简单，批量完成统一提交 | 简单，单条处理完提交 |
| 扩展上限 | Partition 数 = 上限 | 单机 CPU 核数 = 上限 | 单次 poll 耗时 = 上限 | 业务逻辑复杂度 = 上限 |
| Rebalance 风险 | 低（Consumer 数量稳定） | 无影响 | 高（poll 间隔长可能触发） | 无影响 |
| 重复消费处理 | 天然支持（各 Partition 独立） | 容易大量重复 | 支持（整批重试） | 需自行实现幂等 |
| 资源消耗 | 额外 Consumer 实例占内存 | 线程池开销可控 | 内存中缓冲批量数据 | 几乎无额外开销 |
| 不可逆操作 | 是（Partition 增加不可减） | 否 | 否 | 否 |
| 推荐场景 | 第一选择，架构允许时 | 最后手段，极端谨慎 | 有批量 DB 操作的场景 | 任何场景的基础优化 |

## 一句话总结

**Kafka 消费者组并行度 = min(Partition, Consumer)，优化策略按优先级排列为：先优化消费逻辑 + 批量处理，再考虑水平扩展；单 Consumer 内多线程是高风险操作，需要非常谨慎地处理顺序性和 offset 提交。**
