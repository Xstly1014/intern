# Q59 顺序写盘

Kafka 高性能的核心基石是顺序写盘——消息以 append-only 方式追加到日志文件末尾，避免了随机 IO 的磁头寻道开销。6 块 7200rpm 机械盘 RAID10 下顺序写可达 600MB/s，而随机写仅有 100KB/s，差距高达 6000 倍。

## 代码实现：顺序写盘分层示例

### Layer 1 — Kafka 日志存储配置

```properties
# server.properties — Broker 端日志存储核心配置
# 日志目录：建议挂载多块物理盘，Kafka 会将 Partition 均匀分布
log.dirs=/data/kafka-logs

# 单个日志分段文件大小，默认 1GB
# 满了之后滚动创建新 Segment，旧 Segment 变为只读
log.segment.bytes=1073741824

# 日志段保留策略：7 天 or 50GB，先达到者生效
log.retention.hours=168
log.retention.bytes=53687091200

# Topic 级别可覆盖以上配置
# kafka-configs.sh --alter --topic order-events --add-config segment.bytes=536870912
```

Kafka 将每个 Partition 的日志按 `log.segment.bytes` 切分为多个 Segment 文件。当前活跃的 Segment 以 append-only 方式写入，旧 Segment 变为只读——保证所有写都是顺序追加。

### Layer 2 — 顺序写 vs 随机写磁盘性能测试

```bash
# ===== 顺序写测试（dd 工具）=====
# 直接顺序写入大文件，绕过文件系统缓冲区
dd if=/dev/zero of=/data/test-seq bs=1M count=4096 oflag=direct
# 输出：4294967296 bytes (4.3 GB) copied, 7.2 s, 596 MB/s

# ===== 随机写测试（fio 工具）=====
# 4KB 随机写，direct IO 模式
fio --name=randwrite --ioengine=libaio --iodepth=1 \
    --rw=randwrite --bs=4k --direct=1 --size=1G \
    --numjobs=1 --runtime=60 --time_based \
    --filename=/data/test-rand

# 典型输出：WRITE: bw=98KiB/s (100kB/s), iops=24
# 注意：即使 SSD 随机写也只有几十到几百 MB/s，仍有差距
```

```bash
# 多块磁盘并行顺序写（模拟 Kafka 多盘配置）
# 假设挂载 6 块盘 /data1 ~ /data6
for disk in /data1 /data2 /data3 /data4 /data5 /data6; do
    dd if=/dev/zero of=$disk/test-seq bs=1M count=4096 oflag=direct &
done
wait
# 6 块盘聚合吞吐 ≈ 6 × 600MB/s = 3.6GB/s
```

`dd` 顺序写可达 600MB/s（机械盘）或数 GB/s（SSD），而 `fio` 4K 随机写机械盘仅 100KB/s——差距 6000 倍。即使 SSD 随机写也只有 100~500MB/s（取决于模型），仍然显著低于顺序写。

### Layer 3 — Kafka Producer 写消息如何实现顺序写

```java
// Kafka Producer 内部：消息追加到 RecordAccumulator 缓冲区
// 然后批量（batch.size）按 Partition -> Leader Broker 发送
// Broker 端直接追加到活跃 Segment 文件末尾

@Service
public class SeqWriteDemoProducer {
    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    public void sendBatch() {
        // 同一 Partition 的消息按发送顺序追加
        for (int i = 0; i < 10000; i++) {
            kafkaTemplate.send("prices", "AAPL", "price:" + i);
        }
        // Broker 端收到后，按 offset 顺序追加到活跃 Segment
        // 文件布局：offset0|offset1|offset2|...（连续磁盘扇区）
    }
}
```

```properties
# Producer 相关配置，影响写入模式
# batch.size=16384（默认 16KB）
# 消息先在 Producer 端累积到 batch 再一起发送，减少网络往返
batch.size=65536

# linger.ms=0（默认），设为非零值可让更多消息合入同一 batch
linger.ms=5

# 确保消息按序发送（同一 Partition 内有序）
max.in.flight.requests.per.connection=1
```

Broker 收到消息后直接按 offset 顺序追加到当前活跃 Segment（`.log` 文件），文件布局是连续的磁盘扇区，天然形成顺序写。每个 Partition 只有一个活跃 Segment 在写入，避免了多 Segment 并发写造成随机 IO。

### Layer 4 — 机械盘 vs SSD 顺序写性能对比

```bash
# ============ HDD 7200rpm 测试 ============
# 顺序写
dd if=/dev/zero of=/mnt/hdd/test bs=1M count=8192 oflag=direct
# → 约 150~200 MB/s（单盘）、600 MB/s（RAID10 6盘）

# 随机写（4KB 块）
fio --rw=randwrite --bs=4k --direct=1 --size=1G --name=hdd-rand \
    --filename=/mnt/hdd/test-rand
# → 约 100 KB/s（机械盘几乎不可用）

# ============ SSD NVMe 测试 ============
# 顺序写
dd if=/dev/zero of=/mnt/ssd/test bs=1M count=8192 oflag=direct
# → 约 2000~3500 MB/s（NVMe Gen4）

# 随机写（4KB 块，IO Depth 32）
fio --rw=randwrite --bs=4k --direct=1 --size=1G --iodepth=32 \
    --name=ssd-rand --filename=/mnt/ssd/test-rand
# → 约 200~500 MB/s（SSD 随机写仍有差距）
```

```bash
# iostat 监控写入时的磁盘 IO 模式
# 顺序写时：await 低（<1ms），avgqu-sz 小，w/s 高
# 随机写时：await 高（机械盘 5~10ms），w/s 低
iostat -x 1 /dev/sdb

# 关键指标解读：
# r_await / w_await — 平均 IO 响应时间
# avgqu-sz — 平均队列长度（越小越好）
# %util — 磁盘利用率
```

即使使用 SSD，顺序写仍然优于随机写：SSD 的 FTL（Flash Translation Layer）需要 GC 和写放大管理，顺序写可以减少无效写入、降低写放大系数（WAF），从而延长 SSD 寿命。

## 顺序写 vs 随机写 对比

| 维度 | 顺序写（Kafka） | 随机写（数据库 B+ Tree） |
|---|---|---|
| 写入模式 | Append-Only 追加到 Segment 末尾 | 分散写入索引页和数据页 |
| 磁头寻道 | 几乎不需要（磁头不动） | 每次 IO 寻道 5~10ms |
| 机械盘吞吐 | 150~200 MB/s（单盘） | ~100 KB/s |
| SSD 吞吐 | 2000~3500 MB/s（NVMe） | 200~500 MB/s |
| 写放大（WA） | 极低（顺序追加） | 高（B+ Tree 分裂、Redo/Undo 日志） |
| OS 优化 | 预读 + 写合并有效 | 无法利用预读 |
| 数据布局 | 连续磁盘扇区 | 分散磁盘扇区 |
| 存储结构 | 日志结构（Log-Structured） | B+ Tree / ISAM |
| 适用场景 | 高吞吐消息流、日志收集 | 事务型 OLTP、随机读写查询 |

## 一句话总结

**一句话总结：Kafka 选择 append-only 日志结构（而非 B+ Tree）的根本原因在于顺序写盘——机械盘下吞吐差距达 6000 倍，SSD 下也达数倍，这是 Kafka 高吞吐的物理基石。**
