# Q68 粘性分区器

粘性分区器（Sticky Partitioner）是 Kafka 2.4+ 对无 key 消息的默认分区策略：Producer 在一段时间内将消息固定发往同一个 Partition，攒满 Batch 后再切换到下一个 Partition，以此获得更大的 Batch 和更高的吞吐，同时不增加单条延迟。

RoundRobin 将每条无 Key 消息轮流分发到不同 Partition，导致每个 Batch 仅含 1~2 条消息，造成大量小请求。Sticky Partitioner 则先将消息聚合到同一个 Partition 的 Batch 中，攒满后才切换，大幅减少网络往返次数。

## 代码分层演示

### Layer 1 — 分区器配置

```java
// application.yml — 指定分区器
spring:
  kafka:
    producer:
      properties:
        partitioner:
          class: org.apache.kafka.clients.producer.StickyPartitioner  // Kafka 2.4+ 默认
      batch-size: 16384       // 16KB，Batch 大小
      linger-ms: 5            // 等待 5ms 攒批
```

```bash
# 命令行工具 — 查看分区器配置
kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name my-topic --describe
```

### Layer 2 — RoundRobin 分区器行为演示

```java
// RoundRobinPartitioner — 无 Key 消息轮流分发（Kafka 2.4 之前的默认行为）
// 每条消息都计算一次取模，导致消息均匀但分散
public class RoundRobinPartitioner implements Partitioner {
    private final AtomicInteger counter = new AtomicInteger(0);

    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        int numPartitions = cluster.partitionCountForTopic(topic);
        int next = counter.getAndIncrement();
        return next % numPartitions; // 每条消息都取模，Batch 永远攒不满
    }
}

// 测试：发送 6 条无 Key 消息
@Test
void testRoundRobin() {
    for (int i = 0; i < 6; i++) {
        ProducerRecord<String, String> record = new ProducerRecord<>("demo", "msg" + i);
        kafkaTemplate.send(record);
    }
    // 结果：msg0→P0, msg1→P1, msg2→P2, msg3→P0, msg4→P1, msg5→P2
    // 每个 Partition 收到 2 条，但每条可能触发独立 Batch
}
```

### Layer 3 — Sticky Partitioner 行为演示

```java
// StickyPartitioner — 粘在一批，攒满后才切（Kafka 2.4+ 默认）
// 源码位于：org.apache.kafka.clients.producer.internals.StickyPartitionCache
public class StickyPartitioner implements Partitioner {
    // 内部维护 partition → Deque<ProducerBatch> 映射
    // ProducerBatch 未满时，无 Key 消息持续追加到同一个 Batch
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        if (keyBytes == null) {
            return stickyPartitionCache.partition(); // 返回当前粘住的 Partition
        }
        return Utils.toPositive(Utils.murmur2(keyBytes)) % numPartitions;
    }
}

// 测试：发送 6 条无 Key 消息，batch.size=16384, linger.ms=5
@Test
void testSticky() {
    for (int i = 0; i < 6; i++) {
        ProducerRecord<String, String> record = new ProducerRecord<>("demo", "msg" + i);
        kafkaTemplate.send(record);
    }
    // 结果：msg0~msg5 全部进入同一个 Partition 的同一个 Batch
    // 下次 Batch 满或 linger.ms 到期后随机切换下一个 Partition
}
```

```bash
# 命令行验证分区效果
kafka-run-class.sh kafka.tools.GetOffsetShell \
  --bootstrap-server localhost:9092 --topic demo --time -1
# 观察各 Partition 消息数差异：Sticky 下某一 Partition 消息明显集中
```

### Layer 4 — 自定义分区器

```java
// 自定义分区器：实现 Partitioner 接口
// 场景：按消息体中的业务字段动态选 Partition
public class BusinessPartitioner implements Partitioner {

    @Override
    public void configure(Map<String, ?> configs) {}

    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        String valueStr = new String(valueBytes);
        int numPartitions = cluster.partitionCountForTopic(topic);

        if (valueStr.contains("VIP")) {
            return 0; // VIP 消息固定去 Partition 0（优先处理）
        } else if (valueStr.contains("URGENT")) {
            return numPartitions - 1; // 紧急消息去最后一个 Partition
        }
        // 其余按 key hash（有 key）或 sticky（无 key）行为
        if (keyBytes != null) {
            return Utils.toPositive(Utils.murmur2(keyBytes)) % numPartitions;
        }
        return ThreadLocalRandom.current().nextInt(numPartitions);
    }

    @Override
    public void close() {}
}
```

## 对比表

| 维度 | RoundRobin 分区器 | Sticky Partitioner（Kafka 2.4+） |
|:---|:---|:---|
| **默认状态** | Kafka 2.3 及之前默认 | Kafka 2.4 起默认 |
| **分区策略** | 每条无 Key 消息轮流取模 | 攒在同一 Partition 直到 Batch 满 |
| **Batch 大小** | 通常很小（1~2 条/Batch） | 通常较大（满 Batch 才发送） |
| **网络请求** | 较多（每条消息可能独立请求） | 较少（一批消息一次请求） |
| **吞吐量** | 较低（受小 Batch + 多请求限制） | 较高（大 Batch 减少请求开销） |
| **单条延迟** | 取决于 linger.ms | 取决于 linger.ms（不增加） |
| **有 Key 消息** | 按 hash(key) 分区 | 按 hash(key) 分区（不受影响） |
| **负载均衡** | 严格均匀 | Batch 粒度均匀（整体仍均衡） |
| **切换时机** | 每条消息都切换 | Batch 满 / linger.ms 到期后切换 |
| **配置参数** | `RoundRobinPartitioner` | `StickyPartitioner` / `UniformStickyPartitioner` |

## 一句话总结

**Sticky Partitioner 不改 linger.ms 就能让无 Key 消息的 Batch 从 1 条涨到满，网络请求数下降数倍而延迟不变——这本质上是用 0 代价换来的吞吐红利。**
