# Q61 零拷贝

Kafka 使用零拷贝（Zero-Copy）技术将日志文件直接传输到网络 Socket，数据不经过用户空间。传统 IO 需要 4 次数据拷贝和 4 次上下文切换，sendfile 零拷贝仅需 2 次拷贝和 2 次上下文切换——性能提升 2~3 倍，CPU 占用大幅降低。这是 Kafka 顺序写 + Page Cache + 零拷贝"三件套"中的最后一环。

上图对比了传统 IO 和零拷贝 sendfile 的完整路径。传统 IO 路径需要 4 次数据拷贝（2 次 DMA + 2 次 CPU 拷贝）和 4 次上下文切换；零拷贝 sendfile 仅需 2 次 DMA 拷贝和 2 次上下文切换，数据在内核空间内从 Page Cache 直接搬运到 Socket Buffer（DMA Gather），完全绕过用户空间。在大量数据发送场景下，CPU 占用可降低 50%~70%。

## 代码实现：零拷贝分层示例

### Layer 1 — 传统 IO：read() + send()（4 次拷贝）

```java
/**
 * 传统 IO 方式：从文件读取数据，通过 Socket 发送
 * 数据路径：磁盘(DMA) → 内核 Read Buffer → 用户 App Buffer(CPU) → 内核 Socket Buffer(CPU) → 网卡(DMA)
 * 拷贝次数：4 次（2 次 DMA + 2 次 CPU）
 * 上下文切换：4 次（read 进出内核 + send 进出内核）
 */
public class TraditionalFileSender {

    public static void sendFile(String filePath, Socket socket) throws Exception {
        byte[] buffer = new byte[65536]; // 64KB 用户空间缓冲区
        int bytesRead;

        try (FileInputStream fis = new FileInputStream(filePath);
             OutputStream out = socket.getOutputStream()) {

            while ((bytesRead = fis.read(buffer)) != -1) {  // ctx-switch: user→kernel→user
                // read() 内部：磁盘(DMA) → 内核 Read Buffer → 用户 buffer (CPU copy)
                out.write(buffer, 0, bytesRead);             // ctx-switch: user→kernel→user
                // write() 内部：用户 buffer → 内核 Socket Buffer (CPU copy)
            }
        }
        // 总共：N 次循环 × 4 次拷贝 × 4 次上下文切换
        // 对于 1MB 文件，使用 64KB buffer：16 次循环 × 4 次拷贝 = 64 次拷贝
    }
}
```

```bash
# 编译运行
javac TraditionalFileSender.java
java TraditionalFileSender /data/kafka-logs/test.log

# 观察 CPU 使用率（top/htop）
# 传统 IO 方式下，内核态 CPU（sy）占比很高——大量时间花在内核-用户态切换和数据拷贝上
```

传统 IO 的核心问题是：数据在用户空间和内核空间之间来回拷贝。先是 `read()` 把数据从内核空间拷到用户空间，然后 `send()` 又把数据从用户空间拷回内核空间——这两次 CPU 拷贝在数据量大时极耗 CPU。

### Layer 2 — 零拷贝：FileChannel.transferTo()

```java
/**
 * 零拷贝方式：FileChannel.transferTo() → 底层调用 sendfile 系统调用
 * 数据路径：磁盘(DMA) → 内核 Page Cache → 网卡(DMA)
 * 拷贝次数：2 次（全部 DMA，0 次 CPU 拷贝）
 * 上下文切换：2 次（进入/退出 sendfile）
 */
public class ZeroCopyFileSender {

    public static void sendFile(String filePath, SocketChannel socketChannel) throws Exception {
        try (FileChannel fileChannel = FileChannel.open(Path.of(filePath),
                     StandardOpenOption.READ)) {

            long position = 0;
            long size = fileChannel.size();
            long transferred = 0;

            while (transferred < size) {
                // transferTo 底层调用 sendfile() — 零拷贝
                transferred += fileChannel.transferTo(
                    position + transferred,
                    size - transferred,
                    socketChannel
                );
            }
        }
        // 数据不经过用户空间，无 CPU 拷贝参与
        // 对于 1MB 文件：仅 2 次 DMA 拷贝 + 2 次上下文切换（sendfile 调用期间）
    }
}
```

```bash
# 需要 NIO 的 SocketChannel（不能是传统 Socket）
# Spring Kafka 内部自动处理，这里展示底层原理

# 测试对比
# 传统 IO：htop 中 CPU sy (system) 占用明显，约 30%~50%
# 零拷贝：htop 中 CPU sy 极低，约 10%~20%，整体 CPU 降 50%+
```

```bash
# 验证系统是否使用 sendfile
# strace 跟踪系统调用
strace -e trace=sendfile -p $(pgrep -f Kafka) 2>&1 | head -20
# 输出示例：
# sendfile(64, 65, NULL, 1048576) = 1048576
# sendfile(64, 65, NULL, 1048576) = 1048576
# 说明 Kafka 确实在用 sendfile 零拷贝传输数据
```

`FileChannel.transferTo()` 在 Linux 上直接映射到 `sendfile()` 系统调用，内核通过 DMA Gather 将 Page Cache 中的数据描述符传给 Socket Buffer，DMA 引擎直接从 Page Cache 读取数据发送到网卡。

### Layer 3 — Kafka Broker 如何使用零拷贝

```properties
# Kafka Broker 端无需额外配置，零拷贝是框架级内置优化
# Kafka 源码中 LogSegment.read() 内部使用 FileChannel.transferTo()
# 流式传输时自动享受零拷贝优势

# 关键：Consumer 拉取数据时，Broker 通过 FileRecords 读取日志
# FileRecords.readInto() → FileChannel.transferTo() → SocketChannel
```

```java
// Kafka 源码简化示意（kafka.server.FileRecords）
// 实际在 kafka.log.FileRecords / kafka.message.FileMessageSet 中
public class KafkaZeroCopyIllustration {

    // Kafka Broker 内部：将日志 Segment 数据通过零拷贝发送给 Consumer
    public long writeTo(TransferableChannel destChannel, long offset, int length) {
        // 内部调用 FileChannel.transferTo(position, count, socketChannel)
        return this.fileChannel.transferTo(offset, length, destChannel);
        // 日志 Segment(.log 文件) → Page Cache → Consumer Socket（零拷贝）
    }
}
```

```bash
# ===== Kafka Consumer 读取时验证零拷贝 =====

kafka-console-consumer.sh --bootstrap-server broker1:9092 \
    --topic test-topic --from-beginning --group test-group

# 2. 观察 Broker 进程的 sendfile 调用

# -c 参数会统计 sendfile 调用次数和耗时，用于定量分析

# 3. 查看网络传输 stats

```

Kafka 框架层已经将零拷贝集成到核心 IO 路径中。只要消息数据在 Page Cache 中（热数据），Consumer 拉取时 Broker 自动通过 `transferTo()` 零拷贝传输。对于刚写入的热消息或频繁消费的消息，零拷贝效果最佳。

### Layer 4 — 零拷贝的条件与局限

```bash
# ===== 条件 1：数据必须在 Page Cache 中 =====
# sendfile 要求源数据在 Page Cache 中（文件页映射）
# 冷数据未缓存 → 需要先从磁盘读取到 Page Cache → 可享受后续零拷贝

# 检查文件是否在 Page Cache
vmtouch /data/kafka-logs/order-events-0/00000000000000000000.log
# Resident Pages 占比越高，零拷贝效果越好

# ===== 条件 2：不能修改数据 =====
# sendfile 是纯转发，数据不经过用户空间 → 无法在应用层修改内容
# 如果 Broker 需要对消息做压缩/加密/转换 → 必须经过用户空间 → 无法零拷贝

# ===== 条件 3：需要 NIO Channel =====
# 传统 java.io.Socket 不支持 transferTo
# 必须用 java.nio.channels.SocketChannel
# Kafka 网络层（基于 Java NIO）天然满足此条件
```

```java
// 条件验证：以下场景无法使用零拷贝
public class ZeroCopyLimitations {

    // 场景 1：需要对内容做转换
    public void withTransformation(FileChannel fc, SocketChannel sc) {
        // 如果需要在发送前解密/解压/过滤 → 数据必须读到用户空间
        // → 无法使用 transferTo → 回退到传统 read+send
        ByteBuffer buf = ByteBuffer.allocate(65536);
        fc.read(buf);
        // ... 解密/解压/过滤操作（必须在用户空间完成）...
        sc.write(buf);
    }

    // 场景 2：需要聚合多条消息
    // 如果 Consumer 拉取涉及多个 Segment → 可能部分走零拷贝、部分不走
    // Kafka 会尽量在单个 Segment 内用 transferTo 批量传输
}
```

```bash
# ===== 局限 4：SSL/TLS 场景 =====
# 新版本 Linux 内核（4.14+）支持 Kernel TLS (kTLS)
# ➕ sendfile + kTLS = 零拷贝 SSL 传输
# Kafka 2.6+ 支持 kTLS，但需要内核版本和 Broker 配置配合

# 检查内核是否支持 kTLS
uname -r  # 需要 >= 4.14

# Kafka Broker 启用 kTLS（需要额外配置）
# listener.name.internal.ssl.principal.mapping.rules=...
# 复杂的 SSL 配置请参考 Kafka 安全文档
```

零拷贝并非万能——它的核心条件是"数据在 Page Cache 中"且"不需要应用层修改"。Kafka 的设计恰好满足这两个条件：消息以日志形式存储在磁盘上（由 Page Cache 缓存）、Broker 不需要对消息做应用层转换。

## 传统 IO vs 零拷贝 sendfile

| 维度 | 传统 IO（read + send） | 零拷贝 sendfile（transferTo） |
|---|---|---|
| 数据拷贝次数 | 4 次（2 次 DMA + 2 次 CPU） | 2 次（全部 DMA，0 次 CPU） |
| 上下文切换次数 | 4 次（read 进/出 + send 进/出） | 2 次（sendfile 进/出） |
| 数据经过用户空间 | 是（App Buffer 中有一份） | 否（数据不离开内核空间） |
| CPU 占用 | 高（CPU 参与 2 次数据拷贝） | 低（DMA 自主搬运） |
| 吞吐量（1MB 消息） | ~500 MB/s（受 CPU 拷贝限制） | ~1500 MB/s（接近 DMA 带宽） |
| 适用场景 | 需要修改/转换数据内容 | 纯转发，不修改数据 |
| Java 实现 | FileInputStream.read + Socket.write | FileChannel.transferTo |
| 底层系统调用 | read() + write() / send() | sendfile() |
| 依赖条件 | 无特殊要求 | 数据在 Page Cache、NIO Channel |
| SSL/TLS | 标准支持（JVM SSL） | 需要 kTLS（Linux 4.14+） |

## 一句话总结

**一句话总结：Kafka 用 sendfile 零拷贝将"磁盘→Page Cache→网卡"的数据路径压缩为 2 次 DMA 拷贝，彻底消除 CPU 数据搬运开销，配合顺序写和 Page Cache 构成"三件套"，是大数据量传输场景下达到 GB/s 级吞吐的关键技术。**
