# Q60 Page Cache

Kafka 大量依赖操作系统的 Page Cache，而不是自己管理内存缓存——写入时消息先进入 OS Page Cache 再异步刷盘，读取时优先从 Page Cache 命中返回，避免直接读磁盘。这样做既避免了双重缓存的内存浪费，又能复用 OS 成熟的 LRU、预读、写合并算法。

上图展示了 Kafka Page Cache 的完整读写路径：写入时，Producer 消息经 Broker 进入 OS Page Cache（内核空间），由 OS 择机异步刷盘；读取时，Consumer 先查 Page Cache，命中（热数据）直接返回，未命中（冷数据）才从磁盘读取并载入 Page Cache。右侧内存分配对比说明：Kafka 刻意将 JVM Heap 设小（4~8GB），把大量物理内存留给 Page Cache 缓存消息数据。

## 代码实现：Page Cache 分层示例

### Layer 1 — Broker 端刷盘配置

```properties
# server.properties — 刷盘策略配置
# 默认值：由 OS 控制刷盘时机（推荐，利用 Page Cache + OS 写合并）
# log.flush.interval.messages 未设置（默认 Long.MAX_VALUE）
# log.flush.interval.ms 未设置（默认 Long.MAX_VALUE）

# ===== 强制刷盘阈值（一般不推荐设置，会破坏顺序写优势）=====
# 每 N 条消息触发一次 fsync
# log.flush.interval.messages=10000

# 每 N 毫秒触发一次 fsync
# log.flush.interval.ms=1000

# ===== Topic 级别刷盘策略 =====
kafka-configs.sh --bootstrap-server broker1:9092 \
    --alter --topic critical-topic \
    --add-config flush.messages=1,flush.ms=0
# 注意：flush.messages=1 表示每条消息都 fsync，吞吐会剧烈下降
```

```bash
# 查看当前刷盘间隔（默认值是未设置，OS 决定）
kafka-configs.sh --bootstrap-server broker1:9092 \
    --describe --topic __consumer_offsets --all | grep flush
# 通常不返回任何值，表示沿用 OS 默认行为
```

Kafka 默认几乎不配置强制刷盘，完全信任 OS 的 Page Cache 管理——这既是 Kafka 高吞吐的关键，也是"把内存留给 Page Cache"策略的体现。除非对数据安全性有极端要求（如金融交易系统），否则不推荐设置强制刷盘。

### Layer 2 — JVM 堆内存配置

```bash
# ===== kafka-server-start.sh 中的 JVM 配置 =====
# 生产环境推荐：-Xmx4g ~ -Xmx8g，把剩余内存留给 Page Cache
export KAFKA_HEAP_OPTS="-Xmx4g -Xms4g"

# 32GB 物理机典型内存分配：
# JVM Heap：4~8GB（Kafka Broker 进程使用）
# Page Cache：20~24GB（OS 自动管理，缓存消息日志）
# OS 开销：约 2~4GB

# ===== 启动时查看 JVM 参数 =====
# 临时设置并启动（测试用）
KAFKA_HEAP_OPTS="-Xmx4g -Xms4g" bin/kafka-server-start.sh config/server.properties

# 确认 JVM 堆大小生效
jps -lv | grep Kafka
# 输出：12345 Kafka -Xmx4g -Xms4g ...
```

```bash
# 查看 Kafka Broker 实际使用的内存
# Heap 使用量（JVM 内部）
jstat -gc $(pgrep -f Kafka) 1s

# 系统级内存分布
free -h
#               total   used    free    shared  buff/cache  available
# Mem:           31G    4.5G    2.0G    0.5G    24.5G       26G
# JVM Heap ≈ 4G, Page Cache ≈ 24G (buff/cache 列)
```

JVM Heap 只分配 4GB 意味着 Kafka 进程本身内存消耗很低，GC 停顿也极短。而 24GB 的 Page Cache 足以缓存数十 GB 的热点消息日志，读取命中率可达 99%+。

### Layer 3 — Page Cache 命中观察

```bash
# ===== 查看 Page Cache 使用情况 =====
# Linux 下 free / cached / buffers 的关系
free -h
# Mem: cached 列即 Page Cache 大小（含 tmpfs）

# 精确查看文件级 Page Cache
vmtouch /data/kafka-logs/order-events-0/*.log
# 输出示例：
# Files: 5
# Directories: 0
# Resident Pages: 524288/1048576  1G/2G  50.0%
# 说明该 Partition 的日志文件有 50% 在 Page Cache 中

# ===== 监控磁盘读写 vs Page Cache =====
# iostat：设备级 IO 统计
iostat -x 1 /dev/sdb
# 顺序写时：w/s 高, await 低, 大部分写入命中 Page Cache
# 大量读时：r/s 低（说明读取被 Page Cache 拦截）

# vmstat：系统级内存和 IO 统计
vmstat 1
# bi (block in / 读取)、bo (block out / 写入)
# bi 低说明大部分读命中 Page Cache，未落到磁盘
```

```bash
# ===== 观察 Page Cache 读命中率 =====
# 1. 先清除 Page Cache（需要 root）
echo 3 > /proc/sys/vm/drop_caches

# 2. Consumer 读消息（第一次：Cache Miss，磁盘读）
# iostat 中 r/s 会明显上升

# 3. Consumer 再读同一条消息（第二次：Cache Hit）
# iostat 中 r/s 几乎为 0，全部命中 Page Cache

# 4. 查看具体文件在 Page Cache 中的页数
cat /proc/sys/vm/min_free_kbytes  # 最小空闲内存
cat /proc/meminfo | grep -E "^(Cached|Dirty|Writeback)"
```

第一次 Consumer 读取时消息从磁盘载入 Page Cache，第二次读取时直接从 Page Cache 命中返回——这就是 Kafka 热数据读取极快的底层原理。

### Layer 4 — 为什么不用 In-Memory Cache（对比 ActiveMQ/Redis）

```java
// 传统消息中间件（如 ActiveMQ）做法：JVM 内维护消息缓存
// 问题 1 — 双重缓存：
//   消息在 JVM Heap 中存一份 + OS Page Cache 又存一份 = 内存浪费
// 问题 2 — GC 压力：
//   缓存消息越多 → Heap 越大 → GC 暂停时间越长
// 问题 3 — 进程重启丢失：
//   JVM 进程挂掉 → JVM Heap 里的缓存消息全部丢失

// Kafka 的做法：不自己缓存，交给 Page Cache
// 优势 1 — 无双重缓存（消息只在 Page Cache 中）
// 优势 2 — GC 压力极低（JVM Heap 仅 4~8GB）
// 优势 3 — 进程重启 Page Cache 仍在（无需重新预热）
```

```bash
# ===== 对比 Redis 的内存模型 =====
# Redis：自己管理内存（malloc），完全不依赖 Page Cache
# Redis 进程挂掉 → 所有数据丢失（除非 AOF/RDB 持久化）
# 适用于：需要精确控制缓存数据的场景

# Kafka + Page Cache 模型
# 适用于：流式消息场景，消息按时间顺序访问
# Page Cache 的 LRU 淘汰策略天然适合 Kafka 的日志访问模式
# 最新的 Segment 最热 → 在 Page Cache 中；老 Segment 冷 → 自然淘汰
```

```bash
# 对比结果验证
# ActiveMQ（JVM Cache）模式：
#   Heap 大 → GC 长暂停 → 吞吐波动
# Kafka（Page Cache）模式：
#   Heap 小 → GC 几乎无影响 → 吞吐平稳

# 测试：简单用 wrk / kafka-producer-perf-test 验证
bin/kafka-producer-perf-test.sh --topic perf-test \
    --num-records 10000000 --record-size 1000 \
    --throughput -1 \
    --producer-props bootstrap.servers=broker1:9092 \
    acks=1
# 注意观察 GC 日志是否出现长时间停顿
```

Kafka 的设计哲学是"把缓存交给更专业的 OS"，这与 Redis/ActiveMQ 的"自己精确控制"形成了明显的架构差异，也解释了为什么 Kafka 能在大吞吐下保持稳定的低延迟。

## Kafka Page Cache vs 手动内存管理

| 维度 | Page Cache（Kafka） | 手动 JVM 缓存（如 ActiveMQ） |
|---|---|---|
| 缓存位置 | OS 内核空间（Page Cache） | JVM 堆内存（Heap） |
| 双重缓存 | 无（唯一一份在 Page Cache） | 有（JVM 一份 + Page Cache 一份） |
| GC 影响 | 极低（JVM Heap 仅 4~8GB） | 高（Heap 大导致 GC 长暂停） |
| 进程重启 | Page Cache 不丢，恢复快 | JVM 缓存全丢，需重新预热 |
| LRU 管理 | OS 内核成熟算法 | 需自行实现 |
| 预读 & 写合并 | OS 自动优化 | 无法利用 OS 预读 |
| 零拷贝兼容 | sendfile 可直接读取 Page Cache | 数据在 JVM Heap，需拷贝到内核 |
| 内存利用率 | 高（共享 Page Cache） | 低（JVM 与 OS 各存一份） |
| 适用场景 | 流式消息、顺序访问 | 精确缓存、小数据量 |

## 一句话总结

**一句话总结：Kafka 放弃手动管理内存缓存，把消息数据全部交给 OS Page Cache——JVM Heap 仅 4~8GB，剩余内存全用于缓存日志数据，既避免了双重缓存浪费和 GC 抖动，又是零拷贝 sendfile 的前提条件。**
