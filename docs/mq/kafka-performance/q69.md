# Q69 Broker 网络模型

Kafka Broker 采用 Java NIO + Reactor 模式构建高性能网络层，核心由 Acceptor（1 线程接连接）、Processor（3 线程读/写 IO）和 KafkaRequestHandler（8 线程处理业务）三级流水线组成，底层依赖 Linux epoll 实现单线程管理数千连接的非阻塞多路复用。

这套三级流水线架构将连接管理、网络 IO 和业务处理彻底解耦：Acceptor 专注建连，Processor 借助 epoll 非阻塞地处理数千连接的读写，Handler 线程池并行处理业务逻辑后通过响应队列将结果返还 Processor 写回客户端。

## 代码分层演示

### Layer 1 — 网络线程配置

```java
// server.properties — Broker 网络线程参数
num.network.threads=3       // Processor 线程数，建议 = CPU 核数
num.io.threads=8            // RequestHandler 线程数，建议 = CPU 核数 × 2
queued.max.requests=500     // RequestChannel 队列大小，满时阻塞
socket.send.buffer.bytes=102400    // SO_SNDBUF
socket.receive.buffer.bytes=102400 // SO_RCVBUF
```

```bash
  --entity-type brokers --entity-name 0 --describe

# JMX 查看线程状态
kafka-run-class.sh kafka.tools.JmxTool \
  --object-name kafka.network:type=SocketServer,name=NetworkProcessorAvgIdlePercent
```

### Layer 2 — Reactor 模式代码结构

```java
// 核心类：kafka.network.SocketServer — 网络服务主入口
// 构造时创建 Acceptor + Processor + Handler 三层组件
public class SocketServer {
    private final int numNetworkThreads;   // Processor 数量
    private final int numIoThreads;        // Handler 数量
    private final Acceptor acceptor;        // 1 个 Acceptor 线程
    private final Processor[] processors;   // numNetworkThreads 个 Processor
    private final KafkaRequestHandlerPool handlers; // Handler 线程池

    // Processor 内部持有 Selector（底层封装 Java NIO Selector）
    // 每个 Processor 绑定独立的 Selector，避免锁竞争
    private class Processor extends AbstractServerThread {
        private final Selector selector;  // Java NIO Selector → Linux epoll

        @Override
        public void run() {
            while (isRunning()) {
                // 1. 注册新连接（Acceptor 移交）
                configureNewConnections();
                // 2. 处理已就绪的 IO 事件（epoll_wait）
                selector.poll(300);  // 阻塞等待 IO 事件
                // 3. 读取请求 → 放入 RequestChannel
                // 4. 检查响应队列 → write 回客户端
                // 5. 关闭断开的连接
            }
        }
    }
}
```

```bash
# 查看 Broker 当前活跃连接数
kafka-run-class.sh kafka.tools.JmxTool \
  --object-name kafka.network:type=SocketServer,name=NetworkProcessorAvgIdlePercent
```

### Layer 3 — RequestChannel 请求队列机制

```java
// kafka.network.RequestChannel — 连接 Processor 和 Handler 的桥梁
public class RequestChannel {
    // 阻塞队列：Processor 放入请求，Handler 取出处理
    private final ArrayBlockingQueue<BaseRequest> requestQueue;
    private final int queueSize;  // queued.max.requests = 500

    // Processor 线程调用：发送请求到队列
    public void sendRequest(Request request) throws InterruptedException {
        // 队列满时阻塞 Processor 线程，形成背压
        requestQueue.put(request);
    }

    // Handler 线程调用：从队列取请求
    public BaseRequest receiveRequest(long timeout) throws InterruptedException {
        return requestQueue.poll(timeout, TimeUnit.MILLISECONDS);
    }

    // 响应队列：按 Processor ID 路由响应回对应 Processor
    private final Map<Integer, BlockingQueue<Response>> responseQueues;
    // Handler 处理完后 → responseQueues[processorId].put(response)
    // Processor 轮询 → responseQueues[myId].poll() → write 给客户端
}
```

```bash
# 监控请求队列堆积情况
kafka-run-class.sh kafka.tools.JmxTool \
  --object-name kafka.network:type=RequestChannel,name=RequestQueueSize
```

## 对比表

| 维度 | Kafka NIO Reactor 模型 | 传统 BIO 线程池模型 |
|:---|:---|:---|
| **IO 模型** | Non-Blocking IO（NIO） | Blocking IO（BIO） |
| **连接管理** | 1 个 Acceptor 线程管理所有新连接 | 每个连接占用 1 个独立线程 |
| **IO 处理** | 少量 Processor 线程（epoll 多路复用） | 每个连接 1 个线程阻塞 read/write |
| **线程开销** | 极低（数千连接只需 3 个线程） | 极高（1000 连接 = 1000 线程） |
| **业务处理** | Handler 线程池（共享，默认 8） | 直接在 IO 线程中处理 |
| **请求排队** | RequestChannel 解耦 IO 和业务 | 无解耦，IO 线程直接处理 |
| **背压机制** | 队列满时阻塞 Processor（天然限流） | 无内置背压 |
| **适用场景** | 高并发长连接（万级 QPS） | 低并发短连接（千级 QPS） |
| **内存消耗** | 低（共享 Selector、堆外 Buffer） | 高（每线程独立栈空间 ~1MB） |
| **底层系统调用** | epoll（O(1) 事件通知） | select/poll（O(n) 轮询） |
| **配置参数** | `num.network.threads` + `num.io.threads` | 线程池大小 |

## 一句话总结

**Kafka Broker 的 Reactor 模型用 "1 个 Acceptor + N 个 Processor + M 个 Handler" 三级流水线，将连接管理、网络 IO 和业务处理彻底解耦，配合 Linux epoll 实现单机管理数千连接，是支撑百万级 QPS 的网络基石。**
