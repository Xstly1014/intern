# Q85 消息积压排查

消息积压是指 Consumer Group 的 Lag（未消费消息数）持续增长，说明消费速度跟不上生产速度。排查核心四步：确认积压量级（kafka-consumer-groups.sh --describe） → 定位根因（消费者是否存活 / 消费速率 / 生产速率 / 下游依赖） → 检查消费者状态（Rebalance / OOM / Full GC） → 执行解决方案（扩容 / 优化逻辑 / 降级 / 转发）。

消息积压排查的核心在于快速定位是"生产过快"还是"消费过慢"。从上面的全景图可以看出，积压的根因只有三个方向：生产者端流量突增、消费者端处理能力不足、或者中间依赖（DB/Redis/下游服务）成为瓶颈。排查时先通过 `kafka-consumer-groups.sh --describe` 确认 Lag 量级和增长趋势，再结合 JMX 指标（records-consumed-rate / records-produced-rate）判断两端速率差异。如果是消费者问题，优先检查 Rebalance 日志和 GC 日志，排除 OOM 和 Full GC。

## 分层代码：积压排查工具箱

### Layer 1 — 查看 Consumer Group Lag

```bash
# 核心命令：查看所有分区 Lag 详情
kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --group my-consumer-group

# 输出关键字段：
# TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# t_order 0          1523000         1587000         64000
# t_order 1          1400000         1550000         150000   ← 该分区积压严重

# 只看 Lag > 0 的分区
kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe --group my-consumer-group \
  | awk '{if($6>0) print $0}'
```

### Layer 2 — 监控生产/消费速率

```bash
# 持续监控 Lag 变化趋势（每 5s 采样，观察增长率）
watch -n 5 "kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe --group my-consumer-group \
  | tail -n +3 | awk '{sum+=\$6} END {print \"Total Lag: \" sum}'"

# JMX 指标获取消费速率
# MBean: kafka.consumer:type=consumer-fetch-manager-metrics,client-id=*
# 关键指标：records-consumed-rate（条/秒）、bytes-consumed-rate（字节/秒）
# 通过 jconsole 或 Prometheus JMX Exporter 采集

# 生产速率（需要 Broker 端 JMX）
# MBean: kafka.server:type=BrokerTopicMetrics,name=MessagesInPerSec
```

### Layer 3 — 紧急扩容方案

```bash
# 1. 增加 Partition（仅支持追加，不能减少）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic t_order \
  --partitions 30

# 2. 启动更多消费者实例（注意：有效消费者数 ≤ Partition 数）
# 在消费者应用中动态扩容实例数
# 检查当前消费者数
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group my-consumer-group --members

# 3. 消费者配置优化（配合扩容）
max.poll.records=200       # 减少单次拉取量，加快 poll 频率
fetch.min.bytes=1048576    # 1MB 批量拉取
fetch.max.wait.ms=100      # 减少等待时间
```

### Layer 4 — 临时降级方案

```java
// 方案1：跳过非核心消息（通过消息头标记）
consumer.poll(Duration.ofMillis(100)).forEach(record -> {
    String priority = new String(
        record.headers().lastHeader("priority").value()
    );
    if ("low".equals(priority) && System.currentTimeMillis() - record.timestamp() > 600_000) {
        // 跳过积压超过 10 分钟的低优先级消息
        log.warn("Skip stale low-priority message, offset={}", record.offset());
        return;
    }
    process(record);
});

// 方案2：转发到新 Topic 消费
Properties producerProps = new Properties();
producerProps.put("bootstrap.servers", "localhost:9092");
KafkaProducer<String, String> proxyProducer = new KafkaProducer<>(producerProps);

consumer.poll(Duration.ofMillis(100)).forEach(record -> {
    // 原始消息直接转发到临时 Topic
    proxyProducer.send(new ProducerRecord<>(
        "t_order_backlog_temp", record.key(), record.value()
    ));
    // 此时原始消费组 offset 在提交，但消息由临时消费者集群处理
});
// 需要同时启动一批消费者订阅 t_order_backlog_temp 并行处理
```

## 消息积压症状与根因对比

| 症状 | 可能根因 | 排查命令 | 解决方案 |
|------|----------|----------|----------|
| Lag 突然飙升，但消费者存活 | 生产端流量突增（大促/上游重放） | `kafka-consumer-groups.sh --describe` 对比历史 Lag；检查 Broker JMX `MessagesInPerSec` | 紧急扩容消费者数 / 增加 Partition；上游限流 |
| Lag 持续缓慢增长 | 消费处理耗时增加（DB 慢查询/下游变慢） | 消费者日志耗时分布；`show processlist` / `slowlog get` | 优化消费逻辑（批量/异步）；优化下游 SQL 索引 |
| 消费者频繁重启，Lag 波动 | OOM / Full GC 导致频繁重启 | `jstat -gcutil <pid> 1000`；GC 日志分析 | 增加 JVM 堆内存；优化内存泄漏；减少 `max.poll.records` |
| 所有消费者 Lag 同时增加 | Consumer Group 正在 Rebalance | 消费者日志 `(Re)joining group` 关键字 | Rebalance 参数调优（参见 Q86） |
| 部分 Partition Lag 很高，其他为 0 | 分区数据倾斜（Key 分布不均） | `kafka-run-class.sh kafka.tools.GetOffsetShell` 查各分区消息数 | 优化分区 Key 策略；对热点 Key 加随机后缀 |
| Lag 突降为 0 后迅速回升 | 消费者提交 offset 但实际未处理完 | 检查消费者是否异步提交 + 处理失败未重试 | 改为处理完再提交；`enable.auto.commit=false` |

## 一句话总结

**消息积压排查四步法：先看 Lag 确认量级，再定位是生产过快还是消费过慢，然后检查消费者 Rebalance/GC 状态，最后按紧急度执行扩容-优化-降级-转发方案，同时建立 Lag 监控告警防线。**
