# Q86 Rebalance 优化

Rebalance 是 Kafka Consumer Group 重新分配 Partition 的过程，期间所有消费者暂停消费。频繁 Rebalance 的三大根因：心跳超时被误判宕机（session.timeout.ms 过短）、消息处理超过 max.poll.interval.ms 被踢出 Group、消费者频繁上下线（发布部署/OOM重启/网络抖动）。优化策略：调大超时参数 + 采用 CooperativeStickyAssignor 增量重平衡（Kafka 2.4+）+ 分批滚动发布。

Rebalance 是 Kafka 消费组可用性的最大敌人之一。未优化时，每次消费者变更（上线/下线/心跳超时）都会触发全量分区重分配（Stop-The-World），导致所有消费者暂停消费。通过合理配置超时参数，并升级到 CooperativeStickyAssignor 增量重平衡策略，可以将 Rebalance 的影响从"全局停摆"降为"局部微调"，迁移量从全量（O(N)）降为必要最小量（O(1)）。

## 分层代码：Rebalance 优化与排查

### Layer 1 — Rebalance 超时参数配置

```properties
# consumer.properties — 核心超时参数

# 心跳超时：Consumer 与 Coordinator 之间的心跳超时
# 默认 10000(10s)，建议调大到 30000(30s)，避免 GC pause 或短暂网络抖动导致误判
session.timeout.ms=30000

# 心跳间隔：Consumer 向 Coordinator 发送心跳的频率
# 建议设为 session.timeout.ms 的 1/3，确保在超时前至少发送 3 次心跳
heartbeat.interval.ms=10000

# Poll 间隔超时：两次 poll() 调用之间的最大时间间隔
# 默认 300000(5min)，如果消息处理耗时 > 此值，consumer 会被踢出
# 必须确保：max.poll.interval.ms > 单批次最长处理时间
max.poll.interval.ms=600000

# 减少单次 poll 拉取量，加快 poll 频率，避免单次处理时间过长
max.poll.records=200

# 新 Group 首次 Rebalance 延迟：单位 ms，默认 0
# 建议 3000，等待短时间内加入的 consumer，避免连续多次 Rebalance
group.initial.rebalance.delay.ms=3000
```

### Layer 2 — 增量协作 Rebalance 配置

```properties
# consumer.properties — 使用 CooperativeStickyAssignor

# Kafka 2.4+ 支持的增量协作式分配策略
# 关键收益：消费者离开时只迁移必要的分区，已分配分区不受影响
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor

# Java 代码方式配置
# props.put(ConsumerConfig.PARTITION_ASSIGNMENT_STRATEGY_CONFIG,
#     "org.apache.kafka.clients.consumer.CooperativeStickyAssignor");
```

## 三种分配策略对比

| 维度 | RangeAssignor（默认） | RoundRobinAssignor | CooperativeStickyAssignor（推荐） |
|------|----------------------|-------------------|----------------------------------|
| 分配方式 | 按 Topic 分区范围顺序分配 | 所有分区轮询依次分配 | 粘性分配 + 增量迁移 |
| 分区均衡性 | 可能不均衡（同 Topic 多 Consumer 时差异大） | 较均衡 | 均衡（继承 RoundRobin 优点） |
| Rebalance 时的迁移量 | 高（全量重新分配，可能全部 Partition 换主） | 高（全量重新分配） | 极低（只迁移必须迁移的分区） |
| Rebalance 期间消费 | Stop-The-World（全部 consumer 撤销并重新分配） | Stop-The-World | 增量协作（已分配分区持续消费） |
| Kafka 版本要求 | 所有版本 | 所有版本 | Kafka 2.4+ |
| 适用场景 | 每个 Topic 分区数能被 Consumer 数整除时可用 | 跨 Topic 均衡性要求高 | 生产环境首选（Rebalance 影响最小） |
| 典型配置 | partition.assignment.strategy=RangeAssignor | partition.assignment.strategy=RoundRobinAssignor | partition.assignment.strategy=CooperativeStickyAssignor |

## 一句话总结

**Rebalance 优化的核心三件套：调大超时参数（session.timeout.ms=30s / max.poll.interval.ms > 最长处理时间）、启用 CooperativeStickyAssignor 增量协作式分配（Kafka 2.4+）、分批滚动发布避免同时重启——三者缺一不可，最终效果是从 Stop-The-World 全量迁移变为增量微调。**
