# Q84 副本数选择

推荐 `replication.factor=3`，配合 `min.insync.replicas=2`：3 副本中允许 1 个宕机后仍能正常读写，在可靠性和性能之间取得最佳平衡。副本越多可用性越高，但写入开销线性增长——每个副本都需要同步一份数据。

副本数的选择本质上是可靠性、性能和成本的三角权衡。上图清晰对比了 rf=1（无冗余不可用）、rf=3（推荐的最优平衡点）以及 rf=5（边际收益递减）三种场景。底部同时展示了跨机架感知的部署拓扑，通过 `broker.rack` 将 3 个副本分布到 3 个物理机架，实现机架级容灾。下面通过分层代码展示副本数从配置到运维的完整链路。

## 代码：副本数从配置到运维

### Layer 1 — replication.factor 配置

```bash
# 创建 Topic 时指定副本数（推荐 rf=3）
kafka-topics.sh --bootstrap-server localhost:9092 \
    --create \
    --topic payment-events \
    --partitions 8 \
    --replication-factor 3 \
    --config min.insync.replicas=2

# min.insync.replicas 含义：
#   acks=all 时，Producer 写入的消息必须被至少 min.insync.replicas 个副本确认
#   rf=3, min.insync=2: 至少 Leader + 1 个 Follower 确认，容忍 1 个副本宕机
#   若 ISR < min.insync，Producer 会收到 NOT_ENOUGH_REPLICAS 异常

# 修改已有 Topic 的 min.insync.replicas
kafka-configs.sh --bootstrap-server localhost:9092 \
    --alter \
    --topic payment-events \
    --add-config min.insync.replicas=2

# 查看 Topic 当前配置
kafka-configs.sh --bootstrap-server localhost:9092 \
    --describe \
    --topic payment-events
```

### Layer 2 — 跨机架感知配置（broker.rack）

```properties
# server.properties — 每个 Broker 配置自己的机架信息
# Broker-1 (rack1 机架)
broker.id=1
broker.rack=rack1
# ...其他配置...

# Broker-2 (rack2 机架)
broker.id=2
broker.rack=rack2

# Broker-3 (rack3 机架)
broker.id=3
broker.rack=rack3

# Kafka 内置机架感知副本分配策略：
# 1. 优先将副本分布到不同机架的 Broker
# 2. 同一个 Partition 的副本不会落在同一个机架
# 3. 机架故障时，其他机架仍有完整数据
```

### Layer 3 — 查看副本分布

```bash
# 查看 Topic 分区副本分布详情
kafka-topics.sh --bootstrap-server localhost:9092 \
    --describe \
    --topic payment-events

# 输出示例（关注 Leader / Replicas / ISR 列）：
# Topic: payment-events  PartitionCount: 8  ReplicationFactor: 3
#   Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
#   Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
#   Partition: 2  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2

# 检查是否有 ISR 收缩的情况（副本未同步）
kafka-topics.sh --bootstrap-server localhost:9092 \
    --describe \
    --under-replicated-partitions

# 查看 Preferred Replica 选举状态
kafka-preferred-replica-election.sh \
    --bootstrap-server localhost:9092

# 通过 kafka-metadata.sh 查看 Broker 的 Rack 信息 (Kafka 3.3+)
kafka-metadata.sh --snapshot /tmp/kraft-combined-logs/__cluster_metadata-0/00000000000000000000.log \
    --command "cat brokers" 2>/dev/null
```

### Layer 4 — 副本数动态增加

```bash
# 副本数只能增加不能减少，通过分区重分配实现
# 步骤 1: 生成重分配 JSON 计划（将当前副本数从 2 扩大到 3）

# 先创建 topics-to-move.json，指定要重分配的 Topic
echo '{"topics":[{"topic":"payment-events"}],"version":1}' > topics-to-move.json

# 生成候选重分配方案（仅生成，不执行）
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
    --topics-to-move-json-file topics-to-move.json \
    --broker-list "1,2,3" \
    --generate

# 步骤 2: 取上述输出的 "Proposed partition reassignment configuration"
# 保存为 reassignment.json，然后执行
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
    --reassignment-json-file reassignment.json \
    --execute

# 步骤 3: 查看重分配进度
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
    --reassignment-json-file reassignment.json \
    --verify

# 注意：重分配是异步操作，大 Topic 可能耗时数小时
# 执行期间会占用额外网络带宽和磁盘 I/O
```

核心要点：**副本数越高可用性越强，但写入延迟和存储成本线性增长**。rf=3 + broker.rack 跨机架 + min.insync.replicas=2 是业界公认的生产环境最佳实践。

## 副本数 1/2/3/4/5 全面对比

| 维度 | rf=1 | rf=2 | rf=3（推荐） | rf=4 | rf=5 |
|---|---|---|---|---|---|
| 宕机容忍数 | 0（不可用） | 0（单副本未同步） | 1（配合 min.insync=2） | 2 | 2 |
| 数据冗余 | 无，Broker 宕机数据丢失 | 仅 1 个 Follower 副本 | 2 个 Follower 副本 | 3 个 Follower 副本 | 4 个 Follower 副本 |
| 写入延迟 | 最低（仅 Leader 写入） | 1x 网络同步开销 | 2x 网络同步开销 | 3x 网络同步开销 | 4x 网络同步开销 |
| 磁盘占用 | 1x | 2x | 3x | 4x | 5x |
| 跨机架容灾 | 不支持 | 最多 2 机架 | 3 机架容灾 | 最多 4 机架 | 最多 5 机架 |
| min.insync 推荐 | 1 | 2（与 rf 相同，无容错） | 2（容忍 1 个宕机） | 2 或 3 | 2 或 3 |
| 适用场景 | 开发/测试 | 不推荐（伪冗余） | **生产环境推荐** | 金融/关键业务 | 极少使用 |
| 边际收益 | — | 低 | **最优** | 低 | 极低 |

## 一句话总结

**副本数选择就是"3 个副本、2 个确认、3 个机架"——rf=3 配合 min.insync.replicas=2 和 broker.rack 跨机架部署，在可靠性、性能和成本三者之间找到了生产环境的最优平衡点。**
