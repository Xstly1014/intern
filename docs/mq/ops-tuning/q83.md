# Q83 分区数选择

分区数选择公式为 `分区数 = max(目标吞吐量 / 单 Partition 吞吐量, 目标消费者数)`，单 Partition 吞吐参考值约 10MB/s 写入或 20MB/s 读取。设少了吞吐不足、消费者并行度受限；设多了 Broker 内存开销大、Controller 管理压力上升、端到端延迟增加。

分区数选择没有"一刀切"的标准答案，需要根据吞吐量需求和消费者规模综合权衡。上图展示了三种典型场景：分区太少导致吞吐受限、分区刚好与需求匹配、分区过多带来管理和性能负担。下面通过分层代码逐步展示分区数的计算、创建、查看和压测验证全流程。

## 代码：分区数从计算到验证

### Layer 1 — 分区数选择公式与计算

```python
#!/usr/bin/env python3
"""分区数推算脚本：基于目标吞吐量和消费者数计算推荐分区数"""

# 参考值：单 Partition 吞吐（实际以压测为准）
PARTITION_WRITE_MBPS = 10   # 写入 ~10MB/s
PARTITION_READ_MBPS  = 20   # 读取 ~20MB/s

target_throughput_mbps = 80     # 目标吞吐量（MB/s）
target_consumer_count  = 6      # 目标消费者数

# 按吞吐量推算
partitions_by_throughput = max(1, target_throughput_mbps // PARTITION_WRITE_MBPS)

# 按消费者数推算（每个消费者至少一个分区）
partitions_by_consumer = target_consumer_count

# 最终推荐值
recommended = max(partitions_by_throughput, partitions_by_consumer)

# 安全余量（预留 30%）
with_buffer = int(recommended * 1.3)

print(f"按吞吐量推算: {partitions_by_throughput} 个分区")
print(f"按消费者数推算: {partitions_by_consumer} 个分区")
print(f"推荐分区数（取大值）: {recommended}")
print(f"加 30% 余量后: {with_buffer}")

# 约束检查
MAX_PER_BROKER = 4000
MAX_PER_CLUSTER = 20000
print(f"\n约束检查:")
print(f"  单 Broker 上限: {MAX_PER_BROKER}，当前 {with_buffer} -> {'OK' if with_buffer <= MAX_PER_BROKER else '超标'}")
print(f"  集群总上限: {MAX_PER_CLUSTER}，当前 {with_buffer} -> {'OK' if with_buffer <= MAX_PER_CLUSTER else '超标'}")
```

### Layer 2 — Topic 分区创建与增加

```bash
# 创建 Topic 时指定分区数（不可逆，一经验证很难减少）
kafka-topics.sh --bootstrap-server localhost:9092 \
    --create \
    --topic order-events \
    --partitions 8 \
    --replication-factor 3

# 动态增加分区数（只能增加，不能减少！）
kafka-topics.sh --bootstrap-server localhost:9092 \
    --alter \
    --topic order-events \
    --partitions 16

# 注意：增加分区会导致有 key 的消息路由发生变化
# 即原来 key=123 落在 Partition-3，增加后可能落在 Partition-11
```

### Layer 3 — 查看分区分布与开销

```bash
# 查看 Topic 分区详情（Leader、Replicas、ISR 分布）
kafka-topics.sh --bootstrap-server localhost:9092 \
    --describe \
    --topic order-events

# 输出示例：
# Topic: order-events  PartitionCount: 8  ReplicationFactor: 3
#   Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
#   Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
#   ...

# 查看各 Broker 上的 Partition 数量（关注负载均衡）
kafka-topics.sh --bootstrap-server localhost:9092 \
    --describe \
    --under-replicated-partitions    # 关注是否有未同步的分区

# 通过 JMX 或 kafka-run-class 查看分区级指标
kafka-run-class.sh kafka.tools.JmxTool \
    --object-name kafka.server:type=BrokerTopicMetrics,name=MessagesInPerSec \
    --jmx-url service:jmx:rmi:///jndi/rmi://localhost:9999/jmxrmi
```

### Layer 4 — 分区数性能压测验证

```bash
# Producer 性能压测：验证目标分区数下的写入吞吐
kafka-producer-perf-test.sh \
    --topic order-events \
    --num-records 10000000 \
    --record-size 1024 \
    --throughput -1 \
    --producer-props bootstrap.servers=localhost:9092 \
        acks=1 \
        compression.type=lz4 \
        linger.ms=5 \
        batch.size=65536

# Consumer 性能压测：验证目标分区数下的消费吞吐
kafka-consumer-perf-test.sh \
    --topic order-events \
    --messages 10000000 \
    --broker-list localhost:9092 \
    --group perf-test-group \
    --threads 8   # 线程数应 ≤ 分区数

# 关注指标：
# - records/sec：每秒处理记录数
# - MB/sec：每秒吞吐量
# - avg latency：平均延迟
# - max latency：最大延迟
```

核心要点：**分区数只能在创建时设定或后续增加，无法减少**，因此规划阶段必须充分压测验证，并预留 20%~30% 的余量。

## 分区数少 vs 分区数多 对比

| 维度 | 设少了 | 设多了 |
|---|---|---|
| 吞吐能力 | 受单 Partition 上限约束，无法水平扩展 | 吞吐有余量，但非越多越好 |
| 消费者并行度 | 消费者数 > 分区数时，多余消费者空闲 | 消费者数远小于分区数时资源浪费 |
| Producer 延迟 | 批量发送效率高，延迟低 | linger.ms 内积攒不够，小批次发送延迟高 |
| Broker 内存 | 每个 Partition 约 1-2MB 元数据，内存占用低 | 分区数 x 副本数 放大内存开销 |
| Controller 负载 | 选举/ISR 变更少，Controller 轻量 | Leader 选举耗时随分区数线性增长 |
| Rebalance 耗时 | Consumer Group 再均衡快 | 分区多时 Rebalance 可能长达数分钟 |
| 文件句柄 | 文件数少，OS 资源占用低 | 每个 Partition 至少 2 个文件（.index + .log） |
| 可逆性 | 后续可增加分区（但 key 路由会变） | **无法减少分区**，只能重建 Topic |

## 一句话总结

**分区数选择就是"按需取大，留足余量"——以吞吐量和消费者数分别推算后取最大值，再加 30% 余量，牢记分区只能加不能减。**
