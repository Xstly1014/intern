# Q87 磁盘容量规划

Kafka 磁盘容量规划公式：日均数据量 = QPS x 平均消息大小(Byte) x 86400(秒) x 副本数 x 保留天数 + 20% 安全余量。例：1 万 QPS x 1KB x 86400 x 3 副本 x 7 天 x 1.2 余量约等于 2.18TB。消息保留有三种策略：按时间删除（delete）、按大小删除（compact-delete）、日志压缩（compact，对每个 Key 只保留最新值），建议日志类 Topic 用时间删除（7 天），状态类 Topic 用 compact。

Kafka 磁盘容量规划需要精确而非模糊。上图展示了标准的六步乘法链公式，每一步参数的取值都直接影响最终容量预估的准确性。特别需要注意的是：QPS 应按日均峰值而非均值计算（大促/活动期间生产速率可能是平时的 3-5 倍），消息大小应按 P99 而非平均（避免少量大消息导致的低估），同时 20% 的安全余量不可省略（覆盖 Segment 索引文件、日志文件头、OS 开销和增长波动）。

## 分层代码：容量规划与保留策略

### Layer 1 — 容量规划计算脚本

```bash
#!/bin/bash
# kafka_capacity_calc.sh — Kafka 磁盘容量规划计算器

# ===== 输入参数（按实际业务填写） =====
QPS=10000                        # 日均峰值 QPS
MSG_SIZE_BYTES=1024              # 平均消息大小（字节）
REPLICA_COUNT=3                  # 副本数
RETENTION_DAYS=7                 # 保留天数
BUFFER_FACTOR=1.2                # 安全余量系数（20%）

# ===== 计算 =====
SECONDS_PER_DAY=86400

# 日均数据量（原始，不含副本）= QPS * MSG_SIZE * 86400
DAILY_RAW_BYTES=$((QPS * MSG_SIZE_BYTES * SECONDS_PER_DAY))

# 含副本的日均数据量
DAILY_WITH_REPLICA_BYTES=$((DAILY_RAW_BYTES * REPLICA_COUNT))

# 总存储需求 = 日均(含副本) * 保留天数 * 安全余量
TOTAL_BYTES=$(echo "$DAILY_WITH_REPLICA_BYTES * $RETENTION_DAYS * $BUFFER_FACTOR" | bc)

# ===== 结果输出（人类可读） =====
echo "========== Kafka 磁盘容量预估 =========="
echo "QPS:              $QPS 条/秒"
echo "消息大小:         $MSG_SIZE_BYTES 字节 ($(echo "scale=1; $MSG_SIZE_BYTES/1024" | bc) KB)"
echo "副本数:           $REPLICA_COUNT"
echo "保留天数:         $RETENTION_DAYS 天"
echo "安全余量:         ${BUFFER_FACTOR}x"
echo "------------------------------------------"
echo "日原始数据量:     $(echo "scale=2; $DAILY_RAW_BYTES/1073741824" | bc) GB"
echo "日含副本数据量:   $(echo "scale=2; $DAILY_WITH_REPLICA_BYTES/1073741824" | bc) GB"
echo "总磁盘需求:       $(echo "scale=2; $TOTAL_BYTES/1099511627776" | bc) TB"
echo "=========================================="
```

```python
# kafka_capacity_calc.py — Python 版本
import math

def calc_kafka_storage(qps: int, msg_size_bytes: int, replicas: int = 3,
                       retention_days: int = 7, buffer: float = 1.2) -> dict:
    """
    计算 Kafka 磁盘存储需求
    返回包含各阶段计算结果的字典
    """
    seconds_per_day = 86400
    daily_raw = qps * msg_size_bytes * seconds_per_day
    daily_with_replica = daily_raw * replicas
    total = daily_with_replica * retention_days * buffer

    return {
        "daily_raw_gb": daily_raw / (1024**3),
        "daily_with_replica_gb": daily_with_replica / (1024**3),
        "total_tb": total / (1024**4),
        "total_gb": total / (1024**3),
    }

# 示例
result = calc_kafka_storage(qps=10000, msg_size_bytes=1024, replicas=3, retention_days=7)
print(f"总磁盘需求: {result['total_tb']:.2f} TB ({result['total_gb']:.0f} GB)")
# 输出: 总磁盘需求: 2.18 TB (2233 GB)
```

### Layer 2 — 按时间/大小保留配置

```properties
# server.properties — Broker 全局默认（可被 Topic 级别覆盖）

# ===== 按时间删除（最常用） =====
# 默认保留 7 天（168 小时），-1 表示不限制
log.retention.hours=168
log.retention.minutes=10080
log.retention.ms=604800000

# ===== 按大小删除 =====
# 每个 Partition 的日志目录最大大小（-1 表示不限制）
log.retention.bytes=-1

# Segment 文件滚动策略
log.segment.bytes=1073741824        # 1GB 滚动一个 Segment 文件
log.segment.ms=86400000             # 24h 滚动一次（与 bytes 满足任一即滚动）

# ===== Topic 级别覆盖（按需配置，优先级高于 Broker 默认） =====
# 创建 Topic 时指定
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic t_order_log \
  --partitions 12 --replication-factor 3 \
  --config retention.ms=604800000 \
  --config segment.bytes=536870912

# 动态修改已有 Topic
kafka-configs.sh --bootstrap-server localhost:9092 \
  --alter --entity-type topics --entity-name t_order_log \
  --add-config retention.ms=259200000
# 将保留时间从 7 天改为 3 天（紧急释放磁盘）
```

### Layer 3 — 日志压缩配置

```properties
# ===== compact 策略配置 =====
# 创建 compact Topic（每个 Key 只保留最新 Value）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic t_user_state \
  --partitions 6 --replication-factor 3 \
  --config cleanup.policy=compact \
  --config min.cleanable.dirty.ratio=0.5 \
  --config delete.retention.ms=86400000

# cleanup.policy=compact      — 日志压缩（保留每个 Key 最新值）
# min.cleanable.dirty.ratio=0.5 — 脏数据比例达到 50% 时触发清理
# delete.retention.ms=86400000  — 删除标记 tombstone 保留 1 天

# ===== compact + delete 组合 =====
# 既按时间删除旧数据，又压缩重复 Key
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic t_event_snapshot \
  --partitions 3 --replication-factor 3 \
  --config cleanup.policy=compact,delete \
  --config retention.ms=2592000000 \
  --config min.cleanable.dirty.ratio=0.3

# compact,delete 含义：先按 retention.ms 删除过期 Segment，再对剩余 Segment 做 compact

# ===== 查看 Topic 配置 =====
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic t_user_state
# 输出中关注：Configs: cleanup.policy=compact,...
```

### Layer 4 — 磁盘使用率监控与告警

```bash
#!/bin/bash
# kafka_disk_monitor.sh — Kafka Broker 磁盘使用率监控

# ===== 配置参数 =====
KAFKA_DATA_DIR="/var/lib/kafka/data"    # Kafka 数据目录
WARN_THRESHOLD=70                        # 警告阈值（%）
CRITICAL_THRESHOLD=80                    # 严重阈值（%）
EMERGENCY_THRESHOLD=90                   # 紧急阈值（%）

# ===== 检查磁盘使用率 =====
USAGE=$(df -h "$KAFKA_DATA_DIR" | awk 'NR==2 {print $5}' | sed 's/%//')
AVAIL=$(df -h "$KAFKA_DATA_DIR" | awk 'NR==2 {print $4}')
TOTAL=$(df -h "$KAFKA_DATA_DIR" | awk 'NR==2 {print $2}')

echo "[$(date '+%Y-%m-%d %H:%M:%S')] Kafka 数据盘：已用 ${USAGE}%，可用 ${AVAIL} / ${TOTAL}"

# ===== 分级告警 =====
if [ "$USAGE" -ge "$EMERGENCY_THRESHOLD" ]; then
    echo "[EMERGENCY] 磁盘使用率 ${USAGE}% >= ${EMERGENCY_THRESHOLD}%！立即扩容！"
    # 应急措施：临时降低部分 Topic 的 retention.ms
    kafka-configs.sh --bootstrap-server localhost:9092 \
      --alter --entity-type topics --entity-name t_log \
      --add-config retention.ms=86400000
    # 发送 P0 告警
elif [ "$USAGE" -ge "$CRITICAL_THRESHOLD" ]; then
    echo "[CRITICAL] 磁盘使用率 ${USAGE}% >= ${CRITICAL_THRESHOLD}%！尽快扩容或清理。"
    # 发送 P1 告警
elif [ "$USAGE" -ge "$WARN_THRESHOLD" ]; then
    echo "[WARNING] 磁盘使用率 ${USAGE}% >= ${WARN_THRESHOLD}%！持续关注。"
    # 发送 P2 告警
else
    echo "[OK] 磁盘使用率正常。"
fi

# ===== 各 Topic 磁盘占用 TOP 10 =====
echo ""
echo "====== Topic 磁盘占用 TOP 10 ======"
du -sh "$KAFKA_DATA_DIR"/*/ 2>/dev/null | sort -rh | head -10
```

## 三种保留策略对比

| 维度 | 按时间删除 (delete) | 按大小删除 (delete) | 日志压缩 (compact) |
|------|-------------------|--------------------|--------------------|
| 核心配置 | `log.retention.hours=168` | `log.retention.bytes=107374182400` | `cleanup.policy=compact` |
| 删除逻辑 | 超过指定时间的 Segment 文件被整体删除 | Partition 总大小超过阈值时删除最旧 Segment | 对相同 Key 的消息，只保留最新的 Value |
| 消息顺序 | 不关心 Key，保证时间顺序 | 不关心 Key，保证时间顺序 | 同 Key 消息顺序保证（不同 Key 不保证） |
| Key 要求 | 无要求 | 无要求 | 必须有 Key（null Key 消息被忽略） |
| 磁盘空间 | 可精确预估（保留天数 x 日增量） | 有上限（不超过配置值） | 取决于唯一 Key 数量（无法精确预估） |
| 删除标记 | 无需 tombstone | 无需 tombstone | 需要发送 null-value 作为 tombstone 标记删除 |
| 适用场景 | 日志、埋点、事件流（有时效性数据） | 磁盘空间有限，需要硬上限 | 状态快照、CDC 变更日志、KTable 数据源 |
| 典型业务 | 订单日志、用户行为日志、API 调用记录 | 临时 Topic 或测试 Topic | 用户状态 Topic (KTable)、产品信息快照 |
| 注意事项 | 保留时间过短可能丢失需要回溯的数据 | Segment 粒度删除，实际占用可能略超阈值 | 不支持单条消息级别的 TTL，延迟删除 |

## 一句话总结

**Kafka 磁盘容量规划 = QPS x 消息大小 x 86400 x 副本数 x 保留天数 x 1.2 安全余量，日志类 Topic 按时间删除（7 天）、状态类 Topic 用 compact 压缩，同时建立磁盘使用率 80% 告警防线，确保容量永远跑在需求前面。**
