# Q18 Headers Exchange 少用原因

Headers Exchange 不看 Routing Key，而是看消息的 **headers 属性**（键值对）来匹配，绑定时通过 `x-match: all`（所有 header 都匹配）或 `x-match: any`（任一 header 匹配）来控制匹配逻辑。它用得少的原因有三点：性能比 Direct/Topic 差（要解析 headers 做匹配）、使用复杂且调试不直观、大多数路由需求 Direct/Topic 都能满足。实际项目中几乎都用 Topic 替代。

上图展示了 Headers Exchange 的匹配逻辑：消息携带 `headers={type=alert, severity=critical}`，Queue A 要求 `all` 匹配（两个都满足）、Queue B 要求 `any` 匹配（任一满足）、Queue C 要求 `all` 但两个都不满足。底部三个色块总结了它用得少的三个原因。下面用代码实现这个多维度路由场景。

## 多维度告警路由实现

### Layer 1 — 配置层：Headers Exchange + all/any 绑定

```java
@Configuration
public class AlertHeadersConfig {
    public static final String EXCHANGE = "exchange.alert.headers";

    @Bean
    public HeadersExchange alertExchange() {
        return new HeadersExchange(EXCHANGE, true, false);
    }

    // Queue A: x-match=all → type=alert 且 severity=critical 才命中
    @Bean
    public Queue criticalAlertQueue() {
        return new Queue("queue.alert.critical", true);
    }

    @Bean
    public Binding criticalBinding(Queue criticalAlertQueue, HeadersExchange alertExchange) {
        Map<String, Object> headers = new HashMap<>();
        headers.put("type", "alert");
        headers.put("severity", "critical");
        return BindingBuilder.bind(criticalAlertQueue)
                .to(alertExchange)
                .whereAll(headers)        // ← x-match=all：两个 header 都必须匹配
                .match();
    }

    // Queue B: x-match=any → severity=critical 或 region=cn 任一命中
    @Bean
    public Queue anyCriticalOrCnQueue() {
        return new Queue("queue.alert.cn-or-critical", true);
    }

    @Bean
    public Binding anyBinding(Queue anyCriticalOrCnQueue, HeadersExchange alertExchange) {
        Map<String, Object> headers = new HashMap<>();
        headers.put("severity", "critical");
        headers.put("region", "cn");
        return BindingBuilder.bind(anyCriticalOrCnQueue)
                .to(alertExchange)
                .whereAny(headers)        // ← x-match=any：任一 header 匹配即可
                .match();
    }
}
```

关键点：`whereAll` 对应 `x-match=all`（AND 逻辑），`whereAny` 对应 `x-match=any`（OR 逻辑）。匹配对象是 `Map<String, Object>`，Exchange 会拿消息 headers 跟这个 Map 做键值比较。

### Layer 2 — 生产者：通过 MessagePostProcessor 写入 headers

```java
@Service
public class AlertHeadersProducer {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendCriticalAlert(String msg) {
        MessagePostProcessor postProcessor = message -> {
            MessageProperties props = message.getMessageProperties();
            // headers 写入消息属性，不是消息体
            props.setHeader("type", "alert");
            props.setHeader("severity", "critical");
            props.setHeader("region", "cn");
            return message;
        };

        // routing key 传空串 —— Headers Exchange 不看 routing key
        // headers = {type=alert, severity=critical, region=cn}
        // → 命中 criticalAlertQueue（all: type ✓ + severity ✓）
        // → 命中 anyCriticalOrCnQueue（any: severity ✓ 或 region ✓）
        rabbitTemplate.convertAndSend(
                AlertHeadersConfig.EXCHANGE,
                "",                    // ← routing key 在 Headers 模式下无效
                msg,
                postProcessor);
    }

    public void sendInfoAlert(String msg) {
        MessagePostProcessor postProcessor = message -> {
            MessageProperties props = message.getMessageProperties();
            props.setHeader("type", "alert");
            props.setHeader("severity", "info");     // ← 不是 critical
            props.setHeader("region", "us");          // ← 不是 cn
            return message;
        };

        // headers = {type=alert, severity=info, region=us}
        // → 不命中 criticalAlertQueue（all: severity≠critical）
        // → 不命中 anyCriticalOrCnQueue（any: severity≠critical 且 region≠cn）
        // → 消息丢弃！
        rabbitTemplate.convertAndSend(
                AlertHeadersConfig.EXCHANGE,
                "",
                msg,
                postProcessor);
    }
}
```

关键点：headers 通过 `MessagePostProcessor` 在发送前注入到消息属性中，不是消息体的一部分。routing key 在 Headers 模式下完全不参与匹配，传空串即可。

### Layer 3 — 消费者：各队列按匹配条件独立消费

```java
@Component
public class AlertHeadersConsumer {

    @RabbitListener(queues = "queue.alert.critical")
    public void handleCritical(String msg) {
        // 只有 type=alert 且 severity=critical 的消息才会进来
        // → 触发电话告警 + 钉钉机器人
        phoneCallService.callOnCallEngineer(msg);
    }

    @RabbitListener(queues = "queue.alert.cn-or-critical")
    public void handleCnOrCritical(String msg) {
        // severity=critical 或 region=cn 任一满足就进来
        // → 记录到告警看板
        dashboardService.recordAlert(msg);
    }
}
```

关键点：两个消费者的触发条件不同——`criticalAlertQueue` 是严格 AND 逻辑（最紧急的才打电话），`anyCriticalOrCnQueue` 是宽松 OR 逻辑（只要是 critical 或来自 cn 区域都记录到看板）。

## Headers vs Direct/Topic 对比

| 维度 | Headers Exchange | Direct Exchange | Topic Exchange |
|---|---|---|---|
| 匹配依据 | 消息 headers（键值对） | Routing Key 完全相等 | Routing Key 通配符匹配 |
| Routing Key | 不使用 | 必须，精确值 | 必须，含 `*` / `#` |
| 匹配模式 | all（AND）/ any（OR） | 仅相等 | 模式匹配 |
| 多维度路由 | 原生支持（多个 header 键） | 不支持 | 支持（点号分隔多段） |
| 性能 | 较低（解析 headers + 键值遍历） | 高（hash 查找） | 略低（通配符匹配） |
| 调试难度 | 高（需查看消息 headers） | 低（看 routing key 即可） | 中（需理解通配符规则） |
| 使用复杂度 | 高（MessagePostProcessor + Map） | 低（传 routing key 字符串） | 中（拼接点号分隔 key） |
| 实际使用频率 | 很低 | 中 | 最高 |
| 可替代性 | 可被 Topic 替代 | 可被 Topic 精确模式替代 | — |

> 面试要点：如果被问到「什么时候用 Headers Exchange」，回答「需要多维度组合匹配且不方便用点号分隔 routing key 表达时」即可。但要补充一句「实际项目中几乎都用 Topic 替代，因为 Topic 更直观、性能更好」。

## 一句话总结

**一句话总结：Headers Exchange 是一个「对暗号」的路由器——不看门牌号（routing key），而是检查你身上的标签（headers）是否全部或任一匹配，功能独特但性能差、调试难，实际项目中几乎被 Topic 的点号分隔多维度 routing key 完全替代。**
