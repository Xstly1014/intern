# Q26 消息 TTL 设置方式

RabbitMQ 的消息 TTL（Time-To-Live）有两种设置方式：**队列级 TTL**（声明 Queue 时设 `x-message-ttl`，该队列所有消息统一过期时间）和**消息级 TTL**（发消息时在 properties 里设 `expiration`，每条消息可不同）。核心区别在于过期检测机制：队列级 TTL 消息进队列就开始计时到点一定过期，消息级 TTL 是到队列头部即将被消费时才检查是否过期。最大的坑是消息级 TTL 存在**队头阻塞问题**——如果队首消息 TTL 没到期，后面的消息即使先过期也不会被移除。两者同时存在时取较小值生效。

上图对比了两种 TTL 设置方式：左侧队列级 TTL 消息进队列即计时，无队头阻塞；右侧消息级 TTL 存在队头阻塞——队首消息未过期时后续消息无法被检测。黑条详细解释了惰性检测机制。下面用代码实现两种方式。

## 两种 TTL 的代码实现

### Layer 1 — 队列级 TTL：声明带 x-message-ttl 的队列

```java
@Configuration
public class QueueTtlConfig {

    @Bean
    public Queue queueLevelTtlQueue() {
        return QueueBuilder.durable("queue.ttl.queue-level")
                .withArgument("x-message-ttl", 30000)  // 队列所有消息 30 秒过期
                .withArgument("x-dead-letter-exchange", "dlx.exchange")  // 过期转 DLX
                .withArgument("x-dead-letter-routing-key", "expired")
                .build();
    }
}
```

关键点：`x-message-ttl=30000` 让该队列内所有消息统一 30 秒过期。队列级 TTL 的过期检测是主动的——消息进队列即开始计时，到点一定过期，不存在队头阻塞。适合需要精确 TTL 的场景。

### Layer 2 — 消息级 TTL：发送时设置 expiration

```java
@Service
public class MessageTtlProducer {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    // 消息级 TTL：每条消息不同过期时间
    public void sendWithCustomTtl(String content, long ttlMs) {
        MessagePostProcessor postProcessor = message -> {
            // expiration 是 String 类型，单位毫秒
            message.getMessageProperties()
                    .setExpiration(String.valueOf(ttlMs));
            return message;
        };

        rabbitTemplate.convertAndSend(
                "",
                "queue.ttl.message-level",  // 直发队列
                content,
                postProcessor);
    }

    // ⚠ 队头阻塞场景演示
    public void demonstrateHeadOfQueueBlocking() {
        // 先发一条 TTL=30min 的消息（成为队首）
        sendWithCustomTtl("msg1-long-ttl", 1800000);  // 30 分钟

        // 再发两条短 TTL 的消息
        sendWithCustomTtl("msg2-short-ttl", 5000);    // 5 秒
        sendWithCustomTtl("msg3-short-ttl", 3000);    // 3 秒

        // msg2 和 msg3 虽然先过期，但要等 msg1 到期后从头部移除
        // 才会被检查到 → 实际等了 30 分钟才被移除
        // 这就是队头阻塞！
    }
}
```

关键点：`setExpiration` 设置消息级 TTL，参数是 String 类型的毫秒值。消息级 TTL 的过期检测是惰性的——只有消息到达队列头部才检查。如果队首消息 TTL 很长，后面短 TTL 的消息会被阻塞。

### Layer 3 — 两者同时存在：取较小值

```java
@Configuration
public class MixedTtlConfig {

    // 队列级 TTL = 30s
    @Bean
    public Queue mixedTtlQueue() {
        return QueueBuilder.durable("queue.ttl.mixed")
                .withArgument("x-message-ttl", 30000)  // 队列级 30s
                .withArgument("x-dead-letter-exchange", "dlx.exchange")
                .withArgument("x-dead-letter-routing-key", "expired")
                .build();
    }
}

@Service
public class MixedTtlProducer {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendWithBothTtl(String content, long msgTtlMs) {
        MessagePostProcessor postProcessor = message -> {
            message.getMessageProperties()
                    .setExpiration(String.valueOf(msgTtlMs));
            return message;
        };

        rabbitTemplate.convertAndSend("", "queue.ttl.mixed", content, postProcessor);

        // 如果 msgTtlMs = 5000 → 实际 TTL = min(30s, 5s) = 5s
        // 如果 msgTtlMs = 60000 → 实际 TTL = min(30s, 60s) = 30s
        // 但即使取了较小值，检测机制仍取决于是否设了消息级 TTL
        // 设了消息级 TTL → 惰性检测（有队头阻塞风险）
        // 只设队列级 TTL → 主动检测（无队头阻塞）
    }
}
```

关键点：两者同时存在时取较小值生效。但即使最终 TTL 是队列级的值，只要消息设了 `expiration`，检测机制仍是惰性的——这是最容易被忽略的坑。建议需要精确 TTL 时只用队列级 TTL，不混用。

## 队列级 TTL vs 消息级 TTL 对比

| 维度 | 队列级 TTL（x-message-ttl） | 消息级 TTL（expiration） |
|---|---|---|
| 设置方式 | 声明 Queue 时设参数 | 发消息时在 properties 设值 |
| 灵活性 | 队列内所有消息统一 TTL | 每条消息可不同 TTL |
| 过期检测 | 主动检测（进队列即计时） | 惰性检测（到队列头部才检查） |
| 队头阻塞 | 无 | 有 |
| 精度 | 精确 | 不精确（取决于队列头部消息） |
| 性能 | 更好（无需逐条检查） | 稍差（到头部时检查） |
| 两者共存 | 取较小值生效 | 取较小值生效 |
| 推荐场景 | 统一 TTL（延迟队列） | 不推荐，改用延迟消息插件 |

> 面试要点：消息级 TTL 的队头阻塞是高频考点。核心原因：RabbitMQ 对消息级 TTL 的过期检测是惰性的，只有消息到达队列头部才检查。面试时能讲清楚「队首消息 TTL=30min 堵住后面 5s 的消息」这个场景，基本就过关了。

## 一句话总结

**一句话总结：消息 TTL 有两种设置方式——队列级 TTL 主动计时无队头阻塞，消息级 TTL 惰性检测有队头阻塞坑；需要精确 TTL 就用队列级，需要每条消息不同延迟就别用 TTL+DLX，直接上延迟消息插件。**
