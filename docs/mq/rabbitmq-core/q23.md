# Q23 死信队列 DLX

死信（Dead Letter）是被「拒绝」且不再处理的消息。消息变成死信有三种情况：消费者 `reject/nack` 且 `requeue=false`、消息 TTL 过期、队列达到最大长度（`x-max-length`）旧消息被挤掉。配置方式是在声明 Queue 时设置 `x-dead-letter-exchange`（死信交换机）和可选的 `x-dead-letter-routing-key`，死信会被发送到指定的 DLX 再路由到死信队列。典型应用场景是延迟队列（消息先带 TTL 进队列，过期后进 DLX 转发到处理队列）和异常消息归档。

上图展示了完整的死信流转链路：消息在业务队列中因三种原因（reject/nack、TTL 过期、队列满）变成死信后，自动转发到 DLX Exchange，再路由到死信队列由专门的死信消费者处理。底部三个色块分别展示了延迟队列、异常排查、重试归档三个典型应用场景。下面用代码实现延迟队列这个最经典的应用。

## 延迟队列实现（DLX 最经典应用）

### Layer 1 — 配置层：业务队列 + DLX + 死信队列

```java
@Configuration
public class DelayQueueConfig {

    // ===== 死信交换机 + 死信队列 =====
    @Bean
    public DirectExchange dlxExchange() {
        return new DirectExchange("dlx.exchange", true, false);
    }

    @Bean
    public Queue dlxQueue() {
        return new Queue("queue.dlx.order", true);
    }

    @Bean
    public Binding dlxBinding(Queue dlxQueue, DirectExchange dlxExchange) {
        // 死信队列绑定到 DLX，routing key = "order.timeout"
        return BindingBuilder.bind(dlxQueue)
                .to(dlxExchange)
                .with("order.timeout");
    }

    // ===== 业务队列（带 TTL + DLX 配置） =====
    @Bean
    public Queue orderDelayQueue() {
        return QueueBuilder.durable("queue.order.delay")
                .withArgument("x-message-ttl", 1800000)           // 消息 30 分钟过期
                .withArgument("x-dead-letter-exchange", "dlx.exchange")  // 过期后转 DLX
                .withArgument("x-dead-letter-routing-key", "order.timeout")  // DLX routing key
                .build();
    }
}
```

关键点：`x-dead-letter-exchange` 指定死信转发的目标 Exchange，`x-dead-letter-routing-key` 指定死信在 DLX 中的 routing key。消息在 `queue.order.delay` 中存活 30 分钟后自动过期，变成死信被转发到 `dlx.exchange`，再路由到 `queue.dlx.order`。

### Layer 2 — 生产者：发送带 TTL 的延迟消息

```java
@Service
public class OrderDelayProducer {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendOrderCreated(String orderId) {
        // 消息进入 queue.order.delay（TTL = 30 分钟）
        // 30 分钟内如果用户没支付 → 消息过期 → 变死信 → 转 DLX → 进死信队列
        // 如果 30 分钟内用户支付了 → 业务层删除延迟消息（或忽略）
        rabbitTemplate.convertAndSend(
                "",                         // 默认 Exchange
                "queue.order.delay",         // routing key = queue 名（直发队列）
                new OrderEvent(orderId, "PENDING"));
        // 消息将在 30 分钟后自动进入死信队列
    }

    // 也支持消息级 TTL（每条消息不同过期时间）
    public void sendCustomDelay(String orderId, long delayMs) {
        MessagePostProcessor postProcessor = message -> {
            message.getMessageProperties().setExpiration(String.valueOf(delayMs));
            return message;
        };
        rabbitTemplate.convertAndSend(
                "",
                "queue.order.delay",
                new OrderEvent(orderId, "PENDING"),
                postProcessor);
        // 注意：队列级 TTL 和消息级 TTL 同时存在时，取较小的值
    }
}
```

关键点：消息发到 `queue.order.delay` 后不需要消费者，只等 TTL 过期。消息级 TTL 通过 `setExpiration` 设置，但要注意 RabbitMQ 对消息级 TTL 的过期检测是惰性的（只有消息到达队列头部才检查），所以建议用队列级 TTL 保证精度。

### Layer 3 — 死信消费者：处理过期订单

```java
@Component
public class DelayQueueConsumer {

    @RabbitListener(queues = "queue.dlx.order")
    public void handleTimeout(OrderEvent event) {
        // 这里收到的消息是 30 分钟前发出的
        // 检查订单状态：如果仍未支付 → 自动取消
        Order order = orderService.getById(event.getOrderId());

        if (order != null && "PENDING".equals(order.getStatus())) {
            // 订单 30 分钟未支付 → 自动取消
            orderService.cancelOrder(order.getId(), "超时未支付，自动取消");
            notificationService.notifyUser(order.getUserId(), "您的订单已超时取消");
        }
        // 如果订单已支付 → 忽略（消息是延迟到达的，业务已完成）
    }
}
```

关键点：死信消费者收到的消息和原始消息内容完全一样，只是它经过了 TTL 过期才到达。消费者需要做幂等检查——如果用户在 30 分钟内已经支付，这条死信消息应该被忽略。

### Layer 4 — 消费失败转死信（reject/nack 场景）

```java
@Component
public class OrderConsumer {

    @RabbitListener(queues = "queue.order.process")
    public void handleOrder(OrderEvent event, Channel channel,
                            @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        try {
            orderService.process(event);
            channel.basicAck(tag, false);  // 处理成功 → ACK

        } catch (Exception e) {
            // 处理失败 → nack + requeue=false → 消息变成死信
            // 死信会被转发到 queue.order.process 配置的 x-dead-letter-exchange
            channel.basicNack(tag, false, false);
            //                         ↑ requeue=false，不重回队列，直接转死信
        }
    }
}
```

关键点：`basicNack(tag, false, false)` 中第三个参数 `requeue=false` 是关键——设为 `true` 会重回队列导致无限循环，设为 `false` 消息才会变成死信转发到 DLX。

## 三种死信触发方式对比

| 维度 | reject/nack | TTL 过期 | 队列满（x-max-length） |
|---|---|---|---|
| 触发条件 | 消费者处理失败 | 消息存活超过 TTL | 队列消息数超过上限 |
| 触发者 | 消费者主动 | Broker 定时检测 | 新消息入队时 |
| requeue 要求 | 必须 requeue=false | 不涉及 | 不涉及 |
| 消息是否被消费过 | 是（消费失败） | 否（未被消费） | 否（未被消费） |
| 典型场景 | 重试上限归档 | 延迟队列 | 队列溢出保护 |
| 代码控制 | basicNack(tag, false, false) | x-message-ttl | x-max-length + x-overflow |

> 注意：死信消息会被 RabbitMQ 添加 `x-death` header，记录死信原因、原始队列、时间戳等信息，方便死信消费者做后续处理。

## 一句话总结

**一句话总结：死信队列是 RabbitMQ 的「消息太平间」——消息因被拒绝、过期或队列满而「死亡」后，不会直接消失而是被转发到 DLX 再路由到死信队列，让延迟队列、异常归档等高级模式成为可能。**
