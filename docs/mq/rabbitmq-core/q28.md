# Q28 镜像队列 vs Quorum Queue

镜像队列（Classic Mirror）是一个 Queue 的消息同步到多个节点（master + mirror），master 挂了 mirror 提升为 master，通过 policy 配置镜像策略（all/exactly/nodes），但已被官方标记弃用（RabbitMQ 3.8+）。Quorum Queue（仲裁队列）基于 **Raft 协议**，消息写入需要多数派节点确认才算成功，天然解决脑裂问题。Quorum Queue 优势是数据安全性更高（多数派持久化）、自动 leader 选举、性能更好；劣势是不支持排他队列、不支持消息优先级、max-length 只能按条数不能按字节。新项目用 Quorum Queue，镜像队列逐步淘汰。

## 镜像队列与 Quorum Queue 的代码实现

### Layer 1 — 镜像队列：通过 Policy 配置（已弃用）

```bash
# 镜像队列通过 Policy 配置，不是声明时设参数
# 1. 设置 ha-mode=all（所有节点镜像）
rabbitmqctl set_policy ha-all "^queue\." \
    '{"ha-mode":"all","ha-sync-mode":"automatic"}'
#                   ↑ all: 所有节点都镜像
#                              ↑ automatic: 自动同步

# 2. 设置 ha-mode=exactly（指定数量镜像）
rabbitmqctl set_policy ha-two "^queue\." \
    '{"ha-mode":"exactly","ha-params":2,"ha-sync-mode":"automatic"}'
#                       ↑ exactly: 精确镜像数
#                                    ↑ ha-params=2: 镜像到 2 个节点

# 3. 设置 ha-mode=nodes（指定节点镜像）
rabbitmqctl set_policy ha-nodes "^queue\." \
    '{"ha-mode":"nodes","ha-params":["rabbit@node1","rabbit@node2"]}'
#                        ↑ nodes: 指定节点名列表
```

```java
// 镜像队列声明（与普通 Classic Queue 完全一样）
// 镜像行为由 Policy 控制，声明代码无特殊参数
@Configuration
@Deprecated  // ← 标记弃用
public class MirrorQueueConfig {

    @Bean
    public Queue mirrorQueue() {
        // 声明普通 Classic Queue
        // 是否镜像由 Policy 匹配队列名前缀决定
        return QueueBuilder.durable("queue.order.mirror")
                .build();
    }
}
// ⚠ 镜像队列在 RabbitMQ 3.8+ 已被标记弃用
// ⚠ 强一致性同步性能差，脑裂可能导致数据丢失
// ⚠ 新项目不要用，用 Quorum Queue 替代
```

关键点：镜像队列的镜像行为通过 Policy 配置，而非声明时的参数。Policy 按队列名正则匹配，匹配到的队列自动成为镜像队列。但镜像队列已被官方弃用——异步同步有数据丢失风险，脑裂时两个 master 各自写入导致数据不一致。

### Layer 2 — Quorum Queue：声明时指定类型（推荐）

```java
@Configuration
public class QuorumQueueConfig {

    @Bean
    public Queue quorumQueue() {
        return QueueBuilder.durable("queue.order.quorum")
                .withArgument("x-queue-type", "quorum")  // ← 关键：声明为仲裁队列
                .withArgument("x-delivery-limit", 3)     // 消息重试上限（可选）
                .withArgument("x-quorum-initial-group-size", 3)  // 初始副本数（可选）
                // x-quorum-initial-group-size 默认等于集群节点数
                .build();
    }

    @Bean
    public DirectExchange orderExchange() {
        return new DirectExchange("exchange.order", true, false);
    }

    @Bean
    public Binding quorumBinding(Queue quorumQueue, DirectExchange orderExchange) {
        return BindingBuilder.bind(quorumQueue).to(orderExchange).with("order.created");
    }
}
```

关键点：`x-queue-type=quorum` 是声明 Quorum Queue 的唯一必选参数。Quorum Queue 基于 Raft 协议，消息写入需要多数派节点确认才算成功。`x-delivery-limit` 限制消息重试次数，超过后消息被丢弃或进入死信。

### Layer 3 — 生产者：发送消息（与普通队列完全一样）

```java
@Service
public class QuorumQueueProducer {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendOrder(String orderId) {
        // 发送方式与普通队列完全一样
        // Quorum Queue 对生产者透明
        rabbitTemplate.convertAndSend(
                "exchange.order",
                "order.created",
                new OrderEvent(orderId));

        // 消息到达 Leader → Leader 发起 Raft 写入
        // → 多数派节点确认 → 返回 ACK 给生产者
        // → 如果少数派节点宕机，不影响写入
    }
}
```

关键点：生产者端无任何特殊处理，Quorum Queue 对生产者完全透明。区别在于 Broker 内部：消息到达 Leader 后，Leader 发起 Raft 写入流程，多数派节点（如 3 节点中的 2 个）确认后才算写入成功。

### Layer 4 — 消费者：配合 x-delivery-limit 实现自动重试

```java
@Component
public class QuorumQueueConsumer {

    @RabbitListener(queues = "queue.order.quorum")
    public void handleOrder(OrderEvent event, Channel channel,
                            @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        try {
            orderService.process(event);
            channel.basicAck(tag, false);

        } catch (Exception e) {
            // nack + requeue=true → 消息重回队列
            // Quorum Queue 会记录重试次数
            // 超过 x-delivery-limit 后消息被丢弃或转死信
            channel.basicNack(tag, false, true);
            //                         ↑ requeue=true，Quorum Queue 会跟踪重试次数
        }
    }
}
```

关键点：Quorum Queue 配合 `x-delivery-limit` 可以实现自动重试上限——消息被 nack 且 requeue=true 后，Quorum Queue 内部记录重试次数，超过 `x-delivery-limit` 后消息自动丢弃或转死信。这是 Classic Queue 没有的能力。

## 镜像队列 vs Quorum Queue 全面对比

| 维度 | 镜像队列（Classic Mirror） | Quorum Queue（仲裁队列） |
|---|---|---|
| 一致性协议 | Master-Mirror 异步同步 | Raft 多数派写入 |
| 数据安全性 | 低（异步同步有窗口） | 高（多数派确认） |
| 脑裂风险 | 有（两个 master 各自写入） | 无（Raft 多数派天然防脑裂） |
| Leader 选举 | 需要额外选举机制 | Raft 自动 leader 选举 |
| 配置方式 | Policy（ha-mode） | 声明时 x-queue-type=quorum |
| 消息重试上限 | 不支持 | x-delivery-limit |
| 排他队列 | 支持 | 不支持 |
| 消息优先级 | 支持 | 不支持 |
| max-length 按字节 | 支持 | 不支持（只能按条数） |
| 性能 | 中（同步开销大） | 好（Raft 优化） |
| 官方态度 | 已弃用（3.8+） | 推荐 |
| 适用场景 | 旧系统维护 | 新项目 / 高可靠场景 |

> 面试要点：镜像队列被弃用的原因和 Quorum Queue 的优势是核心考点。答题路径：镜像队列是 Master-Mirror 异步同步（有数据丢失窗口 + 脑裂风险）→ Quorum Queue 用 Raft 多数派写入（多数节点确认才算成功，天然防脑裂）→ 但 Quorum Queue 有三个限制（不支持排他/优先级/按字节 max-length）→ 新项目用 Quorum Queue。

## 一句话总结

**一句话总结：镜像队列是「一个 Master 写完异步通知 Mirror」的旧方案（有脑裂和丢数据风险，已弃用），Quorum Queue 是「Raft 多数派确认才算写入」的新方案（天然防脑裂，数据更安全），新项目一律用 Quorum Queue。**
