# Q13 RabbitMQ 核心组件

RabbitMQ 的核心架构是一条单向数据链：**Producer → Exchange → (Binding) → Queue → Consumer**。生产者不直接发消息到 Queue，而是发到 Exchange（交换机），Exchange 根据类型和 Binding 规则把消息路由到一个或多个 Queue，消费者从 Queue 取消息。Binding 是 Exchange 和 Queue 之间的绑定关系，可带 Routing Key。这套设计让 RabbitMQ 的路由能力非常灵活——同一个消息可以根据规则分发到不同队列，新增队列只需加一条 Binding，生产者代码零改动。

上图展示了 RabbitMQ 的核心数据流：Producer 把消息丢给 Exchange，Exchange 查 Binding 路由表决定消息去哪些 Queue，Consumer 从各自的 Queue 取消息。关键在于 **Producer 和 Queue 之间完全解耦**——生产者只管发到 Exchange，Queue 的增删改对生产者透明。下面用代码逐层拆解这套架构。

## Before：直连 Queue（RabbitMQ 不推荐的方式）

```java
// 直接发到 Queue（用默认 Exchange，routing key = queue name）
// 虽然能用，但丧失了 Exchange 的路由能力
rabbitTemplate.convertAndSend("", "order.premium", orderEvent);
//                                  ↑ 默认 Exchange，没有路由规则
// 问题：要新增审计队列就得改生产者代码，再发一次到新 Queue
```

直接发 Queue 的问题：每新增一个消费场景，生产者就要多发一次消息，耦合度随业务增长线性上升。

## After：Exchange 路由架构

### Layer 1 — Producer（只发到 Exchange，不管 Queue）

```java
@Service
public class OrderEventPublisher {
    @Autowired private RabbitTemplate rabbitTemplate;

    public void publish(OrderEvent event) {
        // 生产者只指定 Exchange 和 routing key，不关心有哪些 Queue
        rabbitTemplate.convertAndSend(
            "order.exchange",              // Exchange：发到哪个交换机
            "order.created.premium",       // routing key：消息的路由标签
            event                          // 消息体
        );
        // 生产者不知道 order.premium / order.normal / order.audit 这些 Queue 的存在
    }
}
```

关键点：生产者的 `@Autowired` 里没有 Queue 信息，只认 Exchange 名字和 routing key。新增 Queue 不需要改这里。

### Layer 2 — Exchange + Binding（路由规则配置）

```java
@Configuration
public class RabbitMQConfig {

    // ① 声明 Exchange（Direct 类型：按 routing key 精确匹配）
    @Bean
    public DirectExchange orderExchange() {
        return new DirectExchange("order.exchange", true, false);
        //                                              ↑durable  ↑autoDelete
    }

    // ② 声明 Queue
    @Bean
    public Queue premiumQueue() {
        return new Queue("order.premium", true);  // VIP 订单队列，持久化
    }

    @Bean
    public Queue normalQueue() {
        return new Queue("order.normal", true);   // 普通订单队列
    }

    @Bean
    public Queue auditQueue() {
        return new Queue("order.audit", true);    // 审计日志队列
    }

    // ③ 声明 Binding：把 Queue 绑定到 Exchange，带 routing key
    @Bean
    public Binding premiumBinding() {
        return BindingBuilder.bind(premiumQueue())
            .to(orderExchange())
            .with("order.created.premium");  // routing key 精确匹配
    }

    @Bean
    public Binding normalBinding() {
        return BindingBuilder.bind(normalQueue())
            .to(orderExchange())
            .with("order.created.normal");
    }

    @Bean
    public Binding auditBinding() {
        // 审计队列用通配符匹配所有 order.created.* 的消息
        // 注意：这需要 Exchange 类型改为 Topic（支持通配符）
        return BindingBuilder.bind(auditQueue())
            .to(orderExchange())
            .with("order.created.*");  // 匹配所有 order.created.xxx
    }
}
```

关键变化：**Binding 是 Exchange 和 Queue 之间的"路由表"**。生产者发 `order.created.premium`，Exchange 查路由表发现 `premiumQueue` 和 `auditQueue` 都匹配（audit 用通配符），于是消息被投递到这两个 Queue。新增"风控队列"？加一个 `@Bean Binding`，生产者代码零改动。

### Layer 3 — Consumer（从 Queue 取消息，不关心 Exchange）

```java
// Consumer 只认 Queue，不知道 Exchange 的存在
@Component
public class PremiumOrderConsumer {
    @RabbitListener(queues = "order.premium")  // 监听 Queue，不是 Exchange
    @RabbitHandler
    public void handle(OrderEvent event) {
        // 处理 VIP 订单
        orderService.processPremium(event);
    }
}

@Component
public class AuditConsumer {
    @RabbitListener(queues = "order.audit")
    @RabbitHandler
    public void handle(OrderEvent event) {
        // 记录审计日志
        auditService.record(event);
    }
}
```

关键点：消费者只跟 Queue 绑定，完全不知道消息是从哪个 Exchange 路由过来的。Exchange 类型的变更（Direct 改 Topic）对消费者透明。

## 组件职责对照

| 组件 | 职责 | 类比 | 谁配置 | 对其他组件是否感知 |
|---|---|---|---|---|
| Producer | 发消息到 Exchange，带 routing key | 寄信人 | 业务代码 | 只认 Exchange，不认 Queue |
| Exchange | 接收消息，按类型 + routing key 路由 | 邮局分拣中心 | 运维/配置 | 查 Binding 表决定投递 |
| Binding | Exchange 和 Queue 的绑定关系 + routing key 规则 | 分拣规则表 | 运维/配置 | 连接 Exchange 和 Queue |
| Queue | FIFO 存储消息，等待消费 | 信箱 | 运维/配置 | 不关心 Exchange 和 Consumer |
| Consumer | 从 Queue 取消息处理 | 收信人 | 业务代码 | 只认 Queue，不认 Exchange |

## 四种 Exchange 类型对比

| Exchange 类型 | 路由规则 | routing key 用法 | 典型场景 |
|---|---|---|---|
| Direct | 精确匹配 | routing key == binding key | 点对点分流（VIP vs 普通） |
| Topic | 通配符匹配 | `*` 匹配一个词，`#` 匹配多个词 | 日志分级（`log.error.*`） |
| Fanout | 广播 | 忽略 routing key，所有绑定 Queue 都收到 | 事件广播（订单创建通知所有下游） |
| Headers | 头部匹配 | 按 message headers 键值对匹配 | 复杂条件路由（少用） |

**In one sentence: RabbitMQ 的核心设计是"生产者只寄信到邮局（Exchange），邮局按分拣规则表（Binding）投递到信箱（Queue），收信人（Consumer）从信箱取信"——Exchange 是路由器，Binding 是路由表，三者解耦让新增消费场景只需加一条 Binding 而生产者代码零改动。**
