# Q27 持久化机制

RabbitMQ 持久化分三层：**Exchange 持久化**（声明时 `durable=true`，元数据写磁盘，Broker 重启后还在）、**Queue 持久化**（声明时 `durable=true`，元数据写磁盘）、**消息持久化**（发送时 `deliveryMode=2`，消息内容写磁盘）。三者都要开启才算完整持久化，缺一不可。但持久化不等于一定不丢：消息先入内存再异步刷盘，Broker 在刷盘前宕机会丢；镜像队列环境下消息还没同步到镜像节点就宕机也会丢。要更强保证用 **Quorum Queue**（基于 Raft 多数派写入）。持久化会降低吞吐（磁盘 IO），需权衡。

上图展示了三层持久化机制（Exchange → Queue → Message），以及持久化仍可能丢数据的两种风险（异步刷盘窗口和镜像同步延迟）。底部三个色块是完整持久化检查清单。下面用代码实现。

## 三层持久化的代码实现

### Layer 1 — Exchange 持久化：durable=true

```java
@Configuration
public class PersistenceConfig {

    // Exchange 持久化：durable=true
    @Bean
    public DirectExchange persistentExchange() {
        // 第二个参数 durable=true → Exchange 元数据写磁盘
        // Broker 重启后 Exchange 依然存在
        return new DirectExchange("exchange.order", true, false);
        //                                           ↑    ↑
        //                                    durable=true  auto-delete=false
    }
}
```

关键点：`new DirectExchange(name, true, false)` 第二个参数 `durable=true` 让 Exchange 元数据持久化到磁盘。Broker 重启后 Exchange 依然存在。但 Exchange 持久化只保留 Exchange 本身的元数据，不包含 Binding 和消息。

### Layer 2 — Queue 持久化：durable=true

```java
@Configuration
public class PersistenceConfig {

    // Queue 持久化：durable=true
    @Bean
    public Queue persistentQueue() {
        // QueueBuilder.durable() → Queue 元数据写磁盘
        // Broker 重启后 Queue 依然存在（但里面的消息需要消息层持久化）
        return QueueBuilder.durable("queue.order")
                .build();
    }

    // Binding 也会随 Queue 持久化而保留
    @Bean
    public Binding persistentBinding(Queue persistentQueue,
                                      DirectExchange persistentExchange) {
        return BindingBuilder.bind(persistentQueue)
                .to(persistentExchange)
                .with("order.created");
    }
}
```

关键点：`QueueBuilder.durable(name)` 让 Queue 元数据持久化。Broker 重启后 Queue 和它的 Binding 都会保留。但 Queue 里的消息不会自动持久化——如果消息没设 `deliveryMode=2`，Broker 重启后 Queue 在但消息没了。

### Layer 3 — 消息持久化：deliveryMode=2

```java
@Service
public class PersistentMessageProducer {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendPersistentMessage(String orderId) {
        // 方式1：全局配置（推荐）
        // application.yml: spring.rabbitmq.template.delivery-mode=persistent
        // 这样所有消息默认持久化

        // 方式2：单条消息设置
        MessagePostProcessor postProcessor = message -> {
            message.getMessageProperties()
                    .setDeliveryMode(MessageDeliveryMode.PERSISTENT);
            //                                     ↑ deliveryMode=2，消息内容写磁盘
            return message;
        };

        rabbitTemplate.convertAndSend(
                "exchange.order",
                "order.created",
                new OrderEvent(orderId),
                postProcessor);
    }
}
```

关键点：`MessageDeliveryMode.PERSISTENT`（即 `deliveryMode=2`）让消息内容写磁盘。Spring AMQP 默认就是 `PERSISTENT`，但如果手动创建了 `MessageProperties` 需要确认设置。三层持久化缺一不可——只有 Exchange 和 Queue 持久化但消息没持久化，Broker 重启后 Queue 在但消息全丢。

### Layer 4 — Publisher Confirm：确认消息已刷盘

```java
@Configuration
public class ConfirmConfig {

    @Bean
    public RabbitTemplate confirmRabbitTemplate(ConnectionFactory connectionFactory) {
        RabbitTemplate template = new RabbitTemplate(connectionFactory);

        // 开启 Publisher Confirm（确认消息到达 Broker 并可能已刷盘）
        template.setConfirmCallback((correlationData, ack, cause) -> {
            if (ack) {
                // Broker 收到消息并处理成功
                log.info("消息已确认到达 Broker");
            } else {
                // Broker 未收到或处理失败，需要重发
                log.error("消息未确认，原因: {}", cause);
                // TODO: 重发消息
            }
        });

        // 开启 Publisher Return（消息无法路由时退回）
        template.setReturnsCallback(returned -> {
            log.error("消息无法路由: exchange={}, routingKey={}, replyText={}",
                    returned.getExchange(),
                    returned.getRoutingKey(),
                    returned.getReplyText());
            // TODO: 记录无法路由的消息
        });

        template.setMandatory(true);  // 消息无法路由时触发 ReturnsCallback
        return template;
    }
}
```

```yaml
# application.yml
spring:
  rabbitmq:
    publisher-confirm-type: correlated  # 异步确认
    publisher-returns: true              # 开启退回机制
    template:
      mandatory: true                    # 消息无法路由时退回
```

关键点：Publisher Confirm 确认消息到达 Broker，但要注意 Confirm 只代表 Broker 收到消息，不完全等于已刷盘。要更强保证需要配合 Quorum Queue（Raft 多数派写入确认）。

## 持久化层级对比

| 维度 | Exchange 持久化 | Queue 持久化 | 消息持久化 |
|---|---|---|---|
| 参数 | durable=true | durable=true | deliveryMode=2 |
| 持久化内容 | Exchange 元数据 | Queue 元数据 + Binding | 消息内容 |
| 缺失后果 | 重启后 Exchange 消失 | 重启后 Queue 消失 | 重启后 Queue 在但消息没了 |
| 性能影响 | 几乎无 | 几乎无 | 降低吞吐（磁盘 IO） |
| 默认值 | false（需手动开） | false（需手动开） | Spring AMQP 默认 PERSISTENT |
| 必须性 | 生产环境必须 | 生产环境必须 | 生产环境必须 |

| 可靠性方案 | 刷盘保证 | 多节点保证 | 适用场景 |
|---|---|---|---|
| 非持久化 | 无 | 无 | 测试 / 可丢弃的日志 |
| Classic Queue 持久化 | 异步刷盘（有窗口） | 镜像异步同步（有窗口） | 一般生产环境 |
| Quorum Queue | Raft 多数派持久化 | Raft 多数派确认 | 高可靠场景（金融/订单） |
| Publisher Confirm + Quorum | 确认到达 + 多数派 | 多数派确认 | 最高可靠性 |

> 面试要点：持久化不等于不丢是核心考点。两个风险窗口：异步刷盘（内存到磁盘有几毫秒延迟）和镜像同步延迟（master 到 mirror 是异步的）。面试回答策略：先讲三层持久化（缺一不可），再讲两个风险窗口，最后引出 Quorum Queue 作为终极方案。

## 一句话总结

**一句话总结：RabbitMQ 持久化是「三层叠加」——Exchange、Queue、消息都要持久化才算完整，但持久化只保证写磁盘不保证不丢（异步刷盘窗口 + 镜像同步延迟），要真正不丢得用 Quorum Queue 的 Raft 多数派写入。**
