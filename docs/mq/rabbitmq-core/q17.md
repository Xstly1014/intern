# Q17 Fanout Exchange 使用场景

Fanout Exchange 忽略 Routing Key，将消息**广播到所有绑定的 Queue**，每个 Queue 都收到完整的消息副本。它与 Topic Exchange 的本质区别在于：Fanout 是「无脑全广播」不做任何匹配计算，而 Topic 是「按模式选择性路由」。如果业务需要「所有消费者都收到」就用 Fanout，需要「按规则选择性分发」就用 Topic。

上图上半部分展示了 Fanout 的广播机制：一条消息进入 Exchange 后被复制成多份，每个绑定的 Queue 各收到一份完整副本，Routing Key 完全被忽略。下半部分是 Fanout 与 Topic 的逐维度对比——Fanout 胜在性能（零匹配开销），Topic 胜在灵活性。下面用代码实现一个典型的多渠道通知场景。

## 多渠道通知广播实现

### Layer 1 — 配置层：Fanout Exchange + 多个 Queue

```java
@Configuration
public class NotifyFanoutConfig {
    public static final String EXCHANGE = "exchange.notify.fanout";

    @Bean
    public FanoutExchange notifyExchange() {
        // Fanout 不需要 routing key，durable=true 持久化
        return new FanoutExchange(EXCHANGE, true, false);
    }

    @Bean
    public Queue smsQueue() {
        return new Queue("queue.notify.sms", true);
    }

    @Bean
    public Queue emailQueue() {
        return new Queue("queue.notify.email", true);
    }

    @Bean
    public Queue pushQueue() {
        return new Queue("queue.notify.push", true);
    }

    // Fanout 绑定不需要 routing key —— BindingBuilder 没有 .with() 调用
    @Bean
    public Binding smsBinding(Queue smsQueue, FanoutExchange notifyExchange) {
        return BindingBuilder.bind(smsQueue).to(notifyExchange);
        //                                            ↑ 没有 .with("xxx")，Fanout 忽略 routing key
    }

    @Bean
    public Binding emailBinding(Queue emailQueue, FanoutExchange notifyExchange) {
        return BindingBuilder.bind(emailQueue).to(notifyExchange);
    }

    @Bean
    public Binding pushBinding(Queue pushQueue, FanoutExchange notifyExchange) {
        return BindingBuilder.bind(pushQueue).to(notifyExchange);
    }
}
```

关键点：Fanout 的 Binding 调用链没有 `.with("routingKey")` 这一步——因为 routing key 在 Fanout 模式下完全不参与路由判定。绑定了就收，没绑定就不收，没有中间状态。

### Layer 2 — 生产者：routing key 传空串

```java
@Service
public class NotifyFanoutProducer {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void broadcast(NotifyEvent event) {
        // routing key 传空串 ""，Fanout Exchange 会忽略它
        // 一条消息 → 复制到 sms / email / push 三个 Queue
        rabbitTemplate.convertAndSend(
                NotifyFanoutConfig.EXCHANGE,
                "",                    // ← Fanout 忽略 routing key，传什么都一样
                event);
    }
}
```

关键点：即使这里传了 `"some.key"`，Fanout 也会忽略它，三个 Queue 照样全收到。传空串只是约定俗成的写法，表示「这条消息没有路由标签」。

### Layer 3 — 消费者：各队列独立消费，互不影响

```java
@Component
public class NotifyFanoutConsumer {

    @RabbitListener(queues = "queue.notify.sms")
    public void handleSms(NotifyEvent event) {
        // 短信通道：调第三方短信 API
        smsService.send(event.getPhone(), event.getContent());
        // 即使邮件服务挂了，短信照常发送 —— 队列之间互不影响
    }

    @RabbitListener(queues = "queue.notify.email")
    public void handleEmail(NotifyEvent event) {
        // 邮件通道：SMTP 发送
        emailService.send(event.getEmail(), event.getSubject(), event.getContent());
    }

    @RabbitListener(queues = "queue.notify.push")
    public void handlePush(NotifyEvent event) {
        // App 推送通道：调 FCM / 极光推送
        pushService.send(event.getUserId(), event.getContent());
    }
}
```

关键点：三个消费者各自从独立 Queue 取消息，互不影响。如果邮件服务宕机，`queue.notify.email` 会堆积消息，但短信和推送照常工作——这正是 Fanout + 多 Queue 架构的核心优势：**故障隔离**。

## Fanout vs Topic 对比

| 维度 | Fanout Exchange | Topic Exchange |
|---|---|---|
| 路由依据 | 无（忽略 Routing Key） | Routing Key + 通配符匹配 |
| Binding Key | 不使用 | 支持 `*` / `#` 通配符 |
| 消息分发 | 全量复制到所有绑定 Queue | 按模式匹配选择性分发 |
| 匹配开销 | 零（直接遍历绑定列表复制） | 有（逐条遍历 Binding 做通配符匹配） |
| 性能 | 最高 | 略低（Binding 数量多时更明显） |
| 灵活性 | 低（全收或不绑） | 高（精确 / 模糊 / 广播三种模式） |
| 新增 Queue 影响 | 自动收到所有消息（可能收到不需要的） | 需要配 Binding Key 才收到对应消息 |
| 典型场景 | 广播通知、配置变更、用户上线 | 多维度事件路由、日志级别分发 |
| 退化等价 | — | Binding Key = `#` 时等价 Fanout |
| 消费者故障隔离 | 支持（各 Queue 独立消费） | 支持（各 Queue 独立消费） |

> 选择建议：如果所有消费者都需要完整消息 → Fanout（性能最好）；如果消费者需要按规则过滤 → Topic（灵活度最高）。实际项目中 Topic 用 `#` 也能实现广播效果，但 Fanout 的零匹配开销在高频广播场景下更优。

## 一句话总结

**一句话总结：Fanout Exchange 是一个「大喇叭」——不看门牌号、不看收件人，喊一嗓子所有人都听到，性能最好但零灵活性，适合「所有消费者都需要完整消息」的纯广播场景。**
