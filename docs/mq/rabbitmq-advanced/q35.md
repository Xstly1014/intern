# Q35 节点类型 disk/ram

RabbitMQ 集群中的节点分为 **disk 节点**（元数据持久化到磁盘，重启不丢）和 **RAM 节点**（元数据只存内存，重启后从其他节点同步）。集群至少需要一个 disk 节点，否则全部重启后元数据全丢无法恢复。RAM 节点的优势是元数据操作快（不用写磁盘），适合纯计算或查询场景，但生产环境一般全 disk 节点。注意：节点类型只影响元数据存储，消息本身的持久化由 Queue 的 `durable` 和消息 `deliveryMode` 决定。

## 节点类型配置与集群管理

### Layer 1 — 集群搭建：指定节点类型

```bash
# ===== 3 节点集群：2 disk + 1 RAM =====

# Node A — disk 节点（独立启动）
rabbitmq-server -detached
# 默认就是 disk 节点

# Node B — disk 节点（加入集群）
rabbitmqctl stop_app
rabbitmqctl join_cluster rabbit@node-a
# join_cluster 不带 --ram，默认 disk 节点
rabbitmqctl start_app

# Node C — RAM 节点（加入集群）
rabbitmqctl stop_app
rabbitmqctl join_cluster rabbit@node-a --ram    # ← --ram 指定 RAM 节点
rabbitmqctl start_app

# 查看集群状态与节点类型
rabbitmqctl cluster_status
# 输出：
# Disk Nodes: rabbit@node-a, rabbit@node-b
# RAM Nodes: rabbit@node-c
# Running Nodes: rabbit@node-a, rabbit@node-b, rabbit@node-c
```

关键点：`join_cluster` 不带参数默认 disk 节点，带 `--ram` 为 RAM 节点。生产环境建议全 disk 节点，RAM 节点仅用于元数据操作频繁的特殊性能场景。

### Layer 2 — 节点类型转换

```bash
# ===== 运行期更改节点类型 =====

# 将 RAM 节点改为 disk 节点
rabbitmqctl -n rabbit@node-c stop_app
rabbitmqctl -n rabbit@node-c change_cluster_node_type disc
rabbitmqctl -n rabbit@node-c start_app

# 将 disk 节点改为 RAM 节点
rabbitmqctl -n rabbit@node-a stop_app
rabbitmqctl -n rabbit@node-a change_cluster_node_type ram
rabbitmqctl -n rabbit@node-a start_app

# 注意：不能把最后一个 disk 节点改为 RAM 节点
# 否则集群没有 disk 节点，元数据无法持久化
```

关键点：节点类型可以在运行期通过 `change_cluster_node_type` 转换。但集群中至少要保留一个 disk 节点，否则元数据无法持久化。生产环境转换节点类型需谨慎，建议在低峰期操作。

### Layer 3 — 元数据变更操作（为什么需要 disk 节点）

```bash
# ===== 元数据变更操作示例 =====

# 创建 Queue（元数据变更，需持久化到 disk 节点）
rabbitmqadmin declare queue name=order.queue durable=true

# 创建 Exchange（元数据变更）
rabbitmqadmin declare exchange name=order.exchange type=direct durable=true

# 创建 Binding（元数据变更）
rabbitmqadmin declare binding source=order.exchange destination=order.queue routing_key=order.created

# 添加用户（元数据变更）
rabbitmqctl add_user admin password123
rabbitmqctl set_permissions admin ".*" ".*" ".*"

# 以上所有操作：
# - 元数据变更请求发送到任意节点
# - 该节点将变更同步到所有节点
# - disk 节点将变更写入磁盘持久化
# - RAM 节点只在内存中保存
# - 如果全 RAM 节点 → 重启后所有 Queue/Exchange/User 全丢！
```

```java
// Spring AMQP 中声明 Queue/Exchange 也会触发元数据变更
@Configuration
public class QueueConfig {
    @Bean
    public Queue orderQueue() {
        // 这个声明会通过 AMQP 协议发送到 Broker
        // Broker 将 Queue 元数据同步到所有节点
        // disk 节点持久化到磁盘，RAM 节点只存内存
        return QueueBuilder.durable("order.queue").build();
    }

    @Bean
    public DirectExchange orderExchange() {
        return new DirectExchange("order.exchange", true, false);
    }
}
```

关键点：所有元数据变更操作（创建 Queue/Exchange/Binding/User）都需要 disk 节点来持久化。即使请求发到 RAM 节点，变更也会同步到 disk 节点写入磁盘。如果集群没有 disk 节点，重启后所有元数据丢失。

## Disk 节点 vs RAM 节点对比

| 维度 | Disk 节点 | RAM 节点 |
|---|---|---|
| 元数据存储 | 内存 + 磁盘 | 仅内存 |
| 重启后 | 从磁盘恢复，不丢失 | 丢失，需从其他节点同步 |
| 元数据操作速度 | 稍慢（需写磁盘） | 快（纯内存操作） |
| 集群要求 | 至少 1 个 | 可选，不能全 RAM |
| 适用场景 | 生产环境标准 | 元数据频繁变更的特殊场景 |
| 推荐数量 | 全部（或至少 2 个） | 一般不用 |
| 消息持久化 | 无关（由 Queue durable 决定） | 无关（同左） |

> 面试要点：disk 节点元数据持久化到磁盘，RAM 节点只存内存。集群至少一个 disk 节点，否则全部重启后元数据全丢。节点类型只影响元数据（Exchange/Queue 定义/Binding/User），消息持久化由 Queue 的 `durable` 和消息 `deliveryMode` 决定，与节点类型无关。生产环境全 disk 节点。

## 一句话总结

**一句话总结：disk 节点把元数据写到磁盘（重启不丢），RAM 节点只存内存（重启需同步）——集群至少留一个 disk 节点保命，节点类型只管元数据存哪，消息持久化是另一套机制（`durable` + `deliveryMode`）。**
