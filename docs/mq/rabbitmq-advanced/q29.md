# Q29 生产者确认机制

RabbitMQ 生产者确认消息到达 Broker 有两种机制：**事务模式**（`txSelect`/`txCommit`/`txRollback`，同步阻塞，性能极差，不推荐）和 **Confirm 模式**（Channel 开启后每条消息获得唯一 `deliveryTag`，Broker 异步回 `ack`/`nack`，推荐）。Confirm 模式又分异步 confirm（注册回调，性能最好）和同步 confirm（`waitForConfirms` 阻塞等待，性能一般）。生产环境用异步 confirm 配合重试机制保证消息可靠投递。

## 异步 Confirm 模式的代码实现

### Layer 1 — 配置层：开启 Publisher Confirm

```yaml
# application.yml
spring:
  rabbitmq:
    publisher-confirm-type: correlated  # 异步 confirm（推荐）
    # publisher-confirm-type: simple    # 同步 confirm
    # publisher-confirm-type: none      # 不开启（默认）
    publisher-returns: true              # 消息无法路由时退回
```

```java
@Configuration
public class ConfirmConfig {

    @Bean
    public RabbitTemplate confirmRabbitTemplate(ConnectionFactory connectionFactory) {
        RabbitTemplate template = new RabbitTemplate(connectionFactory);

        // ConfirmCallback：Broker 确认消息是否到达
        template.setConfirmCallback((correlationData, ack, cause) -> {
            if (ack) {
                // Broker 收到消息并处理成功
                log.info("消息已确认, deliveryTag={}",
                        correlationData != null ? correlationData.getId() : "null");
            } else {
                // Broker 未收到或处理失败
                log.error("消息未确认, cause={}", cause);
                // TODO: 从本地消息表重发
                if (correlationData != null) {
                    retryService.retry(correlationData);
                }
            }
        });

        // ReturnsCallback：消息到达 Broker 但无法路由到 Queue
        template.setReturnsCallback(returned -> {
            log.error("消息无法路由: exchange={}, routingKey={}, replyCode={}, replyText={}",
                    returned.getExchange(),
                    returned.getRoutingKey(),
                    returned.getReplyCode(),
                    returned.getReplyText());
            // TODO: 记录无法路由的消息，人工处理或转备用队列
        });

        template.setMandatory(true);  // 消息无法路由时触发 ReturnsCallback
        return template;
    }
}
```

关键点：`publisher-confirm-type=correlated` 开启异步 confirm 模式。`ConfirmCallback` 在 Broker 确认消息后异步回调——`ack=true` 表示成功，`ack=false` 表示失败（Broker 没收到或内部错误）。`ReturnsCallback` 处理消息到达 Broker 但无法路由到任何 Queue 的情况。

### Layer 2 — 生产者：发送带 CorrelationData 的消息

```java
@Service
public class ConfirmProducer {
    @Autowired
    private RabbitTemplate confirmRabbitTemplate;

    public void sendOrder(String orderId) {
        // CorrelationData 关联消息 ID，confirm 回调时用它找到原消息
        CorrelationData correlationData = new CorrelationData(orderId);

        confirmRabbitTemplate.convertAndSend(
                "exchange.order",
                "order.created",
                new OrderEvent(orderId),
                correlationData);
        // 发送后立即返回，不等 Broker 确认
        // Broker 异步回调 ConfirmCallback
    }
}
```

关键点：`CorrelationData` 是消息的唯一标识，confirm 回调时通过它找到原消息进行重试。发送后立即返回不阻塞，Broker 确认后异步触发 `ConfirmCallback`。

### Layer 3 — 失败重试：本地消息表兜底

```java
@Service
public class RetryService {

    @Autowired
    private MessageRepository messageRepository;
    @Autowired
    private ConfirmProducer confirmProducer;

    // 定时扫描未确认的消息，重发
    @Scheduled(fixedDelay = 30000)  // 每 30 秒扫描一次
    public void retryUnconfirmedMessages() {
        List<MessageRecord> unconfirmed = messageRepository
                .findByStatusAndCreatedAtBefore(
                        "UNCONFIRMED",
                        LocalDateTime.now().minusMinutes(1));  // 1 分钟前未确认的

        for (MessageRecord record : unconfirmed) {
            if (record.getRetryCount() >= 3) {
                record.setStatus("DEAD");
                messageRepository.save(record);
                log.error("消息重试 3 次仍失败, orderId={}", record.getOrderId());
                continue;
            }
            // 重发消息
            confirmProducer.sendOrder(record.getOrderId());
            record.setRetryCount(record.getRetryCount() + 1);
            messageRepository.save(record);
        }
    }
}
```

关键点：本地消息表是消息可靠投递的最终兜底——发送消息时同时写本地表，confirm 回调成功后更新状态为「已确认」。定时扫描超时未确认的消息进行重试，超过重试上限标记为死信。即使 Broker 宕机，重启后也能从本地表恢复。

## 事务模式 vs Confirm 模式对比

| 维度 | 事务模式 | 同步 Confirm | 异步 Confirm |
|---|---|---|---|
| API | txSelect/txCommit/txRollback | confirmSelect + waitForConfirms | confirmSelect + ConfirmCallback |
| 阻塞特性 | 每条消息阻塞 | 批量发送后阻塞 | 完全非阻塞 |
| 吞吐量 | ~1,000 msg/s | ~10,000 msg/s | ~30,000+ msg/s |
| 性能损耗 | 极大（降一个数量级） | 中等 | 小 |
| 确认粒度 | 事务级别 | 批量级别 | 单条/批量 |
| 失败处理 | txRollback 回滚 | waitForConfirms 返回 false | ack=false 回调 |
| 推荐度 | 不推荐 | 折中方案 | 推荐 |
| 生产环境 | 不用 | 少用 | 标准方案 |

> 面试要点：事务模式和 Confirm 模式的区别是高频考点。核心对比：事务是同步强阻塞（每条消息等 Broker 确认），Confirm 是异步非阻塞（连续发送，Broker 异步回调）。性能差距约 30 倍。生产环境用异步 Confirm + CorrelationData + 本地消息表兜底。

## 一句话总结

**一句话总结：事务模式是「发一条等一条」的同步阻塞方案（性能极差不推荐），Confirm 模式是「连续发送异步等回调」的非阻塞方案（性能好推荐），生产环境用异步 Confirm + 本地消息表兜底实现消息可靠投递。**
