# Q37 Federation 联邦

Federation 是不同 RabbitMQ Broker（或集群）之间通过 AMQP 协议**单向转发消息**的机制，不需要 Erlang 集群互联。与集群的区别：集群是共享元数据 + 低延迟局域网，本质是一个逻辑 Broker；Federation 是松耦合的 Broker 间转发，各 Broker 独立运行，通过网络连接。适用场景是跨机房/跨地域消息同步、不同团队 Broker 间数据共享、低带宽环境下的消息分发。不适合需要强一致性的场景。

## Federation 配置

### Layer 1 — 启用 Federation 插件

```bash
# ===== 两个 Broker 都需要启用 Federation 插件 =====

# 在 upstream（北京）和 downstream（上海）Broker 上执行
rabbitmq-plugins enable rabbitmq_federation

# 如果使用 Management UI 管理联邦配置，还需要启用 management 插件
rabbitmq-plugins enable rabbitmq_federation_management

# 验证插件已启用
rabbitmq-plugins list | grep federation
# [e] rabbitmq_federation ...
# [e] rabbitmq_federation_management ...
```

关键点：Federation 是插件机制，需要显式启用。`rabbitmq_federation` 提供核心功能，`rabbitmq_federation_management` 提供 Web UI 管理界面。两端 Broker 都需要启用。

### Layer 2 — 配置 Upstream 连接参数

```bash
# ===== 在 downstream Broker（上海）上配置 upstream =====

# 方法1：通过 rabbitmqctl 设置 upstream 参数
rabbitmqctl set_parameter federation-upstream beijing \
  '{"uri":"amqp://admin:password@beijing-broker:5672","expires":3600000}'

# 参数说明：
# - uri: upstream Broker 的 AMQP 连接地址
# - expires: Federation Link 空闲超时（毫秒），超时后自动断开

# 方法2：通过 rabbitmqadmin 或 Management UI 配置
# Admin → Federation Upstreams → Add upstream
```

```bash
# ===== 设置 Federation 策略（指定哪些 Exchange/Queue 开启联邦）=====

# 对特定 Exchange 开启联邦
rabbitmqctl set_policy --apply-to exchanges \
  federation-exchange \
  "^exchange\.order\." \
  '{"federation-upstream":"beijing"}'

# 参数说明：
# --apply-to exchanges: 只对 Exchange 生效
# "^exchange\.order\.": 匹配以 exchange.order. 开头的 Exchange
# federation-upstream: 指定使用名为 beijing 的 upstream

# 对特定 Queue 开启联邦（Queue 级别联邦）
rabbitmqctl set_policy --apply-to queues \
  federation-queue \
  "^queue\.order\.federated" \
  '{"federation-upstream":"beijing"}'
```

关键点：Federation 的配置分两步——先设置 upstream 连接参数（URI、超时等），再设置策略指定哪些 Exchange/Queue 开启联邦。策略用正则匹配队列/交换机名称，灵活控制联邦范围。

### Layer 3 — Spring AMQP 消费联邦消息

```java
// ===== 下游 Broker（上海）的消费者正常消费即可 =====
// Federation 对客户端完全透明，消费者无需感知联邦

@Component
public class FederatedOrderConsumer {

    // 下游 Broker 上的联邦 Exchange/Queue
    // 消息来源：上游 Broker 通过 Federation Link 转发过来
    @RabbitListener(queues = "queue.order.federated")
    public void handle(OrderEvent event) {
        // 这条消息可能来自北京 Broker
        // Federation Link 自动从 upstream 消费并转发到本地
        orderService.process(event);
    }
}

// ===== 上游 Broker（北京）的生产者正常发送即可 =====
@Service
public class OrderProducer {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendOrder(OrderEvent event) {
        // 发送到上游 Broker 的 Exchange
        // Federation Link 自动消费并转发到下游
        rabbitTemplate.convertAndSend(
                "exchange.order.federated",
                "order.created",
                event);
    }
}
```

关键点：Federation 对客户端完全透明——生产者发送到上游 Exchange，消费者从下游 Queue 消费，中间的 Federation Link 自动完成消息转发。客户端代码无需任何联邦相关逻辑。

## 集群 vs Federation 对比

| 维度 | 集群（Cluster） | Federation（联邦） |
|---|---|---|
| 连接方式 | Erlang 节点互联 | AMQP 协议连接 |
| 元数据 | 全节点共享 | 各自独立 |
| 网络要求 | 低延迟局域网 | 可跨地域，容忍高延迟 |
| 耦合度 | 紧耦合（一个逻辑 Broker） | 松耦合（各自独立运行） |
| 故障影响 | 节点挂了影响集群 | Broker 挂了不影响另一个 |
| 一致性 | 强一致（元数据同步） | 最终一致（异步转发） |
| 数据复制 | 队列级别（Quorum/Mirror） | Exchange/Queue 级别 |
| 适用场景 | 同机房高可用 | 跨机房/跨地域同步 |
| 配置复杂度 | 低（join_cluster） | 中（插件 + upstream + 策略） |

> 面试要点：Federation 是不同 Broker 间通过 AMQP 协议单向转发消息，不需要 Erlang 集群互联。与集群的区别：集群是共享元数据 + 低延迟局域网，是一个逻辑 Broker；Federation 是松耦合的独立 Broker 间转发，容忍高延迟。适用跨地域同步、不同团队数据共享。不适合强一致性场景。

## 一句话总结

**一句话总结：集群是「同一屋檐下共享一切」的紧耦合（Erlang 互联 + 元数据共享 + 低延迟），Federation 是「各自独立、通过网络单向转发消息」的松耦合（AMQP 连接 + 容忍高延迟 + 跨地域）——前者追求高可用强一致，后者追求跨地域松耦合。**
