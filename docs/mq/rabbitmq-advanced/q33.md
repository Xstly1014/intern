# Q33 背压与流控

RabbitMQ 背压的根因是消费速率跟不上生产速率，大量 unacked 消息堆积在 Broker 内存，达到内存水位后触发 flow control，Broker 反向阻塞所有生产者连接。解法是多道防线逐层兜底——prefetch 限制单消费者在途消息、横向扩消费者提升整体消费速率、业务级背压从源头降速，再以内存水位配置和消息持久化做 Broker 层保护，核心是让消费速率匹配生产速率，prefetch 是第一道防线。

## 背压与流控的代码实现

### Layer 1 — 合理设置 prefetch（第一道防线）

```yaml
# application.yml — 全局 prefetch 与并发配置
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual      # 手动 ack，处理完再确认
        prefetch: 20                  # ← 每个消费者最多 20 条 unacked
        concurrency: 5                # 每个监听器初始 5 个消费者线程
        max-concurrency: 20           # 峰值弹性扩到 20
```

```java
// 单个 Listener 级别覆盖 prefetch
@Component
public class OrderConsumer {

    // prefetch=20：限制每个消费者未确认消息数
    // 避免单个消费者囤积过多 unacked 占用 Broker 内存
    @RabbitListener(queues = "queue.order",
            concurrency = "5",          // 5 个消费者实例
            ackMode = "MANUAL")
    public void handle(OrderEvent event, Channel channel,
                       @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        try {
            orderService.process(event);   // 业务处理
            channel.basicAck(tag, false);  // 处理成功才 ack → 释放 unacked 配额
        } catch (Exception e) {
            channel.basicNack(tag, false, false); // 失败不 requeue，转死信
        }
    }
}
```

```java
// 手动设置 prefetch（覆盖全局配置）
@Configuration
public class PrefetchConfig {
    @Bean
    public SimpleRabbitListenerContainerFactory orderFactory(
            ConnectionFactory connectionFactory) {
        SimpleRabbitListenerContainerFactory factory =
                new SimpleRabbitListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setAcknowledgeMode(AcknowledgeMode.MANUAL);
        factory.setPrefetchCount(20);     // ← 核心：限制 unacked 数
        factory.setConcurrentConsumers(5);
        factory.setMaxConcurrentConsumers(20);
        return factory;
    }
}
```

关键点：prefetch 限制每个消费者未确认消息上限。prefetch 过大（Spring AMQP 默认 250）会让单个消费者囤积大量 unacked，堆积在 Broker 内存引发背压；设为 10~50 让消费者"拿一条处理一条"，配合手动 ack，处理完才释放配额。这是背压的第一道防线。

### Layer 2 — 横向扩消费者：分摊负载

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 10               # 初始 10 个消费者
        max-concurrency: 50           # 峰值弹性扩到 50
        prefetch: 20                  # 每个消费者 20 unacked
        # 总在途 unacked = 消费者数 × prefetch
        # 50 × 20 = 1000 条在途，分摊到多消费者，单消费者压力小
```

```java
// 水平扩容：多实例部署消费者，Queue 默认轮询分发
// 消息会被均匀分发到所有消费者，单消费者 unacked 自然下降
@Component
public class ScaledOrderConsumer {

    // 多实例部署时，每个实例各自起 concurrency 个消费者
    // Queue 在多个消费者间轮询（round-robin）分发
    @RabbitListener(queues = "queue.order",
            concurrency = "10-50")     // ← 10~50 个消费者，弹性扩缩
    public void handle(OrderEvent event, Channel channel,
                       @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        orderService.process(event);
        channel.basicAck(tag, false);
    }
}
```

```text
// 结合 prefetch 的总并发计算
// 总在途 unacked = 消费者数 × prefetch
// 扩消费者：分母变大，单个消费者分到的消息变少
// 例：1000 msg/s 生产，50 消费者 × prefetch 20 = 1000 并发处理
//     单消费者只需 20 msg/s，Broker 内存中 unacked 总量可控
```

关键点：横向扩消费者增大"分母"——Queue 默认轮询分发，消费者越多每个分到的越少，单消费者 unacked 下降，Broker 内存压力随之下降。concurrency 控制单实例消费者数，多实例部署进一步水平扩展。注意总在途 = 消费者数 × prefetch，仍需配合 prefetch 防止单点囤积。

### Layer 3 — Broker 内存水位配置（rabbitmq.conf）

```ini
# /etc/rabbitmq/rabbitmq.conf
# 内存水位：达到该比例触发内存报警 + 阻塞所有 publishing 连接（flow control）
# 默认 0.4（即可用内存的 40%）
vm_memory_high_watermark.relative = 0.4

# 也可用绝对值
# vm_memory_high_watermark.absolute = 2GB

# 分页比例：达到 high_watermark 的该比例时，开始把持久化消息刷盘（paging）
# 默认 0.5，即 0.5 × 0.4 = 0.2 内存时开始刷盘，提前释放内存
vm_memory_high_watermark_paging_ratio = 0.5

# 磁盘水位：剩余磁盘低于该值阻塞 publishers（disk alarm）
disk_free_limit.relative = 1.0     # 默认剩余磁盘 < 1×内存时报警
```

```ini
# 调优建议
# 1. 0.4 是默认值，留 60% 余量给其他进程，一般够用
# 2. 不要调到 0.7+ 才限流：太晚触发，容易 OOM 杀进程
# 3. 节点内存大时可适当上调（如 0.5），但需监控 paging 频率
# 4. 配合 paging_ratio 提前刷盘，并开启消息持久化（deliveryMode=2）
```

关键点：vm_memory_high_watermark 是 Broker 兜底的流控开关——内存达水位即阻塞所有生产者连接（背压传导给生产者），防止 OOM。默认 0.4 留足余量，不建议调到 0.7 才触发（OOM 风险）；paging_ratio=0.5 让持久化消息在达水位前就刷盘，缓解内存。这是 Broker 层的最后一道防线，不应依赖它做常规限流——常规应靠 prefetch + 扩消费者。

### Layer 4 — 业务级背压：消费者通知生产者降速

```java
// 消费者：处理不过来时，通过反馈通道通知生产者降速
@Component
public class BackpressureAwareConsumer {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    @RabbitListener(queues = "queue.order", concurrency = "10")
    public void handle(OrderEvent event, Channel channel,
                       @Header(AmqpHeaders.DELIVERY_TAG) long tag,
                       @Header(AmqpHeaders.CONSUMER_QUEUE) String queue) throws IOException {
        try {
            // 监控自身处理延迟 / 队列堆积
            if (backpressureDetector.isOverloaded(queue)) {
                // 消费不过来 → 通知生产者降速（业务级背压）
                rabbitTemplate.convertAndSend(
                        "exchange.feedback", "producer.throttle",
                        new ThrottleSignal(event.getProducerId(), 0.3)); // 降到 30%
                // 当前消息 nack + 不重入，转死信避免堆积
                channel.basicNack(tag, false, false);
                return;
            }
            orderService.process(event);
            channel.basicAck(tag, false);
        } catch (Exception e) {
            channel.basicNack(tag, false, false);
        }
    }
}
```

```java
// 生产者：监听降速信号，动态调整发送速率
@Service
public class BackpressureAwareProducer {

    private final AtomicInteger rateLimit = new AtomicInteger(100); // 初始 100%

    @RabbitListener(queues = "queue.throttle.signal")
    public void onThrottle(ThrottleSignal signal) {
        // 收到消费者的降速信号 → 调整发送速率
        rateLimit.set((int) signal.getRatePercent());
        log.warn("收到背压信号，生产速率降至 {}%", signal.getRatePercent());
    }

    public void sendOrder(OrderEvent event) {
        // 令牌桶限流：按 rateLimit 控制发送速率
        if (!rateLimiter.tryAcquire(rateLimit.get())) {
            // 限流降级：丢弃 / 缓存 / 返回限流响应
            log.warn("生产者限流降级，缓存或拒绝消息");
            return;
        }
        rabbitTemplate.convertAndSend("exchange.order", "order.created", event);
    }
}
```

关键点：业务级背压是应用层的主动反压——消费者监控自身负载，处理不过来时通过反馈通道（独立 Queue / HTTP 回调 / 降级开关）通知生产者降速，从源头减少消息量。它弥补了 prefetch（只限单消费者）和扩消费者（受资源上限）的不足，是"治本"的限流降级手段。

## 五种解决方案对比

| 维度 | ① prefetch | ② 横向扩消费者 | ③ 限流降级 | ④ 内存水位 | ⑤ 消息持久化 |
|---|---|---|---|---|---|
| 原理 | 限制每消费者 unacked 上限 | 增加消费者数分摊负载 | 通知生产者降速 | 内存达水位阻塞 publishers | 消息刷盘释放内存 |
| 作用层 | 消费者端 | 消费者端 | 业务/应用层 | Broker 端 | Broker 端 |
| 效果 | 防单点囤积，第一道防线 | 提升整体消费速率 | 从源头减量，治本 | 兜底防 OOM | 缓解内存压力 |
| 起效速度 | 即时 | 需扩容部署 | 需反馈回路 | 即时（被动触发） | 异步刷盘 |
| 适用场景 | 所有消费者必配 | 消费可水平扩展 | 生产消费可协同 | Broker 兜底保护 | 持久化消息队列 |

> 面试要点：背压链路是核心考点。答题路径：先讲问题链路（生产 &gt; 消费 → unacked 堆积占 Broker 内存 → 达内存水位 0.4 → flow control 阻塞 publishers）→ 再讲五道防线分层（消费者层 prefetch + 扩消费者、业务层限流降级、Broker 层内存水位 + 持久化）→ 强调核心是让消费速率匹配生产速率，prefetch 是第一道防线，Broker 水位只是兜底不能依赖做常规限流。

## 一句话总结

**一句话总结：RabbitMQ 背压的本质是消费速率跟不上生产速率导致 unacked 堆积占满 Broker 内存——解法是多道防线逐层兜底：prefetch 限单消费者在途（第一道防线）、横向扩消费者提速率、业务级背压从源头降速，内存水位与消息持久化做 Broker 层兜底，核心是让消费速率匹配生产速率。**
