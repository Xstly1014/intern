# Q30 消费者 ACK 机制

消费者 ACK 机制控制 Broker 何时删除已投递的消息：`autoAck=true` 时 Broker 投递后立即标记已消费并删除，不等消费者处理完成，消息可能丢失；`autoAck=false`（推荐）时消费者必须显式 ACK，Broker 收到 `basicAck`/`basicNack`/`basicReject` 响应后才删除消息，未确认的消息会重新入队。

上图对比了两种确认模式的根本差异：`autoAck=true` 把删除时机交给 Broker 的投递动作，消费者还没处理完消息就已经消失；`autoAck=false` 把删除权交给消费者的 ACK 调用，未确认的消息会重新入队兜底。下方代码展示如何在 Spring AMQP 中落地手动确认。

## 分层代码示例（Spring AMQP）

### Layer 1 — 配置：autoAck=false 的 ContainerFactory

关闭自动确认、限制预取数量，是手动 ACK 的入口配置。

```java
@Configuration
public class RabbitAckConfig {

    @Bean
    public SimpleRabbitListenerContainerFactory<OrderMessage> ackContainerFactory(
            ConnectionFactory connectionFactory) {
        SimpleRabbitListenerContainerFactory<OrderMessage> factory =
                new SimpleRabbitListenerContainerFactory<>();
        factory.setConnectionFactory(connectionFactory);
        // 关键：关闭自动确认（autoAck=false），改为手动 ACK
        factory.setAcknowledgeMode(AcknowledgeMode.MANUAL);
        // 限制单个消费者同时未确认的消息数，防止 unacked 堆积撑爆 Broker 内存
        factory.setPrefetchCount(50);
        return factory;
    }
}
```

**关键点**：`AcknowledgeMode.MANUAL` 即 `autoAck=false`，消费者必须显式 ACK；`setPrefetchCount` 限制未确认消息上限，避免「忘了 ACK」导致 unacked 无限堆积。

### Layer 2 — 消费者：正确 ACK（成功 basicAck / 失败 basicNack）

消费者在 try 中处理成功后 `basicAck`，在 catch 中 `basicNack(requeue=false)` 让消息进死信队列，避免无限重试。

```java
@Component
public class OrderConsumer {

    @RabbitListener(queues = "order.queue", containerFactory = "ackContainerFactory")
    public void handle(OrderMessage msg,
                       Channel channel,
                       @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        try {
            // 业务处理
            processOrder(msg);
            // 处理成功 → 显式 ACK，Broker 才删除消息
            channel.basicAck(tag, false);
        } catch (Exception e) {
            // 处理失败 → basicNack，requeue=false 不重入队，直接进死信队列
            channel.basicNack(tag, false, false);
        }
    }
}
```

**关键点**：成功走 `basicAck(tag, false)`；失败走 `basicNack(tag, false, false)`（第二个 `false` 为 requeue），消息不重入队而是路由到死信队列；切忌忘记 ACK，否则消息一直留在 unacked 状态。

### Layer 3 — 三种 ACK 方法对比示例

三种方法语义不同：`basicAck` 表示成功，`basicNack`/`basicReject` 表示拒绝，区别在于是否支持批量与 requeue 参数。

```java
// 1. basicAck：处理成功，通知 Broker 删除消息
//    multiple=false 只确认当前这条；true 则确认该 tag 及之前所有未确认消息
channel.basicAck(deliveryTag, false);

// 2. basicNack：处理失败，可批量拒绝
//    multiple=true 拒绝该 tag 及之前所有消息；requeue 控制是否重新入队
channel.basicNack(deliveryTag, true, false);  // 批量拒绝，不重入队 → 死信队列

// 3. basicReject：只拒绝单条消息（无 multiple 参数）
//    requeue=true 重新入队；requeue=false 路由到死信队列
channel.basicReject(deliveryTag, false);      // 拒绝单条，进死信队列
```

**关键点**：`basicAck` 成功确认；`basicNack` 支持 `multiple` 批量 + `requeue`；`basicReject` 仅单条 + `requeue`；生产中失败通常 `requeue=false` 配合死信队列，防止 poison message 无限重投。

## 对比表

### autoAck=true vs autoAck=false

| 维度 | autoAck = true | autoAck = false（推荐） |
|---|---|---|
| 确认时机 | Broker 投递后立即确认 | 消费者显式调用 ACK 后确认 |
| 消息删除 | 投递即删除，不等处理完成 | 收到 ACK 响应才删除 |
| 消费者宕机 | 消息已删除，直接丢失 | 未 ACK 消息重新入队，不丢失 |
| 可靠性 | 低，可能丢消息 | 高，至少消费一次 |
| 吞吐量 | 高（少一次网络往返） | 略低（多一次 ACK 往返） |
| 适用场景 | 允许丢消息的高吞吐日志 | 订单、支付等业务消息 |

### basicAck vs basicNack vs basicReject

| 方法 | 含义 | 支持批量(multiple) | requeue 参数 | 典型场景 |
|---|---|---|---|---|
| basicAck | 确认处理成功 | 支持，true 确认该 tag 及之前全部 | 无 | 业务正常完成 |
| basicNack | 拒绝消息(处理失败) | 支持，true 拒绝该 tag 及之前全部 | 有，控制是否重入队 | 批量失败、poison message |
| basicReject | 拒绝单条消息 | 不支持，仅单条 | 有，控制是否重入队 | 单条消息无法处理 |

**一句话总结：消费者 ACK 机制的本质是把消息删除权从「Broker 投递即删」交还给「消费者处理完才确认」——`autoAck=false` 配合 `basicAck`/`basicNack`/`basicReject`，让消息要么被成功消费后删除，要么重新入队或进死信队列，既不丢失也不无限重试。**
