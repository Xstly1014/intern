# Q31 prefetch 预取机制

prefetch（预取）是消费者通过 `basicQos(prefetchCount)` 设定的、每次从 Queue 预先拉取到本地缓冲的消息条数；消费者处理完并 ACK 后，RabbitMQ 才会按该配额再推下一批。它只在 `autoAck=false`（手动 ACK）时生效，值的大小直接在吞吐、内存与公平性之间做权衡。

图中三行分别对应 prefetch 设过小、过大、适中三种场景：值越小，每条消息都要一次 ACK 往返，吞吐被网络 RTT 拖低；值越大，单消费者本地堆积越多，内存压力上升、其他消费者被饿死、宕机时还有大量 unacked 重新入队。下面用 Spring AMQP 分三层来看怎么配、怎么按场景分、怎么动态调。

## Layer 1 — ContainerFactory 统一配置 prefetch

在容器工厂层设定全局预取数，对应底层 `channel.basicQos(prefetchCount)`。

```java
@Configuration
public class RabbitConfig {

    /**
     * Layer 1：在 ContainerFactory 层统一设定 prefetch。
     * SimpleRabbitListenerContainerFactory 的 setPrefetchCount 即对应 basicQos(prefetchCount)。
     * 关键：只在 AcknowledgeMode.MANUAL / AUTO（即 autoAck=false）时才生效。
     */
    @Bean
    public SimpleRabbitListenerContainerFactory prefetchFactory(ConnectionFactory cf) {
        SimpleRabbitListenerContainerFactory factory = new SimpleRabbitListenerContainerFactory();
        factory.setConnectionFactory(cf);
        // 手动 ACK：等业务处理完再 ack，prefetch 配额才会真正起作用
        factory.setAcknowledgeMode(AcknowledgeMode.MANUAL);
        // 全局默认预取数：Spring AMQP 默认 250，多数业务偏大，建议按处理速度调小
        factory.setPrefetchCount(10);
        // 并发消费者数：总在途消息 ≈ concurrency × prefetch
        factory.setConcurrentConsumers(2);
        factory.setMaxConcurrentConsumers(8);
        return factory;
    }
}
```

关键点：prefetch 必须配手动 ACK 才生效；总在途消息量 ≈ `concurrentConsumers × prefetch`，调 prefetch 时要同步考虑并发数，否则光调一个维度会失衡。

## Layer 2 — 按业务处理速度给不同队列配不同 prefetch

prefetch 没有"通用最优值"，按单条处理耗时经验调：处理快、轻量任务放大预取吃满吞吐；处理慢、重任务压低预取守住内存与公平。

```java
/**
 * Layer 2：按业务处理速度给不同队列配不同 prefetch。
 * 处理越快、单条越轻 -> prefetch 越大（榨干网络与 CPU）；
 * 处理越慢、单条越重 -> prefetch 越小（避免堆积与不公平）。
 */
public class PrefetchByScene {

    // 日志/埋点：处理极快、纯写库 -> 放大预取
    @Bean(name = "fastFactory")
    public SimpleRabbitListenerContainerFactory fastFactory(ConnectionFactory cf) {
        SimpleRabbitListenerContainerFactory f = new SimpleRabbitListenerContainerFactory();
        f.setConnectionFactory(cf);
        f.setAcknowledgeMode(AcknowledgeMode.MANUAL);
        f.setPrefetchCount(100);   // 快任务设大
        return f;
    }

    // 订单/支付：处理慢、可能调外部接口 -> 压低预取，保证公平与及时 ACK
    @Bean(name = "slowFactory")
    public SimpleRabbitListenerContainerFactory slowFactory(ConnectionFactory cf) {
        SimpleRabbitListenerContainerFactory f = new SimpleRabbitListenerContainerFactory();
        f.setConnectionFactory(cf);
        f.setAcknowledgeMode(AcknowledgeMode.MANUAL);
        f.setPrefetchCount(5);     // 慢任务设小
        return f;
    }

    // 监听端按需指定用哪个 factory
    @RabbitListener(queues = "q.log", containerFactory = "fastFactory")
    public void onLog(Message msg, Channel channel) throws IOException {
        // ... 轻量处理 ...
        channel.basicAck(msg.getMessageProperties().getDeliveryTag(), false);
    }

    @RabbitListener(queues = "q.order", containerFactory = "slowFactory")
    public void onOrder(Order o, Message msg, Channel channel) throws IOException {
        // ... 慢处理：扣库存、调支付 ...
        channel.basicAck(msg.getMessageProperties().getDeliveryTag(), false);
    }
}
```

关键点：用不同 `containerFactory` 隔离不同队列的预取策略；经验值——快任务 50~100、慢任务 5~10；务必显式 `basicAck`，否则 prefetch 形同虚设（消息永不释放）。

## Layer 3 — 运行期动态调整 prefetch

应对流量峰谷，不停机修改预取数；变更对新拉取的批次生效，已缓冲的不受影响。

```java
/**
 * Layer 3：运行期动态调整 prefetch，应对流量峰谷。
 * 改完对新拉取的批次立即生效；部分版本需 stop/start 才能应用到 channel 的 basicQos。
 */
@Service
public class PrefetchTuner {

    @Autowired
    private RabbitListenerEndpointRegistry registry;

    public void tune(int newPrefetch) {
        registry.getListenerContainers().forEach(c -> {
            if (c instanceof AbstractMessageListenerContainer<?, ?> amqc) {
                amqc.setPrefetchCount(newPrefetch);
                // 触发消费者重启以应用新 Qos
                amqc.stop();
                amqc.start();
            }
        });
    }

    // 定时按积压长度自适应：积压多 -> 调大；积压少 -> 调小
    @Scheduled(fixedDelay = 30_000)
    public void autoTune() {
        int backlog = queueDepth("q.order");   // 自定义：查队列消息数
        int target = backlog > 1000 ? 50 : (backlog > 100 ? 20 : 5);
        tune(target);
    }

    private int queueDepth(String queue) { /* 调用 RabbitMQ HTTP API 或 AmqpTemplate */ return 0; }
}
```

关键点：动态调 prefetch 会引发消费者短暂重启，已缓冲消息不变；务必配合监控（unacked 数、消费速率、内存）小步调整，避免一次调过大引发雪崩；自适应算法要设上下限，防止极端值。

## 对比表：prefetch 设大 vs 设小 vs 适中

| 维度 | 设过大（如 100+） | 设过小（如 1） | 设适中（5~100，按速度） |
|---|---|---|---|
| 本地缓冲 / unacked | 大量堆积，内存压力大 | 几乎不缓冲 | 适量，可控 |
| 吞吐 | 单消费者高，整体未必 | 网络往返多，吞吐低 | 流水线不断，吞吐高 |
| 多消费者公平 | 易饿死其他消费者 | 公平但低效 | 公平且高效 |
| 宕机影响 | 大量 unacked 重入队，重复消费风险 | 几乎无重入队 | 重入队量小、可控 |
| 适用场景 | 处理极快、轻量任务 | 处理极慢 / 需严格顺序 | 多数常规业务 |
| 备注 | Spring AMQP 默认 250 偏大 | 仅 autoAck=false 生效 | 仅 autoAck=false 生效 |

**一句话：prefetch 是在"少跑一趟网络"和"少囤一兜消息"之间找平衡——快任务放大预取吃满吞吐，慢任务压低预取守住内存与公平，且只在手动 ACK 下才真正生效。**
