# Q36 Quorum Queue 仲裁队列

Quorum Queue 基于 **Raft 共识协议**实现：Leader 负责读写，Follower 复制日志。写入流程是客户端发消息到 Leader → Leader 写本地日志并并行复制到所有 Follower → 多数派（N/2+1）确认后 Leader commit 并返回成功 → Follower 异步 apply 到状态机。它比镜像队列更可靠的原因是：多数派写入保证少数节点宕机不丢数据、Raft 的 term 和投票机制保证只有一个 Leader（无脑裂）、Leader 挂了 Follower 自动选举新 Leader 无需人工干预。

## Quorum Queue 配置与使用

### Layer 1 — 声明 Quorum Queue

```java
// ===== Quorum Queue 声明（Spring AMQP）=====

@Configuration
public class QuorumQueueConfig {

    // Quorum Queue：基于 Raft 协议的仲裁队列
    @Bean
    public Queue orderQuorumQueue() {
        return QueueBuilder.durable("queue.order.quorum")
                .withArgument("x-queue-type", "quorum")          // 队列类型：仲裁队列
                .withArgument("x-quorum-initial-group-size", 3)   // 初始副本数：3（建议奇数）
                // Quorum Queue 强制持久化，无需设置 durable（始终 true）
                // 不支持 x-message-ttl（用策略替代）、不支持 priority（最高优先级）
                .build();
    }

    @Bean
    public DirectExchange orderExchange() {
        return new DirectExchange("exchange.order", true, false);
    }

    @Bean
    public Binding binding(Queue orderQuorumQueue, DirectExchange orderExchange) {
        return BindingBuilder.bind(orderQuorumQueue)
                .to(orderExchange)
                .with("order.created");
    }
}
```

关键点：`x-queue-type=quorum` 是核心参数，声明后该队列自动使用 Raft 协议在集群多数派节点间复制消息。`x-quorum-initial-group-size` 指定初始 Raft 组大小（建议 3 或 5，奇数节点）。Quorum Queue 强制持久化，不能关闭。

### Layer 2 — 生产者发送（与普通队列无差异）

```java
// ===== 生产者代码完全一样，无需感知 Quorum Queue =====

@Service
public class OrderProducer {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendOrder(OrderEvent event) {
        // 发送到 Quorum Queue 和发到 Classic Queue 的代码完全一样
        // RabbitTemplate 不需要任何特殊配置
        rabbitTemplate.convertAndSend(
                "exchange.order",
                "order.created",
                event,
                message -> {
                    // Quorum Queue 强制持久化，deliveryMode 自动为 2
                    message.getMessageProperties().setDeliveryMode(MessageDeliveryMode.PERSISTENT);
                    return message;
                });
    }
}
```

关键点：从客户端角度看，Quorum Queue 和 Classic Queue 的使用方式完全一样。生产者发送代码无需任何修改，Broker 内部透明处理 Raft 复制。

### Layer 3 — 消费者（与普通队列无差异）

```java
// ===== 消费者代码也完全一样 =====

@Component
public class OrderConsumer {

    @RabbitListener(queues = "queue.order.quorum", concurrency = "5")
    public void handle(OrderEvent event, Channel channel,
                       @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        try {
            orderService.process(event);
            channel.basicAck(tag, false);
            // ack 后 Broker 内部 commit Raft 日志
            // 多数派节点同步标记消息为已消费
        } catch (Exception e) {
            channel.basicNack(tag, false, false);
            // nack 后消息不会被删除，等待重新投递
            // Raft 保证消息在多数派节点上一致
        }
    }
}
```

关键点：消费者代码也无需修改。`basicAck` 后 Broker 内部通过 Raft 协议在多数派节点上标记消息已消费。`basicNack` 后消息不删除，Leader 会重新投递给其他消费者。

### Layer 4 — 运维管理命令

```bash
# ===== Quorum Queue 运维命令 =====

# 查看 Quorum Queue 的 Raft 组成员
rabbitmqctl list_queues name type quorum_state

# 输出示例：
# queue.order.quorum  quorum  Leader
# （在 Leader 节点上执行显示 Leader，在 Follower 节点上显示 Follower）

# 查看 Quorum Queue 副本分布
rabbitmqctl list_queues name type pid node messages

# 添加 Quorum Queue 副本（扩容 Raft 组）
rabbitmq-queues grow_member all --node rabbit@new-node

# 移除 Quorum Queue 副本（缩容）
rabbitmq-queues shrink_member rabbit@node-c

# Quorum Queue 不支持以下操作：
# - x-message-ttl（消息级 TTL，需用策略替代）
# - 优先级队列（max priority）
# - x-ha-policy（镜像策略，Quorum 自带 Raft 复制）
```

关键点：Quorum Queue 的运维命令独立于 Classic Queue。`rabbitmq-queues` 命令管理 Raft 组成员的增减。注意 Quorum Queue 不支持消息级 TTL 和优先级队列，这些是 Mirrored Queue 的能力。

## Mirrored Queue vs Quorum Queue

| 维度 | Mirrored Queue | Quorum Queue |
|---|---|---|
| 共识协议 | 主从同步（非 Raft） | Raft 多数派写入 |
| 写入确认 | master 写入即返回 | 多数派确认后返回 |
| 数据一致性 | 全同步（可能脑裂） | Raft 保证强一致 |
| Leader 选举 | master 挂了 mirror 提升 | Raft 投票选举新 Leader |
| 脑裂风险 | 有（分区时可能双 master） | 无（Raft term 保证唯一 Leader） |
| 节点故障容忍 | 取决于镜像数 | N/2 - 1 个（3 节点容 1 个） |
| 消息持久化 | 可选 | 强制持久化 |
| 消息级 TTL | 支持 | 不支持 |
| 优先级队列 | 支持 | 不支持 |
| 推荐度 | 逐步废弃 | 生产推荐 |
| 适用场景 | 旧系统迁移 | 新系统标准选择 |

> 面试要点：Quorum Queue 基于 Raft 协议——Leader 负责读写，Follower 复制日志，多数派确认后才 commit。比镜像队列更可靠的三个原因：多数派写入（少数节点宕机不丢数据）、无脑裂（Raft term 和投票保证唯一 Leader）、自动选举（Leader 挂了 Follower 自动接管）。生产环境用 Quorum Queue 替代 Mirrored Queue。

## 一句话总结

**一句话总结：Quorum Queue 用 Raft 把消息写入变成「Leader 写日志 → 多数派确认 → commit」的多数派共识流程——少数节点挂了不丢数据、Leader 挂了自动选举无脑裂，比镜像队列的「master 写即返回」在一致性和容灾上强一个级别。**
