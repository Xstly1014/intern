# Q32 消息重试与死信

`basicNack(requeue=true)` 会让失败消息原封不动地重新入队并被再次消费，Broker 端没有任何重试次数或延迟控制，结果就是无限重投循环。正确做法是给重试加上"次数上限 + 延迟节奏 + 死信兜底"——生产环境推荐 TTL + DLX 多级延迟队列实现阶梯式重试。

上图上半部分点出 `requeue=true` 的死循环本质，下半部分展开推荐方案：消费失败后不再裸 requeue，而是 republish 到带 TTL 的重试队列，消息"睡"够延迟后由 DLX 自动回到原队列；每升一级换更长 TTL 的队列，超过最大级别才进死信队列——重试次数和节奏都变得可控。

## Layer 1 — 方案1：Redis 记录重试次数

最轻量的兜底方案：在 Broker 之外用计数器记录重试次数，超阈值就 `nack(requeue=false)` 放进死信队列。

```java
// ===== 方案1：Redis 记录重试次数，配合 requeue=true =====
@RabbitListener(queues = "order.queue")
public void handle(OrderMsg msg, Message message, Channel channel) throws IOException {
    long tag = message.getMessageProperties().getDeliveryTag();
    String key = "retry:" + message.getMessageProperties().getMessageId();
    try {
        orderService.process(msg);
        channel.basicAck(tag, false);
        stringRedisTemplate.delete(key);            // 成功：清理计数
    } catch (Exception e) {
        Long count = stringRedisTemplate.opsForValue().increment(key);
        stringRedisTemplate.expire(key, Duration.ofMinutes(10)); // 防止脏数据残留
        if (count != null && count > MAX_RETRY) {
            channel.basicNack(tag, false, false);   // 超阈值：不重入队 → 队列 DLX 进死信队列
            stringRedisTemplate.delete(key);
        } else {
            channel.basicNack(tag, false, true);    // 未超阈值：重新入队再次消费
        }
    }
}
```

**关键点**
- 以 `messageId` 为 key 在 Redis 记录重试次数，规避了 `requeue=true` 后消息头不可变的问题。
- 成功后删除计数；超过阈值用 `nack(requeue=false)` 让队列 DLX 把消息投到死信队列。
- 局限：`requeue=true` 是立即重投递、无延迟，瞬时故障下可能瞬间打满消费者，不适合需要退避的场景。

## Layer 2 — 方案2：TTL + DLX 多级重试队列（推荐）

把"立即重投"换成"延迟重投"：消费失败后主动 ack 原消息并 republish 到带 TTL 的重试队列，消息过期后由该队列的 DLX 自动回到原队列重新消费。每个重试级别配一个不同 TTL 的队列。

```java
// ===== 方案2：TTL + DLX 多级重试队列（推荐）=====

// --- 队列 / 交换机配置 ---
@Configuration
public class RetryQueueConfig {

    @Bean
    public DirectExchange retryExchange() { return new DirectExchange("retry.exchange"); }

    // 重试队列1：TTL=10s，过期后由 DLX 回到原队列
    @Bean
    public Queue retryQueue10s() {
        return QueueBuilder.durable("retry.10s")
                .withArgument("x-message-ttl", 10_000)
                .withArgument("x-dead-letter-exchange", "order.exchange")
                .withArgument("x-dead-letter-routing-key", "order.create")
                .build();
    }
    @Bean
    public Binding bind10s() {
        return BindingBuilder.bind(retryQueue10s()).to(retryExchange()).with("retry.10s");
    }

    // 重试队列2：TTL=30s，过期后回到原队列
    @Bean
    public Queue retryQueue30s() {
        return QueueBuilder.durable("retry.30s")
                .withArgument("x-message-ttl", 30_000)
                .withArgument("x-dead-letter-exchange", "order.exchange")
                .withArgument("x-dead-letter-routing-key", "order.create")
                .build();
    }
    @Bean
    public Binding bind30s() {
        return BindingBuilder.bind(retryQueue30s()).to(retryExchange()).with("retry.30s");
    }

    @Bean
    public Queue deadLetterQueue() { return QueueBuilder.durable("order.dlq").build(); }
}

// --- 消费者：失败后按重试级别 republish 到对应 TTL 队列 ---
@RabbitListener(queues = "order.queue")
public void handle(OrderMsg msg, Message message, Channel channel) throws IOException {
    long tag = message.getMessageProperties().getDeliveryTag();
    try {
        orderService.process(msg);
        channel.basicAck(tag, false);
    } catch (Exception e) {
        Integer retry = (Integer) message.getMessageProperties().getHeader("x-retry-count");
        int count = retry == null ? 0 : retry;
        if (count >= MAX_RETRY) {
            rabbitTemplate.convertAndSend("", "order.dlq", msg);          // 终态：死信队列
        } else {
            String routingKey = count == 0 ? "retry.10s" : "retry.30s";   // 按级别路由
            rabbitTemplate.convertAndSend("retry.exchange", routingKey, msg, m -> {
                m.getMessageProperties().setHeader("x-retry-count", count + 1);
                return m;
            });
        }
        channel.basicAck(tag, false);  // 原消息已转发，直接 ack（不再 requeue）
    }
}
```

**关键点**
- 各重试队列只配 `x-message-ttl` + `x-dead-letter-exchange`（指向原队列的 exchange），消息过期后自动回到原队列，无需手动调度。
- 消费失败时主动 ack 原消息并 republish 到重试队列，靠 `x-retry-count` 头选择对应级别的 TTL 队列——这一步是关键：原消息不再走 `requeue=true`。
- 阶梯 TTL（10s → 30s → 1min）让重试节奏可控；超过最大级别直接进死信队列，终态明确、可观测、可补偿。

## Layer 3 — 方案3：Spring RetryTemplate 配置

Spring AMQP 的 `RetryTemplate` 把重试逻辑封装成消费者侧的拦截器，在进程内同步重试（指数退避），耗尽后抛异常让消息进死信队列，无需额外队列。

```java
// ===== 方案3：Spring RetryTemplate（内存重试，无需额外队列）=====

@Configuration
public class RetryListenerConfig {

    @Bean
    public RetryOperationsInterceptor retryInterceptor() {
        ExponentialBackOffPolicy backOff = new ExponentialBackOffPolicy();
        backOff.setInitialInterval(1000);   // 初始 1s
        backOff.setMultiplier(2.0);         // 倍数 2
        backOff.setMaxInterval(5000);       // 上限 5s

        RetryTemplate template = new RetryTemplate();
        template.setBackOffPolicy(backOff);
        template.setRetryPolicy(new SimpleRetryPolicy(3));   // 最多 3 次

        RetryOperationsInterceptor interceptor = new RetryOperationsInterceptor();
        interceptor.setRetryOperations(template);
        // 重试耗尽：拒绝且不重入队 → 队列 DLX 投递死信队列
        interceptor.setRecoveryCallback(ctx -> {
            throw new AmqpRejectAndDontRequeueException("retry exhausted");
        });
        return interceptor;
    }

    @Bean
    public SimpleRabbitListenerContainerFactory<?> retryFactory(
            ConnectionFactory cf, RetryOperationsInterceptor interceptor) {
        SimpleRabbitListenerContainerFactory<?> factory = new SimpleRabbitListenerContainerFactory<>();
        factory.setConnectionFactory(cf);
        factory.setAdviceChain(interceptor);   // 挂载重试拦截器
        return factory;
    }
}
```

**关键点**
- `RetryTemplate` 在消费者线程内同步重试（阻塞该线程），不经过 Broker，适合偶发瞬时故障。
- 指数退避避免压垮下游；耗尽后抛 `AmqpRejectAndDontRequeueException`，由队列 DLX 进死信队列。
- 局限：重试期间占用消费者线程、进程重启会丢失重试状态、不适合分钟级长延迟重试。

## 三种重试方案对比

| 维度 | 方案1 业务记录次数 | 方案2 TTL+DLX 多级队列 ★ | 方案3 RetryTemplate |
|---|---|---|---|
| 重试位置 | Broker 重新投递 | Broker + TTL 延迟队列 | 消费者进程内（内存） |
| 延迟控制 | 无延迟（立即重投） | 阶梯 TTL（10s/30s/1min） | 指数退避（内存阻塞） |
| 重试状态存储 | Redis / 消息头 | 消息头 x-retry-count | 内存计数 |
| 进程重启影响 | 不丢失（Redis 持久化） | 不丢失（消息留在队列） | 丢失重试状态 |
| 额外组件 | 需 Redis | 需多个队列 / Exchange | 无 |
| 适用场景 | 简单计数兜底 | 生产推荐、长延迟重试 | 瞬时故障、短重试 |

**一句话总结：别让 `requeue=true` 裸跑——用 TTL + DLX 把"立即无限重投"换成"阶梯式延迟重试 + 死信兜底"，重试次数可控、延迟节奏可调、终态明确可补偿。**
