# Q34 RabbitMQ 集群架构

RabbitMQ 集群的核心特点是**元数据全节点共享、消息默认不复制**——Exchange/Queue/Binding/User 等元数据在所有节点间同步，但 Classic Queue 的消息只存在创建该 Queue 的 master 节点上。一个节点挂了，元数据仍可从其他节点访问；但如果挂的是某个 Queue 的 master 节点且没配镜像队列，该 Queue 的消息就丢了。生产环境建议至少 3 节点集群 + Quorum Queue，消息在多数派节点上持久化，挂少数节点不影响。

上图展示了集群的两个核心机制：元数据在所有节点间同步（绿色虚线），但 Classic Queue 的消息实体只存在 master 节点上。消费者连到非 master 节点时请求会路由到 master。底部对比了三种故障场景：无镜像队列丢消息、镜像队列自动切换、Quorum Queue 基于多数派天然容灾。下面用代码实现集群搭建和 Quorum Queue 配置。

## 集群搭建与 Quorum Queue 配置

### Layer 1 — 集群搭建：Erlang Cookie + join_cluster

```bash
# ===== 3 节点集群搭建 =====

# 1. 所有节点使用相同的 Erlang Cookie（集群认证）
# Node A (rabbit@node-a)
echo "my_cluster_cookie" > /var/lib/rabbitmq/.erlang.cookie
chown rabbitmq:rabbitmq /var/lib/rabbitmq/.erlang.cookie
chmod 400 /var/lib/rabbitmq/.erlang.cookie

# 2. 启动 Node A（独立启动）
rabbitmq-server -detached

# 3. Node B 加入集群
# 先停止本地数据库，以磁盘节点身份加入
rabbitmqctl stop_app
rabbitmqctl join_cluster rabbit@node-a    # 默认 disk 节点
rabbitmqctl start_app

# 4. Node C 加入集群
rabbitmqctl stop_app
rabbitmqctl join_cluster rabbit@node-a    # 默认 disk 节点
rabbitmqctl start_app

# 5. 查看集群状态
rabbitmqctl cluster_status
# 输出示例：
# Disk Nodes: rabbit@node-a, rabbit@node-b, rabbit@node-c
# Running Nodes: rabbit@node-a, rabbit@node-b, rabbit@node-c
```

关键点：所有节点必须共享相同的 Erlang Cookie 才能组成集群。`join_cluster` 默认以 disk 节点加入。加入集群前需 `stop_app` 停止本地 RabbitMQ 应用（但不断开 Erlang 节点通信），加入后 `start_app` 恢复。

### Layer 2 — 队列类型对比配置

```java
// ===== Classic Queue（默认，消息不复制）=====
@Bean
public Queue classicOrderQueue() {
    return QueueBuilder.durable("queue.order.classic")
            .build();
    // 消息只存在创建该 Queue 的节点上
    // master 挂了 → 消息丢失（未持久化）或需重启恢复（持久化）
}

// ===== Mirrored Queue（镜像队列，全同步复制）=====
@Bean
public Queue mirroredOrderQueue() {
    return QueueBuilder.durable("queue.order.mirrored")
            .withArgument("x-queue-type", "classic")
            .withArgument("x-ha-policy", "all")           // 所有节点镜像
            .withArgument("x-ha-sync-mode", "automatic")   // 自动同步
            .build();
    // master 挂了 → mirror 自动提升为 master
    // 缺点：全同步性能开销大，脑裂时可能数据不一致
}

// ===== Quorum Queue（推荐，Raft 多数派写入）=====
@Bean
public Queue quorumOrderQueue() {
    return QueueBuilder.durable("queue.order.quorum")
            .withArgument("x-queue-type", "quorum")        // 仲裁队列
            .build();
    // 消息在多数派节点上持久化
    // 挂少数节点不影响，自动选举 Leader，无脑裂风险
}
```

关键点：三种队列类型在集群中的数据分布完全不同。Classic Queue 消息只在单节点；Mirrored Queue 全同步复制到所有镜像节点；Quorum Queue 基于 Raft 多数派写入，兼顾可靠性和性能。生产环境统一用 Quorum Queue。

### Layer 3 — Spring AMQP 连接集群

```yaml
# application.yml — 连接 RabbitMQ 集群
spring:
  rabbitmq:
    addresses: node-a:5672,node-b:5672,node-c:5672   # 集群所有节点
    username: admin
    password: ${RABBITMQ_PASSWORD}
    virtual-host: /production
    # 连接失败自动重连
    connection-timeout: 10000
    # Spring AMQP 自动选择可用节点，单节点挂了自动切换
```

```java
// 生产者/消费者代码无需感知集群拓扑
// Spring AMQP 的 CachingConnectionFactory 内部维护多个节点连接
// 单节点故障时自动 failover 到其他节点

@Service
public class OrderProducer {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendOrder(OrderEvent event) {
        // 连哪个节点无所谓，元数据全集群共享
        // 消息路由到 Queue 所在的 master 节点
        rabbitTemplate.convertAndSend(
                "exchange.order",
                "order.created",
                event);
    }
}
```

关键点：Spring AMQP 配置集群地址列表后，客户端代码无需任何改动。`CachingConnectionFactory` 内部维护多个节点连接，自动 failover。消费者连到非 master 节点时，Broker 内部透明路由消息到 master 节点。

### Layer 4 — 节点故障演练

```bash
# ===== 模拟节点故障 =====

# 查看各节点上的 Queue 分布
rabbitmqctl list_queues name type pid node messages

# 模拟 Node B 宕机
rabbitmqctl -n rabbit@node-b stop_app

# 集群状态：Node B 离线，Node A 和 C 仍正常
rabbitmqctl cluster_status
# Running Nodes: rabbit@node-a, rabbit@node-c
# （rabbit@node-b 已不在列表）

# Classic Queue（master 在 Node B）→ 消息不可用
# Quorum Queue → 多数派仍存活（A+C），正常读写
rabbitmqctl list_queues name type messages

# 恢复 Node B
rabbitmqctl -n rabbit@node-b start_app
# Node B 重新加入集群，自动同步缺失的数据
```

关键点：Quorum Queue 在少数节点宕机时仍能正常工作（3 节点挂 1 个）。恢复后自动追赶落后的日志。Classic Queue 如果 master 节点挂了且无镜像，消息直接不可用。

## Classic Queue vs Mirrored Queue vs Quorum Queue

| 维度 | Classic Queue | Mirrored Queue | Quorum Queue |
|---|---|---|---|
| 消息分布 | 单节点（master） | 全节点镜像复制 | 多数派持久化（Raft） |
| 节点故障 | master 挂了消息丢 | mirror 提升为 master | 少数派挂了不影响 |
| 数据一致性 | 无保证 | 全同步（可能脑裂） | Raft 多数派（无脑裂） |
| 性能 | 最高（无复制开销） | 中（全同步开销） | 中高（多数派写入） |
| 持久化 | 可选（deliveryMode） | 可选 | 强制持久化 |
| 推荐度 | 仅开发/测试 | 逐步废弃 | 生产推荐 |
| 最少节点 | 1 | 2+ | 3（建议奇数） |

> 面试要点：RabbitMQ 集群的核心特点是「元数据共享，消息默认不复制」。Classic Queue 消息只在 master 节点，挂了就丢；Mirrored Queue 全同步但有脑裂风险；Quorum Queue 基于 Raft 多数派写入，挂少数节点不丢数据，是生产环境的标准选择。至少 3 节点集群 + Quorum Queue。

## 一句话总结

**一句话总结：RabbitMQ 集群是「元数据全共享、消息看队列类型」——Classic Queue 消息只待在 master 节点上（挂了就丢），Quorum Queue 用 Raft 多数派写入让消息在多数节点上持久化（挂少数不丢），生产环境至少 3 节点 + Quorum Queue 才是正解。**
