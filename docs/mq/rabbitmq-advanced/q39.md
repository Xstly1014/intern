# Q39 消息追踪

线上消息丢失排查的核心工具是 **firehose 追踪**（`rabbitmqctl trace_on`，开启后 Broker 把所有消息的副本发到 `amq.rabbitmq.trace` Exchange，订阅即可查看所有进出消息）。辅助工具包括 Management Plugin（Web UI 查看 Queue 消息数/unacked 数）、`rabbitmqctl list_queues`（命令行查看队列状态）、日志查看。排查思路是全链路确认：生产者是否收到 confirm ack → Queue 是否有消息 → 消费者是否 ACK → 是否有 DLX 拦截。注意 firehose 性能开销大，排查完必须关掉。

## 消息追踪排查代码

### Layer 1 — Firehose 追踪：开启与消费

```bash
# ===== Firehose 追踪操作 =====

# 1. 开启 firehose（临时开启，重启后失效）
rabbitmqctl trace_on

# 2. 在另一个终端，用 rabbitmqadmin 或代码订阅 amq.rabbitmq.trace
#    这个 Exchange 是 topic 类型，routing key 为：
#    - publish.<exchange_name>  消息被发布时
#    - deliver.<queue_name>     消息被投递给消费者时

# 3. 查看所有进出消息
rabbitmqadmin get queue=amq.rabbitmq.trace ackmode=ack_requeue_true count=10

# 4. 排查完毕，立即关闭 firehose（重要！）
rabbitmqctl trace_off
```

```java
// ===== Java 代码订阅 trace Exchange 查看消息流转 =====

@Component
public class TraceConsumer {

    // 订阅 firehose trace Exchange，查看所有进出 Broker 的消息
    @RabbitListener(bindings = @QueueBinding(
            value = @org.springframework.amqp.rabbit.annotation.Queue(
                    value = "queue.debug.trace", durable = "false", autoDelete = "true"),
            exchange = @Exchange(value = "amq.rabbitmq.trace", type = "topic"),
            key = "#"))  // # 匹配所有 routing key
    public void trace(Message message) {
        String routingKey = message.getMessageProperties().getReceivedRoutingKey();
        // routingKey 格式：publish.<exchange> 或 deliver.<queue>

        if (routingKey.startsWith("publish.")) {
            // 消息被发布到 Broker
            String exchange = routingKey.substring("publish.".length());
            log.info("[TRACE] 消息发布到 exchange={}, body={}",
                    exchange, new String(message.getBody()));
        } else if (routingKey.startsWith("deliver.")) {
            // 消息被投递给消费者
            String queue = routingKey.substring("deliver.".length());
            log.info("[TRACE] 消息投递到 queue={}, body={}",
                    queue, new String(message.getBody()));
        }
    }
}
```

关键点：`trace_on` 开启后 Broker 把每条进出消息的副本发到 `amq.rabbitmq.trace` Exchange（topic 类型）。routing key 为 `publish.<exchange>` 或 `deliver.<queue>`，可以区分消息是「发布进来」还是「投递出去」。注意 firehose 会复制所有消息，性能开销大，排查完必须 `trace_off`。

### Layer 2 — Management Plugin 与 rabbitmqctl 排查

```bash
# ===== Management Plugin 排查（Web UI: http://broker:15672）=====

# Queues 页面查看：
# - messages: 队列中的消息总数
# - messages_ready: 待消费的消息数
# - messages_unacknowledged: 已投递但未 ACK 的消息数
# - consumers: 消费者数量
# 如果 messages_unacknowledged 持续增长 → 消费者处理太慢或没 ACK

# ===== rabbitmqctl 命令行排查 =====

# 查看各队列消息数和 unacked 数
rabbitmqctl list_queues name messages messages_ready \
  messages_unacknowledged consumers

# 输出示例：
# name                   messages  messages_ready  unacked  consumers
# queue.order            0         0               0        5         ← 正常
# queue.payment          15000     15000           0        0         ← 堆积！无消费者
# queue.notification     0         0               800      3         ← unacked 堆积！

# 查看 Exchange 消息流入流出速率
rabbitmqctl list_exchanges name messages_in messages_out

# 查看连接状态
rabbitmqctl list_connections name state channels
# state=blocked → 被 flow control 阻塞

# 查看 Channel 状态
rabbitmqctl list_channels pid number consumer_count \
  messages_unacknowledged
```

关键点：`list_queues` 是排查消息丢失/堆积的起点——先看 `messages` 是否为 0（消息是否到 Queue），再看 `messages_unacknowledged` 是否持续增长（消费者是否 ACK），最后看 `consumers` 是否为 0（是否有消费者）。

### Layer 3 — 全链路排查代码

```java
// ===== 全链路排查：生产者 → Queue → 消费者 → DLX =====

// 1. 确认生产者收到 confirm ack
@Service
public class OrderProducer {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    private final Set<String> unconfirmed = ConcurrentHashMap.newKeySet();

    public void sendOrder(OrderEvent event) {
        String msgId = event.getOrderId();
        unconfirmed.add(msgId);

        CorrelationData correlationData = new CorrelationData(msgId);
        rabbitTemplate.convertAndSend(
                "exchange.order", "order.created", event, correlationData);
        // 如果 ConfirmCallback 回调 ack=true → 消息到达 Broker
        // 如果 ack=false → 消息没到 Broker，需重发
    }

    // ConfirmCallback 回调
    @PostConstruct
    public void init() {
        rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
            if (correlationData != null) {
                String msgId = correlationData.getId();
                if (ack) {
                    unconfirmed.remove(msgId);
                    log.info("消息确认到达 Broker: {}", msgId);
                } else {
                    log.error("消息未到达 Broker: {}, cause: {}", msgId, cause);
                    // 这里就知道消息在生产者 → Broker 环节丢了
                }
            }
        });
    }
}

// 2. 确认消费者 ACK（检查 unacked 是否持续增长）
@Component
public class OrderConsumer {

    @RabbitListener(queues = "queue.order")
    public void handle(OrderEvent event, Channel channel,
                       @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        try {
            orderService.process(event);
            channel.basicAck(tag, false);
            log.debug("消息 ACK 成功: {}", event.getOrderId());
        } catch (Exception e) {
            log.error("消息处理失败，nack: {}", event.getOrderId(), e);
            // 如果这里没 ack/nack → 消息一直 unacked → Broker 内存堆积
            channel.basicNack(tag, false, false);
        }
    }
}

// 3. 确认是否有 DLX 拦截（检查死信队列）
@Component
public class DeadLetterConsumer {

    @RabbitListener(queues = "queue.order.dlq")
    public void handleDeadLetter(OrderEvent event, Message message) {
        String reason = (String) message.getMessageProperties()
                .getHeader("x-death");
        log.error("消息进入死信队列: orderId={}, reason={}",
                event.getOrderId(), reason);
        // x-death 头信息包含：
        // - queue: 原队列名
        // - reason: 死信原因（expired/rejected/maxlen）
        // - time: 进入死信的时间
        // 这里可以判断消息是 TTL 过期、被拒绝还是超过队列长度上限
    }
}
```

关键点：全链路排查的四个环节用代码闭环：生产者的 `ConfirmCallback` 确认消息到 Broker、`list_queues` 确认 Queue 有消息、消费者的 `basicAck` 确认消费成功、死信队列消费者检查是否有消息被 DLX 拦截。任何一个环节断了，就是消息丢失的根因。

## 四种排查工具对比

| 工具 | 适用场景 | 性能开销 | 优势 | 劣势 |
|---|---|---|---|---|
| Firehose | 精确追踪单条消息流转 | 极大（复制所有消息） | 看到所有进出消息 | 必须排查完关掉 |
| Management UI | 日常监控、快速定位 | 小 | 直观、实时 | 仅看聚合数据 |
| rabbitmqctl | 脚本化监控、自动化 | 小 | 命令行、可编排 | 无历史趋势 |
| 日志 | 异常排查、根因定位 | 无 | 记录所有异常 | 需手动搜索 |

> 面试要点：消息丢失排查的核心工具是 firehose（`trace_on` 开启后 Broker 把所有消息副本发到 `amq.rabbitmq.trace` Exchange）。排查思路是全链路确认：生产者 confirm ack → Queue messages 数 → 消费者 basicAck → DLX 死信队列。firehose 性能开销大，排查完必须 `trace_off`。日常监控用 Management UI + rabbitmqctl。

## 一句话总结

**一句话总结：消息丢失排查就是「全链路逐段确认」——生产者 confirm ack 确认到 Broker、`list_queues` 确认 Queue 有消息、消费者 basicAck 确认消费成功、死信队列确认没被 DLX 拦截，firehose 是精确追踪单条消息的核武器但排查完必须关。**
