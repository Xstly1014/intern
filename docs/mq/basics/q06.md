# Q6 消息队列对比选型

选型看四个核心维度：**吞吐量、延迟、可靠性、功能特性**。Kafka 吞吐最高适合日志和流处理；RabbitMQ 延迟最低、路由最丰富适合业务消息；RocketMQ 兼顾高吞吐和事务消息适合电商交易；ActiveMQ 是老牌产品但新项目不建议使用。

上图按"吞吐量"和"延迟"两个维度定位了四大 MQ 的位置。RabbitMQ 在左上角（低延迟低吞吐），Kafka 在右下角（高吞吐高延迟），RocketMQ 在中间偏右（兼顾），ActiveMQ 在左下角（都不突出）。下面用代码看每种 MQ 的典型用法。

## RabbitMQ — 低延迟业务消息

### 生产者层 — Exchange 路由，支持复杂路由规则

```java
@Service
public class OrderService {
    @Autowired private RabbitTemplate rabbitTemplate;

    public void publishOrderEvent(Order order) {
        // Direct Exchange：按 routing key 精确路由
        rabbitTemplate.convertAndSend(
            "order.exchange",           // Exchange
            "order.created.premium",    // routing key（可支持通配符）
            new OrderCreatedEvent(order)
        );
        // 特点：微秒级延迟，丰富的 Exchange 类型（Direct/Topic/Fanout/Headers）
    }
}
```

适用场景：订单事件分发、任务队列、RPC 调用。延迟低到微秒级，但单机吞吐万级 TPS。

## Kafka — 高吞吐日志流处理

### 生产者层 — 批量发送，追求吞吐

```java
@Service
public class LogService {
    @Autowired private KafkaTemplate<String, String> kafkaTemplate;

    public void sendLog(LogEntry log) {
        // 写入 Topic，Kafka 会批量发送 + 压缩
        kafkaTemplate.send("app.logs", log.getPartitionKey(), log.toJson());
        // 特点：批量发送 + 顺序写盘 + 零拷贝，单机百万级 TPS
    }
}

// 配置：批量发送参数
props.put("batch.size", 16384);              // 批次大小 16KB
props.put("linger.ms", 5);                   // 最多等 5ms 凑批
props.put("compression.type", "lz4");        // 压缩减少网络开销
```

适用场景：日志收集、用户行为追踪、实时流处理。吞吐极高但延迟在毫秒级（批量发送需要等凑批）。

## RocketMQ — 事务消息 + 电商场景

### 生产者层 — 支持事务消息，确保本地事务和消息发送原子性

```java
@Service
public class TradeService {
    @Autowired private TransactionMQProducer producer;

    public void sendTradeMessage(TradeOrder order) {
        Message msg = new Message("trade.topic", "pay",
            order.getId(), order.toJson().getBytes());

        // 事务消息：先发半消息 → 执行本地事务 → 根据结果 commit/rollback
        producer.sendMessageInTransaction(msg, new LocalTransactionExecutor() {
            @Override
            public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
                // 执行本地数据库事务
                tradeRepo.save(order);
                return LocalTransactionState.COMMIT_MESSAGE;  // 本地事务成功 → commit 消息
            }
        });
    }
}
```

适用场景：电商交易、金融转账、需要分布式事务保证的场景。十万级 TPS + 事务消息是核心优势。

## ActiveMQ — 老牌但新项目不推荐

### 生产者层 — JMS 标准实现，API 成熟但性能瓶颈

```java
@Service
public class LegacyService {
    @Autowired private JmsTemplate jmsTemplate;

    public void sendLegacyMessage(String message) {
        // 标准 JMS API，学习成本低
        jmsTemplate.convertAndSend("legacy.queue", message);
        // 问题：万级 TPS，底层架构老，社区活跃度下降
    }
}
```

适用场景：遗留系统维护、JMS 标准兼容需求。新项目建议选 RabbitMQ 或 Kafka 替代。

## 四大 MQ 全维度对比

| 维度 | RabbitMQ | Kafka | RocketMQ | ActiveMQ |
|---|---|---|---|---|
| 开发语言 | Erlang | Scala/Java | Java | Java |
| 单机吞吐量 | 万级 TPS | 百万级 TPS | 十万级 TPS | 万级 TPS |
| 消息延迟 | μs 级 | ms 级 | ms 级 | ms 级 |
| 消息模型 | Queue + Exchange | Topic + Partition | Topic + Queue | Queue + Topic |
| 消费模式 | 推模式 Push | 拉模式 Pull | 拉模式 Pull | 推/拉均支持 |
| 事务消息 | 不支持 | 支持（较重） | 原生支持（轻量） | 支持 |
| 消息顺序 | 单 Queue 有序 | 单 Partition 有序 | 单 Queue 有序 | 不保证 |
| 消息回溯 | 不支持 | 支持（按 offset） | 支持（按时间） | 不支持 |
| 路由能力 | 极强（4 种 Exchange） | 弱（Topic 分区） | 一般（Tag + SQL92） | 一般 |
| 运维复杂度 | 中等 | 较高（依赖 ZK/KRaft） | 中等 | 低 |
| 最佳场景 | 业务消息、低延迟 | 日志、流处理、大数据 | 电商、金融事务 | 遗留系统 |

**In one sentence: 选型就是在"快"和"多"之间做取舍——RabbitMQ 快但量小适合业务消息，Kafka 多但慢适合日志流处理，RocketMQ 在中间还送了事务消息的礼物适合电商，ActiveMQ 是昨天的明星今天别再请上台了。**
