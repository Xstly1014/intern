# Q12 消息积压本质

消息积压的本质就一句话：**生产速度持续大于消费速度**。原因只有三类：消费者处理太慢（代码慢、下游慢）、消费者挂了（宕机、OOM、频繁异常重试）、消费能力不足（分区数不够、并发度太低）。排查链路：先看积压量趋势 → 再看消费者状态 → 最后定位是代码慢还是下游慢。

## 监控层 — 及时发现积压

### Kafka 积压监控 — 对比 LEO 和消费 offset

```java
// Kafka 积压 = Partition 的 LEO（最新 offset） - Consumer Group 的 committed offset
// 监控代码示例：定时拉取积压量

@Scheduled(fixedRate = 30000)  // 每 30 秒检查一次
public void monitorLag() {
    // 获取 Topic 所有 Partition 的 LEO
    Map<TopicPartition, Long> endOffsets = kafkaConsumer.endOffsets(partitions);

    for (Map.Entry<TopicPartition, Long> entry : endOffsets.entrySet()) {
        TopicPartition tp = entry.getKey();
        long endOffset = entry.getValue();
        long committedOffset = kafkaConsumer.committed(tp).offset();
        long lag = endOffset - committedOffset;  // 积压量

        if (lag > THRESHOLD) {
            alertService.send("积压告警: " + tp + " lag=" + lag);
        }
    }
}
```

### RabbitMQ 积压监控 — 看 Queue 消息数

```java
// RabbitMQ 积压 = Queue 中的 Ready 消息数 + Unacked 消息数
// 通过 RabbitMQ Management API 获取

@Scheduled(fixedRate = 30000)
public void monitorQueueDepth() {
    QueueInfo queue = rabbitAdmin.getQueueInfo("order.queue");
    long readyMessages = queue.getMessageCount();      // 待消费
    long unackedMessages = queue.getConsumersUsing();   // 处理中

    if (readyMessages > THRESHOLD) {
        alertService.send("积压告警: order.queue ready=" + readyMessages);
    }
}
```

## 解决方案一：消费者处理太慢 → 优化消费逻辑

### Before — 逐条处理 + 慢 DB 查询

```java
@RabbitListener(queues = "order.queue")
public void handle(OrderEvent event) {
    // 每条消息查一次 DB，耗时 100ms → TPS = 10
    User user = userRepo.findById(event.getUserId());     // 50ms
    Product product = productRepo.findById(event.getProductId());  // 50ms
    processOrder(event, user, product);
}
```

### After — 批量处理 + 缓存优化

```java
@RabbitListener(queues = "order.queue", concurrency = "10")  // 10 个并发消费者
public void handle(List<OrderEvent> events) {
    // 批量查询，一次查 N 个用户和商品
    Set<Long> userIds = events.stream().map(OrderEvent::getUserId).collect(toSet());
    Map<Long, User> userMap = userRepo.findByIdIn(userIds);     // 一次查询，均摊 5ms

    // 批量处理 → TPS 从 10 提升到 500+
    events.forEach(event -> {
        User user = userMap.get(event.getUserId());
        processOrder(event, user);
    });
}
```

关键变化：从逐条查 DB 改为批量查询 + 并发消费者，TPS 从 10 提升到 500+。

## 解决方案二：消费者挂了 → 快速恢复

### 异常处理 — 防止无限重试堵死消费

```java
@RabbitListener(queues = "order.queue")
public void handle(OrderEvent event, Channel channel, @Header(AmqpHeaders.DELIVERY_TAG) long tag)
        throws IOException {
    try {
        processOrder(event);
        channel.basicAck(tag, false);
    } catch (BusinessException e) {
        // 业务异常 → 不重试，直接进死信队列
        channel.basicReject(tag, false);  // requeue=false → 进死信队列
    } catch (Exception e) {
        // 系统异常 → 有限重试（3 次），超过进死信
        int retryCount = getRetryCount(event);
        if (retryCount < 3) {
            channel.basicNack(tag, false, true);  // requeue=true，重试
        } else {
            channel.basicReject(tag, false);  // 超过 3 次 → 死信
            alertService.send("消息重试超限，进入死信: " + event.getMessageId());
        }
    }
}
```

## 三类原因对比

| 原因类型 | 典型表现 | 排查方法 | 解决方案 |
|---|---|---|---|
| 消费者处理太慢 | TPS 低、单条耗时高 | 看消费耗时分布、GC 日志 | 批量处理、缓存、优化 DB 查询 |
| 消费者挂了 | 消费者数为 0 或频繁重启 | 看服务健康检查、OOM 日志 | 修复异常、限制重试次数、死信兜底 |
| 消费能力不足 | 消费者活着但 TPS 到瓶颈 | 看 Partition/Consumer 比例 | 增加 Partition、增加 Consumer 实例 |
| 临时应急 | 突发流量导致积压 | 看积压增长速率 | 限流降级 + 临时扩容消费者 |

**In one sentence: 消息积压的本质就是"进水管比出水管粗"——生产速度持续大于消费速度，要么拧小进水管（限流），要么换粗出水管（扩容消费者 + 优化消费逻辑），排查时顺着"积压在涨吗 → 消费者活着吗 → TPS 够吗 → 慢在哪"四步走就能定位根因。**
