# Q11 消息幂等性

消息重复的根因是**网络不可靠 + ACK 机制**：消费者处理完了但 ACK 没送到 Broker → Broker 认为没消费 → 重投。幂等性的核心是让消费者**对同一条消息处理多次的效果等于处理一次**。工程上三种方案：唯一 ID 去重（Redis SETNX）、数据库唯一约束、状态机校验。

上图上半部分展示重复消费的根因链路，下半部分三种解法。核心思路是：既然 ACK 一定会丢、消息一定会重复，那就让消费者"处理两次和一次的效果一样"。下面用代码落地三种方案。

## 方案一：唯一 ID 去重（Redis SETNX）

### Consumer 层 — Redis 判断是否已处理

```java
@Component
@RabbitListener(queues = "order.points")
public class PointsConsumer {
    @Autowired private RedisTemplate<String, String> redisTemplate;
    @Autowired private PointsService pointsService;

    @RabbitHandler
    public void handle(OrderCreatedEvent event, Channel channel,
                       @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        String idempotentKey = "idempotent:points:" + event.getMessageId();

        // SETNX：key 不存在则设置成功返回 true，已存在返回 false
        // TTL 设置原则：消息最大处理周期的 2 倍（如消息最多可能被重投 12 小时，TTL 设 24 小时）
        Boolean isFirst = redisTemplate.opsForValue()
            .setIfAbsent(idempotentKey, "1", 24, TimeUnit.HOURS);

        if (Boolean.TRUE.equals(isFirst)) {
            // 第一次处理 → 正常执行
            pointsService.addPoints(event.getUserId(), event.getPoints());
        } else {
            // 已处理过 → 直接 ACK，不重复执行
            log.warn("消息 {} 已处理过，跳过", event.getMessageId());
        }
        channel.basicAck(tag, false);
    }
}
```

关键点：每条消息必须带唯一 `messageId`（UUID 或 业务 ID + 类型），作为去重 key。Redis 过期时间设 24 小时，覆盖消息重投的时间窗口。

## 方案二：数据库唯一约束

### 数据层 — 唯一索引兜底

```java
// 数据库表：points_record
// CREATE TABLE points_record (
//   id BIGINT PRIMARY KEY,
//   order_id VARCHAR(64) NOT NULL,
//   user_id BIGINT NOT NULL,
//   points INT NOT NULL,
//   UNIQUE KEY uk_order_id (order_id)  -- 订单 ID 唯一约束
// );

@Component
@RabbitListener(queues = "order.points")
public class PointsConsumer {
    @Autowired private PointsRecordRepo pointsRecordRepo;

    @RabbitHandler
    public void handle(OrderCreatedEvent event) {
        try {
            PointsRecord record = new PointsRecord();
            record.setOrderId(event.getOrderId());  // 唯一约束字段
            record.setUserId(event.getUserId());
            record.setPoints(event.getPoints());
            pointsRecordRepo.save(record);  // 重复 order_id → 抛 DuplicateKeyException
        } catch (DuplicateKeyException e) {
            // 唯一约束冲突 → 说明已处理过 → 吞掉异常，幂等返回
            log.warn("订单 {} 积分已发放，跳过", event.getOrderId());
        }
    }
}
```

关键点：即使 Redis 挂了，数据库唯一约束也能兜住。`order_id` 作为天然幂等键，重复插入直接报错。

## 方案三：状态机校验

### 业务层 — 更新前检查状态

```java
@Component
@RabbitListener(queues = "order.payment")
public class PaymentConsumer {
    @Autowired private OrderRepository orderRepo;

    @RabbitHandler
    public void handle(PaymentEvent event) {
        Order order = orderRepo.findById(event.getOrderId()).orElseThrow();

        // 状态机校验：只有 UNPAID 状态才能变成 PAID
        if (order.getStatus() == OrderStatus.UNPAID) {
            order.setStatus(OrderStatus.PAID);
            order.setPaidAt(LocalDateTime.now());
            orderRepo.save(order);
            // 第一次处理 → 状态从 UNPAID → PAID
        } else {
            // 已是 PAID 状态 → 跳过，天然幂等
            log.info("订单 {} 状态为 {}，跳过支付回调", event.getOrderId(), order.getStatus());
        }
    }
}
```

关键点：利用业务状态的不可逆性。`UNPAID → PAID` 只能发生一次，重复消息进来时状态已经是 `PAID`，自然跳过。但"先查再改"有并发风险，可用乐观锁替代。

## 方案四：数据库乐观锁 — 原子更新防并发

### 数据层 — 单条 UPDATE 利用版本号防重复

```java
// 乐观锁：直接在 UPDATE 语句中加条件，原子操作无需先查询
@RabbitListener(queues = "order.payment")
public void handle(PaymentEvent event) {
    // 利用 status 作为版本条件：只有 status=0（未支付）时才能更新
    int affected = orderRepo.updateStatusToPaid(
        event.getOrderId(),        // WHERE id = ?
        OrderStatus.UNPAID.val()   // AND status = 0
    );
    // SQL: UPDATE order SET status=1, paid_at=NOW() WHERE id=? AND status=0

    if (affected == 0) {
        // 影响行数=0 → 说明 status 已经不是 0 → 已处理过 → 幂等跳过
        log.info("订单 {} 已支付，跳过重复回调", event.getOrderId());
    }
}
```

关键点：与方案三的"先查再改"不同，乐观锁把状态判断放进 SQL 的 WHERE 条件里，数据库行锁保证原子性，不会出现两个消费者同时查到 `UNPAID` 然后都更新的并发问题。

## 方案五：Token 机制 — 接口层令牌校验

### 接口层 — 前置生成 Token，消费时验证

```java
// 1. 业务发起方先申请 Token（如订单创建时生成）
public String createOrderToken(Order order) {
    String token = UUID.randomUUID().toString();
    redisTemplate.opsForValue().set("order:token:" + token, "1", 10, TimeUnit.MINUTES);
    return token;
}

// 2. 消费者处理时校验 Token 并删除（原子操作）
@RabbitListener(queues = "order.process")
public void handle(OrderEvent event) {
    String tokenKey = "order:token:" + event.getToken();
    
    // DEL 命令返回删除的 key 数量：1=首次（Token 存在），0=重复（Token 已删）
    Boolean isFirst = redisTemplate.delete(tokenKey);
    
    if (Boolean.TRUE.equals(isFirst)) {
        processOrder(event);  // Token 存在 → 首次处理
    } else {
        log.warn("Token {} 已被消费，跳过", event.getToken());
    }
}
```

关键点：Token 机制适用于接口防重场景（如支付回调、表单提交），和 Redis SETNX 思路类似但更强调"一次性令牌"——用完即删，天然防重。

## 五种幂等方案对比

| 维度 | Redis SETNX 去重 | 数据库唯一约束 | 状态机校验 | 数据库乐观锁 | Token 机制 |
|---|---|---|---|---|---|
| 实现层 | 缓存层 | 数据库层 | 业务层 | 数据库层 | 缓存层 |
| 可靠性 | 中（Redis 挂了失效） | 高（数据库兜底） | 高（业务逻辑保证） | 高（行锁保证原子） | 中（依赖 Redis） |
| 性能 | 高（Redis 内存操作） | 中（数据库 IO） | 中（需先查询状态） | 高（单条 UPDATE） | 高（Redis DEL） |
| 通用性 | 高（任何消息都能用） | 中（需要唯一业务 ID） | 低（需要有状态流转） | 中（需要版本字段） | 高（适用于接口防重） |
| 并发安全 | 是（SETNX 原子） | 是（唯一约束） | 否（先查再改有间隙） | 是（WHERE 条件原子） | 是（DEL 原子） |
| 推荐组合 | 第一层快速拦截 | 第二层兜底 | 有状态业务额外加 | 状态机替代方案 | 接口防重场景 |

**In one sentence: 消息幂等性就是让"处理两次等于处理一次"——根因是 ACK 丢了 Broker 会重投，解法是 Redis SETNX 快速拦截 + 数据库唯一约束/乐观锁兜底 + 状态机校验业务层防护 + Token 机制接口防重，TTL 设为消息最大处理周期的 2 倍，多层保险让重复消息无论从哪条路进来都不会产生副作用。**
