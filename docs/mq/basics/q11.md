# Q11 消息幂等性

消息重复的根因是**网络不可靠 + ACK 机制**：消费者处理完了但 ACK 没送到 Broker → Broker 认为没消费 → 重投。幂等性的核心是让消费者**对同一条消息处理多次的效果等于处理一次**。工程上三种方案：唯一 ID 去重（Redis SETNX）、数据库唯一约束、状态机校验。

上图上半部分展示重复消费的根因链路，下半部分三种解法。核心思路是：既然 ACK 一定会丢、消息一定会重复，那就让消费者"处理两次和一次的效果一样"。下面用代码落地三种方案。

## 方案一：唯一 ID 去重（Redis SETNX）

### Consumer 层 — Redis 判断是否已处理

```java
@Component
@RabbitListener(queues = "order.points")
public class PointsConsumer {
    @Autowired private RedisTemplate<String, String> redisTemplate;
    @Autowired private PointsService pointsService;

    @RabbitHandler
    public void handle(OrderCreatedEvent event, Channel channel,
                       @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        String idempotentKey = "idempotent:points:" + event.getMessageId();

        // SETNX：key 不存在则设置成功返回 true，已存在返回 false
        Boolean isFirst = redisTemplate.opsForValue()
            .setIfAbsent(idempotentKey, "1", 24, TimeUnit.HOURS);

        if (Boolean.TRUE.equals(isFirst)) {
            // 第一次处理 → 正常执行
            pointsService.addPoints(event.getUserId(), event.getPoints());
        } else {
            // 已处理过 → 直接 ACK，不重复执行
            log.warn("消息 {} 已处理过，跳过", event.getMessageId());
        }
        channel.basicAck(tag, false);
    }
}
```

关键点：每条消息必须带唯一 `messageId`（UUID 或 业务 ID + 类型），作为去重 key。Redis 过期时间设 24 小时，覆盖消息重投的时间窗口。

## 方案二：数据库唯一约束

### 数据层 — 唯一索引兜底

```java
// 数据库表：points_record
// CREATE TABLE points_record (
//   id BIGINT PRIMARY KEY,
//   order_id VARCHAR(64) NOT NULL,
//   user_id BIGINT NOT NULL,
//   points INT NOT NULL,
//   UNIQUE KEY uk_order_id (order_id)  -- 订单 ID 唯一约束
// );

@Component
@RabbitListener(queues = "order.points")
public class PointsConsumer {
    @Autowired private PointsRecordRepo pointsRecordRepo;

    @RabbitHandler
    public void handle(OrderCreatedEvent event) {
        try {
            PointsRecord record = new PointsRecord();
            record.setOrderId(event.getOrderId());  // 唯一约束字段
            record.setUserId(event.getUserId());
            record.setPoints(event.getPoints());
            pointsRecordRepo.save(record);  // 重复 order_id → 抛 DuplicateKeyException
        } catch (DuplicateKeyException e) {
            // 唯一约束冲突 → 说明已处理过 → 吞掉异常，幂等返回
            log.warn("订单 {} 积分已发放，跳过", event.getOrderId());
        }
    }
}
```

关键点：即使 Redis 挂了，数据库唯一约束也能兜住。`order_id` 作为天然幂等键，重复插入直接报错。

## 方案三：状态机校验

### 业务层 — 更新前检查状态

```java
@Component
@RabbitListener(queues = "order.payment")
public class PaymentConsumer {
    @Autowired private OrderRepository orderRepo;

    @RabbitHandler
    public void handle(PaymentEvent event) {
        Order order = orderRepo.findById(event.getOrderId()).orElseThrow();

        // 状态机校验：只有 UNPAID 状态才能变成 PAID
        if (order.getStatus() == OrderStatus.UNPAID) {
            order.setStatus(OrderStatus.PAID);
            order.setPaidAt(LocalDateTime.now());
            orderRepo.save(order);
            // 第一次处理 → 状态从 UNPAID → PAID
        } else {
            // 已是 PAID 状态 → 跳过，天然幂等
            log.info("订单 {} 状态为 {}，跳过支付回调", event.getOrderId(), order.getStatus());
        }
    }
}
```

关键点：利用业务状态的不可逆性。`UNPAID → PAID` 只能发生一次，重复消息进来时状态已经是 `PAID`，自然跳过。

## 三种幂等方案对比

| 维度 | Redis SETNX 去重 | 数据库唯一约束 | 状态机校验 |
|---|---|---|---|
| 实现层 | 缓存层 | 数据库层 | 业务层 |
| 可靠性 | 中（Redis 挂了失效） | 高（数据库兜底） | 高（业务逻辑保证） |
| 性能 | 高（Redis 内存操作） | 中（数据库 IO） | 中（需先查询状态） |
| 通用性 | 高（任何消息都能用） | 中（需要唯一业务 ID） | 低（需要有状态流转） |
| 复杂度 | 低 | 中 | 中 |
| 推荐组合 | 第一层 | 第二层兜底 | 有状态业务额外加 |

**In one sentence: 消息幂等性就是让"处理两次等于处理一次"——根因是 ACK 丢了 Broker 会重投，解法是用 Redis SETNX 快速拦截 + 数据库唯一约束兜底 + 状态机校验业务层防护，三层保险让重复消息无论从哪条路进来都不会产生副作用。**
