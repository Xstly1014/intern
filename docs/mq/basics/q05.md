# Q5 推模式 vs 拉模式

推模式是 Broker 主动把消息推给消费者，消费者被动接收；拉模式是消费者主动向 Broker 请求消息，Broker 被动响应。RabbitMQ 用推模式（Broker 主动 `Basic.Deliver`），Kafka 用拉模式（消费者 `poll()` 主动拉取）。

上图核心区别在"谁主动"：推模式中 Broker 掌握主动权，有消息就推给消费者；拉模式中消费者掌握主动权，按自己的节奏去拉。下面用代码看两种模式的实际写法差异。

## RabbitMQ 推模式 — Broker 主动推送

### Consumer 层 — 被 `@RabbitListener` 回调，无需主动请求

```java
@Component
public class OrderConsumer {
    // RabbitMQ Broker 有消息就主动推过来，触发这个方法
    // 消费者不需要主动请求，被动等待回调
    @RabbitListener(queues = "order.created.queue")
    public void handle(OrderCreatedEvent event) {
        // Broker 推一条消息 → 这里被调用一次
        processOrder(event);
    }
}
```

### 流控层 — 用 prefetch 限制推送速率

```java
// RabbitMQ 通过 prefetch 控制推多少：消费者"未确认"消息数达到 prefetch 就暂停推送
// SimpleRabbitListenerContainerFactory 配置
factory.setPrefetchCount(50);
// 含义：消费者最多同时持有 50 条未 ACK 的消息
// 超过 50 条 → Broker 停止推送，等消费者 ACK 后再推
```

关键点：推模式下消费者无法拒绝消息——Broker 推了就得收。唯一的安全阀是 `prefetch`，限制"同时在手"的消息数，防止消费者被压垮。

## Kafka 拉模式 — 消费者主动 poll

### Consumer 层 — 主动调用 `poll()` 拉取消息

```java
@Component
public class OrderConsumer {
    private final KafkaConsumer<String, OrderCreatedEvent> consumer;

    // 消费者主动发起拉取请求
    public void startConsuming() {
        consumer.subscribe(Collections.singletonList("order.created"));
        while (true) {
            // 主动 poll：告诉 Broker "给我一批消息"
            ConsumerRecords<String, OrderCreatedEvent> records =
                consumer.poll(Duration.ofMillis(1000));  // 最多等 1 秒

            for (ConsumerRecord<String, OrderCreatedEvent> record : records) {
                processOrder(record.value());
            }

            // 处理完后手动提交 offset
            consumer.commitSync();
        }
    }
}
```

### 批量层 — 一次 poll 拉一批，按自身能力控制速率

```java
// Kafka 消费者可以控制每次拉多少
props.put("max.poll.records", 500);        // 每次 poll 最多 500 条
props.put("fetch.min.bytes", 1024 * 1024); // 至少攒够 1MB 才返回
props.put("fetch.max.wait.ms", 500);       // 最多等 500ms

// 消费者处理慢 → poll 间隔长 → Broker 自然不会塞更多消息
// 消费者处理快 → poll 间隔短 → 自动提高吞吐
```

关键变化：拉模式下消费者完全掌控节奏——处理慢就 `poll` 得少，处理快就 `poll` 得多。Broker 不会主动塞消息，消费者不会被压垮。

## 推 vs 拉对比

| 维度 | 推模式 Push（RabbitMQ） | 拉模式 Pull（Kafka） |
|---|---|---|
| 数据流向 | Broker → Consumer 主动推 | Consumer → Broker 主动拉 |
| 谁掌握主动权 | Broker | Consumer |
| 实时性 | 高，消息到达即推送 | 略低，取决于 poll 间隔 |
| 流控方式 | prefetch 限制同时在手消息数 | 消费者按自身速率 poll |
| 消费者被压垮风险 | 有，prefetch 设大了可能堆积 | 无，消费者按能力拉取 |
| 批量处理 | 不天然支持，逐条推送 | 天然支持，一次 poll 拉一批 |
| 消费者空闲时 | Broker 持续检查，有消息就推 | 消费者不 poll 就不消耗资源 |
| 适用场景 | 低延迟、实时通知 | 高吞吐、日志收集、流处理 |

**In one sentence: 推模式是"Broker 喂你吃，你控制不了嘴张多大"——实时但可能噎着；拉模式是"你自己去取餐台拿，想吃多少拿多少"——吞吐可控但不够实时，RabbitMQ 选了前者追求低延迟，Kafka 选了后者追求高吞吐。**
