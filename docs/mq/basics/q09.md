# Q9 消息投递语义

消息投递有三种语义：**At Most Once**（最多一次，消息可能丢但不会重复——生产者发完不管，消费者读完立即提交 offset）、**At Least Once**（至少一次，消息不会丢但可能重复——生产者重试 + 消费者处理完再 ACK）、**Exactly Once**（精确一次，不丢不重复）。RabbitMQ 默认是 At Least Once（ACK 机制），Kafka 默认也是 At Least Once（acks=all + 手动提交 offset），但 Kafka 通过幂等生产者 + 事务可以实现 Exactly Once（Kafka 0.11+ 支持）。

上图三种语义的可靠性递增，但实现成本也递增。绝大多数业务场景用 At Least Once + 幂等消费就够了，不一定要追求 Exactly Once。下面用代码看 RabbitMQ 和 Kafka 分别怎么配置这些语义。

## RabbitMQ — 默认 At Least Once

### ACK 机制 — 消费者手动确认

```java
// RabbitMQ 默认：At Least Once
// 消费者处理完消息后手动 ACK，未 ACK 的消息会重新入队

@RabbitListener(queues = "order.queue", ackMode = "MANUAL")
public void handle(OrderCreatedEvent event, Channel channel,
                   @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
    try {
        processOrder(event);
        channel.basicAck(tag, false);        // 处理成功 → ACK，Broker 删除消息
    } catch (Exception e) {
        channel.basicNack(tag, false, true); // 处理失败 → NACK + requeue，消息重新入队
        // 风险：如果一直失败 → 消息反复重投 → 重复消费 → 必须做幂等
    }
}
```

### 生产者确认 — 确保消息到达 Broker

```java
// Publisher Confirm：Broker 收到消息后回调确认
rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
    if (!ack) {
        log.error("消息未到达 Broker，原因: {}", cause);
        // 重发
        retryService.resend(correlationData);
    }
});
```

## Kafka — 默认 At Least Once，可升级到 Exactly Once

### At Least Once — acks=all + 手动提交 offset

```java
// Kafka 默认：At Least Once
props.put("acks", "all");                    // 所有副本确认才算发送成功
props.put("enable.auto.commit", "false");     // 手动提交 offset

// 消费者处理完再提交 offset
ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
for (ConsumerRecord<String, String> record : records) {
    processMessage(record.value());
}
consumer.commitSync();  // 处理完才提交 → 如果处理失败不提交 → 下次 poll 重新拉取 → 可能重复
```

### Exactly Once — 幂等生产者 + 事务

```java
// 1. 幂等生产者：防止 Producer 重试导致 Broker 收到重复消息（Kafka 0.11+ 支持）
props.put("enable.idempotence", "true");  // Kafka 自动去重（基于 PID + SeqNumber）

// 2. 事务消息：生产者发送 + offset 提交在一个事务里
producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("order.created", order.toJson()));

    // 消费者侧：处理消息 + 提交 offset 在同一事务
    producer.sendOffsetsToTransaction(
        new OffsetAndMetadata(record.offset() + 1), "consumer-group");
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
}
```

## 三种语义对比

| 维度 | At Most Once | At Least Once | Exactly Once |
|---|---|---|---|
| 消息丢失 | 可能丢 | 不会丢 | 不会丢 |
| 消息重复 | 不会重复 | 可能重复 | 不会重复 |
| 实现机制 | fire and forget | ACK + 重试 | 幂等 + 事务 |
| 性能开销 | 最低 | 中等 | 最高 |
| RabbitMQ | autoAck=true | 手动 ACK + Confirm | 不原生支持 |
| Kafka | acks=0 | acks=all + 手动 commit | idempotence + 事务 |
| 适用场景 | 监控指标、日志 | 订单、支付（+幂等） | 金融转账、精确计数 |

**In one sentence: 消息投递语义是可靠性和成本的阶梯——At Most Once 是"发了就不管"可能丢消息，At Least Once 是"没确认就重发"可能重复但配合幂等能覆盖 99% 场景，Exactly Once 是"幂等+事务双重保险"最可靠但成本最高，工程上通常选 At Least Once + 幂等消费作为性价比最优解。**
