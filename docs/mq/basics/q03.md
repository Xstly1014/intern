# Q3 同步 vs 异步

判断标准只有一句话：**调用方这一刻需不需要拿到结果**。需要→同步（支付扣款、权限校验）；不需要→异步（通知、日志、统计）。再叠加三个辅助判断：下游慢不慢、流量大不大、要不要事务一致，就能覆盖 99% 的决策场景。

上图从上到下四个判断节点，命中任何一个就停止往下走。核心逻辑是"排除法"：先排除必须同步的场景（需要结果、需要事务），剩下的都倾向异步。下面用两个典型场景的代码对比来落地这个判断。

## 场景一：同步 — 支付扣款（必须立即拿到结果）

### Controller 层 — 同步等待银行返回

```java
@RestController
@RequestMapping("/pay")
public class PaymentController {
    @Autowired private PaymentService paymentService;

    @PostMapping
    public Result pay(@RequestBody PaymentDTO dto) {
        // 同步调用：必须等待扣款结果，不能说"排队中稍后通知"
        PaymentResult result = paymentService.charge(dto);
        if (result.isSuccess()) {
            return Result.ok("支付成功");
        }
        return Result.fail("余额不足或扣款失败");
    }
}
```

### Service 层 — 同步调用银行网关，耗时可控但必须等

```java
@Service
public class PaymentService {
    @Autowired private BankGateway bankGateway;

    public PaymentResult charge(PaymentDTO dto) {
        // 同步 HTTP 调用银行网关，耗时 200~800ms
        // 用户在收银台等着，这一步必须等
        return bankGateway.deduct(dto.getCardNo(), dto.getAmount());
    }
}
```

关键点：支付场景**必须同步**——用户在收银台等着"支付成功"或"余额不足"的结论。如果改成异步，用户看到"扣款请求已排队"，根本不知道该不该继续操作。

## 场景二：异步 — 订单通知（不需要等结果）

### Controller 层 — 下单后立即返回

```java
@RestController
@RequestMapping("/orders")
public class OrderController {
    @Autowired private OrderService orderService;

    @PostMapping
    public Result create(@RequestBody OrderDTO dto) {
        orderService.createOrder(dto.toOrder());
        return Result.ok("下单成功");  // 立即返回，不等通知发送
    }
}
```

### Service 层 — 核心逻辑 + 投递事件

```java
@Service
public class OrderService {
    @Autowired private OrderRepository orderRepo;
    @Autowired private OrderEventPublisher publisher;

    @Transactional
    public void createOrder(Order order) {
        orderRepo.save(order);                           // 写库
        publisher.publish(new OrderCreatedEvent(order));  // 投递 MQ，不等通知
    }
}
```

### Consumer 层 — 通知服务各自消费，互不阻塞

```java
@Component
@RabbitListener(queues = "order.created.sms")
public class SmsConsumer {
    @RabbitHandler
    public void handle(OrderCreatedEvent event) {
        smsService.sendOrderConfirm(event.getPhone());   // 1200ms？无所谓
    }
}

@Component
@RabbitListener(queues = "order.created.email")
public class EmailConsumer {
    @RabbitHandler
    public void handle(OrderCreatedEvent event) {
        emailService.sendOrderReceipt(event.getEmail()); // 1500ms？无所谓
    }
}
```

关键变化：用户只需要知道"下单成功"，不需要等短信和邮件发完。通知是"锦上添花"的操作，放到消费者侧异步处理，主流程响应时间从 2.7s 降到 55ms。

## 同步 vs 异步判断对比

| 判断维度 | 同步调用 | 异步消息 |
|---|---|---|
| 结果需求 | 调用方必须立即拿到结果 | 调用方不需要结果或可容忍延迟 |
| 响应时间 | 所有下游串行执行的总和 | 本地事务 + MQ 投递耗时 |
| 一致性 | 强一致，失败即回滚 | 最终一致，消息可能延迟到达 |
| 故障影响 | 下游宕机 → 调用方直接失败 | 下游宕机 → 消息暂存 MQ 等恢复 |
| 典型场景 | 支付扣款、权限校验、库存扣减 | 通知、日志、统计、数据同步 |
| 事务成本 | 可用本地事务或分布式事务 | 需要消息可靠投递 + 幂等消费 |
| 复杂度 | 简单直接，调用链清晰 | 引入 MQ，增加运维和排错成本 |

**In one sentence: 同步是"我等你干完我才走"——用于必须拿到结果的场景；异步是"我告诉你一声你慢慢干"——用于结果可以等的场景，判断标准就是问自己一句"调用方这一刻需不需要这个结果"。**
