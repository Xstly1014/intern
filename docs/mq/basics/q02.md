# Q2 三大核心作用

解耦是"我不认识你，但你可以听我说话"；异步是"我说完就走，你慢慢处理"；削峰是"洪水来了先蓄到水库，按灌溉能力放水"。三者共用同一个 MQ 基础设施，但切入点不同：解耦解决"谁需要知道"，异步解决"要不要等结果"，削峰解决"流量超出下游承受力"。

上图三个场景共用同一个 MQ，但切入角度不同：解耦关注"谁需要知道"，异步关注"要不要等结果"，削峰关注"流量超出承受力怎么办"。下面逐场景用代码拆解。

## 场景一：解耦 — 新增服务不改老代码

### Before：紧耦合，加一个服务改一次

```java
@Service
public class OrderService {
    @Autowired private InventoryService inventoryService;
    @Autowired private PaymentService paymentService;
    @Autowired private SmsService smsService;
    // 产品经理说：下单后要加积分！→ 改这里
    // @Autowired private PointsService pointsService;

    public void createOrder(Order order) {
        orderRepo.save(order);
        inventoryService.deduct(order.getSkuId());
        paymentService.charge(order.getAmount());
        smsService.notify(order.getUserId());
        // pointsService.addPoints(order.getUserId(), order.getPoints());
        // 每加一个下游，OrderService 就多一行依赖、多一次发布
    }
}
```

### After：发布事件，下游各自订阅

**生产者层 — OrderService 只关心"订单创建了"**

```java
@Service
public class OrderService {
    @Autowired private OrderEventPublisher publisher;

    public void createOrder(Order order) {
        orderRepo.save(order);
        publisher.publish(new OrderCreatedEvent(order));  // 只发事件，不关心谁来消费
    }
}
```

**消费者层 — 每个下游独立监听，新增积分服务零改动 OrderService**

```java
@Component
@RabbitListener(queues = "order.created")
public class PointsConsumer {
    @RabbitHandler
    public void handle(OrderCreatedEvent event) {
        pointsService.addPoints(event.getUserId(), event.getPoints());
    }
}
// 新增积分服务 = 写一个新 Consumer 类，OrderService 代码一个字不改
```

关键变化：OrderService 从"我知道 N 个下游并逐个调用"变成"我只知道有个事件发生了"。新增第 5 个、第 10 个下游，都是加 Consumer，生产者无感知。

## 场景二：异步 — 用户不等发邮件

### Before：同步调用，用户苦等 3 秒

```java
@Service
public class UserService {
    @Autowired private EmailService emailService;
    @Autowired private SmsService smsService;

    public User register(UserDTO dto) {
        User user = userRepo.save(dto.toUser());     // 50ms
        emailService.sendWelcome(user.getEmail());    // 1500ms — SMTP 握手慢
        smsService.sendVerifyCode(user.getPhone());   // 1200ms — 短信网关慢
        return user;                                  // 总耗时 ≈ 2.7s，用户已经等得不耐烦
    }
}
```

### After：投递 MQ 立即返回，邮件短信后台发

**生产者层 — 注册方法只做核心逻辑 + 投递事件**

```java
@Service
public class UserService {
    @Autowired private UserEventPublisher publisher;

    public User register(UserDTO dto) {
        User user = userRepo.save(dto.toUser());      // 50ms
        publisher.publish(new UserRegisteredEvent(user)); // 5ms 投递 MQ
        return user;                                   // 总耗时 ≈ 55ms，用户秒级拿到响应
    }
}
```

**消费者层 — 邮件和短信各自慢慢发，不影响用户**

```java
@Component
@RabbitListener(queues = "user.registered.email")
public class EmailConsumer {
    @RabbitHandler
    public void handle(UserRegisteredEvent event) {
        emailService.sendWelcome(event.getEmail());  // 1500ms？无所谓，用户已经去用了
    }
}

@Component
@RabbitListener(queues = "user.registered.sms")
public class SmsConsumer {
    @RabbitHandler
    public void handle(UserRegisteredEvent event) {
        smsService.sendVerifyCode(event.getPhone());  // 1200ms？无所谓，用户已经去用了
    }
}
```

关键变化：响应时间从 2.7s 降到 55ms。慢操作（SMTP、短信网关）被移到消费者侧，不阻塞主流程。即使邮件服务宕了，用户照样能注册成功。

## 场景三：削峰 — 秒杀洪峰不打垮数据库

### Before：10k 请求直扑数据库

```java
@RestController
@RequestMapping("/seckill")
public class SeckillController {

    @PostMapping
    public Result execute(@RequestBody SeckillRequest req) {
        // 10,000 个请求同时到达 → 数据库连接池瞬间耗尽 → 服务雪崩
        seckillService.execute(req);  // 直接写库，每个请求占用一个 DB 连接
        return Result.ok();
    }
}
```

### After：请求先入 MQ 排队，消费者按数据库能力拉取

**入口层 — 请求写入 MQ 立即返回**

```java
@RestController
@RequestMapping("/seckill")
public class SeckillController {
    @Autowired private SeckillMessagePublisher publisher;

    @PostMapping
    public Result execute(@RequestBody SeckillRequest req) {
        publisher.sendToQueue(req);   // 10k 请求/s 全部写入 MQ（内存操作，极快）
        return Result.ok("排队中");    // 用户收到"正在处理"
    }
}
```

**消费者层 — 按数据库承受能力消费**

```java
@Component
@RabbitListener(queues = "seckill.queue", concurrency = "10")  // 10 个消费者线程
public class SeckillConsumer {
    @RabbitHandler
    public void handle(SeckillRequest req) {
        seckillService.execute(req);  // 每秒处理 ~1k，数据库压力平稳
    }
}
```

关键变化：10k/s 的洪峰被 MQ 吸收，数据库只承受 1k/s 的平稳流量。MQ 在这里扮演"水库"角色——洪水来了先蓄水，按灌溉渠道的承载力放水。

## 三大作用对比

| 维度 | 解耦 | 异步 | 削峰 |
|---|---|---|---|
| 解决什么问题 | 服务间依赖传染 | 响应时间被慢操作拖累 | 峰值流量打垮下游 |
| 核心机制 | 发布订阅，生产者不认识消费者 | 投递后立即返回，不等消费结果 | MQ 做缓冲池，消费者按自身能力拉取 |
| 典型场景 | 订单创建触发库存/支付/通知/积分 | 用户注册后发邮件/短信 | 秒杀/抢购高并发写入 |
| 不用 MQ 的后果 | 新增下游要改老代码 | 用户等 3 秒才看到"注册成功" | 数据库连接池耗尽，服务雪崩 |
| MQ 的角色 | 广播站 | 转发信箱 | 蓄水池 |

**In one sentence: 解耦让生产者从"指挥下游干活"变成"广播事情发生了"，异步让用户从"等所有事情做完"变成"做完核心就返回"，削峰让下游从"被洪水冲垮"变成"按自己节奏喝水库放出来的水"。**
