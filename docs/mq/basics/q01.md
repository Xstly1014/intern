# Q1 消息队列本质

消息队列的本质是一个"异步数据管道"——生产者把消息丢进去就走，消费者按自己的节奏拉取处理。分布式系统几乎离不开它，是因为它同时解决了三个核心问题：**解耦、异步、削峰**。

上图展示了引入消息队列前后的核心变化：**Before** 中 OrderService 像一个"总指挥"，必须同步调用库存、支付、通知三个服务并等待全部返回；**After** 中 OrderService 只负责把"订单已创建"这件事告诉 Message Queue，下游各自消费，互不阻塞。

## Before：紧耦合的同步调用

```java
@Service
public class OrderService {
    @Autowired private InventoryService inventoryService;
    @Autowired private PaymentService paymentService;
    @Autowired private SmsService smsService;

    @Transactional
    public void createOrder(Order order) {
        orderRepo.save(order);                     // ① 写入订单
        inventoryService.deduct(order.getSkuId());  // ② 同步扣库存
        paymentService.charge(order.getAmount());   // ③ 同步扣款
        smsService.notify(order.getUserId());       // ④ 同步发通知
    }
}
```

问题一目了然：OrderService 手持 3 个 `@Autowired`，任何一个下游宕机，下单直接失败；新增第 4 个下游（比如积分服务）又得改这里重新发版。

## After：基于消息队列的分层解耦

### Layer 1 — OrderController（入口，保持轻量）

```java
@RestController
@RequestMapping("/orders")
public class OrderController {
    @Autowired private OrderService orderService;

    @PostMapping
    public Result create(@RequestBody OrderDTO dto) {
        orderService.createOrder(dto.toOrder());
        return Result.ok();
    }
}
```

### Layer 2 — OrderService（核心变化：不再直接调用下游）

```java
@Service
public class OrderService {
    @Autowired private OrderRepository orderRepo;
    @Autowired private OrderEventPublisher publisher;

    @Transactional
    public void createOrder(Order order) {
        orderRepo.save(order);                           // 只写本地事务
        publisher.publish(new OrderCreatedEvent(order));  // 发事件，不等下游
    }
}
```

关键变化：`@Autowired` 从 3 个下游变成了 1 个 Publisher。OrderService 不再关心"谁需要这个订单"，只负责"订单创建好了，广播出去"。

### Layer 3 — OrderEventPublisher（消息发布层）

```java
@Component
public class OrderEventPublisher {
    @Autowired private RabbitTemplate rabbitTemplate;

    public void publish(OrderCreatedEvent event) {
        rabbitTemplate.convertAndSend(
            "order.exchange",      // 交换机
            "order.created",       // routing key
            event                  // 事件载荷
        );
    }
}
```

### Layer 4 — Message Broker（消息队列本体）

```
Exchange: order.exchange
  └── Queue: order.created.queue
        ├── Consumer: InventoryConsumer  → 扣减库存
        ├── Consumer: PaymentConsumer    → 发起扣款
        └── Consumer: SmsConsumer        → 发送通知
```

### Layer 5 — Consumers（每个下游独立消费，互不干扰）

```java
@Component
@RabbitListener(queues = "order.created.queue")
public class InventoryConsumer {
    @RabbitHandler
    public void handle(OrderCreatedEvent event) {
        inventoryService.deduct(event.getSkuId());
    }
}
// PaymentConsumer、SmsConsumer 结构相同，各自独立监听
```

新增积分服务？写一个 `PointsConsumer` 订阅同一个 Queue，OrderService 代码零改动。

## 对比总结

| 维度 | 同步直连（无 MQ） | 消息队列解耦 |
|---|---|---|
| OrderService 依赖 | N 个下游 `@Autowired` | 1 个 Publisher |
| 新增下游成本 | 改 OrderService 代码 + 重新部署 | 新服务独立订阅 Topic，零改动 |
| 下游故障影响 | 任一下游宕机 → 下单失败 | 消息暂存 MQ，下游恢复后继续消费 |
| 响应耗时 | 所有下游串行执行的总和 | 本地事务 + 投递 MQ 的耗时 |
| 流量峰值 | 直接冲击数据库和下游服务 | MQ 缓冲削峰，下游按自身能力消费 |

**In one sentence: 消息队列是分布式系统的"变速箱"——它让快慢不一、增减频繁的组件之间不再硬碰硬，而是通过一个缓冲层各自按自己的节奏运转。**
