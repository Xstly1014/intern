# Q7 引入 MQ 的代价

引入 MQ 不是免费的午餐，它用五个代价换来解耦和削峰：**系统可用性降低**（MQ 挂了整个链路就断了）、**系统复杂度提高**（多了消息可靠投递、幂等、顺序等要处理）、**一致性问题**（从强一致降级为最终一致）、**延迟增加**（多了一跳网络 + 序列化）、**运维成本**（MQ 集群的部署、监控、扩容都是额外工作）。权衡原则：解耦和削峰收益大于复杂度成本时才引入，简单同步调用能解决的不要硬上 MQ。

上图上半部分是收益（解耦、异步、削峰），下半部分是四个代价。核心矛盾在于：MQ 用"多一个中间层"换来了解耦和削峰，但这个中间层本身就是新的故障点和复杂度来源。下面用代码看这些代价在项目中具体长什么样。

## 代价一：可用性 — MQ 挂了怎么办

### Before：直连调用，没有额外故障点

```java
@Service
public class OrderService {
    @Autowired private InventoryService inventoryService;

    public void createOrder(Order order) {
        orderRepo.save(order);
        inventoryService.deduct(order.getSkuId());  // 直接调用，只要 Inventory 活着就行
    }
}
```

### After：引入 MQ 后，MQ 也必须高可用

```java
@Service
public class OrderService {
    @Autowired private OrderEventPublisher publisher;

    public void createOrder(Order order) {
        orderRepo.save(order);
        publisher.publish(new OrderCreatedEvent(order));
        // 现在故障点变成了：DB 挂、MQ 挂、Consumer 挂
        // 需要额外保证：MQ 集群高可用 + 消息持久化 + 消费者重试
    }
}

// 补偿层：MQ 不可用时的降级方案
@Aspect
@Component
public class MqFallbackAspect {
    @AfterThrowing(pointcut = "execution(* ..OrderEventPublisher.publish(..))", throwing = "ex")
    public void onMqFailure(Exception ex) {
        // MQ 挂了 → 降级：写入本地消息表，定时任务补偿重发
        localMessageRepo.save(pendingMessage);  // 先存库
        log.error("MQ 不可用，消息已存入本地表等待补偿", ex);
    }
}
```

关键变化：原来只有两个服务之间的故障风险，现在多出 MQ 这一层。生产级方案需要 MQ 集群 + 消息持久化 + 本地消息表补偿兜底。

## 代价二：一致性 — 从强一致到最终一致

### 问题场景 — 订单成功但积分没加

```java
@Service
public class OrderService {
    @Transactional
    public void createOrder(Order order) {
        orderRepo.save(order);                           // ① 本地事务提交
        publisher.publish(new OrderCreatedEvent(order));  // ② 投递 MQ
        // ① 和 ② 不是原子操作：如果 ① 成功 ② 失败 → 订单有了但积分没加
    }
}

// 消费者侧：即使投递成功，消费者可能延迟处理
@Component
@RabbitListener(queues = "order.points")
public class PointsConsumer {
    @RabbitHandler
    public void handle(OrderCreatedEvent event) {
        // 用户下单后 2 秒才加积分 → 用户看到"已下单但无积分"
        pointsService.addPoints(event.getUserId(), event.getPoints());
    }
}
```

关键变化：同步调用时订单和积分在同一个事务里，要么都成功要么都失败；引入 MQ 后变成两步——先写订单，再异步加积分，中间有时间窗口，用户可能看到不一致状态。

## 代价三：复杂度 — 要处理的工程问题清单

```java
// 引入 MQ 后，团队需要额外处理的问题：

// 1. 消息可靠投递：生产者确认机制
rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
    if (!ack) {
        // Broker 没收到 → 重发或告警
        retryService.resend(correlationData);
    }
});

// 2. 消息幂等：消费者防重复消费
@RabbitListener(queues = "order.points")
public void handle(OrderCreatedEvent event) {
    // 必须先查 Redis 判断是否已处理过
    if (redisTemplate.opsForValue().setIfAbsent(
        "idempotent:" + event.getMessageId(), "1", 24, TimeUnit.HOURS)) {
        pointsService.addPoints(event.getUserId(), event.getPoints());
    }
    // 否则 MQ 重投时积分会加两次
}

// 3. 消息顺序：多分区时保证不了全局顺序
// 4. 死信队列：消费失败的消息怎么处理
// 5. 消息积压监控：消费速度跟不上生产速度
// 6. 消息回溯：出了问题怎么重新消费
```

## 代价四：延迟增加 — 多一跳网络开销

```java
// 直连调用：OrderService → InventoryService，一次本地网络调用
inventoryService.deduct(skuId);  // 耗时 ~5ms

// 引入 MQ 后：OrderService → MQ → InventoryConsumer
// 多出：序列化 → 网络传输到 MQ → MQ 内部路由 → 网络传输到 Consumer → 反序列化
publisher.publish(new OrderCreatedEvent(order));  // 耗时 ~10~50ms
// 对延迟敏感的场景（如实时风控、交易撮合）要评估这额外延迟是否可接受
```

## 代价五：运维成本 — 多养一整套中间件

```java
// 引入 MQ 后，运维团队需要额外负责的工作：

// 1. 集群部署：RabbitMQ 需要 3 节点集群，Kafka 需要多 Broker + ZK/KRaft
//    docker-compose.yml: rabbit1, rabbit2, rabbit3 + haproxy 负载均衡

// 2. 监控告警：除了应用监控，还要监控 MQ 本身
//    - RabbitMQ: 队列深度、消费者数、连接数、内存使用
//    - Kafka: Lag 指标、Broker 存活、磁盘使用、ISR 缩减

// 3. 容量规划：消息保留策略、磁盘容量、分区数是否够用
//    kafka-configs.sh --alter --topic order.created 
//        --add-config retention.ms=259200000  // 保留 3 天

// 4. 版本升级：Kafka 从 ZK 模式迁移到 KRaft 模式，需要滚动升级
// 5. 安全配置：Vhost 权限、SASL 认证、TLS 加密
```

关键变化：原来运维只管应用服务（Jar 包 + 数据库），现在多了一整套 MQ 中间件——集群部署、监控告警、容量规划、版本升级都是额外工作，小团队可能因此增加半个运维人力。

## 收益 vs 代价对比

| 维度 | 不用 MQ（直连） | 用 MQ |
|---|---|---|
| 可用性 | 依赖下游服务可用 | 多依赖一层 MQ，需集群保障 |
| 一致性 | 强一致，同事务回滚 | 最终一致，有延迟窗口 |
| 复杂度 | 方法调用，简单直接 | 消息可靠投递 + 幂等 + 顺序 + 死信 |
| 延迟 | 直连 ~5ms | 多一跳网络 ~10~50ms |
| 运维成本 | 只管应用服务 | 应用 + MQ 集群 + 监控 + 容量规划 |
| 响应时间 | 所有下游串行总和 | 本地事务 + MQ 投递 |
| 新增下游成本 | 改代码重新发版 | 加 Consumer 即可 |
| 流量峰值 | 直接冲击下游 | MQ 缓冲削峰 |
| 排错难度 | 调用链清晰 | 消息链路追踪复杂 |

**In one sentence: 引入 MQ 就像请了一个中间人帮你传话——你不用亲自跑腿了，但这个中间人可能生病请假（可用性）、可能传错话（一致性）、传话比别人慢半拍（延迟增加）、还得给他发工资管他的考勤（复杂度）、甚至要给他配办公室和安保（运维成本），收益和代价永远是对等的。**
