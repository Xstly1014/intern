# Q7 引入 MQ 的代价

引入 MQ 不是免费的午餐，它用四个代价换来解耦和削峰：**系统可用性降低**（MQ 挂了整个链路就断了）、**系统复杂度提高**（多了消息可靠投递、幂等、顺序等要处理）、**一致性问题**（从强一致降级为最终一致）、**性能开销**（多了一跳网络 + 序列化）。权衡原则：业务能容忍最终一致性和延迟 → 引入 MQ；必须强一致和实时 → 不要引入。

上图上半部分是收益（解耦、异步、削峰），下半部分是四个代价。核心矛盾在于：MQ 用"多一个中间层"换来了解耦和削峰，但这个中间层本身就是新的故障点和复杂度来源。下面用代码看这些代价在项目中具体长什么样。

## 代价一：可用性 — MQ 挂了怎么办

### Before：直连调用，没有额外故障点

```java
@Service
public class OrderService {
    @Autowired private InventoryService inventoryService;

    public void createOrder(Order order) {
        orderRepo.save(order);
        inventoryService.deduct(order.getSkuId());  // 直接调用，只要 Inventory 活着就行
    }
}
```

### After：引入 MQ 后，MQ 也必须高可用

```java
@Service
public class OrderService {
    @Autowired private OrderEventPublisher publisher;

    public void createOrder(Order order) {
        orderRepo.save(order);
        publisher.publish(new OrderCreatedEvent(order));
        // 现在故障点变成了：DB 挂、MQ 挂、Consumer 挂
        // 需要额外保证：MQ 集群高可用 + 消息持久化 + 消费者重试
    }
}

// 补偿层：MQ 不可用时的降级方案
@Aspect
@Component
public class MqFallbackAspect {
    @AfterThrowing(pointcut = "execution(* ..OrderEventPublisher.publish(..))", throwing = "ex")
    public void onMqFailure(Exception ex) {
        // MQ 挂了 → 降级：写入本地消息表，定时任务补偿重发
        localMessageRepo.save(pendingMessage);  // 先存库
        log.error("MQ 不可用，消息已存入本地表等待补偿", ex);
    }
}
```

关键变化：原来只有两个服务之间的故障风险，现在多出 MQ 这一层。生产级方案需要 MQ 集群 + 消息持久化 + 本地消息表补偿兜底。

## 代价二：一致性 — 从强一致到最终一致

### 问题场景 — 订单成功但积分没加

```java
@Service
public class OrderService {
    @Transactional
    public void createOrder(Order order) {
        orderRepo.save(order);                           // ① 本地事务提交
        publisher.publish(new OrderCreatedEvent(order));  // ② 投递 MQ
        // ① 和 ② 不是原子操作：如果 ① 成功 ② 失败 → 订单有了但积分没加
    }
}

// 消费者侧：即使投递成功，消费者可能延迟处理
@Component
@RabbitListener(queues = "order.points")
public class PointsConsumer {
    @RabbitHandler
    public void handle(OrderCreatedEvent event) {
        // 用户下单后 2 秒才加积分 → 用户看到"已下单但无积分"
        pointsService.addPoints(event.getUserId(), event.getPoints());
    }
}
```

关键变化：同步调用时订单和积分在同一个事务里，要么都成功要么都失败；引入 MQ 后变成两步——先写订单，再异步加积分，中间有时间窗口，用户可能看到不一致状态。

## 收益 vs 代价对比

| 维度 | 不用 MQ（直连） | 用 MQ |
|---|---|---|
| 可用性 | 依赖下游服务可用 | 多依赖一层 MQ，需集群保障 |
| 一致性 | 强一致，同事务回滚 | 最终一致，有延迟窗口 |
| 复杂度 | 方法调用，简单直接 | 消息可靠投递 + 幂等 + 顺序 + 死信 |
| 响应时间 | 所有下游串行总和 | 本地事务 + MQ 投递 |
| 新增下游成本 | 改代码重新发版 | 加 Consumer 即可 |
| 流量峰值 | 直接冲击下游 | MQ 缓冲削峰 |
| 运维成本 | 只管服务 | 服务 + MQ 集群 + 监控 |
| 排错难度 | 调用链清晰 | 消息链路追踪复杂 |

**In one sentence: 引入 MQ 就像请了一个中间人帮你传话——你不用亲自跑腿了，但这个中间人可能生病请假（可用性）、可能传错话（一致性）、还得给他发工资管他的考勤（复杂度），收益和代价永远是对等的。**
