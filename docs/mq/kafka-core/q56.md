# Q56 Log Segment 分段

Log Segment 是 Kafka 将一个 Partition 的日志切分成多个段文件的机制，每个段默认 1GB（log.segment.bytes）或按时间切分（log.roll.hours，默认 168 小时=7 天），每个 Segment 由 .log（消息数据）、.index（稀疏偏移量索引）、.timeindex（时间戳索引）三个文件组成；分段的核心目的是高效消息清理、快速索引查找、灵活文件管理和日志压缩，其中活跃 Segment（active segment）是当前正在写入的段，不能被删除或压缩。

上图展示了一个 Partition 的日志被切分为 3 个 Segment，每个 Segment 由 .log（消息数据）、.index（稀疏偏移量索引）、.timeindex（时间戳索引）三个文件组成。前两个 Segment 已封闭可以被清理或压缩，第三个是 Active Segment 正在写入不可操作。当查找 offset=1200 时，Kafka 先在 .index 中二分查找找到小于等于 1200 的最大索引项（offset:1000 对应 pos:8192），再跳转到 .log 对应物理位置顺序扫描定位目标消息。稀疏索引默认每 4KB 添加一个索引项，在内存效率和查找精度间取得平衡。

## 代码小节：Log Segment 配置与操作

### Layer 1 — Segment 配置（log.segment.bytes, log.roll.hours）

```properties
# server.properties — Segment 切分配置

# 按字节切分：单个 Segment 最大大小，默认 1GB
log.segment.bytes=1073741824

# 按时间切分：超过该时间滚动新 Segment，默认 168 小时（7 天）
log.roll.hours=168

# 稀疏索引间隔：每写入 4KB 数据添加一个索引项
index.interval.bytes=4096

# Segment 保留时间（delete 策略使用）
log.retention.hours=72

# Segment 保留大小（-1 表示不限制）
log.retention.bytes=-1

# 日志清理策略：delete 或 compact
log.cleanup.policy=delete
```

### Layer 2 — 查看 Segment 文件（kafka-dump-log.sh）

```bash
# 查看 Partition 目录下的 Segment 文件
ls -lh /tmp/kafka-logs/order-events-0/
# 00000000000000000000.index      ← Segment 0 索引
# 00000000000000000000.log        ← Segment 0 数据
# 00000000000000000000.timeindex  ← Segment 0 时间戳索引
# 00000000000000001000.index      ← Segment 1 索引
# 00000000000000001000.log        ← Segment 1 数据
# 00000000000000001000.timeindex  ← Segment 1 时间戳索引

# 查看 .log 文件内容（消息详情）
kafka-dump-log.sh \
  --files /tmp/kafka-logs/order-events-0/00000000000000000000.log

# 查看 .index 稀疏索引内容（offset → 物理位置映射）
kafka-dump-log.sh \
  --files /tmp/kafka-logs/order-events-0/00000000000000000000.index
# 输出示例：
# offset: 0    position: 0
# offset: 500  position: 4096
# offset: 1000 position: 8192

# 查看 .timeindex 时间戳索引
kafka-dump-log.sh \
  --files /tmp/kafka-logs/order-events-0/00000000000000000000.timeindex
```

### Layer 3 — 索引查找过程（offset → 二分查找 .index → 定位 .log 位置）

```java
// Spring Kafka — 消费者按 offset 消费，底层触发 Segment 索引查找
// 查找流程：offset → 定位 Segment → 二分查找 .index → 顺序扫描 .log
@SpringBootApplication
public class SegmentLookupDemo {

    public static void main(String[] args) {
        SpringApplication.run(SegmentLookupDemo.class, args);
    }

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, String> factory(
            ConsumerFactory<String, String> cf) {
        ConcurrentKafkaListenerContainerFactory<String, String> factory =
                new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(cf);
        return factory;
    }

    // 消费者指定 offset 消费时，Kafka 底层执行：
    // 1. 根据 offset 找到对应的 Segment 文件（文件名即起始 offset）
    // 2. 在该 Segment 的 .index 中二分查找 ≤ offset 的最大索引项
    // 3. 跳转到 .log 对应物理位置，顺序扫描定位精确 offset
    @KafkaListener(topics = "order-events", groupId = "demo-group")
    public void listen(ConsumerRecord<String, String> record,
                       Acknowledgment ack) {
        // record.offset() 对应的消息正是通过上述索引查找定位的
        System.out.printf("partition=%d, offset=%d, value=%s%n",
                record.partition(), record.offset(), record.value());
        ack.acknowledge();
    }
}
```

### Layer 4 — 日志清理策略（delete vs compact）

```properties
# server.properties — 日志清理策略配置

# === delete 策略：按时间或大小删除整个 Segment ===
log.cleanup.policy=delete
log.retention.hours=72          # 超过 72 小时的 Segment 被删除
log.retention.bytes=10737418240 # 或总大小超过 10GB 时删除最旧 Segment
log.segment.delete.delay.ms=60000 # Segment 删除延迟（60s）

# === compact 策略：保留每个 key 的最新值，删除旧版本 ===
# log.cleanup.policy=compact
# log.cleaner.min.compaction.lag.ms=0     # 消息写入后最少等多久才 compact
# log.cleaner.delete.retention.ms=86400000 # tombstone 保留时间（24h）
# log.cleaner.threads=1                    # 清理线程数

# === 混合策略：同时支持 delete + compact ===
# log.cleanup.policy=delete,compact
```

## 日志清理策略对比

| 维度 | delete 策略 | compact 策略 |
|------|------------|-------------|
| 清理方式 | 按时间 / 大小删除整个 Segment | 保留每个 key 的最新值，删除旧版本 |
| 适用场景 | 普通消息流（日志、事件流水） | 状态变更流（用户信息、配置更新） |
| 数据丢失 | 过期数据全部丢失 | 旧版本值丢失，最新值保留 |
| Segment 要求 | 可删除 Active 之外的任何 Segment | 需等 Segment 封闭后才能 compact |
| 关键参数 | log.retention.hours / log.retention.bytes | log.cleaner.min.compaction.lag.ms |
| 消费语义 | 消费者需处理消息过期消失 | 消费者可重新获取最新状态 |
| 性能影响 | 低（直接删除文件） | 较高（需重写 Segment 合并 key） |
| Active Segment | 不可删除 | 不可 compact |

## 一句话总结

**Log Segment 通过将大日志文件切分为多个段文件，实现了高效的消息清理（按 Segment 粒度删除）、快速的索引查找（每段独立稀疏索引 + 二分查找）和灵活的日志压缩，其中 Active Segment 是当前写入段不可被清理或压缩。**
