# Q58 HW 与 LEO

LEO（Log End Offset）是每个副本的日志末端偏移，即下一条要写入的 offset；HW（High Watermark）是所有 ISR 副本中最小的 LEO，代表已被多数副本确认的安全位置，消费者只能消费到 HW 之前的消息。HW 之后的消息只在 Leader 上存在，若 Leader 故障切换后这些消息可能丢失，因此不暴露给消费者。HW 更新有一轮延迟，可能导致 Leader 切换后数据截断或消费者重复消费。

上图展示了 LEO 与 HW 的核心关系：Leader LEO=8、Follower1 LEO=7、Follower2 LEO=5，HW=min(8,7,5)+1=6，消费者只能消费 offset 0-5（HW 之前），offset 6、7 只存在于 Leader 和部分 Follower 上不可消费。HW 更新存在一轮延迟——Leader 在本轮收到 Follower 的 FetchRequest 后计算 HW，但要到下一轮 FetchResponse 才下发给 Follower。这导致 Leader 在两轮之间宕机时，新 Leader 的 HW 可能高于实际同步位置，引发日志截断丢失或消费者重复消费，Kafka 0.11+ 通过 Leader Epoch 机制缓解此问题。

### Layer 2 — HW 更新机制代码模拟（Follower FetchRequest → Leader 更新 HW）

```java
// 模拟 HW 更新机制：Follower FetchRequest → Leader 更新 HW → 下轮下发
public class HwUpdateSimulator {

    static class Replica {
        String name;
        int leo;  // Log End Offset
        int hw;   // High Watermark

        Replica(String name, int leo, int hw) {
            this.name = name;
            this.leo = leo;
            this.hw = hw;
        }
    }

    public static void main(String[] args) {
        Replica leader = new Replica("Leader", 8, 0);
        Replica follower1 = new Replica("Follower-1", 7, 0);
        Replica follower2 = new Replica("Follower-2", 5, 0);

        System.out.println("=== 第 1 轮：Follower 发送 FetchRequest ===");
        System.out.printf("Follower-1 LEO=%d, Follower-2 LEO=%d%n",
                follower1.leo, follower2.leo);

        // ① Leader 收到所有 Follower 的 LEO，计算 HW
        //    HW = min(所有 ISR 副本的 LEO) + 1
        int minLeo = Math.min(leader.leo,
                Math.min(follower1.leo, follower2.leo));
        leader.hw = minLeo + 1;  // HW = min(8,7,5) + 1 = 6
        System.out.printf("Leader 更新 HW = min(%d, %d, %d) + 1 = %d%n",
                leader.leo, follower1.leo, follower2.leo, leader.hw);

        System.out.println("\n=== 第 2 轮：Leader 在 FetchResponse 中下发 HW ===");
        // ② Follower 在下一轮收到更新后的 HW（一轮延迟）
        follower1.hw = leader.hw;
        follower2.hw = leader.hw;
        System.out.printf("Follower-1 HW=%d, Follower-2 HW=%d%n",
                follower1.hw, follower2.hw);

        // ③ 消费者只能消费 HW 之前的消息
        System.out.printf("%n消费者只能消费 offset 0~%d（HW=%d 之前）%n",
                leader.hw - 1, leader.hw);
        System.out.println("offset 6、7 在 HW 之后，消费者不可见");
    }
}
```

### Layer 3 — Leader 切换后 HW 截断场景

```java
// 模拟 Leader 切换后 HW 截断导致的数据丢失场景
public class HwTruncationDemo {

    public static void main(String[] args) {
        // 场景：Leader(LEO=8, HW=6) 宕机，Follower-1(LEO=7) 成为新 Leader
        int oldLeaderLeo = 8;
        int hw = 6;

        int newLeaderLeo = 7;  // 原 Follower-1 的 LEO
        System.out.println("=== Leader 切换发生 ===");
        System.out.printf("旧 Leader: LEO=%d, HW=%d（宕机）%n", oldLeaderLeo, hw);
        System.out.printf("新 Leader（原 Follower-1）: LEO=%d, HW=%d%n", newLeaderLeo, hw);

        // 新 Leader 将日志截断到 HW（删除 HW 之后的消息）
        // offset 6 已在新 Leader 上但未达 HW → 被截断
        System.out.printf("%n新 Leader 截断日志：LEO %d → %d%n", newLeaderLeo, hw);
        System.out.printf("→ offset %d 的消息被删除（数据丢失）%n", newLeaderLeo - 1);
        newLeaderLeo = hw;

        // 其他 Follower 也截断到 HW
        System.out.println("其他 Follower 同步截断到 HW=" + hw);

        // 风险说明
        System.out.println("\n=== 风险分析 ===");
        System.out.println("1. 数据丢失：offset 6 的消息在旧 Leader 上已写入，");
        System.out.println("   但未同步到所有 ISR，Leader 切换后被截断删除");
        System.out.println("2. 重复消费：若消费者已读到 offset 6，");
        System.out.println("   HW 回退后该 offset 不存在，重启后从更早 offset 重新消费");

        // Kafka 0.11+ 解决方案
        System.out.println("\n=== Kafka 0.11+ 解决方案 ===");
        System.out.println("引入 Leader Epoch 机制：");
        System.out.println("  每个 Leader 任期有唯一 epoch 编号");
        System.out.println("  Follower 用 Leader Epoch 替代 HW 判断截断点");
        System.out.println("  避免不必要的日志截断，减少数据丢失");
    }
}
```

### Layer 4 — 消费者消费位置与 HW 的关系

```java
// Spring Kafka — 消费者消费位置永远不超过 HW
@SpringBootApplication
public class ConsumerHwDemo {

    public static void main(String[] args) {
        SpringApplication.run(ConsumerHwDemo.class, args);
    }

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, String> factory(
            ConsumerFactory<String, String> cf) {
        ConcurrentKafkaListenerContainerFactory<String, String> factory =
                new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(cf);
        // 消费者的 fetch 位置由 Broker 保证不超过 HW
        // Broker 在 FetchResponse 中只返回 HW 之前的消息
        return factory;
    }

    @KafkaListener(topics = "order-events", groupId = "hw-demo")
    public void listen(ConsumerRecord<String, String> record,
                       Consumer<String, String> consumer,
                       Acknowledgment ack) {
        // record.offset() 一定 <= HW-1（Broker 保证）
        System.out.printf("消费 offset=%d（HW 之内，安全消费）%n",
                record.offset());

        // 查看当前消费位置
        consumer.assignment().forEach(tp -> {
            long position = consumer.position(tp);
            // position 永远 <= HW，Broker 不返回 HW 之后的消息
            System.out.printf("分区 %s 消费位置=%d（不超过 HW）%n",
                    tp, position);
        });

        ack.acknowledge();
    }

    // 注意：消费者无法直接获取 HW 的精确值（Kafka 协议不暴露 HW 给消费者）
    // 但 Broker 在 FetchResponse 中保证：
    // 1. 只返回 HW 之前的消息
    // 2. FetchResponse 中携带当前 HW（消费者可用于判断是否可提交 offset）
    // 消费者的 committed offset 也不会超过 HW
}
```

## LEO vs HW 对比

| 维度 | LEO | HW |
|------|-----|-----|
| 定义 | 每个副本的日志末端偏移（下一条要写入的 offset） | 所有 ISR 副本中最小的 LEO |
| 作用范围 | 每个副本各自独立维护 | Leader 统一计算并下发给 Follower |
| 更新时机 | 副本写入消息后立即更新 | Leader 收到 Follower FetchRequest 时更新 |
| 消费者可见性 | 消费者不可直接感知 | 消费者只能消费 HW 之前的消息 |
| 故障影响 | Leader 挂了 LEO 丢失 | HW 之后的消息可能丢失（未完全同步） |
| 更新延迟 | 无延迟（实时更新） | 有一轮延迟（下一轮 FetchResponse 才下发） |
| 截断行为 | 只增不减（正常情况） | Leader 切换后截断到 HW |
| 主要用途 | 标记副本写入进度 | 标记消费者可消费的安全边界 |

## 一句话总结

**LEO 是每个副本的日志末端偏移，HW 是所有 ISR 副本中最小的 LEO 代表安全消费边界，消费者只能消费 HW 之前的消息，而 HW 更新的一轮延迟可能导致 Leader 切换后日志截断或重复消费。**
