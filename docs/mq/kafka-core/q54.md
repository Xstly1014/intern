# Q54 KRaft 模式

KRaft 是 Kafka 用内部 Raft 协议取代 ZooKeeper 管理元数据的架构模式，元数据以日志形式存于内部 Topic `__cluster_metadata`，3.3+ 版本生产可用。它带来架构简化、元数据性能提升、故障恢复加快、强一致性四大优势，并支持 combined（混合部署）和 separated（分离部署）两种模式。

## KRaft 部署配置与迁移

### Layer 1 — KRaft 模式基础配置

KRaft 模式通过 `process.roles` 定义节点角色，`controller.quorum.voters` 配置 Raft 投票者列表，无需任何 ZK 相关配置。

```properties
# server.properties — KRaft 模式基础配置（替代 zookeeper.connect）

# 节点角色：broker / controller / broker,controller（combined）
process.roles=broker,controller

# 节点 id（集群内唯一）
node.id=1

# Raft 报票者列表（格式：nodeId@host:port，controller 监听端口）
# 3 节点 Raft 多数派 = 2，容忍 1 个节点故障
controller.quorum.voters=1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093

# 监听器配置
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
controller.listener.names=CONTROLLER
inter.broker.listener.name=PLAINTEXT
advertised.listeners=PLAINTEXT://kafka-1:9092

# 监听器安全协议映射
listener.security.protocol.map=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,SSL:SSL,SASL_PLAINTEXT:SASL_PLAINTEXT,SASL_SSL:SASL_SSL

# 日志目录（KRaft 元数据也存这里）
log.dirs=/var/lib/kafka/data

# --- 注意：KRaft 模式下以下 ZK 配置全部删除 ---
# zookeeper.connect=zk1:2181        ← 删除
# zookeeper.connection.timeout.ms=  ← 删除
```

与 ZK 模式最大的区别是配置中不再出现 `zookeeper.connect`，取而代之的是 `controller.quorum.voters`。Raft 协议内置于 Kafka 进程，元数据复制走 9093 端口的 CONTROLLER 监听器。

### Layer 2 — Combined Mode 部署

Combined Mode 下每个节点同时运行 Controller 和 Broker，3 个节点即可满足 Raft 多数派，适合中小规模集群。

```properties
# === Combined Mode：3 节点同时充当 Controller + Broker ===

# --- Node 1 (server-1.properties) ---
process.roles=broker,controller
node.id=1
controller.quorum.voters=1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
controller.listener.names=CONTROLLER
inter.broker.listener.name=PLAINTEXT
advertised.listeners=PLAINTEXT://kafka-1:9092
log.dirs=/var/lib/kafka/data-1

# --- Node 2 (server-2.properties) ---
process.roles=broker,controller
node.id=2
controller.quorum.voters=1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
controller.listener.names=CONTROLLER
inter.broker.listener.name=PLAINTEXT
advertised.listeners=PLAINTEXT://kafka-2:9092
log.dirs=/var/lib/kafka/data-2

# --- Node 3 (server-3.properties) ---
process.roles=broker,controller
node.id=3
controller.quorum.voters=1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
controller.listener.names=CONTROLLER
inter.broker.listener.name=PLAINTEXT
advertised.listeners=PLAINTEXT://kafka-3:9092
log.dirs=/var/lib/kafka/data-3
```

```bash
# 格式化 KRaft 存储（首次启动前必须执行）
# 生成 Cluster ID
KAFKA_CLUSTER_ID="$(bin/kafka-storage.sh random-uuid)"
echo "Cluster ID: $KAFKA_CLUSTER_ID"    # 如：xtzWWN4bTjitpL3kfd9s5g

# 在每个节点格式化存储目录（用同一 Cluster ID）
bin/kafka-storage.sh format \
  --config config/kraft/server-1.properties \
  --cluster-id $KAFKA_CLUSTER_ID

# 启动各节点（3 个节点都运行同一命令，配置文件不同）
bin/kafka-server-start.sh config/kraft/server-1.properties
bin/kafka-server-start.sh config/kraft/server-2.properties
bin/kafka-server-start.sh config/kraft/server-3.properties

# 验证：查看 Raft Quorum 状态
bin/kafka-metadata-quorum.sh --bootstrap-server kafka-1:9092 describe --status
# 输出：
# ClusterId:              xtzWWN4bTjitpL3kfd9s5g
# LeaderId:               1
# LeaderEpoch:            3
# HighWatermark:          15
# MaxFollowerLag:         0
# MaxFollowerLagTimeMs:   0
```

Combined Mode 优势是部署简单、节点少，但 Controller 工作和 Broker 数据读写共享 CPU 和网络资源，大规模集群下可能互相影响。

### Layer 3 — Separated Mode 部署

Separated Mode 将 Controller 和 Broker 分离，Controller 节点专做元数据管理（Raft 选举、日志复制），Broker 节点只处理数据请求，可独立扩缩容。

```properties
# === Separated Mode：Controller 与 Broker 分离部署 ===

# --- Controller 节点 1 (controller-1.properties) ---
process.roles=controller                    # 仅 Controller
node.id=1
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093
listeners=CONTROLLER://:9093                # 仅 Controller 监听器
controller.listener.names=CONTROLLER
log.dirs=/var/lib/kafka/controller-meta-1
# Controller 节点不需要 PLAINTEXT 监听器，不处理数据请求

# --- Controller 节点 2 (controller-2.properties) ---
process.roles=controller
node.id=2
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093
listeners=CONTROLLER://:9093
controller.listener.names=CONTROLLER
log.dirs=/var/lib/kafka/controller-meta-2

# --- Controller 节点 3 (controller-3.properties) ---
process.roles=controller
node.id=3
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093
listeners=CONTROLLER://:9093
controller.listener.names=CONTROLLER
log.dirs=/var/lib/kafka/controller-meta-3

# --- Broker 节点 4 (broker-4.properties) ---
process.roles=broker                        # 仅 Broker
node.id=4
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093
listeners=PLAINTEXT://:9092                 # 仅数据监听器
inter.broker.listener.name=PLAINTEXT
advertised.listeners=PLAINTEXT://broker-1:9092
log.dirs=/var/lib/kafka/data-4
# Broker 通过 controller.quorum.voters 发现 Controller，不需要 CONTROLLER 监听器

# --- Broker 节点 5 (broker-5.properties) ---
process.roles=broker
node.id=5
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093
listeners=PLAINTEXT://:9092
inter.broker.listener.name=PLAINTEXT
advertised.listeners=PLAINTEXT://broker-2:9092
log.dirs=/var/lib/kafka/data-5
```

```bash
# 启动顺序：先启动 Controller 集群（3 个），再启动 Broker
# Controller 集群形成 Raft 多数派后，Broker 才能注册

# 启动 3 个 Controller 节点
for i in 1 2 3; do
  bin/kafka-server-start.sh config/kraft/controller-$i.properties &
done

# 等待 Raft Leader 选举完成
bin/kafka-metadata-quorum.sh --bootstrap-server controller-1:9093 describe --status

# 启动 Broker 节点（可按需扩容，不影响 Controller）
bin/kafka-server-start.sh config/kraft/broker-4.properties &
bin/kafka-server-start.sh config/kraft/broker-5.properties &

# 验证 Broker 已注册
bin/kafka-broker-api-versions.sh --bootstrap-server broker-1:9092 | head -5
```

Separated Mode 的核心价值在于角色隔离——Controller 的 Raft 选举和元数据复制不受 Broker 大流量影响，Broker 扩缩容也不影响元数据稳定性，适合大规模生产集群。

### Layer 4 — ZK 到 KRaft 迁移步骤

从 ZK 模式迁移到 KRaft 需要经历"双写阶段"（ZK 和 KRaft 同时维护元数据），确保迁移过程不中断服务。

```bash
# === ZK → KRaft 迁移步骤（Kafka 3.4+ 提供迁移工具）===

# 阶段 0：前置检查
# - 确认 Kafka 版本 >= 3.4（推荐 3.6+）
# - 确认所有 Broker 在线且健康
bin/kafka-cluster.sh --bootstrap-server kafka-1:9092 cluster-id
# - 备份 ZK 元数据
bin/zookeeper-shell.sh zk1:2181 get /brokers > /backup/brokers-backup.json

# 阶段 1：在现有 ZK 模式 Broker 上启用 KRaft 迁移模式
# 修改 server.properties，添加迁移配置（重启每个 Broker）
cat >> config/server.properties << 'EOF'
# 启用 ZK → KRaft 迁移
zookeeper.metadata.migration.enable=true
# 配置 KRaft Controller Quorum（3 个新 Controller 节点）
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093
controller.listener.names=CONTROLLER
listener.security.protocol.map=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
EOF

# 逐个重启 Broker（滚动重启，保持集群可用）
bin/kafka-server-start.sh config/server.properties

# 阶段 2：部署 KRaft Controller 节点（Separated Mode）
# 在 controller-1/2/3 上启动纯 Controller 节点
bin/kafka-storage.sh format \
  --config config/kraft/controller-1.properties \
  --cluster-id <原集群-cluster-id>
bin/kafka-server-start.sh config/kraft/controller-1.properties &

# 阶段 3：迁移元数据（Controller 从 ZK 拉取并写入 Raft 日志）
# 查看迁移进度
bin/kafka-metadata-quorum.sh --bootstrap-server kafka-1:9092 describe --status
# 等待迁移完成（MigrationState: IN_PROGRESS → COMPLETED）

# 阶段 4：移除 ZK 依赖（迁移完成后）
# 移除每个 Broker 的 zookeeper.* 配置，添加 KRaft 配置
cat > config/server.properties << 'EOF'
process.roles=broker
node.id=0
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093
listeners=PLAINTEXT://:9092
inter.broker.listener.name=PLAINTEXT
advertised.listeners=PLAINTEXT://kafka-1:9092
log.dirs=/var/lib/kafka/data
EOF

# 滚动重启所有 Broker，确认全部以纯 KRaft Broker 模式运行

# 阶段 5：验证并下线 ZK
# 验证集群功能正常
bin/kafka-topics.sh --bootstrap-server kafka-1:9092 --list
bin/kafka-consumer-groups.sh --bootstrap-server kafka-1:9092 --list

# 确认无误后，关闭 ZooKeeper 集群
# zkServer.sh stop
```

迁移的核心是"双写过渡"——迁移期间 ZK 和 KRaft 同时维护元数据，Controller 边从 ZK 拉取边写入 Raft 日志。完成后移除 ZK 配置，Broker 切换为纯 KRaft 模式，最后安全下线 ZK 集群。整个迁移过程对客户端透明，不需要停机。

## KRaft 部署模式对比

| 维度 | Combined Mode | Separated Mode |
|---|---|---|
| 角色配置 | `process.roles=broker,controller` | Controller: `process.roles=controller`；Broker: `process.roles=broker` |
| 节点数量 | 少（3 节点即可） | 多（Controller 3 + Broker N） |
| 资源隔离 | Controller 与 Broker 共享资源 | Controller 与 Broker 资源完全隔离 |
| 适用规模 | 中小规模集群 | 大规模生产集群 |
| 扩缩容 | 整体扩缩，影响元数据 | Broker 可独立扩缩容 |
| 故障影响 | Broker 高负载可能影响 Controller | 互不影响 |
| 部署复杂度 | 简单（一套配置） | 较复杂（两套配置） |
| 运维成本 | 低 | 中（需分别管理两组节点） |
| Raft 多数派 | 包含数据节点 | 仅 Controller 节点参与 |
| 元数据性能 | 受数据流量干扰 | 稳定（专用资源） |
| 推荐场景 | 开发测试、中小生产 | 大规模生产、超大规模集群 |

## 一句话总结

**KRaft 是 Kafka 把元数据管理从"外挂 ZooKeeper"内化为"自带 Raft 日志"的架构进化，Combined Mode 用最少节点兼顾两种角色，Separated Mode 用角色隔离换取大规模集群的元数据稳定性，新项目应直接从 KRaft 起步。**
