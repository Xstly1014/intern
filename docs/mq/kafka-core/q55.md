# Q55 消息格式演进

Kafka 消息格式经历了 v0（0.9 前）、v1（0.9-0.10）、v2（0.11+）三个版本，v2 通过 Record Batch 打包、varint 变长编码、Header 支持、事务字段四大改进，成为高吞吐和事务特性的基础，生产环境必须使用 v2 格式。

## 消息格式配置与代码实战

### Layer 1 — 消息 Headers 使用

v2 格式支持每条消息携带自定义 headers（键值对），常用于传递 traceId、租户标识等业务元信息，无需侵入 message body。

```java
// Spring Kafka：发送带自定义 headers 的消息
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.support.KafkaHeaders;
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;
import org.apache.kafka.common.header.Headers;

@Service
public class OrderEventPublisher {

    private final KafkaTemplate<String, String> kafkaTemplate;

    public OrderEventPublisher(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    // 方式一：使用 MessageBuilder 设置 headers
    public void publishOrderCreated(Order order, String traceId) {
        Message<String> message = MessageBuilder
            .withPayload(toJson(order))
            .setHeader(KafkaHeaders.TOPIC, "order-events")
            .setHeader(KafkaHeaders.KEY, order.getOrderId())       // partition key
            .setHeader("traceId", traceId)                          // 自定义 header
            .setHeader("eventType", "ORDER_CREATED")                // 自定义 header
            .setHeader("tenantId", order.getTenantId())             // 租户标识
            .setHeader("source", "mobile-app")                      // 来源标识
            .build();

        kafkaTemplate.send(message);
    }

    // 方式二：使用 ProducerRecord 直接设置 headers
    public void publishWithRawHeaders(Order order) {
        ProducerRecord<String, String> record = new ProducerRecord<>(
            "order-events",
            null,                          // partition（null 表示由 partitioner 决定）
            order.getOrderId(),            // key
            toJson(order)                  // value
        );

        // 添加自定义 headers（v2 格式专属能力）
        record.headers().add("traceId", traceId.getBytes(StandardCharsets.UTF_8));
        record.headers().add("version", "2.0".getBytes(StandardCharsets.UTF_8));
        record.headers().add("schema", "order-v3".getBytes(StandardCharsets.UTF_8));

        kafkaTemplate.send(record);
    }
}

// 消费端读取 headers
@KafkaListener(topics = "order-events", groupId = "order-service")
public void onOrderEvent(
        @Payload String payload,
        @Header(KafkaHeaders.RECEIVED_KEY) String key,
        @Header(value = "traceId", required = false) String traceId,      // 读取自定义 header
        @Header(value = "eventType", required = false) String eventType,
        ConsumerRecord<String, String> record
) {
    // headers 不在 payload 中，不侵入消息体结构
    log.info("收到订单事件 traceId={} type={} key={}", traceId, eventType, key);

    // 也可从 ConsumerRecord 直接遍历所有 headers
    Headers headers = record.headers();
    headers.forEach(h -> log.debug("header: {} = {}", h.key(), new String(h.value())));
}
```

Headers 的价值在于业务元信息与消息体解耦——traceId、租户标识等不需要塞进 JSON payload，消费端按需读取，不影响消息体的序列化结构。

### Layer 2 — 幂等 Producer 配置

v2 格式引入 `producerId` 和 `epoch` 字段，使 Broker 能识别并丢弃重试导致的重复消息，实现幂等发送。

```java
// Spring Kafka：幂等 Producer 配置（exactly once 语义的基础）
@Configuration
public class IdempotentProducerConfig {

    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka-1:9092,kafka-2:9092");

        // === 幂等配置（依赖 v2 消息格式的 producerId + epoch）===
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);     // 开启幂等
        props.put(ProducerConfig.ACKS_CONFIG, "all");                   // 幂等要求 acks=all
        props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);    // 无限重试（幂等下安全）
        props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5); // <= 5（幂等限制）

        // 序列化
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        return new DefaultKafkaProducerFactory<>(props);
    }

    @Bean
    public KafkaTemplate<String, String> kafkaTemplate() {
        return new KafkaTemplate<>(producerFactory());
    }
}
```

```properties
# application.yml 方式配置
spring:
  kafka:
    producer:
      bootstrap-servers: kafka-1:9092,kafka-2:9092
      properties:
        enable.idempotence: true          # 开启幂等（Broker 端去重）
        acks: all                          # 必须为 all
        retries: 2147483647                # Integer.MAX_VALUE
        max.in.flight.requests.per.connection: 5  # 幂等下最大 5
```

幂等机制的工作原理：Producer 启动时向 Broker 申请一个全局唯一的 `producerId`，每条消息携带递增的 `sequence number`。Broker 端为每个 `<producerId, partition>` 维护最新的 sequence，收到旧 sequence 的消息直接丢弃。`epoch` 用于 Producer 重启后区分新旧实例，防止"僵尸 Producer"写入。

### Layer 3 — 事务 Producer 配置

v2 格式的事务字段（producerId、epoch、baseSeq）支持跨 Partition 的原子写入——要么全部成功，要么全部回滚。

```java
// Spring Kafka：事务 Producer 配置（跨 Partition 原子写入）
@Configuration
public class TransactionalProducerConfig {

    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka-1:9092");

        // === 幂等（事务前提）===
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        props.put(ProducerConfig.ACKS_CONFIG, "all");

        // === 事务配置（依赖 v2 格式的 producerId + epoch）===
        // transactional.id 必须唯一且稳定（跨重启不变）
        // Broker 用它区分事务 Producer 的"世代"，防止僵尸实例
        props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-tx-producer-1");
        props.put(ProducerConfig.TRANSACTION_TIMEOUT_CONFIG, 60000);  // 事务超时 60s

        return new DefaultKafkaProducerFactory<>(props);
    }

    @Bean
    public KafkaTemplate<String, String> kafkaTemplate() {
        return new KafkaTemplate<>(producerFactory());
    }

    // 事务管理器：将 Kafka 事务与 Spring 事务统一管理
    @Bean
    public KafkaTransactionManager<String, String> kafkaTransactionManager(
            ProducerFactory<String, String> pf) {
        return new KafkaTransactionManager<>(pf);
    }
}
```

```java
// 业务代码：使用 @Transactional 实现跨 Partition 原子写入
@Service
public class OrderTransactionalService {

    private final KafkaTemplate<String, String> kafkaTemplate;

    // 方式一：注解方式（配合 KafkaTransactionManager）
    @Transactional
    public void processOrder(Order order) {
        // 多个 Topic 写入在同一事务内，要么全部可见，要么全部不可见
        kafkaTemplate.send("order-events", order.getOrderId(), toJson(order));
        kafkaTemplate.send("inventory-events", order.getProductId(),
            toJson(buildInventoryEvent(order)));
        kafkaTemplate.send("payment-events", order.getOrderId(),
            toJson(buildPaymentEvent(order)));
        // 如果中间抛异常，三条消息全部回滚（对消费者不可见）
    }

    // 方式二：编程式事务（精确控制事务边界）
    public void processInTransaction(Order order) {
        kafkaTemplate.executeInTransaction(operations -> {
            operations.send("order-events", order.getOrderId(), toJson(order));
            operations.send("inventory-events", order.getProductId(),
                toJson(buildInventoryEvent(order)));

            if (order.getAmount().compareTo(BigDecimal.ZERO) <= 0) {
                throw new IllegalStateException("金额异常，事务回滚");
            }

            operations.send("payment-events", order.getOrderId(),
                toJson(buildPaymentEvent(order)));
            return true;   // 正常提交事务
        });
    }
}
```

```properties
# Broker 端事务相关配置（server.properties）
transaction.state.log.replication.factor=3          # 事务状态日志副本数
transaction.state.log.min.isr=2                     # 事务状态日志最小 ISR
transaction.max.timeout.ms=900000                   # 最大事务超时 15 分钟
# 消费端：配置 isolation.level 控制事务可见性
# read_committed：只消费已提交事务的消息（默认）
# read_uncommitted：消费所有消息（包括未提交事务的）
```

事务的核心流程：Producer 调用 `beginTransaction()` → 发送多条消息（携带 producerId 和递增 sequence）→ 调用 `commitTransaction()` 写入 `__transaction_state` 标记提交。消费端 `isolation.level=read_committed` 时只读取已提交事务的消息，未提交的被过滤。`epoch` 防止僵尸 Producer——新实例 epoch 更大，旧实例的消息会被拒绝。

### Layer 4 — 消息格式版本配置

Broker 端通过 `message.format.version` 控制 Topic 存储的消息格式版本，决定能否使用 v2 的高级特性。

```properties
# === Broker 端消息格式版本配置（server.properties）===

# 全局默认消息格式版本（新集群建议直接设为 3.0）
# 该值影响新建 Topic 的 log.message.format.version
log.message.format.version=3.0

# inter.broker.protocol.version（Broker 间通信协议版本）
inter.broker.protocol.version=3.0

# 消息格式版本降级保护（消息下发给老消费者时转换格式）
# 当消费者版本 < message.format.version 时，Broker 自动转换
# 转换有 CPU 开销，建议所有消费者升级到 0.11+ 避免转换
```

```bash
# 查看 Topic 当前的消息格式版本
bin/kafka-topics.sh --bootstrap-server kafka-1:9092 \
  --describe --topic order-events

# 查看 Topic 级别配置
bin/kafka-configs.sh --bootstrap-server kafka-1:9092 \
  --entity-type topics --entity-name order-events --describe
# 输出可能包含：
#   message.format.version=3.0

# 设置 Topic 级别消息格式版本（覆盖全局默认）
bin/kafka-configs.sh --bootstrap-server kafka-1:9092 \
  --entity-type topics --entity-name order-events \
  --alter --add-config message.format.version=2.0

# === 版本升级时的滚动升级策略 ===
# 1. 先升级所有 Broker 的 inter.broker.protocol.version（不改变消息格式）
# 2. 再逐个升级 Broker 的 log.message.format.version
# 3. 最后升级所有客户端到 0.11+ 以使用 v2 格式

# 警告：如果 Broker 设为 v2 但存在 < 0.11 的消费者，
# Broker 会做格式转换（v2 → v1），CPU 开销大且丢失 headers
```

```java
// 客户端版本检查（确保 Producer/Consumer 支持 v2 格式）
// Kafka Client 0.11+ 默认使用 v2 格式发送，无需额外配置
// 但需确认 Broker 的 message.format.version >= 0.11

// Producer 端无需显式指定 magic version，客户端根据 Broker 版本自动协商
// 如果 Broker 端 message.format.version < 0.11，则 Producer 发送的 v2 消息会被降级

// 验证：检查 Producer 发送的消息是否为 v2 格式
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka-1:9092");
// 0.11+ 客户端默认发送 v2，通过 magic byte = 2 标识
// 可用 kafka-dump-log.sh 查看实际存储格式
```

```bash
# 用 kafka-dump-log.sh 验证磁盘上的实际消息格式
bin/kafka-dump-log.sh \
  --files /var/lib/kafka/data/order-events-0/00000000000000000000.log \
  --print-data-log

# v2 格式输出（magic: 2）：
# baseOffset: 0 lastOffset: 99 count: 100 baseSequence: 0
#   producerId: 1001 producerEpoch: 0 partitionLeaderEpoch: 0
#   isTransactional: false isControl: false
#   position: 0 CreateTime: 1690000000000 size: 4096
#   magic: 2  (← v2 格式标识)
#   crc: 1234567890 isvalid: true

# v1 格式输出（magic: 1）：
# offset: 0 position: 0 CreateTime: 1690000000000
#   keysize: 5 valuesize: 100 magic: 1  (← v1 格式标识)
#   compresscodec: NONE crc: 1234567890
```

消息格式版本的核心权衡：`message.format.version` 设为 v2 才能享受 Batch 打包、varint、headers、事务等全部能力，但要求所有消费者支持 0.11+。生产环境应确保全链路客户端版本统一升级后再切换，避免 Broker 做格式转换的 CPU 开销和 headers 丢失。

## 消息格式版本对比

| 维度 | v0（0.9 前） | v1（0.9-0.10） | v2（0.11+） |
|---|---|---|---|
| magic 版本号 | 0 | 1 | 2 |
| timestamp 字段 | 无 | 有（CreateTime / LogAppendTime） | 有（baseTimestamp + timestampDelta） |
| 消息组织方式 | 每条独立 | 每条独立 | Record Batch 打包多条共享 metadata |
| 编码方式 | 固定长度 | 固定长度 | varint 变长编码（小数字省空间） |
| offset 存储 | 绝对值 | 绝对值 | offsetDelta 增量（varint 编码） |
| Header 支持 | 不支持 | 不支持 | 支持自定义键值对 headers |
| 事务支持 | 不支持 | 不支持 | producerId + epoch + baseSeq |
| 幂等发送 | 不支持 | 不支持 | 支持（sequence number 去重） |
| 压缩方式 | gzip/snappy | gzip/snappy/lz4 | gzip/snappy/lz4/zstd（Batch 整体压缩） |
| 空间效率 | 低 | 中 | 高（Batch 共享 + varint，节省 ~60%） |
| 生产可用版本 | Kafka 0.7+ | Kafka 0.9+ | Kafka 0.11+（推荐 3.0+） |
| 生产建议 | 已废弃 | 兼容老系统 | 必须使用（高吞吐与事务基础） |

## 一句话总结

**v2 格式是 Kafka 从"逐条独立传输"走向"批量打包 + 变长编码 + 事务原子性"的分水岭，它用 Record Batch 共享 metadata 压缩空间，用 headers 解耦业务元信息，用 producerId/epoch 支撑幂等与事务，是 Kafka 高吞吐和 Exactly-Once 语义的格式基石。**
