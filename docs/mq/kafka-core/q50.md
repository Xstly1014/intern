# Q50 __consumer_offsets

Kafka 0.9+ 将消费者 Offset 存储在 Kafka 内部的特殊 Topic `__consumer_offsets` 中，默认 50 个 Partition、副本数为 3。选择 Kafka 而非 ZooKeeper 的原因有三点：ZooKeeper 不适合高频写入而 Kafka 本身就是高吞吐写入系统、Offset 与消息数据在同一系统事务性更好、少依赖一个外部系统简化架构。Offset 以 `(group_id, topic, partition) → offset` 的 key-value 形式存储，key 的哈希值决定存到 `__consumer_offsets` 的哪个 Partition，消费者启动时先从此 Topic 读取上次消费位置。

上图展示了 `__consumer_offsets` 的完整存储机制。左侧是核心流程：Consumer Group 中每个消费者提交 Offset 时，系统以 `(group_id, topic, partition)` 组合成 key，通过哈希取模 `hash(key) % 50` 定位到 `__consumer_offsets` 的某个 Partition（图中以 P12 高亮示例），Offset 值连同 metadata 和 timestamp 作为 Value 写入。消费者启动时反向读取该 Topic 定位上次消费位置，若无记录则根据 `auto.offset.reset` 配置决定从头或从尾开始。底部对比了 0.9 之前用 ZooKeeper 存 Offset 的方案与 0.9+ 用 Kafka 内部 Topic 存 Offset 的方案，ZooKeeper 方案因高频写入瓶颈和跨系统一致性问题已被废弃。

## __consumer_offsets 代码实践

### Layer 1 — 查看内部 Topic

```bash
# 查看 __consumer_offsets Topic 结构（默认 50 个 Partition）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic __consumer_offsets

# 输出示例：
# Topic: __consumer_offsets  PartitionCount: 50  ReplicationFactor: 3
# Topic: __consumer_offsets  Partition: 0   Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
# Topic: __consumer_offsets  Partition: 1   Leader: 2  Replicas: 2,3,1  Isr: 2,3,1

# 查看某个消费者组的 Offset 详情
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group my-consumer-group

# GROUP              TOPIC           PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
```

### Layer 2 — Offset 提交过程（Spring Kafka）

```java
/**
 * Offset 提交过程：Spring Kafka commitSync / commitAsync
 * 底层将 offset 写入 __consumer_offsets Topic
 */
@Configuration
public class KafkaConsumerConfig {

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, String>
            kafkaListenerContainerFactory(ConsumerFactory consumerFactory) {

        ConcurrentKafkaListenerContainerFactory<String, String> factory =
                new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(consumerFactory);
        factory.setConcurrency(3); // 3 个消费者线程

        // 手动提交 Offset（不依赖自动提交）
        factory.getContainerProperties()
                .setAckMode(ContainerProperties.AckMode.MANUAL);

        return factory;
    }
}

/**
 * 消费者监听器：手动提交 Offset 到 __consumer_offsets
 */
@Component
@Slf4j
public class OrderEventConsumer {

    @KafkaListener(topics = "order-events", groupId = "my-consumer-group")
    public void consume(ConsumerRecord<String, String> record,
                        Acknowledgment acknowledgment) {
        try {
            log.info("收到消息: partition={}, offset={}, key={}, value={}",
                    record.partition(), record.offset(), record.key(), record.value());

            // 业务处理
            processOrder(record.value());

            // 手动同步提交：将 offset 写入 __consumer_offsets
            // 底层发送 OffsetCommitRequest 到 Coordinator Broker
            acknowledgment.acknowledge();

        } catch (Exception e) {
            log.error("消费失败，不提交 offset，下次 poll 会重新拉取", e);
            // 不调用 acknowledge()，offset 不会提交
        }
    }

    private void processOrder(String orderJson) {
        // 业务逻辑处理
    }
}
```

### Layer 3 — 消费者启动读取 Offset

```yaml
# application.yml — 消费者启动时的 Offset 读取策略
spring:
  kafka:
    consumer:
      group-id: my-consumer-group
      # auto.offset.reset: 消费者首次加入或找不到已提交 offset 时的行为
      # earliest — 从最早的消息开始消费（可能重复消费）
      # latest   — 只消费启动之后新产生的消息（可能丢失消息）
      # none     — 找不到 offset 则抛异常
      auto-offset-reset: earliest
      # enable.auto.commit: 是否自动提交 offset 到 __consumer_offsets
      # 生产环境建议关闭，改用手动提交避免消息丢失
      enable-auto-commit: false
      auto-commit-interval: 5000 # 自动提交间隔（毫秒），仅 enable-auto-commit=true 时生效
```

```java
/**
 * 消费者启动时的 Offset 定位流程
 * 1. 消费者向 Coordinator 发送 JoinGroupRequest 加入消费者组
 * 2. Coordinator 触发 Rebalance，分配 Partition 给消费者
 * 3. 消费者从 __consumer_offsets 读取上次提交的 offset
 * 4. 若无记录，根据 auto.offset.reset 决定起始位置
 */
@Component
@Slf4j
public class ConsumerStartupListener {

    private final ConsumerFactory consumerFactory;

    public ConsumerStartupListener(ConsumerFactory consumerFactory) {
        this.consumerFactory = consumerFactory;
    }

    /**
     * 手动创建消费者并定位 offset
     */
    public void manualOffsetSeek() {
        try (KafkaConsumer<String, String> consumer =
                     consumerFactory.createConsumer()) {

            // 订阅 Topic，触发 Rebalance
            consumer.subscribe(List.of("order-events"));

            // 第一次 poll 触发 Rebalance 和 offset 定位
            ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(5000));

            // 手动定位到指定 offset（可用于跳过或回溯）
            consumer.seek(new TopicPartition("order-events", 0), 1000L);
            log.info("已手动定位到 partition=0, offset=1000");

            // 正常消费循环
            while (true) {
                records = consumer.poll(Duration.ofMillis(1000));
                for (ConsumerRecord<String, String> record : records) {
                    log.info("消费: p={}, offset={}", record.partition(), record.offset());
                }
                consumer.commitSync(); // 提交到 __consumer_offsets
            }
        }
    }
}
```

### Layer 4 — Offset 存储格式

```java
/**
 * __consumer_offsets 存储的 key-value 结构
 *
 * Key 结构（用于 hash 定位 Partition）:
 *   - group_id     → 消费者组名
 *   - topic        → 消费的 Topic
 *   - partition    → 消费的 Partition 编号
 *   targetPartition = Utils.abs(hashCode(group_id + topic + partition)) % 50
 *
 * Value 结构（存储 offset 和元数据）:
 *   - offset       → 消费到的位置
 *   - metadata     → 自定义元数据（可选）
 *   - timestamp    → 提交时间戳
 *   - leaderEpoch   → Leader 轮次（防止脑裂）
 */
public class OffsetStorageDemo {

    /**
     * 模拟 __consumer_offsets 中存储的记录格式
     */
    public static class OffsetRecord {
        private String groupId;        // 消费者组
        private String topic;          // Topic 名称
        private int partition;         // Partition 编号
        private long offset;           // 当前消费位置
        private String metadata;       // 自定义元数据
        private long timestamp;        // 提交时间戳
        private int leaderEpoch;       // Leader 轮次

        // 计算 target Partition
        // 实际 Kafka 内部: Utils.abs(
        //   (groupId + topic + partition).hashCode()) % 50
        public int calculateTargetPartition() {
            String compositeKey = groupId + topic + partition;
            return Math.abs(compositeKey.hashCode()) % 50;
        }

        // Getters and Setters...
    }

    /**
     * __consumer_offsets 中还有两类特殊记录
     */
    public static class OffsetTopicRecordTypes {
        // 1. Offset 记录：存储 (group, topic, partition) → offset
        //    消费者提交 offset 时写入

        // 2. Group Metadata 记录：存储消费者组元数据
        //    包含成员列表、分区分配方案、Generation ID 等
        //    Rebalance 时由 Coordinator 写入

        // 两类记录通过不同的 Key 类型区分
        // Offset Key     → group_id + topic + partition
        // Metadata Key   → group_id（仅此一项）
    }
}
```

## ZK 存 Offset vs Kafka 存 Offset

| 维度 | ZK 存 Offset (0.9 之前) | Kafka 存 Offset (0.9+) |
|------|------------------------|------------------------|
| 存储位置 | ZooKeeper znode 路径 `/consumers/{group}/offsets/{topic}/{partition}` | Kafka 内部 Topic `__consumer_offsets` |
| 写入性能 | ZK 不适合高频写入，每次提交需写 znode 并触发 watch | Kafka 原生高吞吐写入，批量顺序写日志 |
| 一致性 | 跨系统（ZK + Kafka），事务性差，可能 offset 和消息状态不一致 | 同一系统内，事务性更好 |
| 架构依赖 | 依赖 ZK + Kafka 两套系统 | 仅依赖 Kafka（ZK 仅用于集群元数据管理） |
| 可扩展性 | ZK 集群写入瓶颈限制消费者数量扩展 | Kafka Partition 扩展性强，支持大规模消费者组 |
| 故障恢复 | ZK 故障影响 offset 读取 | Kafka Broker 故障有副本机制保障 |
| 羊群效应 | 消费者大量同时 watch znode 触发 herd effect | 无 watch 机制，通过 Coordinator 协调避免 |
| Group 管理 | 消费者组成员存储在 `/consumers/{group}/owners` | Group Metadata 存储在 `__consumer_offsets` 中 |
| 偏移精度 | 可能因 ZK 写入延迟导致 offset 不精确 | 顺序写入日志，offset 精度高 |

## 一句话总结

**`__consumer_offsets` 是 Kafka 0.9+ 将消费者 Offset 从 ZooKeeper 迁移到 Kafka 内部 Topic 的核心设计，通过 `(group_id, topic, partition)` 哈希定位 50 个 Partition 实现高吞吐写入和系统内事务一致性。**
