# Q45 ISR 机制

ISR（In-Sync Replicas）是与 Leader 保持同步的副本集合（含 Leader 自己），Follower 持续从 Leader 拉取数据，落后超过 `replica.lag.time.max.ms`（默认 10s）就被踢出 ISR、追上后重新加入。Leader 故障时 Controller 只从 ISR 中选新 Leader，因为 ISR 里的副本数据最接近 Leader、选举它们数据丢失最少；若开启脏选举从非 ISR 选，可用性高但可能丢数据。

图中 ISR 边界（绿色虚线框）内是 Leader 与两个同步正常的 Follower，Broker 3 因 LEO 落后 Leader 超过 10s 被踢出 ISR。Leader 宕机后，推荐做法是从 ISR 中选举 Broker 2 为新 Leader（Clean Election，数据不丢）；若开启脏选举则可能选到 Broker 3，虽然集群恢复可用但会丢失 18 条尚未同步的消息。下面的代码展示如何配置 ISR 阈值、查看 ISR 状态以及配合 `acks=all` 使用。

## ISR 配置与选举实践代码

### Layer 1 — ISR 相关配置

```bash
# server.properties
# Follower 落后 Leader 超过该时间（默认 10s）即被踢出 ISR
replica.lag.time.max.ms=10000
# 写入成功至少需要的 ISR 副本数，与 acks=all 配合
# 若 ISR 中副本数 < 该值，Producer 写入会抛 NotEnoughReplicasException
min.insync.replicas=2
# 副本因子
default.replication.factor=3
```

`replica.lag.time.max.ms` 是 ISR 进出的判据：Follower 在该时间内追上 Leader 的 LEO 就留在 ISR，否则被移除。`min.insync.replicas` 则是写入的"刹车"——当可用副本不足时宁可拒绝写入也不冒丢数据的风险。

### Layer 2 — 查看 ISR 状态

```bash
# 查看 Topic 的副本分布与 ISR 集合
kafka-topics.sh --bootstrap-server broker0:9092 \
  --describe --topic order-topic

# 正常状态：3 个副本都在 ISR 中
# Topic: order-topic  Partition: 0  Leader: 0  Replicas: 0,1,2  Isr: 0,1,2

# Broker 3 同步落后后（此处假设 4 副本场景），ISR 缩减
# Topic: order-topic  Partition: 0  Leader: 0  Replicas: 0,1,2,3  Isr: 0,1,2

# 实时监控 ISR 缩减告警（可用 JMX 指标）
# kafka.server:type=ReplicaManager  UnderReplicatedPartitions
# 该值 > 0 表示存在副本不在 ISR 中的 Partition，应告警
```

`Isr` 列就是当前同步副本集合，运维应持续监控 `UnderReplicatedPartitions` 指标，一旦 ISR 缩减需立即排查 Follower 落后原因（网络、磁盘 IO、GC 等）。

### Layer 3 — unclean leader election 配置

```bash
# server.properties
# 生产环境强烈建议关闭脏选举，避免选到数据落后的副本造成丢失
unclean.leader.election.enable=false

# 若可用性优先于一致性（如日志类可丢数据场景），可开启
# unclean.leader.election.enable=true

# 动态修改（无需重启 Broker，Kafka 2.x+ 支持）
kafka-configs.sh --bootstrap-server broker0:9092 \
  --entity-type brokers --entity-default \
  --alter --add-config unclean.leader.election.enable=false
```

关闭脏选举意味着：当 ISR 为空（所有 Follower 都掉队）时集群宁可对该 Partition 不可写，也不选一个数据不全的副本当 Leader——这是用可用性换数据安全。

### Layer 4 — Producer acks=all 配合 ISR

```java
// acks=all：Leader 收到消息后等待所有 ISR 副本同步完成才返回成功
// 配合 min.insync.replicas=2，保证消息至少写入 2 个副本
Properties props = new Properties();
props.put("bootstrap.servers", "broker0:9092,broker1:9092,broker2:9092");
props.put("acks", "all");
props.put("enable.idempotence", "true"); // 幂等生产者，配合 acks=all 防重复
props.put("retries", Integer.MAX_VALUE);
props.put("max.in.flight.requests.per.connection", "5");

Producer<String, String> producer = new KafkaProducer<>(props);
try {
    // 若 ISR 中副本数 < min.insync.replicas，此处抛 NotEnoughReplicasException
    producer.send(new ProducerRecord<>("order-topic", "order-001", "payload")).get();
} catch (ExecutionException e) {
    // ISR 不足时的降级处理：重试或告警
    if (e.getCause() instanceof NotEnoughReplicasException) {
        System.err.println("ISR 副本不足，写入被拒绝，触发告警");
    }
}
```

`acks=all` + `min.insync.replicas=2` 是生产环境黄金组合：消息至少落到 2 个 ISR 副本才算写入成功，即使 Leader 立刻宕机，另一份副本也在 ISR 中可被安全选举。

| 维度 | 从 ISR 选举（推荐） | 从非 ISR 选举（脏选举） |
|---|---|---|
| 数据安全性 | 数据几乎不丢失 | 可能丢失大量未同步消息 |
| 可用性 | ISR 为空时 Partition 不可用 | 任何存活副本都可当选，可用性高 |
| 一致性 | 强一致，新 Leader 数据最全 | 弱一致，新 Leader 数据落后 |
| 适用场景 | 订单、支付等核心业务 | 日志、监控等可丢数据场景 |
| 配置 | unclean.leader.election.enable=false | unclean.leader.election.enable=true |
| 选举速度 | 仅 ISR 内选择，快 | 可选任意副本，快但风险高 |

## 一句话总结

**ISR 是 Leader 选举的"白名单"——只从同步跟得上的副本里选接班人，宁可短暂不可用也不让落后副本带病上岗。**
