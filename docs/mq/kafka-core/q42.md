# Q42 Topic 与 Partition

Topic 是逻辑消息分类，Partition 是 Topic 的物理分片——一个 Topic 包含多个 Partition，每个 Partition 是一个有序、不可变的追加日志（append-only log），消息按 key 哈希分配到特定 Partition，从而实现水平扩展、并行消费和负载均衡。

上图展示了一个 Topic 拆分为 3 个 Partition 的结构：Producer 发送消息时携带 key（如 orderId），Kafka 对 key 取哈希后对 Partition 数取模，将消息路由到固定 Partition。每个 Partition 是一个独立的 append-only 日志，分布在不同 Broker 上——Partition 内消息按 offset 严格有序，但跨 Partition 不保证顺序。注意 order-001、order-004、order-007 都进了 Partition 1（key 模 3 = 1），而 order-003、order-006 进了 Partition 0（key 模 3 = 0），相同 key 永远落同一 Partition。

## 代码实现：Topic 与 Partition 操作

### Layer 1 — Topic 创建与 Partition 指定

```bash
# 命令行创建 Topic：12 个 Partition，3 副本
kafka-topics.sh --create \
  --bootstrap-server broker1:9092 \
  --topic topic-order \
  --partitions 12 \
  --replication-factor 3

# 查看 Topic 分区分布
kafka-topics.sh --describe \
  --bootstrap-server broker1:9092 \
  --topic topic-order
```

```java
// AdminClient 编程式创建
public void createTopic() {
    AdminClient admin = AdminClient.create(props);
    // 12 个 Partition，3 个副本
    NewTopic topic = new NewTopic("topic-order", 12, (short) 3);
    admin.createTopics(Collections.singleton(topic));
}
```

`--partitions 12` 决定了这个 Topic 的最大消费并行度——最多 12 个消费者同时消费。Partition 数创建后只能增加不能减少。

### Layer 2 — Producer 按 Key 路由到 Partition

```java
@Service
public class OrderProducer {
    @Autowired
    private KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public void send(OrderEvent event) {
        // key = orderId，Kafka 默认对 key 取哈希后取模路由
        // 相同 orderId 永远进同一 Partition，保证同一订单事件顺序
        kafkaTemplate.send("topic-order", event.getOrderId(), event);
    }
}
```

```java
// 自定义 Partitioner：按 userId 路由而非默认 key 哈希
public class UserIdPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        OrderEvent event = (OrderEvent) value;
        int numPartitions = cluster.partitionCountForTopic(topic);
        // 同一用户的订单事件进同一 Partition
        return Math.abs(event.getUserId().hashCode()) % numPartitions;
    }
}
```

默认分区器是 `DefaultPartitioner`：有 key 时按 `murmur2(key) % partitionCount` 路由，无 key 时走粘性分区（Sticky Partitioner）轮询。自定义 Partitioner 通过 `partitioner.class` 配置指定。

### Layer 3 — Consumer 从 Partition 消费

```java
@Component
@Slf4j
public class OrderConsumer {

    @KafkaListener(topics = "topic-order", groupId = "order-group")
    public void handle(
            @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
            @Header(KafkaHeaders.OFFSET) long offset,
            OrderEvent event) {
        log.info("P{} offset={} order={}", partition, offset, event.getOrderId());
        // 每个 Partition 内按 offset 顺序消费
        processOrder(event);
    }
}
```

消费者从分到的 Partition 中按 offset 顺序拉取消息，一个 Partition 只被 Consumer Group 内一个消费者消费。如果需要严格保证全局顺序，只能用 1 个 Partition（但牺牲了并行度）。

## Partition 数量影响对比

| 维度 | Partition 少 | Partition 多 |
|---|---|---|
| 吞吐量 | 低，并行度不足 | 高，多 Broker 分散负载 |
| 消费并行度 | 低，消费者数受限于 Partition 数 | 高，支持更多消费者并行 |
| Broker 利用率 | 集中在少数 Broker | 均匀分布到多 Broker |
| 元数据开销 | 小 | 大，Controller 管理成本高 |
| Rebalance 耗时 | 短 | 长，分区多重平衡慢 |
| 端到端延迟 | 低 | 略高，消费者协调更多分区 |
| 可靠性 | 副本分布有限 | 副本可分布更多 Broker |
| 文件句柄 | 少 | 多，每个 Partition 对应日志文件 |

## 一句话总结

**一句话总结：Partition 是 Kafka 把"一个 Topic 的海量消息"切成"多个可独立并行处理的有序日志"的物理手段——切得越多并行度越高但开销越大，切得越少顺序性越强但吞吐受限。**
