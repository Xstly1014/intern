# Q48 Rebalance 重平衡

Rebalance 是 Consumer Group 内 Partition 和消费者的重新分配过程。触发时机有三种：消费者加入（新启动或扩容）、消费者退出（宕机或主动关闭）、订阅的 Topic 变化（新增 Partition）。Rebalance 期间所有消费者停止消费（Stop The World），直到分配完成，频繁触发会导致消费延迟。

## Rebalance 代码分层

### Layer 1 — Rebalance 相关配置

Rebalance 的核心是三个超时参数：`session.timeout.ms` 控制心跳超时，`heartbeat.interval.ms` 控制心跳频率，`max.poll.interval.ms` 控制两次 poll 的最大间隔。参数设置不当会导致不必要的 Rebalance。

```yaml
spring:
  kafka:
    consumer:
      # 会话超时：消费者心跳超过此时间未上报，Broker 判定宕机触发 Rebalance
      # 默认 10s，业务处理慢时建议调大，避免误判
      session-timeout-ms: 30000

      # 心跳间隔：消费者发送心跳的频率
      # 建议为 session.timeout.ms 的 1/3，确保超时前能发 3 次心跳
      heartbeat-interval-ms: 10000

      # 两次 poll 最大间隔：消费者处理消息超过此时间也会触发 Rebalance
      # 默认 5min，批量处理或慢业务必须调大
      max-poll-interval-ms: 300000

      # 单次 poll 最大记录数：配合 max-poll-interval-ms 控制单批处理量
      # 处理慢就调小，确保在 max-poll-interval-ms 内处理完
      max-poll-records: 500
```

关键关系：`heartbeat.interval.ms` 应为 `session.timeout.ms` 的 1/3 左右，确保超时前至少发出 3 次心跳；`max-poll-records` 要配合 `max-poll-interval-ms` 确保单批消息能在间隔内处理完。

### Layer 2 — 分配策略配置

通过 `partition.assignment.strategy` 指定 Partition 分配策略。默认是 RangeAssignor，生产环境推荐 StickyAssignor 以减少 Rebalance 时的分区迁移。

```yaml
spring:
  kafka:
    consumer:
      properties:
        # 默认策略：RangeAssignor（按范围连续划分）
        # partition.assignment.strategy: org.apache.kafka.clients.consumer.RangeAssignor

        # 推荐策略：StickyAssignor（粘性分配，尽量保持原分配）
        partition.assignment.strategy: org.apache.kafka.clients.consumer.StickyAssignor

        # Kafka 2.4+ 增量协作策略（最优）
        # partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
```

切换到 StickyAssignor 后，当某个消费者退出时，只有该消费者持有的 Partition 会被重新分配，其余消费者的 Partition 保持不变，大幅减少重复消费。

### Layer 3 — ConsumerRebalanceListener 监听 Rebalance 事件

通过 `ConsumerRebalanceListener` 可以在 Rebalance 发生时执行自定义逻辑——最典型的用法是在分区被回收前同步提交 offset，避免重复消费。

```java
@Bean
public ConcurrentKafkaListenerContainerFactory<String, String> kafkaListenerContainerFactory(
        ConsumerFactory<String, String> consumerFactory) {
    ConcurrentKafkaListenerContainerFactory<String, String> factory =
            new ConcurrentKafkaListenerContainerFactory<>();
    factory.setConsumerFactory(consumerFactory);

    // 注册 Rebalance 监听器
    factory.getContainerProperties().setConsumerRebalanceListener(new ConsumerRebalanceListener() {

        @Override
        public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
            // 分区被回收前调用：同步提交当前 offset，防止 Rebalance 后重复消费
            log.info("分区即将被回收: {}", partitions);
            // 此处可通过 Acknowledgment 或手动 consumer.commitSync() 提交
            // 确保已处理但未提交的 offset 不丢失
        }

        @Override
        public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
            // 分配到新分区后调用：可做初始化工作
            // 例如从数据库恢复消费位置、预热缓存等
            log.info("分配到新分区: {}", partitions);
        }
    });

    return factory;
}
```

`onPartitionsRevoked` 是防止重复消费的关键回调——在分区被回收前提交已处理的 offset，确保 Rebalance 后新消费者不会从旧位置重新消费。

### Layer 4 — 增量协作 Rebalance 配置

Kafka 2.4+ 引入的 CooperativeStickyAssignor 将传统的 Eager Rebalance（全部撤销再重新分配）改为增量协作模式——只撤销需要迁移的分区，其余分区继续消费，大幅缩短 Stop The World 窗口。

```yaml
spring:
  kafka:
    consumer:
      properties:
        # Kafka 2.4+ 增量协作 Rebalance
        partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
```

```java
// ========== Eager vs Cooperative 对比 ==========
//
// 传统 Eager Rebalance（全部撤销 → 全部停止 → 重新分配）:
//   Consumer-0: [P0, P1] --撤销全部--> [] --停止--> [P0]    （P1 被迁移）
//   Consumer-1: [P2, P3] --撤销全部--> [] --停止--> [P1, P2, P3]
//   问题：即使 Consumer-0 保留 P0，也要先撤销再重新分配，全部 Stop The World
//
// 增量协作 Cooperative Rebalance（只撤销迁移分区 → 其余继续 → 增量分配）:
//   Consumer-0: [P0, P1] --只撤销 P1--> [P0] --继续消费--> [P0]    （P0 不停）
//   Consumer-1: [P2, P3] --不撤销--> [P2, P3] --增量获取 P1--> [P1, P2, P3]
//   优势：只有被迁移的 P1 短暂停止，P0/P2/P3 全程不停消费
//
// 注意：从 Eager 切换到 Cooperative 需要滚动重启，不能一次性全部切换
```

增量协作 Rebalance 的核心改进是把"全部撤销再分配"变成"只撤销迁移分区"，让大部分消费者在 Rebalance 期间保持消费不中断。

## Rebalance 分配策略对比

| 策略 | 分配方式 | 优点 | 缺点 |
|---|---|---|---|
| RangeAssignor | 按 Partition 序号范围连续划分，前 N/2 给第一个消费者 | 简单直观，Kafka 默认策略 | 多 Topic 时第一个消费者总是多分，不均衡 |
| RoundRobinAssignor | 所有 Topic 的 Partition 轮询逐个交替分配 | 跨 Topic 分配更均匀 | Rebalance 时分区大范围迁移 |
| StickyAssignor | 初始均匀分配，Rebalance 时尽量保持原分配不变 | 迁移最小，减少重复消费 | 实现逻辑稍复杂 |
| CooperativeStickyAssignor | 增量协作，只撤销需迁移的分区 | 其余分区不停消费，影响最小 | 需 Kafka 2.4+，滚动升级 |

## 一句话总结

**Rebalance 是 Consumer Group 的分区重分配机制——触发时全部消费者 Stop The World，通过调大超时参数避免误触发、使用 StickyAssignor 减少分区迁移、启用增量协作策略让大部分消费者不停消费，三者配合可将 Rebalance 影响降到最低。**
