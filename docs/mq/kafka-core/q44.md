# Q44 Leader 与 Follower

每个 Partition 有多个副本，其中一个是 Leader 负责该 Partition 的所有读写，其余是 Follower 从 Leader 异步拉取数据做同步、不直接服务客户端。读写都走 Leader 保证了一致性、简化了设计并维护全局顺序，Follower 的核心作用是高可用——Leader 故障时从 ISR 中的 Follower 选举新 Leader 继续提供服务。

图中展示了 Partition-0 在 3 个 Broker 上的 3 个副本：Broker 0 上的副本是 Leader，负责所有客户端读写；Broker 1、2 上的副本是 Follower，只从 Leader 异步 fetch 数据。生产者写消息和消费者读消息都只连 Leader，Follower 不服务任何客户端请求——这是 Kafka 与 MySQL 主从架构的本质区别，下面的代码演示了副本配置、客户端自动路由到 Leader 以及 Leader 故障切换的全过程。

## 副本配置与故障切换代码

### Layer 1 — 副本配置

```bash
# server.properties
# 副本总数：每个 Partition 有 3 个副本（1 Leader + 2 Follower）
default.replication.factor=3
# 写入成功需要的最小同步副本数，配合 acks=all 使用，防止只剩 1 个副本时仍写入
min.insync.replicas=2
```

副本因子决定数据冗余度，`min.insync.replicas` 决定容灾底线——两者配合才能在可用性与持久性之间取得平衡。

### Layer 2 — Producer 只写 Leader

```java
// Producer 只需知道 topic，Kafka 客户端自动路由到 Partition 的 Leader
Properties props = new Properties();
props.put("bootstrap.servers", "broker0:9092,broker1:9092,broker2:9092");
props.put("acks", "all");          // 等待所有 ISR 副本确认，保证不丢消息
props.put("retries", 3);           // 发送失败自动重试
props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");

Producer<String, String> producer = new KafkaProducer<>(props);
// 客户端从元数据获知 Partition-0 的 Leader 是 Broker 0，直接连它写入
producer.send(new ProducerRecord<>("order-topic", "order-001", "payload"));
```

Producer 完全不关心谁是 Leader——客户端通过 metadata 自动发现并连接 Leader，Leader 变化时自动重连新 Leader。

### Layer 3 — Consumer 只读 Leader

```java
// Consumer 同样只连 Leader 读消息，客户端自动发现 Leader 位置
Properties props = new Properties();
props.put("bootstrap.servers", "broker0:9092,broker1:9092,broker2:9092");
props.put("group.id", "order-consumer-group");
props.put("auto.offset.reset", "earliest");
props.put("enable.auto.commit", "false");
props.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Arrays.asList("order-topic"));
while (true) {
    // poll 时客户端向 Partition 的 Leader 发起 fetch 请求
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> r : records) {
        System.out.println(r.partition() + ":" + r.offset() + " " + r.value());
    }
    consumer.commitSync();
}
```

Consumer 和 Producer 一样只与 Leader 通信，Follower 永远不会接到消费请求，这保证了消费者看到的顺序与 Leader 写入顺序一致。

### Layer 4 — Leader 故障切换演示

```bash
# 1. 查看 Partition 的 Leader 和副本分布
kafka-topics.sh --bootstrap-server broker0:9092 \
  --describe --topic order-topic

# 输出示例：Leader 在 Broker 0，ISR 包含 0,1,2
# Topic: order-topic  Partition: 0  Leader: 0  Replicas: 0,1,2  Isr: 0,1,2

# 2. 模拟 Leader 所在 Broker 0 宕机（kill 进程）
# Controller 感知到 Broker 0 下线，从 ISR 中选举 Broker 1 为新 Leader

# 3. 再次查看，Leader 变为 1，读写自动恢复不受影响
kafka-topics.sh --bootstrap-server broker1:9092 \
  --describe --topic order-topic

# Topic: order-topic  Partition: 0  Leader: 1  Replicas: 0,1,2  Isr: 1,2
# Broker 0 已不在 ISR 中，Broker 1 接管成为 Leader
```

Leader 故障切换对客户端透明——Producer/Consumer 感知到连接断开后会刷新 metadata，自动连到新 Leader，整个过程通常在秒级完成。

| 维度 | Kafka Leader/Follower | MySQL 主从 |
|---|---|---|
| 读写路由 | 读写都走 Leader，Follower 不服务 | 主库写、从库可读 |
| 同步方式 | Follower 主动 pull 拉取 | 从库 relay log 回放 |
| 故障切换 | 从 ISR 选举新 Leader，秒级自动 | 需手动或 MHA 工具切换 |
| 一致性保证 | Leader 维护全局顺序 | 主从延迟可能导致读不一致 |
| 设计复杂度 | 客户端无需关心读写分离 | 需应用层读写分离逻辑 |
| Follower 定位 | 纯备份，待命接替 Leader | 承担读流量，读写分离 |

## 一句话总结

**Kafka 的 Leader 独揽读写、Follower 只做数据备份待命，用"单点服务 + 副本兜底"换取强一致性与高可用。**
