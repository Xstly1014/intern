# Q46 Controller 控制器

Controller 是 Kafka 集群中一个被选中的 Broker（通过 ZooKeeper 临时节点争抢或 KRaft 仲裁选出），负责集群级管理。职责包括 Partition Leader 选举、分区/副本管理、Broker 上下线感知和元数据广播；Controller 故障时其持有的临时节点消失，其他 Broker 感知后重新争抢角色自动故障转移，转移期间集群短暂不可管理但已有 Partition 的读写不受影响。

图中 ZooKeeper（或 KRaft）上的 `/controller` 临时节点由各 Broker 争抢，Broker 0 抢到后成为集群唯一的 Controller，承担 4 项管理职责。Controller 宕机后临时节点自动消失，Broker 1、2 重新争抢，Broker 1 胜出接管——整个转移秒级完成，期间已有 Partition 的读写照常进行。下面的代码展示 Controller 选举机制、状态查看、故障模拟以及 KRaft 去 ZK 模式的配置。

## Controller 选举与管理实践代码

### Layer 1 — Controller 选举过程（ZK 临时节点 / KRaft）

```bash
# === ZooKeeper 模式（Kafka 2.x）===
# 每个 Broker 启动时尝试在 ZK 创建临时节点 /controller
# 创建成功者成为 Controller，失败者监听该节点
# 临时节点随 Controller 会话存活，宕机即消失

# 查看 ZK 中的 controller 节点
zkCli.sh -server zk1:2181
[zk: ...] get /controller
# {"version":1,"brokerid":0,"timestamp":"1722200000000"}
# brokerid=0 即 Broker 0 是 Controller

# === KRaft 模式（Kafka 3.3+，去 ZK）===
# Controller 以仲裁（quorum）方式自选举，无需外部 ZK
# 配置 process.roles=broker,controller 的节点同时充当两者
```

ZK 模式靠临时节点的"创建即占有、断开即释放"特性实现争抢；KRaft 模式则用 Raft 协议内置选举，去掉了 ZK 这层外部依赖。

### Layer 2 — 查看 Controller 状态

```bash
# 查看哪个 Broker 是 Controller（Kafka 命令行工具）
kafka-broker-api-versions.sh --bootstrap-server broker0:9092 \
  --command-config /tmp/client.properties 2>/dev/null | head -1

# 更直接的方式：通过 kafka-metadata 查询
# ZK 模式下查看 /controller 节点
kafka-zookeeper-shell.sh zk1:2181 get /controller
# 输出：{"brokerid":0,...}  -> Broker 0 是 Controller

# KRaft 模式下查看 Controller 信息
kafka-metadata-quorum.sh --bootstrap-server broker0:9092 \
  describe --status
# LeaderId: 0   VoterCount: 3   ...
```

运维应明确知道当前 Controller 在哪个 Broker 上，排查集群管理类问题时首先检查 Controller 是否健康。

### Layer 3 — 模拟 Controller 故障切换

```bash
# 1. 确认当前 Controller 是 Broker 0
kafka-zookeeper-shell.sh zk1:2181 get /controller
# {"brokerid":0,"timestamp":"..."}

# 2. kill 掉 Broker 0 进程，模拟 Controller 宕机
# kill -9 <broker0_pid>

# 3. ZK 临时节点 /controller 立即消失
# 其他 Broker 感知到节点变化，重新争抢 Controller 角色

# 4. 几秒后查看，Controller 已转移到 Broker 1
kafka-zookeeper-shell.sh zk1:2181 get /controller
# {"brokerid":1,"timestamp":"..."}  -> Broker 1 成为新 Controller

# 5. 关键验证：已有 Partition 的读写未中断
kafka-console-producer.sh --bootstrap-server broker1:9092 --topic order-topic
# 仍然可以正常发送消息（Leader 在其他存活的 Broker 上）
```

Controller 故障转移的"无损"特性至关重要：管理面短暂中断，但数据面（Partition 读写）持续可用，这正是 Controller 与 Partition Leader 解耦的好处。

### Layer 4 — KRaft 模式配置（Kafka 3.3+ 去 ZK）

```bash
# server.properties —— KRaft 模式（推荐，Kafka 3.3+ 生产可用）
# 节点角色：同时担任 broker 和 controller
process.roles=broker,controller
# 节点 ID，集群内唯一
node.id=1
# 控制器仲裁组，列出所有 controller 节点
controller.quorum.voters=1@broker1:9093,2@broker2:9093,3@broker3:9093
# 监听器：controller 间通信用 9093，客户端用 9092
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
controller.listener.names=CONTROLLER
# 不再需要 zookeeper.connect 配置

# 格式化 KRaft 存储目录（首次启动）
kafka-storage.sh format \
  --config server.properties \
  --cluster-id $(kafka-storage.sh random-uuid)

# 启动 Broker（无需先启动 ZK）
kafka-server-start.sh server.properties
```

KRaft 模式下 Controller 选举由 Raft 协议在 `controller.quorum.voters` 内部完成，不再依赖 ZK 临时节点——少了一层外部组件，故障域更小、元数据传播更快。

| 维度 | ZK 模式 Controller | KRaft 模式 Controller |
|---|---|---|
| 选举依赖 | ZooKeeper 临时节点 /controller | Raft 协议内部仲裁 |
| 外部组件 | 需要 ZK 集群（3/5 节点） | 无需 ZK，Broker 自治 |
| 元数据存储 | ZooKeeper znode | Kafka 内部 topic __cluster_metadata |
| 元数据传播 | Controller 通过 UpdateMetadata 请求推送 | Raft 日志同步，更高效 |
| 故障转移速度 | 依赖 ZK session timeout，秒级 | Raft 选举，亚秒级 |
| 生产可用版本 | Kafka 0.x ~ 3.x | Kafka 3.3+ |
| 运维复杂度 | 需维护 ZK 集群，组件多 | 单组件，运维简化 |
| 扩展性 | ZK 成为元数据瓶颈 | 可支持更多 Partition |

## 一句话总结

**Controller 是 Kafka 集群的"大管家"——管选举、管分区、管上下线、管广播，自己挂了立刻有人顶上，且数据面读写丝毫不受影响。**
