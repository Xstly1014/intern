# Q57 副本同步机制

Kafka 副本同步采用 Follower 主动拉取（Pull）Leader 数据的方式：Follower 通过 FetchRequest 携带自己的 LEO 向 Leader 请求消息，Leader 从 LEO 开始读取数据返回并更新 HW，Follower 写入本地日志后更新 LEO 并持续轮询保持同步；若 Follower 的 LEO 落后 Leader 超过 replica.lag.time.max.ms（默认 10s）则被踢出 ISR，追上后重新加入。

上图展示了 Kafka 副本同步的完整流程：Follower 主动向 Leader 发送 FetchRequest 并携带自己的 LEO，Leader 从该 LEO 开始读取消息返回给 Follower，同时更新 HW 并在响应中下发给 Follower，Follower 写入本地日志后更新 LEO 并持续轮询保持同步。若 Follower 的 LEO 落后 Leader 超过 replica.lag.time.max.ms（默认 10s）则被踢出 ISR，追上后重新加入。Kafka 选择 Pull 而非 Push 模式，让 Follower 自行控制拉取速率避免被压垮，且复用 FetchRequest 逻辑使消费者也能拉取数据，一套协议同时服务副本同步和消息消费。

## 代码小节：副本同步配置与排查

### Layer 1 — 副本同步配置（replica.lag.time.max.ms, num.replica.fetchers）

```properties
# server.properties — 副本同步相关配置

# Follower 落后 Leader 超过此时间被踢出 ISR（默认 10s）
replica.lag.time.max.ms=10000

# Follower 拉取线程数（增大可加速同步，默认 1）
num.replica.fetchers=1

# Follower 每次拉取最大等待时间
replica.fetch.wait.max.ms=500

# Follower 每次拉取最大字节数
replica.fetch.max.bytes=1048576

# 最小 ISR 副本数（生产者 acks=all 时要求的最小同步副本数）
min.insync.replicas=2

# Follower 拉取的最小字节数（攒够才返回）
replica.fetch.min.bytes=1
```

### Layer 3 — 模拟 Follower 同步过程（LEO 更新 + HW 更新）

```java
// 模拟 Follower 拉取 Leader 数据的同步过程
public class FollowerSyncSimulator {

    // Leader 端日志
    static class LeaderLog {
        List<String> messages = new ArrayList<>();
        int leo = 0;  // Log End Offset：下一条要写入的 offset

        // Leader 接收 FetchRequest，返回从 followerLEO 开始的消息
        FetchResponse fetch(int followerLEO) {
            List<String> data = new ArrayList<>();
            for (int i = followerLEO; i < leo; i++) {
                data.add(messages.get(i));
            }
            // Leader 同时在响应中返回当前 HW
            return new FetchResponse(data, leo);
        }

        void append(String msg) {
            messages.add(msg);
            leo++;
        }
    }

    // Follower 端日志
    static class FollowerLog {
        String name;
        List<String> messages = new ArrayList<>();
        int leo = 0;   // Follower 自己的 LEO
        int hw = 0;    // 从 Leader 获知的 HW

        FollowerLog(String name) { this.name = name; }

        // Follower 发送 FetchRequest 并写入返回的数据
        void pullFromLeader(LeaderLog leader) {
            // ① Follower 向 Leader 发 FetchRequest（携带当前 LEO）
            System.out.printf("[%s] 发送 FetchRequest(LEO=%d)%n", name, leo);
            FetchResponse resp = leader.fetch(this.leo);

            // ③ Follower 写入本地日志，更新 LEO
            this.messages.addAll(resp.data);
            int oldLeo = this.leo;
            this.leo = this.messages.size();

            // Follower 从响应中获取 Leader 下发的 HW
            this.hw = resp.leaderHw;

            System.out.printf("[%s] 拉取 %d 条消息，LEO: %d → %d，HW=%d%n",
                    name, resp.data.size(), oldLeo, this.leo, this.hw);
        }
    }

    static class FetchResponse {
        List<String> data;
        int leaderHw;
        FetchResponse(List<String> data, int leaderHw) {
            this.data = data;
            this.leaderHw = leaderHw;
        }
    }

    public static void main(String[] args) {
        LeaderLog leader = new LeaderLog();
        FollowerLog follower = new FollowerLog("Follower-1");

        // 模拟 3 轮同步
        for (int round = 1; round <= 3; round++) {
            // Leader 接收新消息
            leader.append("msg-" + round);
            System.out.printf("=== 第 %d 轮：Leader 写入消息，LEO=%d ===%n", round, leader.leo);

            // Follower 持续轮询拉取
            follower.pullFromLeader(leader);
        }
    }
}
```

### Layer 4 — Follower 落后排查与恢复

```bash

kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --under-replicated-partitions

# 2. 检查 Broker 日志中 ISR 变更记录
# 搜索日志中的 ISR 缩容和扩容事件
grep -E "Shrinking ISR|Expanding ISR" /opt/kafka/logs/server.log
# 示例输出：
# [2024-01-01 10:00:00] Shrinking ISR from 0,1,2 to 0,1
# [2024-01-01 10:02:30] Expanding ISR from 0,1 to 0,1,2

# 3. 调整副本拉取线程数加速同步（需重启 Broker）
# server.properties:
#   num.replica.fetchers=4

# 4. 适当增大 replica.lag.time.max.ms 避免频繁踢出
# server.properties:
#   replica.lag.time.max.ms=30000

# 5. 检查网络延迟和磁盘 IO（Follower 落后通常是硬件瓶颈）
# 检查网络：ping 各 Broker 节点
# 检查磁盘：iostat -x 1

# 6. 执行 Preferred Leader Election 重新均衡 Leader

```

## Push vs Pull 副本同步对比

| 维度 | Push（Leader 推送） | Pull（Follower 拉取，Kafka 采用） |
|------|-------------------|-------------------------------|
| 数据流向 | Leader → Follower（Leader 主动推） | Follower → Leader 请求（Follower 主动拉） |
| 速率控制 | Leader 控制，可能压垮慢 Follower | Follower 控制，按自身能力拉取 |
| 故障处理 | Leader 需检测 Follower 状态并重试 | Follower 恢复后自动重新拉取 |
| 逻辑复用 | 需独立推送逻辑 | 复用 FetchRequest（消费者也用同一协议） |
| 网络效率 | 实时推送，小包多，网络开销大 | 批量拉取，可攒批发送 |
| 背压控制 | Leader 需实现复杂背压机制 | 天然背压（拉不动就不拉） |
| 实现复杂度 | 高（Leader 管理所有 Follower 状态） | 低（Follower 自管理，Leader 无状态） |
| 延迟 | 低（实时推送） | 略高（取决于拉取间隔） |

## 一句话总结

**Kafka 副本同步采用 Pull 模式，Follower 通过 FetchRequest 携带 LEO 向 Leader 拉取数据，Leader 返回消息并更新 HW 下发给 Follower，Follower 写入后更新 LEO 持续轮询，落后超过 10s 的 Follower 会被踢出 ISR，追上后重新加入。**
