# Q47 Consumer Group

Consumer Group 是一组共同消费一个或多个 Topic 的消费者集合。核心规则有两条：组内分摊——一个 Partition 只能被组内一个消费者消费，Partition 在组内消费者间分配；组间独立——不同 Consumer Group 互不影响，各自消费完整 Topic 数据。这套机制统一了发布订阅（组间）和点对点（组内）两种消费模型。

上图展示了一个 3 Partition 的 Topic 同时被两个 Consumer Group 消费的场景。Group A 有 3 个消费者，每个消费者恰好分到 1 个 Partition，达到满并行；Group B 只有 1 个消费者，它独自承担全部 3 个 Partition。关键在于：同一条消息对 Group A 只被消费一次（组内点对点分摊），同时 Group B 也会独立消费到同一条消息（组间发布订阅）。下面通过代码看 Consumer Group 的配置与使用。

## Consumer Group 代码分层

### Layer 1 — Consumer Group 配置

Consumer Group 的核心配置是 `group.id`，它决定消费者属于哪个组。Spring Kafka 通过 `spring.kafka.consumer.group-id` 统一配置。

```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    consumer:
      group-id: order-consumer-group-a       # 关键：指定 Consumer Group
      auto-offset-reset: earliest            # 无 offset 时从头开始消费
      enable-auto-commit: false              # 关闭自动提交，手动控制
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.JsonDeserializer
      properties:
        spring.json.trusted.packages: "com.example.kafka.dto"
```

`group.id` 相同的消费者实例属于同一个 Group，Kafka 会自动将 Partition 在它们之间分摊。

### Layer 2 — 多 Group 独立消费

不同 `group.id` 的消费者互不影响，各自消费完整的 Topic 数据。这正是发布订阅模型的体现。

```java
// ========== Group A 的消费者 ==========
@KafkaListener(topics = "order-events", groupId = "order-consumer-group-a")
public void handleOrderForGroupA(String message) {
    log.info("[Group A] 收到订单: {}", message);
    // Group A 的业务逻辑：写入订单库
    orderService.saveOrder(message);
}

// ========== Group B 的消费者 ==========
// 不同 groupId，独立消费完整 Topic，与 Group A 互不影响
@KafkaListener(topics = "order-events", groupId = "order-consumer-group-b")
public void handleOrderForGroupB(String message) {
    log.info("[Group B] 收到订单: {}", message);
    // Group B 的业务逻辑：推送通知
    notificationService.pushNotification(message);
}
```

两个方法监听同一个 Topic，但 `groupId` 不同。同一条订单消息会同时被 Group A（入库）和 Group B（通知）各消费一次，而 Group A 内部如果有多个实例，则只有一个实例处理这条消息。

### Layer 3 — 消费者扩容

当消费速度跟不上生产速度时，只需多启动几个相同 `group.id` 的消费者实例，Kafka 会自动 Rebalance 将 Partition 分摊到新消费者上，提高并行度。

```java
// 消费者代码不变，只需多启动实例
@KafkaListener(topics = "order-events", groupId = "order-consumer-group-a")
public void handleOrder(String message) {
    processOrder(message);
}

// ========== 扩容方式 ==========
// 方式一：多实例部署（水平扩容）
//   启动 3 个相同 group-id 的 Spring Boot 实例
//   Kafka 自动将 3 个 Partition 分给 3 个实例，各消费 1 个
//
// 方式二：单实例多线程（ConcurrentKafkaListenerContainerFactory）
@Bean
public ConcurrentKafkaListenerContainerFactory<String, String> kafkaListenerContainerFactory(
        ConsumerFactory<String, String> consumerFactory) {
    ConcurrentKafkaListenerContainerFactory<String, String> factory =
            new ConcurrentKafkaListenerContainerFactory<>();
    factory.setConsumerFactory(consumerFactory);
    factory.setConcurrency(3);  // 3 个消费线程，相当于 3 个逻辑消费者
    return factory;
}
```

注意：消费者数量超过 Partition 数量时，多余的消费者会闲置。例如 3 个 Partition 启动 5 个消费者，则有 2 个消费者分不到 Partition。

### Layer 4 — Consumer Group 状态查看

使用 Kafka 自带的 `kafka-consumer-groups.sh` 脚本查看 Consumer Group 的 Partition 分配情况和消费进度（Lag）。

```bash
# 1. 查看所有 Consumer Group
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list

# 输出示例：
# order-consumer-group-a
# order-consumer-group-b

# 2. 查看指定 Group 的 Partition 分配与消费进度
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-consumer-group-a

# 输出示例：
# GROUP                  TOPIC          PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID       HOST          CLIENT-ID
# order-consumer-group-a  order-events  0          1500            1500            0    consumer-1@host1  /192.168.1.1  consumer-1
# order-consumer-group-a  order-events  1          1480            1500            20   consumer-2@host2  /192.168.1.2  consumer-2
# order-consumer-group-a  order-events  2          1500            1500            0    consumer-3@host3  /192.168.1.3  consumer-3

# LAG 列 = LOG-END-OFFSET - CURRENT-OFFSET，表示积压未消费的消息数
# LAG 持续增长说明消费速度跟不上生产速度，需要扩容
```

`LAG` 是监控消费进度的核心指标，Lag 持续增长意味着消费跟不上生产，需要增加消费者实例。

## Consumer Group 模型对比

| 维度 | 组内消费者 | 组间关系 |
|---|---|---|
| Partition 分配 | 一个 Partition 只被组内一个消费者消费 | 不同 Group 各自独立分配 Partition |
| 消费完整性 | 组内合起来消费完整 Topic | 每个 Group 都消费完整 Topic 数据 |
| 消费模型 | 组内 = 点对点分摊 | 组间 = 发布订阅 |
| 同一消息投递 | 组内只投递给一个消费者 | 每个 Group 各投递一次 |
| 扩容效果 | 消费者数 ≤ Partition 数才有意义 | 互不影响，各自独立扩容 |
| 典型场景 | 订单消费入库（分摊提高吞吐） | 入库 + 通知 + 统计（多 Group 各司其职） |

## 一句话总结

**Consumer Group 用一套机制统一了两种消费模型——组内分摊 Partition 实现点对点，组间独立消费实现发布订阅，同一条消息对每个 Group 各投递一次、对 Group 内部只投递一次。**
