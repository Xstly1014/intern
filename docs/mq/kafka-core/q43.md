# Q43 Partition 与消费者数量关系

Kafka 规定一个 Partition 只能被 Consumer Group 内一个消费者消费——当消费者数小于等于 Partition 数时所有分区都有人消费，超出部分消费者空闲不报错；理想状态是消费者数等于 Partition 数，实现最大并行度且无浪费。

上图用两个场景直观对比了消费者数与 Partition 数的关系。**左侧**：8 个消费者面对 12 个 Partition，Kafka 将分区均匀分配——C0~C3 各分到 2 个 Partition（2P），C4~C7 各分到 1 个 Partition（1P），12 个 Partition 全部被消费，并行度为 8。**右侧**：15 个消费者面对 12 个 Partition，只有 C0~C11 能分到 Partition（各消费 1P），C12~C14 无分区可分进入空闲状态——不会报错，但也不消费任何消息，白白占用资源。

## 代码实现：消费者组管理

### Layer 1 — Consumer Group 配置

```java
@Component
@Slf4j
public class OrderConsumer {

    // concurrency = 8：Spring Kafka 在单个 JVM 内创建 8 个消费线程
    // 相当于 Consumer Group 内有 8 个消费者，各自分到 Partition
    @KafkaListener(
        topics = "topic-order",        // 12 个 Partition
        groupId = "order-group",
        concurrency = "8"              // 8 个消费者线程
    )
    public void handle(OrderEvent event) {
        processOrder(event);
    }
}
```

```yaml
spring:
  kafka:
    consumer:
      group-id: order-group
      # 也可部署 8 个独立实例，每个 concurrency=1，效果相同
      # Consumer Group 内总消费者数 = 实例数 × concurrency
```

`concurrency` 决定了单个实例内的消费线程数。当 `concurrency` 超过 Partition 数时，多余线程会空闲——这就是场景二的代码体现。

### Layer 2 — 消费者空闲检测

```java
@Component
@Slf4j
public class RebalanceListener implements ConsumerAwareRebalanceListener {

    @Override
    public void onPartitionsAssigned(Consumer<?, ?> consumer,
                                     Collection<TopicPartition> partitions) {
        if (partitions.isEmpty()) {
            // 消费者数 > Partition 数时，多余消费者会走到这里
            log.warn("当前消费者未分配到任何 Partition，处于空闲状态");
            // 可触发告警，或通知 K8s 自动缩容
            alertService.notifyIdleConsumer(consumer.toString());
        } else {
            log.info("分配到 {} 个分区: {}", partitions.size(), partitions);
        }
    }

    @Override
    public void onPartitionsRevoked(Consumer<?, ?> consumer,
                                    Collection<TopicPartition> partitions) {
        log.info("回收 {} 个分区: {}", partitions.size(), partitions);
    }
}
```

`onPartitionsAssigned` 回调中 `partitions.isEmpty()` 为 true 即说明该消费者空闲。生产环境中应监控此状态，及时缩容避免资源浪费。

### Layer 3 — 动态扩容消费者

```bash
# 方式一：增加 Partition 数（只能增不能减）
# 从 12 扩到 16，让更多消费者有活干
kafka-topics.sh --alter \
  --bootstrap-server broker1:9092 \
  --topic topic-order \
  --partitions 16
```

```java
// 方式二：增加单实例并发数（需重启生效）
@KafkaListener(
    topics = "topic-order",
    groupId = "order-group",
    concurrency = "12"    // 从 8 扩到 12，匹配 12 个 Partition
)
public void handle(OrderEvent event) {
    processOrder(event);
}
```

```bash
# 方式三：水平扩容消费者实例（K8s 弹性伸缩，无需重启）
# 新实例加入后触发 Rebalance，自动重新分配 Partition
kubectl scale deployment order-consumer --replicas=12
```

扩容前需确认 Partition 数：如果消费者数已等于 Partition 数，继续加实例只会产生空闲消费者。此时应先增加 Partition 数（方式一），再扩容消费者（方式三）。

## 消费者数与 Partition 数关系对比

| 场景 | 消费者数 | Partition 数 | 结果 |
|---|---|---|---|
| 消费者 < Partition | 8 | 12 | 部分消费者消费 2 个分区，全部覆盖，并行度 8 |
| 消费者 = Partition | 12 | 12 | 每个消费者消费 1 个分区，理想状态，并行度 12 |
| 消费者 > Partition | 15 | 12 | 12 个消费者各消费 1 个分区，3 个空闲不报错 |
| 消费者 = 1 | 1 | 12 | 1 个消费者消费全部 12 个分区，无并行 |
| 消费者 = 0 | 0 | 12 | 无消费，消息积压在 Broker |

## 一句话总结

**一句话总结：Partition 数是 Consumer Group 消费并行度的天花板——消费者多了会空闲浪费，消费者少了会吞吐不足，只有消费者数等于 Partition 数时才能既不浪费也不积压。**
