# Q53 ZooKeeper 作用

ZooKeeper 在 Kafka 中承担 Broker 注册、Topic/Partition 元数据存储、Controller 选举、Consumer Group 管理四项核心职责，是早期 Kafka 的元数据中枢。Kafka 3.3+ 的 KRaft 模式用内部 Raft 协议取代了 ZK，解决运维复杂、元数据瓶颈和扩展受限三大问题。

## ZK 元数据操作与选举流程

### Layer 1 — ZK 节点结构

ZK 用树形结构组织 Kafka 元数据，每个路径对应一类信息，临时节点的生命周期绑定会话心跳。

```
# ZK 中的 Kafka 元数据节点树
/
├── /brokers
│   ├── /ids                    # 临时节点，Broker 注册（Broker 宕机则消失）
│   │   ├── /0                  # {"host":"kafka-0","port":9092,"endpoints":["PLAINTEXT://..."]}
│   │   ├── /1
│   │   └── /2
│   ├── /topics                 # 持久节点，Topic 与 Partition 分布
│   │   ├── /order-topic
│   │   │   └── /partitions
│   │   │       ├── /0          # {"leader":1,"isr":[1,2,0]}
│   │   │       ├── /1
│   │   │       └── /2
│   │   └── /payment-topic
│   └── /seqid                  # 自增 id 分配
├── /controller                 # 临时节点，Controller 争抢（首个创建者获胜）
├── /controller_epoch           # Controller 纪元，每次选举 +1
├── /admin
│   ├── /reassign_partitions    # Partition 重分配任务
│   └── /delete_topics          # 待删除 Topic 队列
├── /config                     # 动态配置
│   ├── /topics
│   ├── /brokers
│   └── /users
└── /consumers                  # 0.9 前 consumer offset（已废弃，0.9 后移到 __consumer_offsets）
    └── /order-group
        └── /offsets
            └── /order-topic/0  # {"version":1,"offset":1500}
```

### Layer 2 — 查看 ZK 元数据

使用 `zookeeper-shell.sh` 连接 ZK 并查看 Kafka 注册的元数据，是排查 Broker 状态和 Partition 分布的常用手段。

```bash
# 连接 ZooKeeper（Kafka 自带的 zookeeper-shell.sh）
bin/zookeeper-shell.sh zk1:2181

# 查看 Broker 列表（存活的 Broker id）
ls /brokers/ids
# 输出: [0, 1, 2]

# 查看某个 Broker 的详细信息
get /brokers/ids/0
# 输出: {"listener_security_protocol_map":{"PLAINTEXT":"PLAINTEXT"},
#        "endpoints":["PLAINTEXT://kafka-0:9092"],"jmx_port":9999,
#        "host":"kafka-0","timestamp":"1690000000000","version":4,"port":9092}

# 查看所有 Topic
ls /brokers/topics
# 输出: [order-topic, payment-topic, __consumer_offsets]

# 查看某 Topic 的 Partition 分布（哪个 Broker 是 Leader）

# 输出: {"controller_epoch":12,"leader":1,"version":1,
#        "leader_epoch":5,"isr":[1,2,0]}

# 查看当前 Controller 是哪个 Broker
get /controller
# 输出: {"version":1,"brokerid":1,"timestamp":"1690000000000"}

# 查看 Controller 纪元（每轮选举自增）
get /controller_epoch
# 输出: 12
```

### Layer 3 — Broker 注册与心跳

Broker 启动时在 ZK 创建临时节点 `/brokers/ids/[id]`，节点存活依赖 ZK 会话心跳；会话超时则节点消失，Controller 感知后触发故障恢复。

```java
// Broker 启动时向 ZK 注册（Kafka 源码 KafkaBroker.scala 简化逻辑）
public class KafkaBrokerRegistration {

    private final String zkConnect = "zk1:2181,zk2:2181,zk3:2181";
    private final int brokerId = 1;                    // broker.id
    private final String host = "kafka-1";
    private final int port = 9092;
    private final int sessionTimeoutMs = 15000;        // 会话超时 15s，超时则临时节点消失

    public void register() throws Exception {
        // 1. 创建 ZK 客户端，建立会话（维持心跳）
        ZooKeeper zk = new ZooKeeper(zkConnect, sessionTimeoutMs, event -> {
            // 会话事件回调：连接断开、会话过期等
            if (event.getState() == KeeperState.Expired) {
                System.out.println("ZK 会话过期，临时节点已被删除，需重新注册");
            }
        });

        // 2. 创建临时节点 /brokers/ids/1
        //    ephemeral = true → 会话断开自动删除
        String brokerInfo = String.format(
            "{\"version\":4,\"host\":\"%s\",\"port\":%d," +
            "\"endpoints\":[\"PLAINTEXT://%s:%d\"],\"jmx_port\":9999," +
            "\"timestamp\":%d}",
            host, port, host, port, System.currentTimeMillis()
        );

        zk.create("/brokers/ids/" + brokerId,
                  brokerInfo.getBytes(),
                  ZooDefs.Ids.OPEN_ACL_UNSAFE,
                  CreateMode.EPHEMERAL);   // 关键：临时节点

        System.out.println("Broker " + brokerId + " 已注册到 ZK，临时节点已创建");

        // 3. 会话心跳由 ZK 客户端自动维持（每 tickTime 发一次 ping）
        //    Broker 宕机 → 心跳停止 → 会话超时 → 临时节点消失 → Controller 收到 NodeDeleted 事件
    }
}
```

这里的关键在于 `CreateMode.EPHEMERAL`——临时节点与 ZK 会话绑定，Broker 进程一旦崩溃，心跳中断，会话超时后节点自动消失，这是 ZK 感知 Broker 故障的核心机制。

### Layer 4 — Controller 选举过程

Controller 选举通过争抢创建 `/controller` 临时节点实现，首个创建成功的 Broker 成为 Controller，其余监听该节点变化，节点消失时再次争抢。

```java
// Controller 选举：临时节点争抢机制（Kafka 源码 KafkaController.scala 简化）
public class ControllerElection {

    private final ZooKeeper zk;
    private final int brokerId;
    private volatile boolean isActiveController = false;

    public void elect() throws Exception {
        try {
            // 1. 尝试创建 /controller 临时节点（争抢）
            //    只有第一个创建成功，其余抛 NodeExistsException
            String controllerInfo = String.format(
                "{\"version\":1,\"brokerid\":%d,\"timestamp\":%d}",
                brokerId, System.currentTimeMillis()
            );

            zk.create("/controller",
                      controllerInfo.getBytes(),
                      ZooDefs.Ids.OPEN_ACL_UNSAFE,
                      CreateMode.EPHEMERAL);   // 临时节点，Controller 宕机自动释放

            // 2. 创建成功 → 成为 Controller
            isActiveController = true;
            System.out.println("Broker " + brokerId + " 当选 Controller");

            onControllerFailover();   // 执行 Leader 选举、Partition 重分配等

        } catch (KeeperException.NodeExistsException e) {
            // 3. 创建失败 → 已有 Controller，注册监听等待下次机会
            isActiveController = false;
            System.out.println("Broker " + brokerId + " 竞选失败，已有 Controller 存在");

            // 监听 /controller 节点删除事件（当前 Controller 宕机）
            zk.exists("/controller", event -> {
                if (event.getType() == EventType.NodeDeleted) {
                    System.out.println("Controller 节点消失，重新发起选举");
                    try { elect(); } catch (Exception ex) { /* retry */ }
                }
            });
        }
    }

    // Controller 故障恢复：重新选举 Leader、更新 ISR、触发 Partition rebalance
    private void onControllerFailover() {
        // 1. 递增 controller_epoch

        // 4. 启动 Partition rebalance（若 auto.rebalance 开启）
    }
}
```

这套争抢机制依赖 ZK 的 `EPHEMERAL` + `exists` watcher：Controller 宕机时 `/controller` 消失，所有监听的 Broker 收到 `NodeDeleted` 事件并发起下一轮争抢。但 watcher 是一次性的，高并发下可能出现"惊群效应"，这也是 KRaft 改用 Raft 选举的原因之一。

## ZK 模式 vs KRaft 模式对比

| 维度 | ZK 模式 | KRaft 模式 |
|---|---|---|
| 外部依赖 | 依赖外部 ZooKeeper 集群 | 无外部依赖，元数据存内部 Topic |
| 部署复杂度 | 需维护 Kafka + ZK 两套系统 | 仅维护 Kafka 一套系统 |
| 元数据存储 | ZK znode 树结构 | `__cluster_metadata` 内部 Topic（日志形式） |
| 元数据同步 | ZK watcher 推送（可能丢事件） | Raft 日志强一致复制 |
| Controller 选举 | 争抢创建 `/controller` 临时节点 | Raft 协议选举 Leader |
| 故障恢复速度 | 慢（watcher 惊群 + 全量元数据加载） | 快（Raft 增量日志） |
| Partition 扩展上限 | 受 ZK 元数据同步限制（约 20 万） | 支持百万级 Partition |
| 生产可用版本 | Kafka 0.8+ 一直可用 | Kafka 3.3+ 生产可用 |
| Consumer offset 存储 | 0.9 前存 ZK（已废弃） | 0.9+ 统一存 `__consumer_offsets` |
| 运维成本 | 高（需独立监控、调优 ZK） | 低（单一系统） |
| 新项目建议 | 不推荐 | 直接使用 KRaft 模式 |

## 一句话总结

**ZooKeeper 是早期 Kafka 的元数据中枢，靠临时节点做 Broker 存活检测和 Controller 争抢选举，KRaft 用 Raft 日志把这套外部协调机制内化成了 Kafka 自己的强一致元数据流，从"维护两套系统"收敛为"一套系统自洽"。**
