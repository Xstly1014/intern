# 01 · 基础概念

## 什么是限流

限流（Rate Limiting）是一种流量控制手段：**限制单位时间内允许通过的请求（或操作）数量，超过阈值的部分被拒绝或延迟**。它不关心请求是否合法、下游是否健康，只关心"流量有没有超标"，本质是用"牺牲一部分请求"换"系统活着"。

限流就像在系统入口装了一个阀门：阈值内的请求正常通过，超出的部分被拒绝或排队等待。

### 限什么：限流的对象

- **速率**：每秒请求数（QPS/TPS），最常见的限流对象
- **并发数**：同一时刻正在处理的请求数量
- **资源**：CPU 使用率、连接数、线程数等系统负载指标
- **维度**：可以按用户、API 接口、IP、租户分别设置不同的阈值

### 为什么限：解决的问题

- **过载保护**：防止突发流量（秒杀、热点事件）压垮系统
- **防恶意流量**：拦截爬虫、刷接口、暴力破解
- **保护下游**：避免自身流量把数据库或依赖服务打挂
- **成本控制**：把流量控制在已购买的容量范围内
- **削峰填谷**：把不均衡的请求平滑成稳定的处理速率

### 在哪限：生效的位置

客户端、CDN/边缘节点、负载均衡、API 网关、应用层、服务间调用、数据库连接层都可以限流，生产中常见的是"网关统一限流 + 应用层细粒度限流"的多级组合。

### 怎么限：核心算法

四大经典算法：固定窗口、滑动窗口、漏桶、令牌桶，外加 GCRA 和基于负载的自适应限流。它们的区别在于"如何计数"和"是否允许突发"，详见 [02 核心算法](/rate-limiting/algorithms)。

### 被限后怎么办：拒绝策略

- **直接拒绝**：返回 HTTP 429，可带 Retry-After 提示客户端何时重试
- **排队等待**：请求进入队列匀速处理（削峰）
- **预热放行**：冷启动期间逐步放大阈值（Warm Up）

### 限流器的代码契约

无论哪种算法，限流器对外只暴露一个判断：

```java
// 限流器的核心契约：这个请求现在能不能过？
RateLimiter limiter = RateLimiter.create(100); // 阈值 100 QPS
if (limiter.tryAcquire()) {
    handleRequest();   // 放行：正常处理
} else {
    return 429;        // 被限流：拒绝并告知客户端
}
```

所有框架（Guava、Sentinel、Nginx、网关）的差异，都只是这个判断背后的计数方式和部署位置不同。

## 与相邻概念的边界

限流常和熔断、降级、并发控制一起出现，但职责不同：

| 维度 | 限流 | 熔断 | 降级 | 并发控制 |
|---|---|---|---|---|
| 触发条件 | 流量超过预设阈值 | 下游失败率/延迟超标 | 容量不足或故障 | 并发数超过上限 |
| 作用对象 | 入口请求速率 | 对某个下游的调用 | 非核心功能 | 并发线程/连接数 |
| 目的 | 防止入口过载 | 防止被下游拖垮 | 保住核心功能 | 防止资源耗尽 |
| 视角 | 主动防御，不看下游健康 | 被动响应下游故障 | 容量取舍 | 资源隔离 |
| 典型结果 | 拒绝或排队多余请求 | 快速失败，暂停调用 | 关闭非核心功能 | 等待或拒绝 |

## 并发控制详解

### 什么时候要控制并发

当**瓶颈不在"每秒来多少"，而在"同时有多少个在处理"**时，就要控制并发数。限流管的是入口流速，并发控制管的是"同时在途的任务数"。

根据 Little's Law（并发数 = 速率 × 响应时间），哪怕每秒请求数不变，只要下游变慢，在途任务就会越堆越多，最终占满资源。这正是只有限流不够、必须控制并发的原因。

需要控制并发数的四种情况：

- **资源有限且被独占**：连接、线程、文件句柄、许可证，占着一个就少一个
- **下游承受的是"同时压力"而非"每秒压力"**：比如数据库同时执行的 SQL 数量
- **任务耗时长**：慢调用会放大在途数量，把资源耗尽
- **需要资源隔离**：防止某一类慢任务把共享资源吃光，拖垮其他业务

### 典型实际场景

- **数据库连接池**：MySQL 的 `max_connections` 有限，HikariCP 的 `maximumPoolSize` 就是并发控制，连接耗尽会导致全站报错
- **爬虫 / 调用第三方 API**：限制同时发出的 HTTP 请求数，避免打爆连接池或被对方封禁
- **线程池**：`corePoolSize` / `maximumPoolSize` 控制批处理、异步任务的同时执行数
- **舱壁隔离**：某个接口变慢时，用独立线程池/信号量把它隔离起来（Resilience4j Bulkhead、Sentinel 线程池隔离）
- **数据迁移 / 批量写入**：控制并发写库数量，避免把数据库 IO 打满
- **消息消费**：Kafka / MQ 消费者的消费线程数，本质是对消费侧的并发控制
- **文件 IO 任务**：上传下载、日志处理，受文件句柄数和磁盘 IO 能力限制
- **网关连接数限制**：Nginx 的 `limit_conn` 按 IP 限制同时连接数
- **集群级保护**：所有服务对某个弱依赖（如支付通道）的总并发上限

### 代码契约：Semaphore

```java
// 用 Semaphore 控制"最多 10 个任务同时执行"
private static final Semaphore SLOTS = new Semaphore(10);

public Result query() throws InterruptedException {
    SLOTS.acquire();           // 拿槽位：满了就等待（或直接拒绝）
    try {
        return db.query();     // 执行期间占用一个并发名额
    } finally {
        SLOTS.release();       // 结束必须归还，否则槽位泄漏
    }
}
```

连接池、线程池本质上都是这个模式的封装，只是把"槽位"换成了连接和线程。

## 限流 vs 并发控制

| 维度 | 限流（速率） | 并发控制 |
|---|---|---|
| 控制对象 | 每秒进入的请求数 | 同时处理中的任务数 |
| 防范的风险 | 单位时间请求太多 | 在途任务占满独占资源 |
| 对响应时间 | 不敏感 | 非常敏感（慢调用堆积） |
| 典型实现 | 令牌桶、滑动窗口 | Semaphore、连接池、线程池 |
| 典型场景 | API 入口防过载、防刷 | 连接池、爬虫、批处理、舱壁隔离 |

::: tip 一句话总结
限流管"每秒来多少"，并发控制管"同时在干多少"；熔断防被下游拖垮，降级弃非核心保核心。
:::
