# 数据访问与存储层：让事实可靠、查询高效

数据层不是“一个 MySQL”。它根据数据的正确性、访问模式、延迟、规模和保留期，组合事务数据库、缓存、搜索、对象存储和分析系统。原则是：**一个业务事实有且只有一个权威来源，其他副本都可由它重建。**

## 1. 存储选型

| 类型 | 擅长 | 不适合替代 |
|---|---|---|
| MySQL/PostgreSQL | 事务、约束、关系查询、权威事实 | 海量全文搜索、无限水平扩展 |
| Redis | 热点缓存、计数、短期状态、限流 | 无设计地保存唯一业务事实 |
| Elasticsearch/OpenSearch | 全文检索、聚合、筛选 | 订单强一致事务库 |
| 对象存储 | 图片、视频、附件、归档 | 高频小记录随机更新 |
| ClickHouse/数仓 | OLAP、报表、历史分析 | 在线交易写入与点查 |

选型前先写访问模式：按什么 Key 读写、QPS、单条大小、数据总量、一致性、保留期和恢复目标。Polyglot Persistence 不是每种数据库都用一次，而是有证据地匹配需求。

## 2. 数据所有权与访问层

每个领域服务拥有其数据和 Schema 迁移权。Repository/DAO 隔离存储细节，业务层表达业务查询而非拼接任意表。禁止服务 B 直接更新服务 A 的表；跨域查询通过 API、事件构建只读投影或数据平台完成。

数据库凭证按服务最小授权，读写分离账户；Schema 变更由版本工具（Flyway/Liquibase）管理并进入发布流程。

## 3. 事务数据库设计

- 主键避免业务可变字段；全局 ID 需权衡趋势性、热点和信息泄露。
- 唯一约束保障幂等和业务不变量，不只依赖代码 `if` 检查。
- 索引按真实查询和排序建立，关注选择性、覆盖、回表和写放大。
- 大字段与冷热数据拆分；金额用定点数并携带币种，时间统一存明确时区/UTC。
- 慢查询通过执行计划、扫描行数和锁等待分析，避免无界查询与 N+1。

连接池上限要由数据库总连接预算反推：`实例数 × 每实例连接数` 不能超过数据库安全容量。扩容应用时尤其容易把数据库连接打满。

## 4. 缓存设计

### Cache-Aside

```text
读：查缓存 → miss → 查数据库 → 写缓存
写：更新数据库 → 删除缓存（必要时延迟双删/CDC 失效）
```

缓存 Key 包含环境、版本、租户和业务 ID；TTL 加随机抖动防雪崩。缓存穿透用空值短缓存、布隆过滤器或入口校验；热点 Key 用请求合并、本地缓存或分片；缓存故障时通过限流保护数据库。任何缓存方案都要回答允许多旧、如何失效、失败后能否重建。

不要把分布式缓存和 Spring `@Transactional` 想象成一个原子事务。强一致读取应回权威库，缓存只做性能副本。

## 5. 读写分离、分片与副本

主从复制通常异步，写后立即读可能看不到；可对关键链路读主、传递版本/位点或显示“处理中”。分库分表只有在单库容量、写入或维护窗口成为可证明瓶颈时采用。分片键要匹配主要查询并避免热点；跨分片分页、Join、唯一约束、迁移和扩容成本必须提前设计。

## 6. 搜索、对象和分析数据

搜索索引是数据库事实的派生副本，通过 Outbox/CDC 同步，记录版本并可全量重建。对象上传使用短期签名直传、内容扫描、不可猜测 Key、元数据入库和生命周期清理。分析链路与 OLTP 隔离，报表不能直接拖垮生产主库；个人数据删除和保留策略也要传播到搜索、数仓、备份和对象存储。

## 7. 备份与恢复

RPO 是可接受丢失多少数据，RTO 是多快恢复。备份策略要包含全量/增量、binlog/WAL、跨地域副本、加密、保留期和权限。**备份成功不等于可恢复**：必须定期在隔离环境恢复，校验完整性、耗时、应用兼容性和操作手册。

## 8. 观测与故障

监控连接池利用率、QPS、P95/P99、慢查询、锁等待、死锁、复制延迟、磁盘与 IOPS、缓存命中/淘汰/热 Key、索引同步延迟和备份恢复结果。常见事故是缓存雪崩压垮数据库、只读请求打到延迟副本、错误索引导致 CPU 飙升、应用扩容耗尽连接，以及 Schema 变更锁大表。

Schema 发布遵循 expand/contract：先新增兼容结构，发布双读写或回填，切流验证后再删除旧字段。不要让一个版本同时要求“新列必须存在”和“旧版本完全不认识新语义”。
