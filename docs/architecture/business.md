# 业务服务层：把业务意图转化为一致、可追溯的状态变化

业务服务层拥有系统最不可替代的部分：业务语言、用例、规则、状态机、数据所有权和一致性边界。网关决定请求能否进入，BFF 把终端契约翻译成用例，安全层提供可信主体；业务层最终回答：**当前主体是否可执行这个业务意图，哪些规则必须成立，状态如何变化，产生了什么事实。**

## 1. 运行时位置与边界

![业务服务层在系统中的运行时边界](/architecture/business-runtime-boundary.svg)

| 相邻层 | 交互内容 | 业务层不能外包的责任 |
|---|---|---|
| API 网关/BFF | Command、Query、主体、租户、幂等键、deadline | 资源授权、状态规则、价格和事务 |
| 身份与安全 | 可信身份、策略能力、审计基础设施 | 基于业务资源的最终授权 |
| 数据层 | Repository、事务、锁、查询和持久化能力 | 聚合边界、何时提交、冲突语义 |
| MQ/中间件 | 可靠传递、顺序、重试、延迟 | 事件含义、幂等、补偿和最终状态 |
| 外部系统 | 支付、物流、风控等适配端口 | 供应商结果如何影响业务状态 |

业务服务不应返回 JPA Entity 给外部，也不允许其他服务直接修改自己的表。数据表是实现细节，API、事件和明确的读模型才是跨边界契约。

## 2. 一次命令的执行管线

![业务命令从接收到提交的处理管线](/architecture/business-command-pipeline.svg)

1. 接收明确业务意图，例如 `CancelOrderCommand`，而不是通用 `updateOrder`。
2. 校验用例级前置条件：主体、租户、幂等键、必要参数和 deadline。
3. 在短本地事务内按 tenant 与 ID 读取聚合，取得最新版本。
4. 执行资源级授权；授权与状态检查都基于最新业务事实。
5. 调用聚合行为方法维护不变量，不暴露任意 setter。
6. Repository 保存变更，唯一约束/版本号/条件更新处理并发竞争。
7. 同事务保存 Outbox/审计事实，提交后异步发布集成事件。
8. 将领域结果映射为稳定用例结果；BFF 再负责 HTTP/终端契约。

远程 HTTP、等待 MQ Broker、大文件和不受控计算不应留在数据库事务中。

## 3. 业务层拥有什么

### 拥有

- 领域术语、实体、值对象、聚合、领域服务和策略。
- Command/Query 用例、资源级授权入口和事务边界。
- 状态机、不变量、幂等业务事实、并发冲突语义。
- 领域事件、对外集成事件的语义与版本。
- Saga/流程状态、补偿语义、对账与人工修复入口。
- 业务 SLI，例如下单成功率、状态停留时间和补偿积压。

### 不拥有

- 客户端页面 DTO、Cookie、HTTP 状态和终端兼容分支。
- 通用 Token 签发、WAF、全局流量路由和证书平台。
- 其他上下文的数据库表和跨库 Join 写入。
- Kafka/RabbitMQ SDK 细节、供应商支付 SDK 和数据库方言。

这些能力通过入站/出站端口连接，领域代码不依赖 Spring MVC、JPA 注解或厂商客户端才是理想方向；简单 CRUD 可适度简化，但所有权和状态约束不能消失。

## 4. Command 与 Query 分开思考

![命令模型与查询模型的职责差异](/architecture/business-command-query.svg)

**命令**表达意图并可能改变事实：强调授权、不变量、幂等、并发和事务，返回业务标识/结果，而不是任意修改后的整张表。

**查询**不改变业务事实：可使用投影、批量、缓存、搜索和专用读模型，按权限过滤并标注新鲜度。CQRS 不意味着必须部署两套服务或数据库；先分离模型和责任，再按性能与独立演进需求拆物理设施。

## 5. 模块化单体还是微服务

| 判断维度 | 模块化单体优先 | 拆服务可能有价值 |
|---|---|---|
| 业务耦合 | 规则经常共同修改 | 语言、规则和数据所有权稳定分离 |
| 团队 | 一个团队共同发布 | 独立团队端到端拥有能力与值班 |
| 一致性 | 大量跨模块强事务 | 可用 API/事件和最终一致性协作 |
| 容量 | 资源特征相似 | 某能力 CPU、存储或流量显著独立 |
| 故障 | 同进程爆炸半径可接受 | 必须隔离发布与运行故障 |
| 平台 | 分布式治理尚不成熟 | 契约、观测、交付和运维已到位 |

先建立代码和数据所有权边界，再物理拆分。把一个混乱单体直接切成许多共享数据库的服务，只会增加网络失败而不增加业务自治。

## 6. 核心设计原则

- **围绕业务能力划分**，不按 Controller/Service/DAO 横向拆服务。
- **一个事实一个写入所有者**，其他服务通过契约请求或订阅事实。
- **本地强一致，跨边界显式最终一致**，不能假装远程调用属于本地事务。
- **状态变化可追溯**，关键动作有幂等事实、版本和业务审计。
- **失败是模型的一部分**，超时、重复、乱序、补偿失败和人工介入都有状态。
- **先保证正确性再优化吞吐**，锁、缓存、并行和异步不能破坏不变量。

## 8. 最小上线基线

- 每个写接口对应明确业务意图、资源授权、不变量和幂等语义。
- 聚合和本地事务足够小，事务中不等待不确定远程 I/O。
- 并发竞争由唯一约束、版本/条件更新等可证明机制处理。
- 业务数据和 Outbox 同事务提交，消费者可重复、乱序和重放。
- 跨服务流程有显式状态、超时、补偿、对账和人工处理入口。
- API/事件有所有者、Schema、兼容策略和消费者清单。
- 技术指标能关联业务结果与状态积压，不把 HTTP 200 当业务成功。
