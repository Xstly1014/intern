# 业务服务层：系统真正创造价值的地方

业务服务层拥有领域规则、业务状态和数据一致性边界。网关、缓存和 MQ 都是支撑手段；“订单何时可取消、库存何时扣减、优惠怎样叠加”才是系统不可替代的核心。

## 1. 从业务能力划分边界

```text
电商域
├─ 商品上下文：商品、类目、属性、上下架
├─ 交易上下文：购物车、价格快照、订单状态
├─ 库存上下文：可售、预占、扣减、释放
├─ 支付上下文：支付单、渠道、退款、对账
└─ 履约上下文：出库、配送、签收、售后
```

服务边界优先来自业务语言、规则和数据所有权，而非按 Controller、Service、DAO 横向拆服务。一个服务拥有自己的模型和数据库写权限；其他服务通过 API 或事件协作，不能直接改它的表。

## 2. 模块化单体还是微服务

| 条件 | 模块化单体更合适 | 微服务拆分更有价值 |
|---|---|---|
| 团队 | 小团队、协作紧密 | 多团队独立负责能力 |
| 发布 | 同一节奏 | 需要独立发布 |
| 伸缩 | 流量相似 | 某能力资源特征显著不同 |
| 一致性 | 大量本地事务 | 能接受明确的最终一致性 |
| 故障 | 爆炸半径可接受 | 必须隔离故障 |
| 运维 | 平台能力有限 | 已具备服务治理与可观测能力 |

微服务不是目标。先在一个 Spring Boot 应用中建立强模块边界，等独立伸缩、团队自治或故障隔离收益超过分布式成本时再物理拆分。

## 3. 服务内部的逻辑结构

```text
接口适配器（REST / RPC / MQ Consumer）
                ↓
应用层（用例编排、事务、权限入口）
                ↓
领域层（实体、值对象、聚合、领域服务、规则）
                ↓
端口 ← 基础设施适配器（DB / MQ / 第三方）
```

这不是用户所问的项目文件夹架构，而是业务服务内部保持依赖方向的方式：领域规则不依赖 Spring、数据库或供应商 SDK，基础设施通过接口适配领域需求。简单 CRUD 不必套完整 DDD，但边界、所有权和状态约束仍需明确。

## 4. 聚合、状态机和不变量

聚合是一个事务内必须保持一致的最小边界。订单聚合可以保证“已支付订单不能重复支付”“已完成订单不能取消”，但不应把库存、支付、物流所有对象塞进一个巨大聚合。跨聚合约束通过应用流程、预留/确认、事件和补偿实现。

```java
public class Order {
    private OrderStatus status;
    private Money payableAmount;

    public void markPaid(PaymentId paymentId, Money paidAmount) {
        if (status != OrderStatus.PENDING_PAYMENT) {
            throw new IllegalOrderState(status, "markPaid");
        }
        if (!payableAmount.equals(paidAmount)) {
            throw new PaymentAmountMismatch();
        }
        this.status = OrderStatus.PAID;
        registerEvent(new OrderPaid(id, paymentId));
    }
}
```

状态变化通过行为方法完成，而不是任意 `setStatus`。数据库约束、乐观锁和领域校验共同防止并发破坏不变量。

## 5. 事务与一致性

### 本地事务

一个服务内优先使用数据库本地事务，范围尽量短，不在事务中等待远程 HTTP、MQ 确认或大文件处理。隔离级别按异常风险选择，并用唯一约束、条件更新或版本号处理并发。

### 跨服务事务

不要追求把所有服务锁进一个 ACID 事务。常见方案：

- **Saga**：每步本地提交，失败执行语义明确的补偿；补偿不等于数据库回滚。
- **TCC**：Try 预留、Confirm 确认、Cancel 释放，适合库存/资金等强控制场景，但开发成本高。
- **Outbox**：业务数据和待发事件同事务保存，后台可靠发布，解决“库成功但消息没发”。
- **对账修复**：用事实记录和周期性核对收敛长尾不一致，是生产系统不可缺的最后防线。

## 6. 幂等与并发

写接口接受业务幂等键，并把 `主体 + 操作 + 幂等键` 建唯一约束；重复请求返回原结果，而非重复执行。消息消费者用事件 ID/业务版本去重。关键更新可使用 `UPDATE ... WHERE status = ? AND version = ?`，根据受影响行数判断竞争结果。

分布式锁不是默认解法。先考虑唯一约束、乐观锁、串行分区和状态机；使用 Redis 锁时要明确租约、续期、fencing token、进程暂停和锁失效后的正确性。

## 7. 服务通信

- 查询或当前决策必须立即获得结果：同步 HTTP/gRPC。
- 已经发生的业务事实需要通知多个订阅者：领域/集成事件。
- 长流程：显式流程管理器/Saga，保存步骤状态和补偿结果。
- 禁止形成深层同步调用链和循环依赖；为每个调用设超时、并发舱壁和错误语义。

API 与事件都要版本化。事件表达过去式事实，如 `OrderPaid`，不把“请发短信”伪装成领域事件；内部领域事件转换为稳定的集成事件后再出服务边界。

## 8. Java 运行时细节

Spring Boot 服务关注线程池隔离、HTTP/DB 连接池、JVM 内存、GC、类加载和优雅停机。线程池队列不能无限；数据库连接数不是越多越好；虚拟线程适合大量阻塞 I/O，但不会消除数据库、下游容量和锁竞争。所有异步执行器都要传递 Trace 和安全上下文并设背压。

Resilience4j 可提供超时、限流、舱壁和熔断；策略按下游和用例区分。重试必须服从幂等和总延迟预算。

## 9. 测试策略

| 层次 | 重点 |
|---|---|
| 单元测试 | 领域规则、状态机、边界值，无基础设施依赖 |
| 集成测试 | 数据库约束、事务、序列化、MQ/缓存适配器 |
| 契约测试 | API/事件生产者与消费者兼容性 |
| 端到端测试 | 少量关键用户旅程与部署连通性 |
| 性能/韧性测试 | 峰值、慢依赖、超时、积压、故障恢复 |

Testcontainers 可提高真实中间件集成测试的可信度。测试不仅覆盖成功，还要覆盖重复、乱序、并发、超时、部分失败和补偿失败。

## 10. 指标与常见误区

除 JVM/HTTP 指标外，必须有业务指标：下单成功率、状态停留时长、库存预占失败、支付成功率、补偿积压。技术成功但业务失败仍是事故。

常见误区包括按数据库表一表一服务、服务共享数据库、贫血模型中所有规则堆进一个 Service、超长同步链、跨服务大事务、无上限重试，以及只写 happy path 不设计人工修复。
