# 错误契约、国际化与客户端兼容

错误是 API 契约的一等部分。客户端需根据错误判断是修改输入、重新登录、刷新状态、退避重试还是联系支持。若所有错误都是 HTTP 200 + “操作失败”，客户端、CDN/网关、监控和 SLO 都无法正确理解。

## 1. 三层错误语义

![BFF 错误从内部原因到客户端契约的映射](/architecture/bff-error-model.svg)

1. **HTTP 状态**：给通用网络组件与客户端的粗粒度语义。
2. **稳定错误码**：给客户端程序分支，不随文案/内部异常类改名。
3. **人类可读信息与字段错误**：用于展示和定位，不应成为程序唯一判断依据。

## 2. 状态码契约

| 情况 | 常用状态 | 客户端行为 |
|---|---:|---|
| JSON/协议无法解析 | 400 | 修正请求，不原样重试 |
| 凭证缺失/无效 | 401 | 刷新凭证或重新登录 |
| 主体已验证但禁止 | 403 | 不重试，可提示权限不足 |
| 资源不存在/需隐藏存在性 | 404 | 刷新列表或返回 |
| 幂等载荷/状态/版本冲突 | 409 | 查询原结果或刷新状态 |
| 前置条件/ETag 失效 | 412 | 重新读取后决定是否再提交 |
| 请求格式正确但业务不接受 | 422 或团队统一约定 | 显示领域校验结果 |
| 配额/限流 | 429 | 根据 `Retry-After` 抖动退避 |
| 临时无法完成/依赖不可用 | 503 | 只在幂等与总预算内重试 |
| 上游超时 | 504 | 结果可能未知，写操作查状态/幂等重试 |

## 3. 错误 Body

```json
{
  "code": "ORDER_STATE_CONFLICT",
  "message": "订单当前状态不允许取消",
  "requestId": "01J...",
  "details": {
    "currentState": "SHIPPED"
  },
  "fieldErrors": []
}
```

- `code` 稳定、有命名规则和所有者。
- `message` 不包含栈、SQL、内部服务名或凭证细节。
- `requestId` 用于支持查询，不允许客户端用它获得其他用户日志。
- `details` 是按错误码定义的有类型数据，不是任意 debug map。
- `fieldErrors` 使用稳定字段 path 和错误码，不只返回一句合并文本。

## 4. 内部异常到外部错误

不将 Java 异常类名当公开错误码。应建立明确映射：

- 协议解析/结构校验由接入层直接产生 400 和字段错误。
- 用例返回有类型结果/领域错误，由 API Error Mapper 映射稳定契约。
- 下游客户端把连接、超时、限流和下游业务错误区分建模。
- 未知异常映射为通用 500，内部保留 exception fingerprint 与 Trace，对外不泄露。

不能把下游 404 无条件改成 BFF 500，也不能把所有下游 5xx 直接透传其 Body，因为它可含内部细节且与外部契约不稳定。

## 5. 校验错误

Field path 使用契约字段名，例如 `items[2].quantity`，不使用 Java 属性内部路径。字段错误码如 `required`、`invalid_format`、`out_of_range`、`unsupported_value` 可供客户端定位和本地化。不回传密码、Token 等敏感 rejected value。

## 6. 国际化责任

| 内容 | 建议所有者 |
|---|---|
| 稳定错误码 | 服务端 API 契约 |
| 页面操作与品牌文案 | 客户端，便于随 App 发布与离线 |
| 服务端动态合规/业务文案 | 服务端按 locale 生成，同时保留 code |
| 日志/审计 | 结构化 code 和原始事实，不依赖翻译文本查询 |

Locale 来自用户设置、终端明确选择或受控 `Accept-Language`，有默认和 fallback。不将任意 locale 变成无界缓存 Key/指标标签。

## 7. 老客户端兼容

![BFF 对多个客户端版本的兼容策略](/architecture/bff-version-compatibility.svg)

移动 App 不能强制所有用户立即升级。BFF 应根据真实版本分布制定：

- 最低支持版本、建议升级版本和强制升级的紧急条件。
- 兼容代码按 API/version adapter 集中，不把 `if (appVersion...)` 散布到领域层。
- 新字段给老客户端的缺失/默认语义，新枚举的 fallback。
- 安全漏洞无法兼容时可停用老版本，但要有明确响应与升级路径。

不信任客户端自报版本做高风险授权。版本主要是兼容/体验信号，可被伪造。

## 8. 部分成功与状态码

聚合查询中，可选区块失败不一定需要 207。可在契约中返回主资源 + 每区块可用性，但监控必须记录 partial result，不将 HTTP 200 当作完整成功。对写操作不用“部分成功”隐藏跨领域事务，而应定义业务流程和补偿。

## 9. 上线检查

- 每个错误是否有 HTTP 语义、稳定 code 和客户端建议行为？
- 写请求超时是否表达“结果未知”而不是错报失败？
- 下游错误是否经显式映射，不透传内部 Body/类名？
- 字段错误 path/code 是否可机器处理且不泄露敏感值？
- 客户端是否使用 code 而不是文案做程序分支？
- 老 App 版本的流量、错误、兼容适配和淘汰日期是否可观测？
- 部分结果是否在响应与指标中都可见？
