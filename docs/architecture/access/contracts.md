# API 契约、输入校验与版本演进

API 契约不只是一份接口文档，而是客户端与服务端之间可独立发布的协议。它包含路径、方法、Header、Body、状态码、字段语义、默认值、分页、幂等、错误码和废弃时间。任何一项在客户端依赖后改变，都可能是破坏性变更。

## 1. 契约从设计到淘汰

![API 契约生命周期](/architecture/bff-contract-lifecycle.svg)

1. 根据用户交互定义业务意图，不从数据库表倒推 API。
2. 用 OpenAPI/JSON Schema/Protobuf 定义机器可读契约，包含正反例与错误。
3. 在 CI 检查 lint、安全基线、破坏性差异和代码实现一致性。
4. 生成客户端类型/模拟服务，但不让生成类型泄漏进领域模型。
5. 通过消费者契约测试和端到端关键旅程验证。
6. 发布后按 API 版本、App 版本和调用方观测使用。
7. 废弃时先通知、迁移、限制新接入，证明无流量后才删除。

## 2. URI、Method 与业务意图

URI 表示资源，Method 表示通用操作语义。`GET` 应安全且无副作用，`PUT` 通常表示幂等整体替换，`PATCH` 是部分更新，`POST` 用于创建或无法自然映射的命令。

对明确业务动作，`POST /orders/{id}/cancel` 往往比一个万能 `PATCH /orders/{id}` 更好：它表达意图，可独立授权、审计和返回冲突。但不必机械追求 REST 纯度，契约稳定与语义可理解更重要。

## 3. 输入校验的四个层次

| 层次 | 例子 | 所有者 |
|---|---|---|
| 解析 | JSON 语法、Content-Type、数字/日期能否解析 | Web 框架/接入层 |
| 结构 | 必填、长度、格式、枚举、列表上限 | request schema |
| 交叉字段 | `startTime &lt; endTime`、二选一、条件必填 | 接入层/用例输入 |
| 业务不变量 | 库存足够、订单可取消、优惠券可用 | 领域层 |

校验注解不应远程查库或调用服务。否则对象反序列化期间就产生 I/O、不可控并发和错误映射。

## 4. 未知字段、null 与缺失

- 对公网 JSON 请求，是否拒绝未知字段要按 API 契约明确。严格拒绝可发现拼写错误，但会降低前向兼容。
- “字段缺失”、`null`、空字符串和空列表必须有不同或明确合并的语义。
- PATCH 需要表达“不修改”、“设为 null”和“设为某值”，普通 Java `null` 无法同时表达三态，应使用 Json Merge Patch、Json Patch 或显式 wrapper。
- 默认值是契约的一部分，从 `false` 改为 `true` 可能是破坏性变更。

## 5. 规范化不是悄悄修改

可规范化电话国际格式、语言标签、时区名、首尾空格，但不能悄悄截断过长值、对金额四舍五入或将未知枚举映射成默认业务状态。对安全敏感值，规范化和签名验证的顺序必须一致。

## 6. 时间、金额与枚举

### 时间

时刻使用包含偏移的 ISO 8601 或 epoch，业务日期用 `YYYY-MM-DD`，时区用 IANA ID（如 `Asia/Shanghai`）。不要用无时区的“2026-07-31 09:00:00”表示全局时刻。

### 金额

使用字符串小数 + currency，或最小货币单位整数 + currency。不使用二进制浮点数传金额，不根据小数位默认币种。

### 枚举

客户端应对未知响应枚举值有 fallback，服务端不应随意重用旧枚举值改语义。请求枚举可严格拒绝未知值，并返回字段错误。

## 7. 分页、排序与过滤

| 方案 | 适用 | 问题 |
|---|---|---|
| offset/limit | 小数据、浅页、运营跳页 | 深页慢，数据变化时重复/漏项 |
| cursor/keyset | 持续变化的信息流、大表 | 不便任意跳页，需稳定唯一排序 |

Cursor 应是不透明、签名或可校验的，编码排序键、方向和必要查询上下文。不接受任意字段排序/过滤，使用白名单防止昂贵查询和数据泄露。

## 8. 幂等契约

创建、支付、导入等写 API 要定义：

- 哪些请求必须携带 `Idempotency-Key`，键长度、字符集与作用域。
- 同一键与不同请求载荷冲突时返回 409，不默默执行新请求。
- 正在处理、已成功、已确定失败和结果未知的重放语义。
- 保留时间必须覆盖客户端可能重试窗口。

BFF 负责校验和传递契约，真正幂等事实应与业务结果一起持久化在用例所有者。

## 9. 兼容性分类

| 变更 | 通常风险 |
|---|---|
| 新增可选响应字段 | 理论兼容，但严格反序列化客户端可失败 |
| 新增枚举值 | 老客户端可无 fallback |
| 新增必填请求字段 | 破坏性，旧客户端不传 |
| 删除/改名/改类型 | 破坏性 |
| 收紧长度或校验 | 对已存在输入可破坏 |
| 从缺失改为 `null` | 对部分客户端是破坏性 |
| 改变默认值/错误码/排序 | 语义破坏，Schema diff 可能检不出 |

除机器 diff 外，重要 API 需保留真实老 App SDK/契约样例运行兼容测试。

## 10. 上线检查

- 契约是否包含 Header、错误、分页、幂等和默认值，不只是成功 Body？
- 输入大小、深度、列表长度、未知字段和 null 语义是否明确？
- 校验器是否不执行远程 I/O 和领域规则？
- 时间、金额、枚举和 Cursor 是否有精确表示？
- 破坏性差异是否在 CI 阻断，语义变更是否人工评审？
- 是否有真实老客户端/消费者契约测试？
- 废弃 API 是否有调用方清单、日期、迁移方案和无流量证据？
