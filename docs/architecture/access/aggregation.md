# 聚合、并发、扇出与部分失败

商品详情页可能需要商品、库存、价格、评价和推荐。BFF 聚合能减少客户端网络往返并裁剪数据，但也会把一个入口请求放大为多个内部调用。没有预算、并发和部分失败设计的聚合，会成为级联故障放大器。

## 1. 聚合预算模型

![BFF 聚合的 deadline、并发与扇出预算](/architecture/bff-aggregation-budget.svg)

总 deadline 要包含 BFF 本地处理、连接池排队、下游调用、结果组装与响应传输余量。不能给五个下游各配等于 BFF 总超时的超时。

| 下游 | 优先级 | 失败策略示例 |
|---|---|---|
| 商品基础信息 | 必需 | 失败则整个页面失败 |
| 实时价格/可售库存 | 关键 | 不伪造价格；可显示暂不可购或失败 |
| 评价摘要 | 可选 | 返回 `unavailable` 或省略区块 |
| 推荐 | 增值 | 快速降级为空列表，不阻塞主内容 |

优先级是产品契约，不应由某个开发者在 catch 中随意决定。

## 2. 串行、并行与依赖图

独立查询应并行，有数据依赖的调用才串行。例如需先查商品才知道商家 ID，但如果 request 已有可信商品 ID，库存和评价可并行。

并行不等于无界。每个 BFF 请求、每个下游和整个实例都要有并发上限。在 Java `CompletableFuture`/Reactor 中把 500 个列表项目直接 flatMap 为 500 个 RPC，会在高流量下耗尽连接池。

## 3. 扇出放大

```text
内部调用率 ≈ 入口 RPS × 平均扇出 × 平均尝试次数
```

1,000 RPS 的页面、平均 8 个下游调用、故障期平均 1.5 次尝试，会对内部制造 12,000 RPS。扇出是容量模型和 SLO 的一级指标，不能只在 Trace 中偶然看到。

## 4. N+1 与批量化

对 50 个订单逐个查商品/用户会制造 N+1。解决顺序：

1. 让数据所有者提供有界批量 API，定义最大 ID 数、去重、顺序与缺失项语义。
2. GraphQL 使用 request-scoped DataLoader 将同一事件循环的 Key 批量化。
3. 高频稳定查询建立专用读模型，而不是每次在 BFF 重建跨域 Join。
4. 不让 BFF 为了解决 N+1 直接连接别人的数据库。

## 5. 部分失败的契约

![BFF 聚合的部分失败决策](/architecture/bff-partial-failure.svg)

| 方式 | 适用 | 注意 |
|---|---|---|
| 整体失败 | 主体资源/关键事实不可用 | 保留 5xx/503 语义和 request ID |
| 省略可选字段 | 客户端已定义缺失语义 | 不能与真实空值混淆 |
| 显式 `unavailable` | 客户端需展示部分降级 | 结构需稳定且可观测 |
| 使用陈旧缓存 | 数据允许陈旧且有时间标记 | 价格/库存等不能随意 stale |
| 异步补齐 | 不影响当前交互的重计算 | 不要为当前请求建无界后台任务 |

不应用默认值伪造成功，例如价格服务失败就返回 0，库存失败就返回“有货”。

## 6. 错误传播与取消

某个必需下游确定失败后，取消尚未完成的可选调用，释放连接和 CPU。取消是合作式的：必须传播 deadline/cancellation，下游客户端与服务也要响应。不能假设 Future cancel 后远程已停止。

## 7. 重试与 Hedging

BFF 查询只对明确短暂错误、可幂等请求，在剩余 deadline 内有界重试。如果网关/Mesh 已重试，BFF 通常不再叠加。

Hedging 在首次请求超过延迟阈值后并发第二次，取首个成功。它会增加下游负载，只适合少数幂等、尾延迟敏感、有充足容量的读取，并需全局 hedge 预算。

## 8. 聚合缓存

缓存整个页面响应会组合多个数据所有者的新鲜度与权限，失效复杂。优先：

- 由数据所有者缓存稳定查询。
- BFF 只缓存公开、高复用、短 TTL 的投影，或 request-scoped 去重。
- 个性化响应 Key 必须包含主体/租户/权限/语言等真正变体，否则会串数据。
- 不缓存含短期签名 URL、一次性 Token 和未脱敏敏感数据的整体响应。

## 9. GraphQL 专项风险

- 查询深度、字段数、列表乘法和 Resolver 成本纳入复杂度预算。
- 使用 Persisted Query/允许列表降低公网任意查询风险。
- DataLoader 必须 request-scoped，缓存 Key 包含租户/权限变体。
- 字段级授权不能只在 UI 隐藏，Resolver/读模型必须执行。
- GraphQL 部分错误虽可 HTTP 200 + `errors`，观测必须读 GraphQL 执行结果，不将其全记为成功。

## 10. 上线检查

- 总 deadline、下游子预算和响应余量是否协调？
- 下游是真正独立并行，还是存在隐式数据依赖？
- 每请求/每下游/每实例的扇出与并发是否有上限？
- 是否使用批量 API、DataLoader 或读模型解决 N+1？
- 每个字段/区块是必需还是可选，部分失败是否在契约中可见？
- 重试/Hedge 是否与网关、Mesh 协调并有全局预算？
- 缓存 Key 是否包含所有权限与个性化变体？
