# 性能、缓存、可观测与测试

BFF 的性能瓶颈往往不是本地 JSON 转换，而是下游扇出、连接池排队、大响应、序列化、缓存变体、阻塞线程和失败时的重试放大。观测必须同时回答“用户看到什么”和“一个入口请求在内部制造了什么”。

## 1. 容量维度

| 维度 | 主要驱动 |
|---|---|
| 入口 RPS | 终端流量、轮询、客户端重试 |
| 内部调用率 | RPS × 扇出 × 尝试次数 |
| 并发 | RPS × 端到端停留时间，长流单独算 |
| 线程/Event Loop | 阻塞 I/O、下游慢、序列化 CPU |
| 下游连接 | 下游集群数、并发、HTTP/2 流、超时 |
| 内存 | 并发 Body/响应、聚合中间结果、缓存、日志 |
| 带宽 | 页面响应大小、图片是否误经 BFF、压缩 |

压测应使用真实扇出、下游延迟分布、响应大小和客户端版本比例，不只是所有下游都瞬时成功的空响应。

## 2. MVC、WebFlux 与虚拟线程

- Spring MVC + 平台/虚拟线程适合阻塞客户端生态，仍需限制下游连接、在途请求和排队。虚拟线程不会扩容数据库连接池。
- WebFlux 适合下游客户端、序列化和整条热路径都非阻塞的高并发 I/O。JDBC、阻塞 SDK 或大 CPU 任务不能占 Event Loop。
- 两者都需要 deadline、cancellation、bulkhead、有界并发和上下文传播；编程模型不会自动创造韧性。

## 3. 响应大小与序列化

- 按 API 监控 request/response bytes 分位数，过大响应会同时增加 BFF 内存、CPU、网络与客户端解析成本。
- 图片、视频和大文件应走对象存储/CDN 签名 URL，不经 BFF 内存中转。
- 批量/导出使用异步任务或流式响应，同时设数量、字节、时长和慢客户端上限。
- 压缩有 CPU 代价，不重复压缩已压缩格式，对小响应不必启用。

## 4. 缓存层次

| 缓存 | 适用 | 关键风险 |
|---|---|---|
| HTTP/CDN | 公开、稳定 GET | `Vary`、身份、串用户 |
| BFF 本地 | 小、热、短期参考数据 | 实例不一致、无界 Key、发布冷启 |
| BFF 分布式 | 跨实例复用的投影 | 新故障依赖、序列化、失效与权限变体 |
| request-scoped | 同一聚合内去重/DataLoader | 不能误设为全局造成串租户 |
| 数据所有者 | 稳定查询与读模型 | 通常是首选，因为最知道失效语义 |

缓存个性化聚合前要列出所有响应变体：subject、tenant、role/scope、locale、App 版本、实验桶、数据版本。变体过多时命中率很低，不应缓存整体。

## 5. 可观测模型

![BFF 入口、聚合下游与用户结果的观测关联](/architecture/bff-observability.svg)

### API 入口

- Rate、HTTP status/error code、P50/P95/P99、request/response bytes。
- channel、API version、App major/minor 的受控低基数维度。
- 解析/校验失败类别、幂等键缺失/冲突。

### 聚合

- 每个入口请求的下游调用数、唯一下游数、重试和取消数。
- 下游队列/Connect/TTFB/总耗时、状态和降级。
- complete/partial/stale 结果率，可选区块缺失率。
- 连接池、线程池/Event Loop、在途请求和队列。

### 业务体验

BFF 可记录“订单 API 已被接受”，但业务成功由用例所有者定义。页面聚合则应与 RUM/客户端指标关联，因为 BFF 响应快不代表页面可交互。

## 6. 日志与 Trace

- 结构化记录 API ID、契约版本、终端、状态、错误码、扇出、partial/stale、耗时和响应大小。
- 不默认打印 request/response Body、Token、Cookie 和个人数据。调试采样也需字段白名单与时限。
- 一个 BFF server span，每个下游尝试独立 client span，并行分支保留同一 trace。
- 将 API/route、下游名、结果类别放低基数 span attribute，不放完整 URI/用户 ID。

## 7. 测试金字塔

| 层次 | 覆盖 |
|---|---|
| 单元 | Mapper、规范化、错误映射、部分失败决策、预算计算 |
| Web slice/component | JSON、Header、校验、状态码、SecurityContext、过滤器顺序 |
| 契约 | OpenAPI diff、消费者契约、下游 stub，包含错误/超时 |
| 集成 | 真实 HTTP/gRPC 客户端、序列化、鉴权、连接池与可观测 |
| 端到端 | 少量关键用户旅程和生产形态连通 |
| 性能/韧性 | 真实扇出、慢/失败下游、取消、重试、大响应、上下文 |

## 8. 故障测试

- 必需下游超时：快速整体失败并取消可选调用。
- 可选下游超时：按契约返回 partial，不拖到总 deadline。
- 连接池耗尽：队列有界，其他下游/路由有 bulkhead。
- 缓存故障：在安全容量内回源，防止击穿，不串用户。
- 日志/遥测后端故障：有界缓冲和丢弃计数，不阻塞请求线程。
- 一个 BFF 实例/可用区终止：剩余容量承接，在途请求影响可观测。

## 9. 上线检查

- 容量是否同时计算入口 RPS、扇出、尝试、并发、响应大小和连接池？
- MVC/WebFlux/虚拟线程的选择是否与实际依赖模型一致？
- 大文件是否绕过 BFF，大导出是否异步/流式且有上限？
- 缓存是否有清晰所有者、新鲜度和完整权限变体？
- 指标是否区分 complete/partial/stale，下游尝试是否与入口请求分开？
- 是否对真实老 App 契约、错误、慢下游和上下文传播做回归？
