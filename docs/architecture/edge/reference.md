# 生产参考架构：按规模落地客户端与边缘层

本篇把前面组件组合成三套参考架构，并给出从需求到上线的设计模板。参考架构不是固定答案；选择组件的依据应是业务风险、用户分布、流量、团队和成本。

![系统边缘架构从小型到全球化的演进](/architecture/edge-reference-evolution.svg)

## 1. 小型系统：简单但具备生产底线

适用：内部工具、早期产品、单地域、流量不大、团队人数少。

```text
Web/App
  ↓ HTTPS
云 DNS
  ↓
云 CDN/WAF（静态资源 + 基础防护）
  ↓
云 L7 Load Balancer
  ↓
2+ 个 Spring Boot 实例（跨两个故障域）
```

### 必须具备

- DNS、域名和证书自动续期与到期告警。
- 全站 HTTPS，正确 CORS/安全 Header。
- 静态资源内容哈希 + CDN 长缓存。
- 基础 WAF、请求大小、登录/短信限流。
- 至少两个应用实例，readiness 与优雅停机。
- 入口日志、HTTP 指标、外部合成探测。
- 数据库备份恢复和简单应急手册。

### 暂时不必具备

自建 DNS、双 CDN、服务网格、多地域双活、复杂 Bot 平台和多层网关。优先使用云托管能力，减少需要值守的系统。

## 2. 成长型系统：多区、分层保护和可观测

适用：公网业务、移动用户、多团队、峰值明显、开始有可用性要求。

```text
客户端（幂等/退避/RUM）
  ↓
Managed DNS + GSLB
  ↓
CDN + Anti-DDoS + WAF/Bot
  ├─ 静态 → CDN / Object Storage
  └─ 动态 → Origin Shield / 安全回源
                  ↓
         Regional L7 LB（多 AZ）
                  ↓
         API Gateway / BFF 集群
                  ↓
             Java 业务服务
```

### 新增能力

- 按地域/运营商的 RUM 和合成监控。
- CDN 缓存键、Shield、请求合并和精确失效。
- 源站仅允许可信回源，真实 IP/Header 信任链。
- WAF 规则灰度、Bot 风险评分、分层限流。
- 多 AZ 容量、跨区策略、连接排空和压测。
- 边缘配置即代码、审计、灰度和回滚。
- 备用地域或可验证的恢复方案，明确 RTO/RPO。

## 3. 大型/全球系统：多地域、Cell 和供应商治理

适用：全球用户、核心交易、高 SLO、多个业务域和平台团队。

```text
全球客户端
  ↓
多权威 DNS / Anycast Global Edge
  ↓
多供应商 CDN/Anti-DDoS（按业务风险选择）
  ↓
地域边缘 Cell
  ├─ WAF/Bot/Rate Limit
  ├─ Regional LB/Gateway
  └─ BFF/核心服务 + 地域数据能力
  ↓
全局控制面：流量目录、身份、配置、可观测、发布与容灾
```

### 关键治理

- 按用户/租户 Cell 化，限制单次故障爆炸半径。
- 控制面与数据面分离，最后有效配置可持续承载。
- 多供应商配置抽象、一致性验证和退出演练。
- 流量调度与数据主权、写入拓扑和合规一致。
- 错误预算驱动发布，自动金丝雀与地域门禁。
- 24×7 值班、供应商升级渠道、故障演练和容量预测。

多供应商不是为了架构图对称。只有单供应商风险超过双套配置、日志、证书、缓存语义和运维成本时才值得。

## 4. 创建订单参考链路

```text
App
  │ POST /orders + Access Token + Idempotency-Key
  ▼
DNS/GSLB：选择健康、合规的最近边缘
  ▼
Anti-DDoS：清洗 L3/L4 攻击
  ▼
TLS Edge：TLS 1.3/h2，清洗 Forwarded Header
  ▼
Bot/WAF：设备风险、Schema、Body、速率；不判断库存业务
  ▼
CDN：POST bypass，受控安全回源
  ▼
Regional LB：健康检查、连接复用、选择 Gateway
  ▼
API Gateway：Token 初检、用户/租户限流、路由
  ▼
BFF / Order Service
```

### 关键契约

- App 总超时内有限重试，同一业务意图使用同一幂等键。
- 各层覆盖外部伪造身份和转发 Header。
- WAF/网关返回稳定错误和 request/event ID。
- LB 不自动重试不安全的 POST。
- 订单服务即使客户端断开仍按幂等规则完成或可查询。
- 边缘日志不记录 Token、完整订单 Body 和敏感数据。

## 5. 静态站点参考链路

```text
HTML: short TTL + stale-while-revalidate
  └─ 引用 app.[content-hash].js / style.[hash].css
       └─ long TTL + immutable

图片: /images/{id}/{version}/{size}.webp
  └─ CDN 图片转换结果 + long TTL

发布顺序：先上传新哈希资源 → 验证 → 发布 HTML
回滚顺序：HTML 指回旧哈希；旧资源仍保留
```

这避免全站 purge 和“HTML 已更新但资源未上传”的短暂白屏。

## 6. 文件上传参考链路

```text
Client → API 申请 upload session
       ← 短期签名、对象 Key、分片规则
Client → 隔离对象存储分片直传
Client → API 完成上传
       → 服务校验摘要/大小
       → 扫描/审核/重编码
       → 发布 Bucket/状态
       → CDN 分发
```

Java API 只管理授权、元数据和状态，不转发大文件字节。上传凭证限制 Key 前缀、大小、类型和有效期。

## 7. 长连接参考链路

```text
Client ─ WebSocket/SSE ─ Edge/LB ─ Realtime Gateway
  │          心跳 < 最小空闲超时
  │          断线：指数退避 + 抖动
  │          重连：lastEventId / cursor
  └──────── 身份过期：安全刷新/重连
```

容量按并发连接、新建/重连速率、每连接内存、消息带宽和 fan-out 计算。部署时逐步摘流，不能让百万连接同时重连。

## 8. 边缘架构设计文档模板

### 8.1 背景和目标

- 用户地域、终端、运营商和网络特征。
- 峰值/平均 RPS、带宽、并发连接、请求/响应大小。
- SLO、延迟目标、RTO/RPO、合规和预算。

### 8.2 域名和信任边界

- 域名、用途、公开/内部、所有者、证书和 DNS。
- 边缘、源站、管理面之间的网络和身份信任。
- 哪些 Header 被删除、重写、签名和传播。

### 8.3 流量和缓存

- 静态/动态/上传/下载/长连接路径。
- 缓存键、TTL、Vary、失效、错误缓存和源站保护。
- 调度、健康、超时、重试、限流和优先级。

### 8.4 安全

- DDoS、WAF、Bot、API Schema、凭证和上传。
- Fail-open/closed、误报、白名单、审计和应急。

### 8.5 可靠性和运维

- 故障域、容量余量、控制面、切流和回滚。
- RUM、Synthetic、指标、日志、告警、Runbook。
- 压测、混沌、证书轮换和容灾演练。

## 9. 端到端上线总清单

### 客户端

- [ ] 超时、取消、幂等、有限重试和弱网状态明确。
- [ ] 连接复用、并发和缓存有界，旧版本兼容。
- [ ] Token 安全存储，RUM 脱敏并可关联 request ID。

### DNS

- [ ] 域名/注册商/DNS 账号安全、续费、TTL 和负缓存可控。
- [ ] 多地/多运营商 A/AAAA、DNSSEC 和切流演练通过。

### CDN

- [ ] 缓存分类、键、TTL、Vary、Purge 和错误缓存明确。
- [ ] 源站隐藏、Shield、回源限流和防击穿已验证。

### 安全

- [ ] DDoS、WAF、Bot、业务滥用和上传各有分层防线。
- [ ] 规则灰度、误报、事件 ID、白名单到期和应急流程完整。

### LB 与协议

- [ ] L4/L7 拓扑、健康、算法、连接池和超时一致。
- [ ] TLS/证书/h1/h2/h3/gRPC/长连接兼容与降级通过。
- [ ] Forwarded Header、Host、SNI 和未知路由默认安全。

### 可靠性

- [ ] 峰值与故障容量覆盖带宽、连接、TLS、回源和日志。
- [ ] 有界队列、过载保护、流量优先级和重试防放大。
- [ ] 多区/多地域切流、回切、数据和依赖条件完成演练。

### 可观测与变更

- [ ] RUM + Synthetic + Edge/Server 遥测形成闭环。
- [ ] 各层错误来源、配置版本和端到端关联可查询。
- [ ] 配置即代码、评审、灰度、门禁、回滚和紧急权限完备。

## 10. 最终取舍原则

1. 用托管服务减少无差异运维，但保留配置、数据和迁移可见性。
2. 先解决确定的风险，不为遥远规模一次性引入双 CDN、多活和复杂 Mesh。
3. 先把超时、幂等、缓存、安全、观测和恢复做好，再追求组件数量。
4. 每个新增代理层都必须带来可量化收益，并承担延迟、故障和调试成本。
5. 用户端成功率是最终标准，任何单组件“99.99%”都不是端到端承诺。
