# 可靠性、容量与多地域：边缘系统如何承受故障和洪峰

边缘系统处在所有流量的必经路径，任何小概率故障都会被庞大请求量放大。可靠性设计不只是部署两个实例，而是确保 DNS、网络、证书、CDN、WAF、LB、NAT、网关及其控制面在组件故障、流量洪峰和错误变更下仍能提供可接受服务。

## 1. 先定义目标

### SLI/SLO

边缘层可用性应从用户侧定义，例如：

- 有效请求能成功解析 DNS、建立 TLS，并到达网关的比例。
- 静态资源在目标时间内完整返回的比例。
- 各地域/运营商的入口 P95/P99 延迟。
- 边缘产生的非预期 5xx/连接失败率。

只看 LB 健康后端数不能代表用户可用。DNS、运营商、证书或 CDN 局部故障时，源站可能完全健康。

### RTO/RPO

边缘配置通常不涉及业务数据 RPO，但配置、证书、域名和规则同样要备份与重建。RTO 定义地域或供应商故障后多久恢复；配置 RPO 定义最多丢失多少最近变更。

## 2. 容量不等于 QPS

边缘容量至少包含：

| 资源 | 量纲 | 可能瓶颈 |
|---|---|---|
| 带宽 | bps/Gbps | 大响应、攻击、跨区回源 |
| 包速率 | pps | 小包 Flood、网卡/内核 |
| 新建连接 | connections/s | TCP、TLS、conntrack、CPU |
| 并发连接 | connections | WebSocket、Keep-Alive、内存 |
| 请求速率 | requests/s | WAF、代理解析、网关 |
| TLS 握手 | handshakes/s | 密码学 CPU、证书链 |
| 回源请求/带宽 | RPS/bps | CDN miss、purge、源站连接池 |
| WAF 检查吞吐 | RPS/bytes | 大 JSON、上传、复杂规则 |
| NAT 端口 | tuples | 大量出站连接、端口耗尽 |
| 日志吞吐 | events/bytes | 攻击时遥测反压与成本 |

一次请求平均 10 KB 和一次请求平均 10 MB，即使 QPS 相同，对带宽和连接占用完全不同。

## 3. 基础估算方法

### 带宽

```text
出口带宽 ≈ RPS × 平均响应字节 × 8 × 峰值/协议系数
```

例：10,000 RPS、平均响应 50 KB，裸数据约 4 Gbps，还未考虑 TCP/TLS 开销、重传和峰值。CDN 字节命中率会显著影响源站带宽。

### 并发

根据 Little's Law：

```text
平均并发 ≈ 到达率 × 平均停留时间
```

10,000 RPS、平均响应 200 ms，约 2,000 个在途请求；但 P99、慢上传、长轮询和 WebSocket 必须单独计算。

### 新建连接

```text
新建连接率 ≈ 请求率 ÷ 每连接平均请求数
```

连接复用从每连接 1 个请求提升到 20 个，可显著减少 TCP/TLS 压力。监控真实复用率，不用理论值。

### 故障余量

若三个可用区各承担约 1/3 流量，要求失去一个区后仍可运行，则每个剩余区至少承受正常约 1/2 总流量，并保留发布、突发和不均衡余量。不能正常时把全部实例跑到 80% 再声称可容忍一机房故障。

## 4. 过载时系统会怎样失败

### 无界排队

请求进入无限队列，表面不丢请求，但延迟不断增加，客户端超时重试，最终形成“重试放大—更多排队—更多超时”的正反馈。正确做法是有界队列、早期拒绝和明确 429/503。

### 重试风暴

客户端、CDN、LB、网关和服务每层重试 2 次，最坏可把一次请求放大到几十次。指定单一主要重试层，限制总预算，并使用退避和抖动。

### 缓存失效洪峰

CDN purge 或热门 Key 同时过期，使源站请求增加几十倍。需要请求合并、stale 内容、回源限速、Shield 和数据库保护。

### 日志反压

攻击期间每个拒绝请求都写完整日志，日志代理、磁盘或网络先被打满。安全事件聚合、采样、限速，关键审计单独通道；遥测失败不能阻塞请求线程。

## 5. 过载保护的层次

```text
Anti-DDoS：丢弃确定的网络攻击
  ↓
CDN：缓存命中、请求合并、回源限速
  ↓
WAF/Bot：阻断恶意与自动化滥用
  ↓
LB/Gateway：连接上限、并发限制、按优先级限流
  ↓
Java 服务：舱壁、有界线程/队列、下游预算、降级
  ↓
数据库/中间件：连接/消费/写入上限
```

外层保护参数不能大于内层总容量。例如后端只能稳定处理 20k RPS，网关限流设 100k 没有保护意义。容量需要从最稀缺下游反推。

## 6. 请求优先级和负载卸载

流量紧张时不是所有请求同等重要：

1. 健康/控制流量：确保系统可管理，但防滥用。
2. 核心交易写入：下单、支付回调。
3. 核心查询：订单状态、商品基本信息。
4. 可降级能力：推荐、评价、个性化。
5. 后台导出、爬虫和批处理：最先限速。

优先级应从可信入口生成，客户端不能自行发送 `X-Priority: critical`。为高优请求预留独立并发/连接配额，避免低优请求占满所有资源。

## 7. 多实例和多可用区

### 消除单点

- LB/网关多实例跨故障域。
- 控制面故障时数据面使用最后有效配置。
- NAT、DNS resolver、证书服务和日志出口也要冗余。
- 每区有完整依赖路径，而不是应用跨区、数据库只在一区。

### 故障域隔离

按区/机架/节点反亲和部署；单一配置变更可能仍同时破坏所有实例，因此还需版本隔离和小批灰度。多实例解决硬件故障，不能解决同构软件 bug。

### Cell-Based Architecture

大规模系统可把用户/租户分配到多个相对独立 Cell，每个 Cell 有自己的入口、网关和服务容量。单 Cell 故障只影响一部分用户，降低爆炸半径；需要全局目录、路由和迁移能力。

## 8. 多地域模式

### Active-Passive

主地域接流，备用地域保持热/温/冷。简单但切换时间和备用容量需演练。冷备不可能提供分钟级 RTO。

### Active-Active Read / Single-Writer

多个地域接查询，写入集中主地域。读取低延迟，写请求可能跨洲；主地域故障需提升新主和处理复制延迟。

### Multi-Writer

多个地域都写，用户延迟最低但数据冲突、全局约束、顺序和运营复杂度最高。只有业务能定义冲突合并或数据天然分区时采用。

边缘调度必须服从数据拓扑。把用户导向最近地域，却让每次数据库写跨洲访问唯一主库，可能比直接进入主地域更慢且更脆弱。

## 9. 故障切流的前置条件

目标地域必须同时满足：

- 入口、证书、WAF、Secret 和第三方白名单完整。
- Java 服务版本和配置兼容。
- 数据达到允许的 RPO，写角色明确。
- Redis、MQ、搜索、对象存储和外部依赖可访问。
- 容量足以接管并包含缓存冷启动余量。
- 合成交易通过，监控和告警正常。
- 有防止双主、重复回调和流量摇摆的机制。

切流不只是改 DNS。要定义决策者、审批（紧急时简化）、执行步骤、观测门槛、回退条件和用户沟通。

## 10. 避免流量摇摆

自动健康检查可能在区域恢复一点后立刻切回，负载一来又故障。策略包括：

- 连续多次成功才恢复。
- 切换后最小驻留时间。
- 逐步增加权重并观察 SLO、容量和数据。
- 故障恢复后先预热缓存和连接。
- 自动切出，人工/受控切回。

## 11. 控制面与数据面

DNS、CDN、WAF、LB 都有控制面配置和承载请求的数据面。可靠设计要求：

- 控制面不可用时数据面继续运行。
- 配置有本地缓存、版本和最后有效状态。
- 配置发布先验证语法和引用资源，再灰度数据面。
- 错误配置能自动回滚，不依赖同一个故障控制面。
- Break-glass 紧急访问有强认证、审计和定期演练。

不要让每个请求同步依赖配置中心、鉴权控制面或管理 API。

## 12. 变更可靠性

边缘事故常由变更而非硬件引起：错误 WAF 规则、证书绑定、全站 purge、LB 超时和 DNS 权重。

配置即代码流程：

```text
Git 变更 → Schema/语法校验 → 静态策略测试 → 测试域名
        → 单 PoP/单地域/小权重灰度 → SLO 门禁
        → 分批全量 → 观察期 → 自动/人工回滚
```

关键配置采用双人评审、变更窗口和 blast radius 限制。高风险动作如全站 purge、删除域名、降低防护、证书替换增加二次确认和速率限制。

## 13. 混沌与灾备演练

演练场景应从小到大：

- 单网关实例终止、节点维护、可用区断流。
- DNS 返回旧/错误地址、某递归解析器失败。
- CDN 回源失效、缓存全 miss、Shield 故障。
- WAF 规则误杀、Bot 评分服务不可用。
- TLS 证书即将过期/错误链、密钥轮换。
- LB 后端慢、连接池耗尽、长连接重连洪峰。
- 主地域切备用、数据复制落后和回切。

每次演练记录实际检测时间、决策时间、执行时间、恢复时间和用户影响，验证 RTO 而不是只宣布“切换成功”。

## 14. 容量测试

边缘压测应区分：

- 缓存 hit 与 miss。
- 短连接与高复用连接。
- TLS 完整握手与会话恢复。
- 小 JSON、大响应、上传、下载和长连接。
- 正常流量与 WAF/Bot 规则命中流量。
- 单区故障、实例缩容和发布期间容量。

逐级加压观察第一个饱和点和过载行为。压测必须有流量隔离、成本上限和停止条件，不能误伤生产用户或第三方。

## 15. 上线检查清单

- [ ] SLO 从用户侧定义，覆盖地域和运营商。
- [ ] 容量模型包含带宽、pps、连接、TLS、RPS、回源和日志。
- [ ] 关键资源有正常峰值、故障接管和发布余量。
- [ ] 所有连接、队列、请求体、重试和并发有界。
- [ ] 高低优流量有独立保护，优先级不能被客户端伪造。
- [ ] 多区包含完整依赖路径，故障域和配置爆炸半径受控。
- [ ] 多地域模式与数据写入拓扑一致，RTO/RPO 可验证。
- [ ] 切流、渐进回切、防摇摆和缓存预热流程明确。
- [ ] 控制面故障不影响已有数据面流量。
- [ ] 变更灰度、自动门禁、回滚和灾备演练持续执行。
