# 架构输入、质量属性、约束与容量建模

架构设计必须从可验证输入开始。没有业务旅程、负载分布和质量目标，“高并发”“低延迟”“高可用”只是形容词，无法决定缓存、分区、副本、灾备和预算。

## 1. 从业务旅程提取系统目标

![业务目标到架构决策的追踪链](/architecture/practice-requirement-trace.svg)

先列出注册、登录、搜索、下单、支付、履约、退款等关键旅程，标记用户、入口、读写状态、外部依赖和完成判定。每条旅程给出业务价值、峰值窗口、失败影响和降级方式。核心目标应能追踪到设计、测试、指标和负责人，避免需求在层间传递时丢失。

## 2. 质量属性要能测量

| 属性 | 必须明确 | 验证方式 |
|---|---|---|
| 性能 | p50/p95/p99、吞吐、payload、地域 | 分层压测与生产分位 |
| 可用性 | SLI 口径、SLO、排除项、错误预算 | 合成探测、真实请求指标 |
| 一致性 | 哪些操作强一致，允许多旧，冲突怎样收敛 | 并发、故障和重放测试 |
| 恢复 | RTO、RPO、数据权威、回切条件 | 备份恢复与切流演练 |
| 安全 | 身份、授权、租户、数据分级、审计 | 威胁建模、策略与渗透测试 |
| 可演进性 | 兼容窗口、发布频率、迁移期限 | 契约测试、双版本运行 |
| 成本 | 单请求/订单成本、预算、容量余量 | 云账单分摊与单位经济性 |

冲突需要显式取舍。例如同步跨地域写入提高一致性，却增加延迟和故障耦合；高冗余提高可用性，也提高固定成本。ADR 要记录选择和放弃项。

## 3. 流量与并发模型

![QPS、并发和下游放大的容量模型](/architecture/practice-capacity-model.svg)

从日活、峰值同时在线、每用户操作频率和峰谷比估算入口 QPS，再按接口占比、重试、扇出和异步任务计算每个依赖的实际负载。Little's Law 可作初始估算：`并发数 ≈ 到达率 × 平均停留时间`，但连接池要按尾延迟、事务占用和慢依赖校准。

不能只测平均值。压测应覆盖突发、热点 key、大 payload、缓存冷启动、GC、扩容滞后、依赖变慢和节点损失。服务能扛住入口 QPS，不代表数据库连接、MQ 分区或第三方配额能承受放大后的请求。

## 4. 数据与存储容量

分别估算业务记录、索引、版本、Outbox、审计、日志、备份和副本：`日增量 = 日请求 × 写比例 × 单条物理大小`。再加入保留期、压缩率、复制因子、索引放大、迁移双写和恢复临时空间。冷热分层和删除规则要与合规保留一致。

## 5. 约束清单

必须记录交付期限、团队技能和 on-call 能力、预算、既有系统、云与 Region、许可证、监管、数据驻留、供应商配额及退出难度。约束不是附注，它决定是否适合微服务、Kubernetes、多活或自建中间件。

## 6. 容量评审输出

- 按旅程和接口拆分的峰值、突发与增长假设。
- 每层吞吐、并发、连接、线程、队列、分区、磁盘和带宽预算。
- 正常、降级、单节点与单 AZ 故障时的容量余量。
- 压测数据、模型误差、触发扩容的领先指标和采购提前量。
- 最大假设、数据来源、owner、复审日期和超出模型后的保护动作。
