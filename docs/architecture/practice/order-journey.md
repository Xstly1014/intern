# 创建订单端到端设计：从用户意图到最终收敛

端到端设计需要同时描述成功路径、超时与未知结果、数据提交、事件传播、外部副作用和人工修复。下面以创建并支付订单为例串联前述各层。

## 1. 同步提交与异步推进

![创建订单的同步事务与异步履约时序](/architecture/practice-order-sequence.svg)

客户端生成 `Idempotency-Key`，网关验证身份、限流并传递 deadline；BFF 校验 DTO 后调用订单用例。订单服务锁定或校验库存，在一个本地事务中写订单、库存预占引用和 Outbox，然后立即返回可查询的订单 ID。发布器把事件送入 MQ，支付、履约和通知各自幂等消费。

请求超时不代表事务失败。客户端用同一幂等键重试或查询，服务端返回第一次结果；绝不能因为没收到响应就创建第二笔订单。

## 2. 状态机与不变量

![订单、库存与支付联合状态收敛](/architecture/practice-order-state.svg)

订单状态由允许的命令迁移，例如 `PENDING_PAYMENT → PAID → FULFILLING → COMPLETED`，以及超时关闭、支付失败、退款分支。不变量包括：同一业务幂等键只有一个订单；可售库存不为负；一笔支付成功只入账一次；关闭订单不能再履约；退款累计不超过已支付额。

跨服务不变量不能靠一次分布式锁假装本地事务。应通过预占、唯一约束、幂等记录、事件版本、补偿和对账，使状态最终收敛并能解释。

## 3. 超时预算和重试归属

客户端 deadline 必须大于边缘、网关、BFF 和订单内部预算之和，并预留网络返回时间。每个依赖只由最接近语义的一层重试：读请求可有限退避；写请求必须有幂等键；支付超时进入 `UNKNOWN`，优先查询供应商状态，不盲目再次扣款。重试次数进入容量模型。

## 4. 消息可靠性

订单与 Outbox 同事务；发布器使用租约和退避，确认后标记已发。消费者在本地事务中检查 message/event ID、执行业务并记录已处理。失败进入有限重试和 DLQ，重放前识别永久错误、修复根因并控制速率。Exactly-once 业务效果来自幂等和约束，不来自口号。

## 5. 未知结果与对账

支付、退款、物流等外部操作可能请求超时但实际成功。集成层保存外部请求号和原始证据，通过主动查询、签名回调和日终对账三条路径收敛。超过时限仍未知时进入人工队列，不对用户误报失败或自动重复副作用。

## 6. 端到端观测

`requestId` 关联一次入口请求，`traceId` 关联调用链，`orderId` 关联长期业务旅程，`eventId` 关联消息投递，`paymentRequestId` 关联供应商。仪表盘同时展示技术 SLI 和订单创建、支付成功、未知状态时长、补偿与对账差异。

## 7. 故障验收

- 网关重复、客户端超时重试不会生成两个订单。
- DB 提交后进程崩溃，Outbox 最终仍能发布。
- MQ 重复、乱序、重平衡不会重复扣款或越过状态机。
- 支付成功但回调丢失，查询或对账能在目标时间内收敛。
- 库存、支付、履约部分失败时，用户状态和后台修复路径清楚。
