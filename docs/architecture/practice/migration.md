# 渐进拆分、绞杀迁移与数据所有权转移

拆分是运行中系统的受控迁移，不是重新画边界。接口、数据、流量、作业、权限、观测和 on-call 所有权都要移动，并始终保留可验证的回退或前向修复路径。

## 1. 选择拆分切口

优先选择边界稳定、业务价值独立、数据耦合较少、风险可控的纵向能力。先统计跨模块调用、共享表、事务、批任务和报表依赖。若新服务仍需大量同步回调旧系统或共同写表，边界尚未成立。

## 2. 绞杀者迁移阶段

![从旧模块到新服务的绞杀迁移](/architecture/practice-strangler-migration.svg)

先在旧边界前建立稳定契约和路由；新服务以只读影子或离线比对验证；随后迁移低风险读流量，再迁移单一写入权威；逐步扩大流量；确认下游、作业和报表已切换后，删除旧写路径和数据。每阶段都定义一致性校验、停止条件与 owner。

## 3. 数据迁移

![数据回填、CDC、切写与校验流程](/architecture/practice-data-migration.svg)

常见流程是创建新 Schema、全量快照回填、CDC 追增量、按主键和业务聚合校验、冻结或短暂停写、切换写权威、继续反向兼容窗口，最后下线旧表。迁移程序必须可重入、有 checkpoint、限速、审计和坏数据隔离。

双写容易出现一边成功一边失败，只能作为有明确收敛机制的临时状态。优先单写权威配合 Outbox/CDC 派生；无法避免双写时，记录操作 ID、差异队列和补偿规则。

## 4. 契约与兼容

API 使用新增可选字段、容忍未知字段和明确弃用窗口；事件先升级消费者，再由生产者发新字段/新版本；数据库采用 expand-migrate-contract。契约测试覆盖新旧组合，不能只测两个最新版本。

## 5. 流量切换与回退

按 tenant、用户或稳定 hash 灰度，避免一次业务旅程跨两套权威。比较响应、状态、事件和数据摘要，而非只看 HTTP 200。切写后若旧系统已不能理解新状态，回退可能造成损坏，此时应停止流量并 forward fix，而不是机械切回。

## 6. 完成定义

- 新服务拥有明确数据写权、SLO、容量、权限、告警、Runbook 和 on-call。
- 旧系统不再被 API、作业、报表、人工脚本和数据库账号隐式依赖。
- 差异连续为零或在阈值内，迁移审计与恢复点保留。
- 临时代理、双写、Feature Flag、兼容字段和额外监控有删除日期。
- 旧代码、表、Topic、权限和基础设施安全退役，成本真正下降。
