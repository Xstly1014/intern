# 从第一版到平台化：按证据演进系统

演进路线不是固定技术清单，而是用当前规模下最低的总复杂度满足目标。每次升级都应有触发信号、预期收益、迁移方案和停止条件。

## 1. 阶段路线

![从模块化单体到平台化与多地域的演进路线](/architecture/practice-evolution-roadmap.svg)

### 阶段一：可上线的模块化单体

按领域模块隔离包、接口和表访问，单进程部署，优先建立身份授权、数据库迁移、结构化日志、指标与 Trace、备份恢复、自动部署、探针和优雅停机。模块间禁止随意跨层访问，为未来拆分保留逻辑边界，但不提前支付网络和分布式事务成本。

### 阶段二：增长与专用能力

真实瓶颈出现后，引入缓存、MQ、搜索、对象存储或任务平台。通知、索引、报表等旁路优先异步化；核心状态仍由明确事务边界维护。每个中间件同时建设容量、权限、备份、观测和故障策略。

### 阶段三：有价值的服务拆分

当领域有稳定 owner，并从独立发布、伸缩、数据或故障隔离获得持续收益时拆出。先立契约与数据所有权，再迁移流量和数据；保留回退窗口。拆分后若同步调用链、共同事务和协调成本更高，应暂停甚至合并。

### 阶段四：平台化

当多个团队重复搭建流水线、身份、观测和运行基线时，平台团队提供 paved road、自助模板、策略与产品化支持。平台成功看采用率、交付时间、可靠性和认知负担，不看平台组件数量。

### 阶段五：多地域

只有全球时延、监管隔离或 Region 级 RTO/RPO 明确要求时进入。先解决数据权威、复制延迟、写入路由、fencing、依赖可用、切流和回切，再决定 active-passive 或 active-active。

## 2. 阶段升级信号

![复杂度升级的证据决策树](/architecture/practice-complexity-decision.svg)

有效信号包括：某模块伸缩差异持续数倍、发布互相阻塞、单故障域不可接受、数据边界稳定、团队能独立 on-call、现有方案在压测或 SLO 中被证明不足。无效信号包括简历驱动、模仿大厂、预测遥远流量和“微服务更先进”。

## 3. 每个阶段都不能推迟的基线

身份与授权、输入和输出契约、数据库迁移、幂等、日志指标 Trace、备份恢复、自动构建部署、Secret、安全补丁、资源边界、告警和 Runbook 从第一版就存在。可以推迟的是规模化平台，不是生产基本功。

## 4. 技术引入契约

任何新组件要回答：解决哪个量化问题；数据和请求怎样进入/退出；故障时用户看到什么；谁维护；升级与备份怎样做；成本上限；替换或退场路径。试点必须限制爆炸半径，并在复审日期根据证据推广、修正或删除。
