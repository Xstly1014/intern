# 总概览：完整系统的运行时架构

一个完整的系统不是“Spring Boot + MySQL”，也不是固定的微服务组件清单。它是一组围绕业务目标协作的运行时能力：**流量入口负责接住请求，业务系统负责作出正确决策，数据系统负责保存事实，平台系统负责让一切持续可靠运行。**

## 1. 全景架构图

![完整系统运行时架构全景图](/architecture/system-landscape.svg)

图是一个参考模型，不是采购清单。网关、BFF、服务和数据库之间也不是只能自上而下：消息消费者会从 MQ 反向触发业务，调度器会定时触发任务，第三方会通过回调进入系统。关键是每条入口都必须经过相同等级的认证、幂等、审计与观测。

## 2. 三条最重要的链路

### 2.1 同步请求链路

![同步请求从客户端到数据层再返回的链路](/architecture/synchronous-request.svg)

同步链路适合用户必须立即知道结果的操作，例如查询商品、提交订单、校验优惠券。它的核心约束是**延迟预算**：若接口目标 P99 是 500 ms，不能让 8 个下游各自拥有 500 ms 超时。应为网关、BFF、业务服务、数据库分配子预算，并限制同步调用深度。

### 2.2 异步事件链路

![订单事件通过 Outbox 和 MQ 分发给多个消费者](/architecture/asynchronous-event.svg)

异步链路适合不要求当前请求立即完成、需要削峰或一对多传播的动作。它降低时间耦合，却引入最终一致性、重复消息、乱序、积压、重试和死信等问题。工程上默认消息可能重复，消费者必须幂等。

### 2.3 运维反馈链路

![从遥测采集、告警到处置和复盘的运维反馈闭环](/architecture/operations-feedback.svg)

没有反馈链路，系统只是“能运行”，不是“可运营”。生产架构必须能回答：哪里慢、谁失败、影响多少用户、从何时开始、变更了什么、能否自动恢复。

## 3. 每一层的职责边界

| 层级 | 核心职责 | 不应该承担 | 常见实现 |
|---|---|---|---|
| 客户端与边缘 | 就近访问、静态加速、攻击拦截、流量分发 | 业务状态机、复杂用户权限 | DNS、CDN、WAF、Nginx、云 LB |
| API 网关 | 统一路由和流量策略 | 订单计算、跨领域长事务 | Spring Cloud Gateway、APISIX、Kong |
| 接入/BFF | 终端适配、请求校验、粗粒度聚合 | 核心规则、持久化事实 | Spring MVC/WebFlux、GraphQL |
| 身份安全 | 身份、权限、租户、密钥、审计 | 替代所有业务校验 | OAuth 2.1/OIDC、Spring Security、IAM |
| 业务服务 | 领域规则、用例、状态变化、一致性边界 | CDN、通用限流、厂商 SDK 扩散 | Spring Boot、DDD、模块化单体/微服务 |
| 数据存储 | 事实持久化、查询、缓存、检索、归档 | 跨服务共享表驱动业务协作 | MySQL、Redis、ES、S3/OSS |
| 异步中间件 | 解耦、削峰、事件传播、任务调度 | 隐藏无边界的系统耦合 | Kafka、RocketMQ、RabbitMQ、XXL-JOB |
| 外部集成 | 隔离第三方模型、故障与版本变化 | 让第三方 DTO 成为内部领域模型 | Adapter、Anti-Corruption Layer |
| 可观测运维 | 发现、定位、响应和复盘问题 | 用海量日志代替明确指标 | OpenTelemetry、Prometheus、Loki/ELK |
| 基础设施交付 | 运行、发布、扩缩、备份和容灾 | 决定业务领域边界 | Docker、Kubernetes、GitHub Actions |

## 4. 横切能力为什么不算普通的一层

安全、可观测性、配置与治理会穿过所有纵向层级。例如 Trace ID 从边缘入口生成或接受，经过网关、BFF、业务服务、数据库和 MQ 传播；身份信息在网关初检后，业务服务仍要对高风险动作执行资源级授权；配置中心下发参数，但业务代码必须验证配置范围并提供默认值。

这类能力应遵循三个原则：

- **统一标准**：统一身份声明、错误码、日志字段、指标名称和 Trace 传播格式。
- **就近执行**：通用策略在网关处理，资源所有者在业务服务做最终授权，不能只靠入口。
- **失败可控**：鉴权服务、配置中心、日志平台故障时，要提前定义 fail-open 还是 fail-closed。支付授权通常关闭放行，非关键埋点通常允许丢弃。

## 5. 以“创建订单”为例走完整链路

| 阶段 | 发生的动作 | 关键控制点 |
|---|---|---|
| 1. 到达边缘 | DNS 解析，WAF 检查，LB 选择网关实例 | DDoS、防重放、TLS、来源 IP |
| 2. 进入网关 | 匹配路由，校验 Token 基本合法性，按用户限流 | 请求体上限、超时、灰度标签 |
| 3. 接入转换 | 校验 DTO，把 App 版本差异转换为统一命令 | 参数错误码、兼容性、Trace 上下文 |
| 4. 身份授权 | 确认用户、租户、设备与下单权限 | 资源级权限、风控信号、审计 |
| 5. 业务决策 | 计算价格、校验商品、预占库存、创建订单 | 幂等键、状态机、事务边界 |
| 6. 保存事实 | 订单与 Outbox 在同一数据库事务提交 | 唯一约束、隔离级别、主从延迟 |
| 7. 发布事件 | Outbox Relay 将 `OrderCreated` 投递 MQ | 可靠投递、分区键、Schema 版本 |
| 8. 异步处理 | 支付、通知、积分等消费者各自处理 | 幂等、重试、死信、积压告警 |
| 9. 返回用户 | 同步链路返回订单号和当前状态 | 统一错误模型、P99、可重试语义 |
| 10. 观测审计 | 日志/指标/Trace 关联整条链路 | 脱敏、采样、SLO、业务指标 |

## 6. 同步调用与异步消息如何选择

| 判断问题 | 倾向同步 | 倾向异步 |
|---|---|---|
| 当前响应是否必须使用结果 | 是 | 否 |
| 调用方是否应立即感知成功/失败 | 是 | 最终获知即可 |
| 是否需要一对多通知 | 较少 | 很适合 |
| 峰值是否远大于消费能力 | 不适合 | 可缓冲削峰 |
| 是否要求强一致提交 | 本地事务内适合 | 需最终一致性设计 |
| 能否接受重复、延迟和乱序 | 通常较少 | 必须处理 |

不要用 MQ 把一个本应原子完成的核心不变量强行拆开，也不要为了“实时”把所有旁路动作塞进同步链路。判断标准不是技术偏好，而是业务对一致性、延迟和失败语义的要求。

## 7. 物理部署不是逻辑分层

### 小型系统

![小型系统运行时架构](/architecture/small-system.svg)

保持代码内部边界，单进程部署通常最经济。不要因为“完整架构”就提前引入 Kubernetes、注册中心和十几个服务。

### 成长型系统

![成长型系统运行时架构](/architecture/growing-system.svg)

先拆具有独立伸缩、发布或故障隔离价值的边界，如搜索、通知、文件处理、结算。

### 大型平台

多地域边缘、多集群网关、多个 BFF、按领域自治的服务和数据、事件平台、统一身份与可观测平台，以及经过演练的同城双活或异地灾备。此时治理重点从“组件能用”转向标准、自治边界、容量、成本和组织协作。

## 8. 完整性检查清单

一套架构设计至少应明确以下内容：

- 业务目标、用户规模、峰值 QPS/TPS、数据量、延迟和可用性目标。
- 信任边界、身份模型、租户隔离、敏感数据分级和审计要求。
- 服务边界、数据所有权、同步/异步契约、事务与一致性策略。
- 超时、重试、熔断、限流、降级、幂等、补偿和人工兜底。
- 日志、指标、Trace、业务看板、SLO、告警负责人和应急预案。
- 容量模型、扩缩容、发布策略、数据库迁移、备份恢复和容灾目标。
- 成本边界、团队所有权、技术债、演进触发条件和退出方案。
