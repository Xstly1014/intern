# 部署策略、渐进交付、数据库兼容与回滚

发布风险随变更大小和暴露范围增长。渐进交付用小批量流量和自动证据限制爆炸半径，但前提是新旧应用、API、消息和数据库能同时运行。

## 1. 策略选择

| 策略 | 优点 | 代价/适用 |
|---|---|---|
| Rolling | 简单、额外资源少 | 新旧共存必须兼容 |
| Blue-Green | 切换/回切快 | 双倍容量、状态外置 |
| Canary | 小流量验证真实生产 | 需稳定分流与自动门禁 |
| Feature Flag | 部署与开放分离 | 分支组合、过期治理 |

## 2. Canary 管线

![Canary 分阶段放量与指标门禁](/architecture/infrastructure-canary-rollout.svg)

部署少量实例→合成检查→1%→5%→25%→100%，每阶段等待覆盖慢错误窗口，比较同地域/终端/流量类别的 SLO、错误、延迟、资源和业务状态。指标缺失默认暂停，不自动判成功。

## 3. 流量分配

按稳定用户/tenant hash 保持会话，避免一次旅程跨版本。管理/高风险流量可后放；影子流量只用于无副作用或严格隔离写入。Canary 容量足以承接分配流量，避免样本因过载失真。

## 4. 数据/API/消息兼容

Schema expand→兼容应用→回填→切读→contract。事件先升级消费者再生产者；API 新字段向后兼容。应用回滚不能撤销已提交数据/事件，必须保证旧版本能读取新状态或使用 forward fix。

## 5. 自动回滚与暂停

门禁超阈值先停止放量；回滚若安全则切旧 digest/配置，验证指标与业务状态。数据库迁移、外部副作用和不可逆任务可能禁止自动回滚，需要预先定义暂停、补偿和 forward fix。

## 6. Feature Flag

Flag 有 owner、默认、作用域、审计、到期和删除。安全/授权不能仅靠 Flag。Kill switch 需独立、快速、演练；关闭功能后处理在途流程和数据。

## 7. 优雅发布

readiness 摘流→传播等待→排空 HTTP/MQ/任务→终止。滚动参数 maxUnavailable/maxSurge 与 PDB/容量协调。发布期间新旧副本总连接不会超过 DB/下游预算。

## 8. 上线检查

- 新旧应用/API/事件/Schema 是否可同时运行？
- Canary 是否稳定分流并比较业务 SLI 与相同流量？
- 缺指标、门禁失败、回滚不可行时是否有明确动作？
- Flag 是否有 owner、到期、审计和数据/在途处理？
- 发布峰值连接、CPU、节点和下游容量是否预留？
