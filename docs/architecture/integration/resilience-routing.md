# 供应商韧性、配额、健康路由与多渠道切换

外部依赖故障不应耗尽全系统资源。每个供应商和接口都有独立容量、deadline、错误与业务降级；多供应商不是简单 fallback，而是路由、能力、用户、资金与对账的一套策略。

## 1. 隔离与调用保护

![供应商级连接池、舱壁与熔断隔离](/architecture/integration-provider-bulkheads.svg)

按 provider/host/接口隔离连接池、并发、队列和熔断。一个短信渠道慢不能占满支付线程；同供应商查询和扣款也可有不同池。队列有界，满时返回明确过载/排队状态。

熔断只保护调用方，半开探测使用无副作用或幂等请求；不能把资金操作当健康探针。

## 2. 配额与限流

供应商配额可能按秒、日、账号、接口或成本。客户端侧 Token Bucket 留安全余量，优先级区分交易与批量；尊重 429/Retry-After。日额度接近耗尽要预测告警，不等全部失败。

重试计入配额和费用。批量/补偿/对账限速，避免恢复时抢占在线请求。

## 3. 健康评分

![多供应商健康评分与路由决策](/architecture/integration-provider-routing.svg)

评分结合近期成功率、P95/P99、429、未知状态、回调延迟、对账差异、剩余配额、成本和能力，不只看 TCP 健康。路由使用最小样本、滞后/平滑和稳定哈希，避免快速抖动全量切换。

技术成功率高但业务拒绝率/对账差异异常仍可能不健康。

## 4. 切换语义

短信查询等无副作用请求可快速 fallback；支付授权不能在 A timeout 后立即用新 key 调 B，可能双扣。先查询 A/等待回调；确认未执行或完成撤销后再启动 B，并创建新的业务尝试关联原操作。

切换还要验证币种、地区、用户同意、风控、退款能力、清算与对账，不能仅有相同 Java 接口。

## 5. 回切与状态一致

供应商恢复后小流量 canary，观察完整状态和回调，不立即全量回切。故障期已在备用渠道创建的操作继续由其完成/对账，不能路由变化后丢失归属。

路由决策持久化 provider、policy version、reason 和 attempt，后续查询/退款准确回到原渠道。

## 6. 降级

可选地图/推荐可隐藏；短信失败可改站内通知；身份核验、价格、支付结果不能伪造默认成功。每项降级定义用户体验、业务状态、恢复动作和最长持续时间。

## 7. 供应商风险治理

维护 SLA、支持升级路径、状态页、事故通知、容量承诺、数据地点、子处理者、审计报告、退出/迁移计划。技术上可替换而合同/数据不可迁移，仍不是可用灾备。

## 8. 上线检查

- Provider/接口是否隔离池、并发、队列、熔断和指标？
- 配额是否预测、分优先级，重试/批量是否计入成本？
- 健康评分是否包含业务结果、回调和对账，而非只看 HTTP？
- 有副作用操作切换是否避免双重执行并保存渠道归属？
- 回切是否 canary 且不迁移未完成操作的所有权？
- 每种降级是否真实业务可接受且有恢复路径？
