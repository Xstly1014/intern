# 容量、过载、健康检查、服务目录与变更运维

稳定运维依赖容量余量、正确健康语义和可追踪变更。系统通常不是资源瞬间归零，而是先排队、重试、连接耗尽，再演化成全站超时。

## 1. 容量模型

![负载、并发、队列与资源饱和关系](/architecture/observability-capacity-model.svg)

Little's Law：并发约等于吞吐 × 停留时间。延迟上升会增加在途并发，进一步耗尽线程/连接并形成正反馈。容量同时考虑 RPS、扇出、重试、bytes、CPU、内存、连接、磁盘、队列和故障冗余。

## 2. Headroom 与预测

按正常峰值、发布重叠、单 AZ/实例故障和恢复追赶保留余量。趋势预测使用增长率、季节性和业务活动；磁盘、证书、配额、分区和连接在耗尽前按交付周期告警。

压测包含真实数据分布、响应大小、缓存冷态、慢依赖和错误重试，而非空响应。

## 3. 过载保护

![从饱和检测到优先级降载](/architecture/observability-overload.svg)

队列/池有界，达到水位后按优先级拒绝、限流、暂停批任务、降低扇出/非关键功能。快速失败保留核心交易容量；无限排队只会让所有请求超时。重试预算与入口限流协同。

## 4. 健康探针

- Startup：初始化未完成，避免过早 liveness 重启。
- Liveness：进程自身无法前进才失败，不依赖外部 DB 导致重启风暴。
- Readiness：能否接新流量；失败后摘流并排空连接。
- Deep synthetic：独立监控关键旅程，不用于每 Pod liveness。

探针有 timeout、低成本和独立资源，不能成为新负载源。

## 5. 服务目录

每服务记录 owner/on-call、仓库、运行环境、依赖/消费者、SLO、数据等级、Dashboard、Runbook、部署和生命周期。目录来自 CI/K8s/Telemetry 自动同步并人工负责语义，避免过期 wiki。

## 6. 变更可观测

部署、配置、Feature Flag、扩缩容、证书、Schema 和路由事件进入统一时间线，包含版本、范围、操作者、审批和 rollback。Canary 同时比较 SLI、业务状态、资源与依赖，不只看 Pod ready。

## 7. 日常运维

定期做 SLO/错误预算、容量、告警、依赖、证书/配额、备份恢复和成本回顾。Toil（重复手工操作）量化，优先自动化高频高风险步骤；自动化仍需权限、dry-run、审计和回滚。

## 8. 上线检查

- 容量是否计入峰值、扇出、重试、故障和追赶余量？
- 队列/池是否有界并按业务优先级降载？
- Startup/Liveness/Readiness 是否语义正确且不造成重启风暴？
- 服务目录是否有 owner、SLO、依赖、Dashboard 和 Runbook？
- 所有变更是否自动叠加到观测时间线并可回滚？
- 日常回顾是否覆盖可靠性、容量、告警、恢复和 Toil？
