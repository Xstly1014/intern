# 生产事件响应、止损、恢复验证与复盘

事件响应优先减少用户影响，然后定位根因。事故中同时调参、扩容、重启和发布会破坏证据并增加风险，需要明确指挥、角色、时间线和变更纪律。

## 1. 生命周期

![生产事件从发现到复盘的生命周期](/architecture/observability-incident-lifecycle.svg)

Detect→Triage→Declare→Contain→Mitigate→Recover→Validate→Communicate→Review。恢复和结案不同：恢复后仍需确认积压、数据一致性、对账和回退保护。

## 2. 角色

- Incident Commander：定优先级、角色、决策与节奏，不陷入单点排障。
- Operations Lead：执行技术止损和恢复。
- Communications Lead：面向内部、客服、客户和管理层定时更新。
- Scribe：记录时间线、假设、动作、结果和链接。

小事故可兼任，但职责仍明确。

## 3. Triage

先确认用户旅程、租户/地域、开始时间、错误预算、数据/安全影响和最近变更。建立共同 Dashboard/时间线，冻结无关变更。没有证据时标注假设，不把相关性当因果。

## 4. 止损策略

![从用户影响选择回滚、降级、限流和切流](/architecture/observability-mitigation.svg)

优先可逆、已演练动作：回滚最近发布/配置、关闭 Feature Flag、限制低优先级、切健康区域/供应商、暂停 Consumer/批任务、扩容已知瓶颈。每次只改变有限变量并观察结果。

数据损坏/安全事件先隔离和保全证据；不要为恢复可用性继续传播错误数据。

## 5. 恢复验证

验证 SLI 恢复、错误预算停止燃烧、资源/队列稳定、积压按计划下降、业务状态/数据对账、降级流量回切和客户操作可重试。观察至少一个能覆盖故障模式的窗口。

## 6. 沟通

固定节奏说明已知影响、开始时间、当前动作、下次更新时间和规避建议；不发布未经证实根因。状态页用用户语言，不暴露攻击/敏感细节。记录外部通知与监管时限。

## 7. 无责复盘

复盘关注系统为何允许错误发生和扩大：触发因素、直接原因、潜在条件、检测/隔离/恢复防线为何失效。行动项具体、有 owner、截止、优先级和验证标准；避免“加强注意”“补文档”作为唯一结论。

## 8. 上线检查

- 是否能在数分钟内确定 IC、沟通、记录和技术负责人？
- 止损动作是否可逆、演练且有权限/审计？
- 数据/安全事件是否先隔离证据而非盲目重启？
- 恢复是否覆盖业务结果、积压、数据一致和回切？
- 沟通是否有固定节奏、用户语言和通知责任？
- 复盘行动项是否被跟踪到验证关闭？
