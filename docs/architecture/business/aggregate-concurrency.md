# 聚合、不变量、状态机与并发控制

聚合是一个事务内必须保持一致的最小业务边界，不是“把相关表全部装进对象树”。好的聚合能在单次提交中保护关键不变量，同时避免巨大锁范围、加载成本和热点。

## 1. 聚合边界

![聚合边界与跨聚合协作](/architecture/business-aggregate-boundary.svg)

订单聚合可拥有订单项、金额快照和订单状态，保证总额与状态转换一致；库存和支付由各自上下文拥有。订单只保存 `PaymentId`/预留 ID 等引用，通过应用流程和事件协作，不直接持有远程聚合对象。

判断某对象是否在同一聚合：它是否必须与根在同一事务立刻一致？是否有独立生命周期和高并发访问？如果只需最终一致或独立伸缩，应通过 ID 引用。

## 2. 不变量

- 单聚合不变量：订单项非空、应付金额等于各项快照求和、已完成不能取消。
- 数据库不变量：唯一业务号、非负约束、外键（聚合内部）、版本唯一。
- 跨聚合规则：库存总量、用户额度、支付状态，需预留/确认或流程协调。

业务对象通过行为方法变化，如 `cancel(reason, actor)`，方法内部校验当前状态并产生领域事件。公开 setter 让调用方绕过规则，最终只能靠“大家记得正确调用”。

## 3. 显式状态机

![订单状态机与非法转换](/architecture/business-state-machine.svg)

为每个状态定义允许命令、目标状态、必要条件、副作用事实和幂等结果。非法转换返回稳定冲突，而不是强行覆盖。状态机不仅是一张枚举图，还包括并发下哪个命令获胜。

避免“状态字段 + 多个布尔值”产生不可达组合，如 `paid=false` 但 `shipped=true`。需要并行子流程时可拆正交状态或流程记录。

## 4. 乐观并发

聚合保存版本号，更新使用 `WHERE id=? AND tenant_id=? AND version=?`，成功后版本 +1；影响 0 行代表被并发修改。重新读取后决定返回冲突、已完成幂等结果，或在总预算内重试纯确定性命令。

JPA `@Version` 可实现基础乐观锁，但仍要把 `OptimisticLockException` 映射为业务冲突，并验证批量更新/原生 SQL 没绕过版本。

## 5. 唯一约束与条件更新

“同一用户只能有一个有效申请”不能只先查再插，两个并发请求会同时通过。用数据库唯一约束/部分索引承载最终原子保证，并将冲突映射为已存在或业务 409。

简单计数/状态可用条件更新：`UPDATE inventory SET available=available-? WHERE sku=? AND available>=?`，根据影响行数判断库存是否足够。前置读取只用于体验，不能承担最终正确性。

## 6. 悲观锁与热点

悲观锁适合冲突高、事务短且必须串行的本地数据，但要固定加锁顺序、设置等待超时、监控死锁，不在持锁时远程调用。热点单行会限制吞吐，需考虑分片计数、排队、预分配或改变业务模型。

分布式锁通常不应保护数据库内本可由事务/约束保证的规则。确需跨进程租约时，考虑进程暂停、网络分区、锁过期和 fencing token；拿到锁不代表仍是最新持有者。

## 7. 事件与版本

领域事件在成功状态变化时注册，包含 aggregate ID、业务版本、发生时间和必要快照。事件处理者可据版本检测重复/乱序。不要在聚合方法里直接发 MQ，否则数据库回滚和消息发送无法原子一致。

## 8. 上线检查

- 聚合是否只包含必须本地强一致的对象，而非完整业务图？
- 每条关键不变量由领域行为和数据库原子机制共同保护？
- 状态机是否定义非法转换、重复命令和并发胜负？
- 乐观锁冲突是否转换成业务语义，而不是裸 500？
- 唯一规则是否有数据库最终防线，避免先查后写竞态？
- 悲观/分布式锁是否有超时、顺序、fencing 和故障测试？
