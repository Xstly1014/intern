# 领域划分、限界上下文与服务边界

服务边界的首要依据是业务语言、规则变化和事实所有权，而不是数据库表、组织当前架构或技术分层。限界上下文定义一套模型和术语在哪个范围内含义一致，它可以先是单体中的模块，未必立即成为微服务。

## 1. 从业务能力到上下文

![从业务能力到限界上下文的划分](/architecture/business-context-map.svg)

电商中的“商品”在不同上下文含义不同：目录关注标题和属性，定价关注价格规则，库存关注 SKU 可用量，订单保存下单时快照。强行共享一个 `Product` 类会让每次变化牵动所有系统。

识别边界时观察：

- 业务人员是否使用不同词汇或相同词汇有不同含义。
- 哪些规则必须在同一事务保持，哪些只需通过事实同步。
- 哪组数据由谁决定，谁只能读取副本。
- 变化是否经常一起发生，发布与容量是否独立。
- 团队是否能端到端拥有开发、数据、SLO 和值班。

## 2. 核心域、支撑域与通用域

| 类型 | 意义 | 投资策略 |
|---|---|---|
| 核心域 | 形成业务差异和竞争力 | 最强团队、深入建模、持续演进 |
| 支撑域 | 业务必要但非主要差异 | 保持清晰边界，适度定制 |
| 通用域 | 行业通用能力 | 优先成熟产品/云服务，隔离供应商 |

支付通道、邮件和身份系统可能是通用能力，但“怎样计算优惠和履约承诺”常是核心规则。分类不是永久标签，应随战略变化复审。

## 3. Context Map 与协作关系

![限界上下文之间的契约关系](/architecture/business-context-relationships.svg)

- **Customer/Supplier**：上游计划兼顾下游需求，但契约和节奏需协商。
- **Conformist**：下游接受上游模型，适合标准服务，但承担耦合。
- **Anti-corruption Layer**：下游用适配器翻译外部模型，保护自身语言。
- **Published Language/Open Host**：通过稳定 API、事件和 Schema 服务多个消费者。
- **Separate Ways**：没有必要集成时各自实现，避免昂贵耦合。

不要用共享 Java Entity Jar 当上下文集成。共享代码会把内部模型、序列化和发布节奏绑定；跨边界应共享契约或生成客户端，而非共享可变领域对象。

## 4. 数据所有权

一个业务事实只有一个权威写入者。订单服务拥有订单状态，库存服务拥有可用量，支付服务拥有支付尝试与结果。其他上下文可持有只读投影，但必须知道来源、版本、新鲜度和修复方式。

禁止：服务 A 直接更新 B 的表、跨服务外键依赖、多个服务共同运行一段修改同一表的 SQL。共享物理数据库的迁移阶段也应使用独立 Schema/账户和明确写入所有权。

## 5. 拆分粒度

过大的上下文导致团队和模型冲突；过小会产生聊天式调用、分布式事务和大量运维单元。一个边界应能表达相对完整业务能力，拥有规则、数据和结果，而不是只有一张表的 CRUD。

“用户服务”往往过于模糊：账号身份、客户档案、会员权益、联系人和组织权限可能属于不同上下文。反过来，也不要把订单的创建、取消、查询各拆成一个服务。

## 6. 发现方法

使用事件风暴梳理命令、事件、参与者、策略、热点和外部系统；用业务流程识别必须同步的决策与可异步事实；以真实变更历史验证哪些模块总是一起修改。输出是可验证假设，不是一次 workshop 后永远不变的图。

边界评审至少包含业务专家、开发、数据、安全和运维，避免只按代码视角划分。

## 7. 边界演进信号

适合拆出独立服务的信号：术语和规则稳定独立、团队所有权清楚、数据可单一归属、独立发布/容量/故障收益明显、跨边界一致性方案可接受。

不适合拆分的信号：跨模块事务频繁、接口每周联动变化、一个团队维护所有模块、服务会共享库、调用链极深或只有“微服务数量”这个理由。

## 8. 上线检查

- 每个上下文是否有业务语言、能力、数据和团队所有者？
- 同名概念在不同上下文是否显式翻译而非强行共享模型？
- 每个事实是否只有一个写入者，副本是否标注来源与新鲜度？
- 上下文关系和契约变更责任是否记录在 Context Map？
- 拆服务收益是否超过远程失败、最终一致和运维成本？
- 是否能先用模块边界验证，再决定物理拆分？
