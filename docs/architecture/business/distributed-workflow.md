# Saga、TCC、跨服务流程与对账修复

跨服务业务无法依靠一个数据库事务解决时，需要把中间状态、失败、超时和恢复显式建模。最终一致不是“消息发出去以后等一等”，而是系统能证明流程最终到达业务允许的终态，或进入可操作的异常态。

## 1. Saga 状态机

![订单 Saga 的状态、补偿与人工处理](/architecture/business-saga-state-machine.svg)

以创建订单为例：创建待确认订单 → 预留库存 → 授权支付 → 确认订单。任一步失败都按已完成步骤决定补偿；支付授权成功后取消不是删除记录，而是发起撤销/退款这一新的业务动作。

Saga 记录 saga ID、业务键、当前状态、步骤尝试、deadline、下一动作、补偿状态、错误和版本。进程重启后从持久状态恢复，不能只依赖内存 Future 或线程等待。

## 2. 编排与协同

| 方式 | 优点 | 风险 |
|---|---|---|
| Orchestration | 流程、超时、补偿和观测集中清楚 | 编排器可能知道过多领域细节 |
| Choreography | 上下文自治、简单流程耦合较低 | 长链难看懂、循环事件、全局状态不清 |

简单两三步事实通知可协同；关键长流程、超时和人工介入多时优先显式流程管理器。编排器只决定流程顺序，具体规则仍由各资源服务执行。

## 3. 补偿不是数据库回滚

已发送邮件无法撤回，已发生支付退款可能收费且失败，库存释放时商品状态可能改变。每个步骤定义业务补偿、幂等键、可重试错误、不可重试错误和补偿失败升级路径。

补偿也会重复、乱序和超时，必须像正向步骤一样有状态与监控。不要无限自动重试不可逆或需人工判断的动作。

## 4. TCC 与预留模型

![TCC Try Confirm Cancel 的资源预留](/architecture/business-tcc-reservation.svg)

Try 创建有过期时间的资源预留，Confirm 消费预留，Cancel 释放。三者都幂等；处理空回滚（Try 未到先 Cancel）、悬挂（Cancel 后迟到 Try）和重复 Confirm。资源服务自身拥有预留表和状态机。

TCC 适合库存、额度等能自然预留且需要更强控制的资源，开发和运维成本较高。不能把普通 CRUD 接口机械包装成 Try/Confirm/Cancel。

## 5. 超时与时间

区分请求 deadline、步骤 timeout、业务过期时间和人工 SLA。调度器可能延迟、时钟可能偏差，业务规则以服务端持久时间为准。超时触发下一状态，但迟到结果仍可能到达，需要版本/状态机判断接受、忽略还是反向补偿。

## 6. 对账与修复

![实时流程与离线对账的闭环](/architecture/business-reconciliation-loop.svg)

对账比较双方权威事实，例如支付渠道流水与内部支付账本、库存预留与订单终态。差异分类为延迟、缺失、重复、金额不符和未知状态；自动修复只处理可证明安全的类别，其余生成工单。

修复工具必须复用业务命令、授权、幂等和审计，不能让运维直接写表。每次修复记录证据、决策、操作者和前后状态。

## 7. 流程可观测

技术指标：步骤成功/失败/超时、重试、队列年龄、补偿失败。业务指标：流程完成率、各状态停留时间、未知结果、人工积压、资金/库存差异。按 saga ID/correlation ID 串起 Trace 和事件，但长流程不能只依赖短期 Trace 保存事实。

## 8. 上线检查

- 每个跨服务流程是否有持久状态机和明确合法终态？
- 每一步和补偿是否幂等，错误是否分可重试/不可重试/未知？
- TCC 是否处理空回滚、悬挂、重复和预留过期？
- 迟到响应与超时动作竞争时是否由版本/状态决定？
- 是否有独立对账证据、自动修复边界和人工工单入口？
- 操作人员是否无需直接改数据库即可安全恢复流程？
