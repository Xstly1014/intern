# 服务通信、契约、超时与级联故障防护

通信方式是业务一致性和故障语义的选择，不只是 HTTP 与 Kafka 的技术偏好。同步调用表达“当前决策必须等待结果”，事件表达“一个事实已发生”，命令消息表达“请异步尝试一个动作”。

## 1. 通信方式选择

![同步查询、异步事实与流程命令的选择](/architecture/business-communication-modes.svg)

| 需求 | 推荐方式 | 关键问题 |
|---|---|---|
| 当前决策必须获取最新结果 | HTTP/gRPC 同步 | deadline、错误、幂等、级联 |
| 多方得知已发生事实 | 集成事件 | 重复、乱序、Schema、滞后 |
| 削峰并异步执行动作 | 命令消息 | 所有者、过期、重试、结果查询 |
| 页面复杂查询 | 读模型/批量 API | 新鲜度、授权、构建延迟 |
| 长业务流程 | Saga/流程管理器 | 状态、补偿、人工恢复 |

不要为了“解耦”把需要立即拒绝的业务校验改成异步，也不要为了简单把十个服务串成同步调用链。

## 2. API 契约

API 定义动作、资源、请求/响应、错误、幂等、分页、deadline 和兼容策略。消费者只依赖公开契约，不能依赖内部数据库字段或异常类。破坏性变更使用扩展-迁移-收缩，先让提供方兼容新旧，再迁移消费者。

gRPC 同样要遵守 Protobuf 字段号不可复用、未知字段和枚举兼容规则。技术类型兼容不代表语义兼容。

## 3. 事件契约

领域事件可包含丰富内部模型；出边界前转换为稳定集成事件。事件用过去式事实，如 `OrderPaid`，包含事件 ID、业务键、发生时间、Schema version 和必要快照。不要让消费者回调生产者查询每个字段，否则异步链重新变成脆弱同步链。

事件最小化与自包含需要平衡：包含消费者完成反应所需的稳定事实，不泄露高敏/无关数据，不复制整张 Entity。

## 4. Deadline 和超时预算

![服务调用链的 deadline 与重试预算](/architecture/business-deadline-budget.svg)

入口 deadline 沿调用链递减传播，每跳为连接池排队、连接、响应和本地处理留预算。下游超时不能等于总超时，服务收到已不足以完成的 deadline 应快速拒绝。

深层链路会同时增加延迟和失败概率。用批量 API、读模型、异步事实和边界重构降低深度，不靠把所有 timeout 调大。

## 5. 重试

只重试瞬时、可重试错误，且操作幂等或有幂等键。指数退避 + jitter，限制尝试次数和总时间；尊重 `Retry-After`。每层都重试会指数放大，通常选择一个了解业务意图的层负责。

写超时表示结果未知，应查询状态或用同幂等键重试，不能立即换 key 再创建一次。

## 6. 舱壁、熔断与限流

- 按下游/用例隔离连接池、线程/并发和队列，避免一个慢依赖占满全部资源。
- 熔断基于足够样本和失败类别，半开探测；它保护调用方，不修复下游。
- 队列和在途请求有界，满时快速拒绝而非内存堆积。
- 降级必须符合业务语义；价格、权限和支付结果不能伪造默认值。
- 客户端、网关、服务和 MQ 重试共同纳入放大系数容量计算。

## 7. 循环依赖与所有权

A 同步调 B、B 又调 A 表明边界或读模型有问题，容易死锁式容量等待和发布耦合。通过明确事实所有者、反向事件、复制只读投影或合并上下文解决，不用新增第三个“协调公共服务”掩盖。

共享客户端库只封装传输、认证和契约生成，不包含业务 fallback 或跨服务事务逻辑。

## 8. 上线检查

- 每个同步调用是否确实属于当前决策必需，能否用事实/读模型降低链深？
- API 和事件是否有 Schema、所有者、兼容检查和消费者清单？
- deadline 是否端到端递减，连接池排队和本地处理是否计入？
- 重试是否仅一层负责，并受幂等、错误分类和总预算约束？
- 每个下游是否有独立并发/连接舱壁和有界队列？
- 降级是否不伪造价格、权限、库存、资金等关键事实？
