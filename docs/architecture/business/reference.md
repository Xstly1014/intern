# Java 业务服务生产参考架构

参考架构以业务能力和数据所有权为中心：同步命令进入明确用例，本地事务维护聚合并写 Outbox，异步流程由持久 Saga 推进，查询通过授权后的投影服务，所有状态都能观测、对账和修复。

## 1. 生产参考拓扑

![Java 业务服务生产参考拓扑](/architecture/business-reference-topology.svg)

- BFF 发送终端无关 Command/Query 和可信上下文，不传 JPA Entity。
- 订单、库存、支付各自拥有写模型、数据库、事务和业务事件语义。
- Broker 传递集成事件，不能提供端到端 exactly-once 业务保证。
- Saga/流程管理器拥有流程状态，不拥有各领域内部规则。
- Read Model 保存来源明确的投影，新鲜度和重建路径可见。
- 对账服务读取双方事实并通过受控命令修复，不直接改表。

## 2. Spring 事务落地

`@Transactional` 放在应用用例的 public 边界；理解代理自调用、异常回滚、传播行为和 readOnly 只是提示。事务方法返回前应完成数据库一致性提交准备，不发布不可撤销外部副作用。

使用 `TransactionTemplate` 可显式控制复杂边界，但不要把远程调用包进模板。事务事件监听器如果在提交后执行失败，仍需可靠队列/Outbox，不能依赖进程内回调保证发布。

## 3. 模块边界

![模块化单体到微服务的业务演进](/architecture/business-evolution.svg)

阶段一在单 Spring Boot 中建立 order/inventory/payment 模块、独立 Schema 迁移和公开 Application API。阶段二只拆出确有团队、容量、发布或故障收益的上下文。拆分使用 expand-contract：先通过接口替代直接依赖，迁移数据所有权，再切流，最后删除旧写路径。

不要双写两个数据库而无一致性协议；迁移期间指定唯一写主，另一侧通过 CDC/事件同步并对账。

## 4. Java 运行时容量

| 资源 | 主要风险 | 控制 |
|---|---|---|
| HTTP/虚拟线程 | 下游慢导致在途激增 | deadline、有界并发、舱壁 |
| DB 连接池 | 线程远多于连接、事务过长 | 按 DB 容量设置、监控等待时间 |
| JVM 堆 | 大聚合/批量/队列积压 | 请求上限、流式/分页、GC 观测 |
| MQ Consumer | 处理慢、重试风暴 | prefetch/并发、暂停、DLQ、背压 |
| Scheduler | 同任务多实例执行 | 租约/fencing、幂等、分片 |

虚拟线程降低阻塞线程成本，但不会增加数据库连接、下游容量或解除锁竞争。线程池/队列不能无界。

## 5. 业务可观测模型

技术 RED 之外，记录业务命令接受/拒绝原因、状态转换、处理时长、幂等命中、并发冲突、Outbox 最老年龄、Saga 状态停留、补偿/人工积压和对账差异。

业务审计记录 actor/subject、资源、动作、前后状态摘要和结果；Trace 适合短调用因果，长流程事实保存在 Saga/事件记录，不依赖 Trace 永久留存。

避免以 order ID/user ID 作为指标标签；放入受控日志/Trace。指标按用例、状态、错误类别和版本等低基数维度聚合。

## 6. 测试矩阵

| 层次 | 重点 |
|---|---|
| 领域单元 | 不变量、状态机、金额、边界值，不依赖 Spring |
| 用例单元/组件 | 授权、编排、幂等结果、端口错误映射 |
| 数据库集成 | 真实隔离、唯一约束、乐观锁、Outbox/Inbox 原子性 |
| 契约 | API/事件兼容、消费者期望、错误和未知字段 |
| 并发/属性测试 | 多命令竞争、重复、乱序、不变量始终成立 |
| 韧性 | 慢下游、超时、崩溃点、重试、积压、补偿失败 |
| 端到端 | 少量关键旅程及真实部署连通，不替代下层测试 |

Testcontainers 使用与生产接近的数据库/Broker。故障测试在事务提交前后、Outbox 发送前后、消费者提交/ACK 前后注入崩溃，验证最终不丢且不重复产生业务效果。

## 7. 发布与数据演进

- API、事件和数据库变更都先向后兼容，再迁移流量/数据，最后收缩旧字段。
- 消费者部署滞后时仍能读取新事件；事件字段删除需消费者无使用证据。
- 数据回填分批、限速、可暂停、可重入，并与在线写入处理竞态。
- 灰度同时观察技术错误和业务状态分布，不能只看 Pod 健康。
- 优雅停机先停止接收，排空请求/消息，提交或回滚事务，释放 lease。

## 8. 完整评审清单

### 边界与模型

- 上下文是否按语言、规则、数据和团队划分，而非按表/技术层？
- Command、聚合、事件和读模型是否各有明确用途与所有者？
- 是否只有一个服务写某业务事实，其他副本有新鲜度和重建策略？

### 一致性与并发

- 不变量是否落在最小聚合/本地事务，跨边界是否显式最终一致？
- 幂等、唯一约束、版本、Outbox/Inbox 和乱序处理是否可证明？
- Saga/TCC 是否覆盖超时、补偿失败、迟到结果、对账和人工修复？

### 通信与运行

- 同步链是否有 deadline、舱壁、有界队列和受控重试？
- API/事件是否兼容发布，消费者和敏感数据使用是否可追踪？
- JVM、连接池、MQ、Outbox、流程状态和业务结果是否共同观测？

### 交付与恢复

- 数据/API/事件变更是否 expand-contract 且可回滚？
- 并发、崩溃窗口、重复乱序、积压和补偿失败是否测试？
- 是否无需直接改库即可对账、重放和人工恢复？
