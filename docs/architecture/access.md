# 接入层与 BFF：把终端交互翻译为稳定业务用例

接入层位于 API 网关与业务服务之间，处理外部协议契约、输入规范化、DTO 转换、终端定制查询和有界的粗粒度组装。BFF（Backend for Frontend）是面向某类终端体验的接入层，例如 App BFF、Web BFF、运营后台 BFF。

BFF 的核心价值不是“多一层转发”，而是隔离两种变化速度：终端页面、交互和版本变化快，领域用例、不变量与数据所有权应尽量稳定。如果这个边界没有建好，BFF 会逐渐变成拥有业务数据库、交易规则和大量跨服务流程的“超级服务”。

## 1. 运行时位置与边界

![接入层与 BFF 运行时边界](/architecture/bff-runtime-boundary.svg)

同一条请求上：

- **API 网关**识别 API 和消费者，执行通用身份初检、配额、流量路由、灰度和上游保护。
- **接入层/BFF**理解终端契约，把外部 DTO 转换为用例输入，按页面需求组装查询结果。
- **应用/业务层**执行用例、资源级授权、领域规则、幂等事实和事务。
- **数据层**保存领域事实；BFF 不跨过服务直接读写其数据库。

这个边界的判断标准是“决策依据属于谁”。例如“App 8.x 把 `shippingAddressId` 传成 `addressId`”是终端契约转换；“订单当前状态是否可取消”必须由订单领域决定。

## 2. 一次请求在 BFF 内的处理顺序

![BFF 请求处理管线](/architecture/bff-request-pipeline.svg)

1. **确定 API 契约**：根据已匹配路由、版本与终端类型选择明确的 request/response schema。
2. **解析与大小限制**：只接受声明的 Content-Type/字符集，对 JSON 深度、集合长度、字段数和 Body 大小设限。
3. **结构校验**：校验必填、类型、格式、长度、枚举、集合数量与未知字段策略。
4. **规范化**：按契约处理时区、语言、电话号码、空白、大小写和默认值，保留原始输入仅用于必要审计。
5. **建立请求上下文**：从可信身份声明和协议元数据创建 subject、tenant、locale、channel、request ID 和 deadline。
6. **DTO 到用例输入**：显式白名单映射，客户端不能控制价格、状态、租户、所有者、审批结果等服务端字段。
7. **调用用例或查询组装器**：写请求优先调用单一领域用例；查询可并行调用有界下游并组装展示模型。
8. **结果转换**：领域对象不直接序列化，显式转为 response DTO，执行字段裁剪、格式化和终端版本兼容。
9. **错误映射**：把解析、校验、授权、冲突、不可用映射为稳定 HTTP + 错误码契约，不泄露异常栈与内部类名。
10. **遥测与审计**：记录 API、版本、终端、校验结果、扇出次数、部分失败、响应大小与耗时，不默认记录 Body。

## 3. 什么适合放在接入层

| 适合 | 不适合 |
|---|---|
| OpenAPI/JSON Schema、内容协商、分页契约 | 订单价格、库存和退款规则 |
| 结构校验、格式规范化、DTO 映射 | 资源级最终授权和状态机 |
| 面向页面的查询聚合和字段裁剪 | 长时业务流程、Saga 和跨领域事务 |
| 终端版本兼容、默认值和展示格式 | 直接访问所有服务数据库 |
| 稳定错误契约、request ID、locale | 将所有异常改成 HTTP 200 |
| 有界并行查询、批量调用、短缓存 | 无界扇出、对写操作盲目重试 |

接入层可以知道“这是 iOS 商品详情页”，但不应成为“商品是否可售”的事实所有者。

## 4. 接入层、BFF 与 API Composition

**接入层**是逻辑角色，可以与单体应用同进程，不必是独立微服务。**BFF**是以终端体验为所有权边界的接入层。**API Composition**是查询时从多个下游组装结果的技术，可由 BFF、GraphQL 层或专用读模型完成。

三者不应与“一个页面一个微服务”划等号。页面会频繁调整，若每个页面都有独立部署，会制造大量微小服务、重复鉴权和共享模型。更常见的所有权是 Web/App/运营等终端域，再在代码内按业务场景模块化。

## 5. 何时需要独立 BFF

### 适合拆分

- Web、App、运营端的发布节奏、响应形状和安全风险显著不同。
- App 需长期兼容老版本，Web 可与服务端同步发布。
- 运营端需大查询、批量操作、字段级授权和强审计。
- 终端团队能独立拥有代码、SLO、值班和下游契约。
- 某终端的流量、计算特征或故障需要独立伸缩与隔离。

### 不必拆分

- 终端契约基本相同，只有少量字段差异。
- 团队很小，独立服务只会增加部署、监控和跨服务调用。
- 模块化单体中已能使用包/模块隔离 Web 适配器与用例。
- 只是为了“架构看起来完整”或复制别人的微服务图。

可先在同一部署单元内建立明确 `web-api`、`app-api`、`admin-api` 模块，只在团队、发布、容量或故障隔离产生真实价值时物理拆分。

## 6. 查询与命令必须分开设计

![BFF 查询聚合与命令接入的不同路径](/architecture/bff-query-command.svg)

### 查询

可按页面使用专用 response DTO、并行查询、批量接口、DataLoader、短缓存和一定陈旧容忍。关键是控制扇出、定义部分失败，并不跨服务直接拼数据库表。

### 命令

应对应一个明确业务意图，如 `CreateOrderCommand`。幂等、资源授权、状态机和事务由领域用例完成。BFF 不应串行执行“减库存→建订单→扣款→发积分”并尝试自己回滚。

## 7. 技术形态

| 形态 | 适用 | 注意 |
|---|---|---|
| Spring MVC REST | 大部分普通 BFF/API | 线程池、阻塞 I/O、超时与下游并发有界 |
| Spring WebFlux | 全链路非阻塞、高并发 I/O/流式 | 不在 Event Loop 调 JDBC/阻塞 SDK，上下文显式传播 |
| GraphQL | 多客户端需自主选字段与组合 | 深度/复杂度限制、N+1、字段授权、Persisted Query |
| gRPC 接入 | 受控机器客户端、内部高性能契约 | Protobuf 兼容、deadline、status 映射、流控 |
| Server-driven UI | 局部动态布局与实验 | Schema 版本、组件白名单、服务端不接管全部 UI 逻辑 |

选择 WebFlux 或 GraphQL 不会自动解决扇出、契约和所有权问题。先定义边界、延迟预算和失败语义，再选技术。

## 9. 最小上线基线

- API 契约有机器可读 Schema、示例、错误码和兼容性检查。
- Controller/Resolver 只做协议适配，不计算核心业务规则、不开跨服务事务。
- 外部 DTO、用例命令、领域对象和响应 DTO 是独立模型，显式白名单映射。
- 查询聚合有总 deadline、每下游预算、扇出/并发上限和部分失败契约。
- 身份上下文来自可信入口，显式传给用例，异步与线程切换不丢失。
- 错误保留 HTTP 语义与稳定错误码，不泄露栈、SQL、下游地址和内部类名。
- 按 API/客户端版本观测 RED、校验失败、下游扇出、响应大小、部分结果和发布版本。
