# 控制面、配置发布与扩展机制

API 网关的数据面处理每个请求，控制面则把 API、路由、凭证策略、配额、上游和插件配置转换为数据面可执行的快照。控制面错误不应立即中断现有流量，但一份错误配置也不能在数秒内自动扩散到所有网关实例。

## 1. 数据面与控制面

![API 网关控制面与数据面](/architecture/gateway-control-data-plane.svg)

### 数据面

- 接收请求、匹配路由、执行插件、调用上游。
- 使用内存中的不可变配置快照，不在热路径上查管理数据库。
- 控制面断开时继续使用最后有效快照。
- 暴露当前配置版本、接收时间和应用状态。

### 控制面

- 管理 API 定义、所有权、环境、租户套餐和密钥引用。
- 验证配置 Schema、语义、路由冲突与资源引用。
- 生成有版本、可签名的完整快照或有序增量。
- 按环境、地域、Cell 和实例波次发布，并跟踪 ACK/NACK。
- 保留审计、差异、审批、发布与回滚记录。

## 2. 配置对象模型

不要把整个网关配置建模为一个无边界 YAML。常见对象包括：

| 对象 | 职责 |
|---|---|
| API / Route | 外部契约、匹配、策略绑定和所有者 |
| Upstream / Cluster | 协议、发现、负载均衡、健康检查和连接池 |
| Consumer / Application | 开发者应用、凭证、订阅 API 产品 |
| Policy | 认证、配额、CORS、超时、重试等可复用策略 |
| Secret Reference | 只引用密钥管理系统中的版本，不将明文秘密嵌入配置 |
| Release | 发布范围、波次、快照版本、观察指标和回滚点 |

对象间引用要有完整性校验。删除上游前必须确认无路由引用；删除认证策略不能让路由自动变为匿名访问；无法解析密钥引用时快照应整体拒绝。

## 3. 配置发布生命周期

![API 网关配置发布生命周期](/architecture/gateway-config-lifecycle.svg)

### 3.1 提交

变更来自 GitOps Pull Request、受控管理 API 或门户。任何方式都应携带变更人、原因、工单/事件、目标环境和预期影响。

### 3.2 静态验证

- Schema 和类型是否正确。
- 路由是否重叠、存在无法达到或过宽的规则。
- Upstream、Policy、Secret 引用是否存在。
- 超时、重试、Body 大小、配额是否在平台安全范围内。
- 管理 API 是否被错误暴露为匿名或公网路由。
- 插件顺序和组合是否合法。

### 3.3 影响分析

输出结构化差异：新增/删除哪些路由，哪些消费者受影响，配额变严还是变宽，上游流量会如何迁移，是否修改认证边界。高风险变更必须多人审批。

### 3.4 预发布验证

将候选快照加载到隔离网关，运行路由契约、恶意输入、鉴权、配额与上游连通性测试。可用脱敏访问日志回放匹配结果，但不对生产上游造成副作用。

### 3.5 波次发布

先发一个非关键实例/Cell，确认快照 ACK、配置应用耗时、进程资源和路由指标。再按故障域分批扩大，避免同时替换一个地域的所有数据面。

### 3.6 观察与回滚

发布系统根据配置应用失败、路由 404/401/429/5xx 突增、无健康上游和网关资源异常自动暂停或回滚。回滚应重新发布上一个已知有效完整快照，而不是手工“反向改回去”。

## 4. 快照、增量和一致性

### 完整快照

每个版本包含完整配置，数据面验证并原子替换当前快照。容易回滚与排查，但大规模配置的网络和编译成本较高。

### 有序增量

推送带全局序号或对象版本的变更。效率高，但要处理丢失、乱序、重复和数据面重连。发现版本空洞时必须停止应用并重拉快照，不能在未知状态上继续合并。

无论哪种模式，配置应有单调版本、内容摘要/签名、生成时间和发布 ID。数据面不接受旧版本覆盖新版本，除非这是明确的受审计回滚。

## 5. 控制面故障时怎样运行

| 故障 | 数据面行为 |
|---|---|
| 控制面短暂不可达 | 继续使用最后有效快照，告警配置年龄 |
| 收到语法/引用无效快照 | NACK 新版本，保留当前版本 |
| 部分实例无法应用 | 停止扩大，保留新旧版本与实例清单，避免无限重试 |
| 配置快照过旧 | 持续服务还是自我摘流按风险定义；通常不应立即中断现有 API |
| 密钥过期且无法刷新 | 高风险鉴权 fail-closed，不使用无限过期密钥 |

“使用最后有效配置”不等于“永远不管陈旧”。必须监控配置年龄和实例版本分歧，否则新路由、凭证撤销和安全规则无法生效。

## 6. 管理面安全

管理 API 的风险高于普通业务 API，因为一次路由或鉴权策略修改可影响全体用户。应实施：

- 管理面与数据面的域名、网络、凭证和扩缩容独立。
- SSO + MFA，服务账号使用短期工作负载身份，禁止共享永久 Token。
- 按对象、环境和动作授权，开发者不能直接改其他团队路由。
- 生产发布与审批分离，紧急通道有时限、理由和事后审计。
- 管理数据库、消息通道和快照存储加密并最小权限。
- 管理操作的审计日志不能由操作者删改。

## 7. 插件与自定义扩展

网关插件在高频、高权限数据面上运行，应比普通业务代码有更严格的准入：

- 明确执行阶段与顺序，例如清洗 Header 必须早于鉴权。
- 不在事件循环中做 JDBC、阻塞 HTTP、文件 I/O 或无界 CPU 计算。
- 所有外部调用有短超时、连接池、并发上限、熔断和明确降级。
- 不无界缓存 Body，大 Body 使用流式、磁盘限额或不启用相关插件。
- 标签和缓存 Key 有界，防止攻击者制造高基数内存增长。
- 插件版本固定，有性能回归、故障注入、灰度与紧急禁用开关。

Spring Cloud Gateway 基于 Reactor/Netty，Filter 内的阻塞调用会占住少量事件循环线程，表现为 CPU 未满但整个网关延迟上升。即使把阻塞代码切到 bounded elastic 线程池，也必须有并发和队列上限，不能只是把无界阻塞移到另一个池。

## 8. 配置漂移与对账

定期对比：

- 期望快照版本 vs. 每个数据面当前版本。
- 控制面对象摘要 vs. 数据面编译后配置摘要。
- 密钥引用版本 vs. 实际加载版本和过期时间。
- 实际路由流量 vs. 配置的上游和灰度比例。

只监控“配置发布 API 返回 200”不足以证明配置已在全部数据面生效。

## 9. 上线检查

- 控制面不可用时，数据面是否继续使用已验证快照？
- 错误配置是否在发布前检测路由冲突、无效引用和危险参数？
- 发布是否按实例/Cell/故障域分批，而不是一次全量推送？
- 数据面 NACK 时是否保留旧版本并停止扩大？
- 是否可一键重发上一个已知有效完整快照？
- 管理面是否独立隔离、MFA、最小权限并完整审计？
- 自定义插件是否通过阻塞检查、资源上限、压测和故障注入？
- 是否监控配置年龄、版本分歧、ACK/NACK 和应用耗时？
