# 限流、配额、超时与韧性

网关的韧性目标不是让所有请求都成功，而是在流量突增、上游变慢或部分故障时，将资源留给可完成的请求，防止失败扩散，并给调用方可操作的错误语义。

## 1. 从入口容量到上游容量

![API 网关分层流控与过载保护](/architecture/gateway-traffic-guard.svg)

流控至少有三个不同目标：

1. **公平性**：一个租户或应用不能吃掉全部共享容量。
2. **保护上游**：上游只能稳定处理 2,000 RPS 时，网关不应传入 10,000 RPS 让其全部超时。
3. **保护网关自身**：即使上游很快，TLS、JWT、大 Body、日志和慢客户端也可能耗尽网关 CPU、内存和连接。

三者不能只用一个全局 RPS 阈值解决。

## 2. 限流与配额的区别

- **限流**强调短时速率，例如每秒 100 个请求，允许短时突发 20。
- **配额**强调较长周期用量，例如每日 100 万次、每月 10 TB 下载。
- **并发限制**关心正在处理的数量，对慢接口比 RPS 更有意义。
- **排队上限**限制等待资源的请求，避免用内存换取必然超时的排队。

对一个平均 20 ms 的查询和一个平均 20 s 的导出，同样 100 RPS 的资源影响完全不同。导出应使用小并发、任务化或异步化，而不是只调低 RPS。

## 3. 限流算法

| 算法 | 特性 | 适用 |
|---|---|---|
| 固定窗口 | 简单，边界可出现两倍瞬时流量 | 低风险长周期配额 |
| 滑动日志 | 精确，每请求状态成本高 | 小规模精确审计 |
| 滑动窗口计数 | 在精度与成本间折中 | 通用 API 限流 |
| 令牌桶 | 平均速率 + 可配突发 | 大多数交互式 API |
| 漏桶/整形器 | 输出速率平滑 | 保护稳定速率下游 |

令牌桶中，补充率是长期平均速率，桶容量是允许的突发量。如果只设大桶但不验证上游瞬时容量，多个沉寂租户可在同一时刻消耗积累令牌，形成合法流量峰值。

## 4. 限流键设计

只按 IP 限流会误伤 NAT 后的企业/校园用户，也会被大量代理 IP 绕过。生产策略通常组合：

```text
route + tenant
route + client application
route + authenticated user
route + source risk group
expensive operation + resource owner
```

键必须使用已验证、有界长度的值。直接用攻击者可控的随机 Header 作 Key，会制造无界高基数状态和存储攻击。

### 分层配额

可先保护全局/集群，再按业务路由，最后按租户和用户分配。例如：

- 网关集群 100k RPS 硬上限。
- 订单写入 8k RPS，保留 2k RPS 给核心付费流量。
- 普通租户单租户 100 RPS，大客户使用独立套餐。
- 单用户创建订单 5 RPS 并允许小突发。

上层限制保护物理容量，下层限制保护公平性；任一层命中都应返回稳定的 429 和机器可识别错误码。

## 5. 本地计数还是集中计数

| 模式 | 优点 | 代价 |
|---|---|---|
| 实例本地 | 无网络依赖、快 | 集群总限额近似，扩缩容会改变总容量 |
| Redis/集中存储 | 全局更准确，支持长周期配额 | 每请求额外网络开销和新故障依赖 |
| 本地配额分片 | 数据面快，控制面周期分配令牌 | 短期不均，需回收和再平衡 |
| 分层混合 | 本地保护实例，集中保护租户配额 | 策略与观测更复杂 |

集中计数失败时必须显式选择行为。登录、短信等滥用成本高的接口可 fail-closed 或使用更严本地限制；普通读 API 可在本地安全上限内降级运行。最危险的设计是计数失败后无限制全部放行。

## 6. 429 契约

被限流的响应应包含：

- HTTP `429 Too Many Requests`。
- 稳定的业务无关错误码，例如 `RATE_LIMITED`。
- 当可准确计算时返回 `Retry-After`，不要给出虚假精度。
- 可选的限额、剩余和重置时间 Header，但不泄露内部物理容量。
- request ID 用于排查。

客户端应使用抖动退避，不能在限额重置瞬间全部同时重试。

## 7. 超时预算

![API 网关超时、重试与取消关系](/architecture/gateway-timeout-retry.svg)

需区分：

| 超时 | 限制的阶段 |
|---|---|
| 请求 Header/Body 超时 | 防止慢客户端长期占用连接 |
| 连接池排队超时 | 等待上游连接的上限 |
| 上游 Connect Timeout | TCP/TLS 建连的上限 |
| Response Header/TTFB Timeout | 等待上游开始响应 |
| Idle Timeout | 流式传输期间多久无任何字节 |
| Total Request Deadline | 包括排队、所有尝试和处理的总预算 |

上游每次尝试的超时不能等于总预算。例如总预算 800 ms，排队最多 50 ms，最多两次尝试，第一次不能占满 800 ms。重试前应根据剩余 deadline 决定是否还值得再尝试。

网关超时只意味着停止等待，上游可能仍在执行。应传播 deadline/取消信号，但写操作仍必须幂等，因为取消与业务提交可能竞争。

## 8. 重试的严格边界

只在同时满足下列条件时重试：

1. 失败属于短暂故障，如连接拒绝、在发送 Body 前连接断开、部分 502/503。
2. 请求可重放：GET/HEAD 通常可；写操作必须有稳定幂等契约。
3. 请求 Body 可安全重放，流式上传不能默认缓存到网关内存。
4. 总预算尚有足够时间。
5. 本请求未超过最大尝试数，集群重试预算也未耗尽。

将每层默认 2 次重试叠加在客户端、CDN、网关、Service Mesh 和 SDK，最坏可将一个请求放大为数十次上游尝试。必须指定唯一主要重试层，并用指标监控 `attempts / original requests`。

## 9. 熔断、被动摘除与并发隔离

- **熔断**按时间窗口统计上游集群失败/慢调用，阈值达到后快速失败，再半开探测。
- **被动摘除**将局部连接失败的某个实例暂时移出。
- **并发隔离/Bulkhead**限制某路由或上游同时占用的连接、内存和在途请求。

熔断的统计维度不能过粗：用一个全局熔断器会让一条慢路由封锁整个上游；也不能过细到每个用户，否则样本不足且状态爆炸。常见作用域是路由 + 上游集群，实例级问题交给被动摘除。

## 10. 负载舍弃与请求优先级

当网关 CPU、内存、连接、事件循环延迟或队列超过安全线时，应主动舍弃负载，而不是继续接收直至进程失联。舍弃顺序可按业务优先级：

1. 拒绝未认证、低信任和明显异常流量。
2. 暂停低优先级批量、导出和可延迟任务。
3. 压缩普通租户突发额度。
4. 保留登录恢复、支付确认、订单查询等关键流量的预留容量。

这要求请求优先级来自受控路由配置和已验证主体，不能相信客户端自报“最高优先级”。

## 11. 常见故障模式

| 现象 | 常见原因 |
|---|---|
| 突然大量 429 | 配额发布错误、限流 Key 维度改变、计数器时钟/过期异常 |
| 网关 504，上游最终成功 | 网关超时小于上游执行时间，取消未生效 |
| 故障时上游 RPS 反而倍增 | 重试叠加，无重试预算 |
| 少量慢请求拖垮全部 API | 共享连接池/并发无隔离 |
| Redis 故障后全站不可用 | 集中限流无降级策略，超时过长 |
| 熔断器反复开闭 | 样本太小、无最小请求数/驻留时间，半开探测过多 |

## 12. 上线检查

- 全局、路由、租户和用户限额的优先关系是否明确？
- 限流 Key 是否已验证、有界，不会制造高基数攻击？
- 计数存储故障时每类 API 的 fail-open/fail-closed 是否经过评审？
- 429 是否有稳定错误码和合理 `Retry-After`？
- 每次尝试超时、总预算、客户端超时是否成套？
- 写请求重试是否依赖真正的业务幂等？
- 网关、Mesh、SDK 中谁是主要重试层？
- 上游变慢、失败和恢复的熔断行为是否通过混沌测试？
- 网关自身过载时是否优先保护高价值请求？
