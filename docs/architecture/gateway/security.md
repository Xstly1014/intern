# 认证、授权与信任边界

网关是外部凭证进入内部系统的第一个集中验证点，但“网关已验证 Token”不等于“下游可以信任任意 Header”，也不等于“业务服务不再需要授权”。正确模型是：网关建立身份上下文，内部传输保证上下文不被篡改，资源所有者执行最终授权。

## 1. 从外部凭证到内部身份

![网关身份验证与信任传递](/architecture/gateway-auth-trust.svg)

完整链路包含：

1. 客户端提交 Access Token、API Key、请求签名或客户端证书。
2. 网关先删除不可信的内部身份 Header。
3. 鉴权插件验证凭证，生成标准主体上下文。
4. 路由策略确认该主体类型、audience 和 scope 允许访问这个 API。
5. 网关通过受信任 Header、内部签名 Token 或 mTLS 身份将最小声明传给上游。
6. 业务服务使用主体和资源当前状态执行对象级授权。

## 2. JWT 本地验证

JWT 适合网关使用本地公钥验签，避免每个请求都同步调用认证中心。不能只验签名，还应验证：

| 检查 | 目的 |
|---|---|
| 允许的签名算法 | 拒绝 `none` 或算法混淆，不盲信 Token Header |
| `iss` | 只信任明确的发行方 |
| `aud` | 防止发给其他系统的 Token 被本 API 接受 |
| `exp` / `nbf` / `iat` | 限制时间窗口，只允许有界时钟偏差 |
| `sub` | 建立稳定主体 ID，不把可变用户名当主键 |
| `azp` / client ID | 识别实际调用应用 |
| tenant / scope | 提供租户上下文和粗粒度能力 |

### JWKS 缓存与轮换

网关根据 `kid` 选择公钥。JWKS 应本地缓存，并有后台刷新、最大陈旧时间和刷新失败告警。轮换必须有重叠期：先发布新公钥，再用新私钥签发，等旧 Token 过期后才删除旧公钥。

未知 `kid` 可触发一次受控刷新，但不能让攻击者用每个随机 `kid` 触发同步 JWKS 请求。需要负缓存、刷新单飞和速率限制。

### 撤销问题

自包含 JWT 在过期前通常无需查库，代价是即时撤销更难。常见方案包括短 Access Token + 可撤销 Refresh Token、高风险路由额外 introspection、用户/会话版本、短期黑名单。不应为了极少数高风险场景，让全部 API 强依赖每请求远程查询。

## 3. Opaque Token 与 Introspection

不透明 Token 需向授权服务查询有效性与声明。优点是撤销与会话控制强，缺点是增加延迟和故障依赖。网关应：

- 按 Token 摘要缓存 introspection 结果，缓存 TTL 不超过 Token 剩余生命。
- 对无效 Token 做短负缓存，防止重复穿透。
- 使用有界连接池、超时、并发上限和熔断。
- 明确故障时 fail-closed 还是允许在极短窗口内使用已缓存结果。

未缓存且无法 introspect 的新凭证通常应 fail-closed。已缓存凭证是否允许 stale，要根据业务风险定义，不能由插件默认值偶然决定。

## 4. API Key 与请求签名

API Key 适合识别合作方应用，不应直接等同终端用户。Key 只在创建时显示一次，服务端存储强哈希或只能验证的表示，支持双 Key 重叠轮换、使用范围、过期、撤销和最后使用审计。

高风险 Open API 可使用 HMAC/非对称签名，签名内容至少覆盖：

```text
HTTP method
normalized path and query
selected signed headers
body digest
timestamp
nonce or request id
```

规范化规则必须有精确契约，包括 URL 编码、Query 排序、空 Body 和 Header 空白。时间窗口防止长期重放，nonce/请求 ID 在窗口内去重。只签名 Path 而不签 Body，攻击者可替换交易内容。

## 5. mTLS 与机器身份

mTLS 同时建立加密通道和客户端证书身份，适合合作方专线、高风险机器 API 与网关到上游的内部信任。需管理：

- 证书主体如何映射到应用/服务身份，不只是“由某 CA 签发”。
- 证书短周期签发、自动轮换与双证书重叠。
- CA bundle 轮换、证书链、SAN 校验与时钟偏差。
- CRL/OCSP 的可用性、缓存和故障策略。
- TLS 终止位置；如果在上一层 LB 终止，网关不能凭一个任意 Header 相信客户端证书。

## 6. 网关授权的上限

网关适合做粗粒度授权，例如：

- 该应用是否订阅 `orders.write` API 产品。
- Token 是否拥有 `order:create` scope。
- 管理端路由是否只允许管理员主体和特定网络来源。
- 租户是否被停用或未开通该 API。

但下列问题必须由业务服务判断：

- 用户是否是订单 123 的所有者。
- 当前订单状态是否允许取消。
- 运营人员能否操作目标门店。
- 数据导出是否超过该角色的字段权限。

原因是资源所有者才掌握最新业务事实。网关为此查订单库，会引入数据所有权混乱、高延迟与新的故障耦合。

## 7. 受信任身份传递

### Header 传递

网关可注入 `X-Subject-Id`、`X-Tenant-Id`、`X-Client-Id`、`X-Scopes`，但前提是：

1. 入口一律删除同名外部 Header。
2. 网关到上游只能通过受信任网络或 mTLS。
3. 上游不允许被公网或绕过网关直连。
4. 字段名、编码、长度和多值规则有统一契约。

### 内部签名 Token

在多跳或不能完全信任网络的场景，网关可交换为短生命内部 Token，受众限定为目标服务，只包含最小声明。这能避免将外部 Token 扩散到所有内部服务，但要考虑签发延迟、密钥轮换和代理链记录。

## 8. CORS 不是认证

CORS 是浏览器的跨源读取约束，不阻止 curl、恶意 App 或服务器调用 API。网关执行 CORS 时要：

- 使用精确 Origin 白名单，携带凭证时不能使用 `*`。
- 按路由约束 Method 和 Header，不全站放开。
- 正确处理 OPTIONS 预检并限流，同时避免每次预检调用上游。
- 添加正确 `Vary: Origin`，避免缓存将一个 Origin 的结果给另一个。

## 9. 敏感日志与审计

访问日志不记录 Authorization、Cookie、API Key、完整请求签名、密码或未脱敏 Body。对身份故障应记录原因类别而不是凭证本身，例如 `token_expired`、`unknown_kid`、`audience_mismatch`。

管理操作需独立审计：谁在什么时间修改了哪个路由的认证/授权策略，修改前后的结构化差异、审批人、发布范围和回滚结果都应可查。

## 10. 上线检查

- 所有外部可伪造的身份 Header 是否先删除后重建？
- JWT 是否验证 algorithm、issuer、audience 和时间声明？
- JWKS 无法刷新时新旧 `kid` 分别怎样处理？
- introspection 故障时已缓存与未缓存凭证的行为是否明确？
- API Key/证书是否支持无停机轮换和立即撤销？
- 上游是否无法绕过网关直连？
- 资源级授权是否仍由业务服务执行？
- 日志、Trace 和错误响应是否不泄露凭证与内部验证细节？
