# 灰度发布、API 版本与协议治理

网关可以决定一个请求进入稳定版本还是候选版本，但它无法替代应用的前后兼容、数据库迁移和消息 Schema 演进。流量分流只是发布系统的一部分，成功的灰度必须把“谁进新版本、如何稳定命中、看什么指标、何时回退”连成闭环。

## 1. 灰度发布链路

![API 网关灰度发布与自动回退](/architecture/gateway-canary-release.svg)

典型过程：

1. 发布平台部署候选集群，但尚未承接用户流量。
2. readiness、合成测试和合成探测通过。
3. 网关先放入内部测试主体或指定租户。
4. 按稳定哈希扩大到 1%、5%、25%、50%、100%。
5. 每个阶段有最小样本量和观察时间，比较候选与基线。
6. 技术指标或业务不变量超阈值时停止扩大并回退。
7. 全量稳定后仍保留旧版本一段可回切窗口。

## 2. 分流条件

| 条件 | 用途 | 风险 |
|---|---|---|
| 随机百分比 | 无状态快速分流 | 同一用户每次可进不同版本 |
| 用户/租户稳定哈希 | 会话稳定、问题可复现 | 大租户流量不均，需分层哈希 |
| Cookie | Web A/B 与会话灰度 | 首次请求无 Cookie，会被清理 |
| 内部 Header | 测试人员、自动化验证 | 必须由网关生成，防外部伪造 |
| 客户端版本 | 新 App 只访问新 API | 版本 Header 可伪造，旧 App 长期存活 |
| 地域/可用区 | 地域性发布和合规 | 用户漫游、切流后版本变化 |

最常用的算法是对 `releaseId + tenantId/userId` 做稳定哈希，将结果落到 0～9999 桶。扩大百分比时保持已进灰度的主体仍在灰度。不要每次改百分比就更换 hash salt，否则用户群会全量洗牌，很难对比与复现。

## 3. 灰度不能只看 5xx

每个阶段至少比较：

- 候选与基线的请求量、5xx、上游重置和超时。
- P50/P95/P99，不只看平均值。
- JVM/CPU/内存/线程/连接池与数据库负载。
- 登录成功率、下单成功率、支付确认率等业务不变量。
- 下游副作用，例如重复消息、库存补偿和审计事件量。

低流量阶段不能只用百分比阈值。一个错误就可让 1% 灰度的错误率看起来极高，因此需要最小样本、绝对错误数和统计置信。高风险不变量则可一次命中就立即停止。

## 4. 镜像流量

镜像将一份真实请求异步复制给候选系统，原请求仍由稳定系统响应。适合验证性能、解析和查询结果，但必须：

- 候选系统的写副作用被禁用、隔离或转为 dry-run。
- Authorization、Cookie、个人数据按合规要求脱敏，不将生产凭证扩散到测试环境。
- 镜像失败、慢响应和连接池不反压原请求。
- 镜像比例和并发有上限，避免将候选系统打垮。
- 不使用镜像结果向用户响应。

## 5. API 版本策略

| 方式 | 例子 | 特点 |
|---|---|---|
| URI | `/v1/orders` | 显式、易观测，但 URI 与版本耦合 |
| Header | `API-Version: 2026-07-01` | URI 稳定，调试和缓存需更严谨 |
| Media Type | `application/vnd.example.v2+json` | 符合内容协商，客户端与工具复杂 |
| 无显式版本 | 兼容演进 | 体验简单，但必须严守非破坏性变更 |

版本不应映射到每次内部发布。`v2` 是对消费者契约的破坏性分支，不是应用 build 号。同一 API 版本可经历数百次后向兼容发布。

### 破坏性变更

包括删除/改名字段、改变类型、收紧校验、改变默认值、改变错误语义或枚举处理。添加字段也不一定安全：严格反序列化客户端可因未知字段失败，新枚举值可让旧客户端崩溃。需在消费者契约测试中验证。

## 6. 版本淘汰

一个可执行的淘汰流程：

1. 从网关指标识别消费者、调用量和最后访问时间。
2. 发布弃用日期、迁移指南和替代版本，与客户端所有者确认。
3. 响应添加标准 `Deprecation`/`Sunset` 信息或团队约定 Header。
4. 先在测试和低风险消费者中验证停用。
5. 到期后返回明确错误，保留有审批的短期例外。
6. 调用量归零并过安全窗口后，再删除上游代码和路由。

对移动 App 必须考虑长尾版本：有些用户数月不更新，不能把服务端发布日程当成客户端升级事实。

## 7. CORS 和安全 Header

网关是统一执行 CORS 与通用安全 Header 的合理位置，但应按 API/域名配置，不是一个全局模板。需注意：

- API JSON 响应与浏览器 HTML 页面需要的 CSP 策略不同。
- `Access-Control-Allow-Origin` 必须来自受控匹配，不盲目回显任意 Origin。
- 网关与上游不能同时添加冲突 CORS Header。
- 错误响应也要包含正确 CORS Header，否则前端只看到“CORS 失败”而不是真实 401/429。

## 8. HTTP、gRPC、WebSocket 与 SSE

![网关的多协议边界](/architecture/gateway-protocol-boundary.svg)

### HTTP/1.1 与 HTTP/2

网关可对客户使用 HTTP/2，对上游使用 HTTP/1.1 或 HTTP/2。要分别设置连接数、并发流、Header 压缩限制和流量控制。一个 HTTP/2 连接上的大量流不应绕过用户/路由配额。

### gRPC

gRPC 使用 HTTP/2，业务状态在 Trailers 的 `grpc-status`。只监控 HTTP 200 会将 gRPC 错误统计为成功。网关需识别 unary 与 streaming，传播 deadline，对 message 大小和最大流时长设限。gRPC-JSON transcoding 还需维护 Protobuf descriptor 与错误映射契约。

### WebSocket

HTTP Upgrade 成功后连接长期存在，普通 RPS 限制不能保护并发连接、每连接消息率和广播扇出。需连接配额、消息大小/速率、心跳、空闲超时和发布时优雅断开。

### SSE

SSE 是长 HTTP 响应，要禁止中间层无限缓冲，使用心跳穿过空闲超时，支持 `Last-Event-ID` 重连。普通响应 TTFB 超时不能直接套用于持续流。

## 9. 请求/响应转换的边界

适合网关的转换：

- 删除 Hop-by-hop Header，重建 Forwarded 信息。
- 统一添加 request ID、trace context 和受信任身份声明。
- 小范围 Path/Host 重写和协议桥接。
- 上游技术错误映射为稳定网关错误。

不适合网关的转换：

- 逐字段构建复杂页面 DTO。
- 同步调用多个服务再组装结果。
- 根据业务状态修改价格、库存或权限。
- 使用无类型脚本长期兼容两套差异巨大的 API。

这些应进入 BFF/防腐层，使用正常代码、测试、版本和所有权管理。

## 10. 上线检查

- 灰度主体是否稳定命中，扩大流量时不全量洗牌？
- 分流 Header/Cookie 是否可被外部伪造？
- 每阶段是否有最小样本、观察时间和自动回退阈值？
- 数据库、缓存、消息和下游契约是否先做到前后兼容？
- 镜像请求是否无业务副作用、无凭证泄露、不反压原请求？
- API 版本是消费者契约还是被误用为内部 build 号？
- gRPC 是否按 `grpc-status` 统计，WebSocket/SSE 是否有长连接专用配额与超时？
- 错误响应是否也保留正确 CORS 和 Trace 信息？
