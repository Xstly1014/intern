# 路由、服务发现与上游连接

路由不是简单的“Path 转发到 URL”。在生产系统中，它同时回答四个问题：请求属于哪个 API，该 API 当前允许访问哪个版本，这个版本有哪些健康实例，网关如何用可控的连接和超时调用它们。

## 1. 路由对象应包含什么

一条可运维的路由至少包含：

| 类别 | 关键字段 |
|---|---|
| 身份 | 稳定的 `routeId`、API 名称、所有团队、值班联系方式 |
| 匹配 | Host、Method、Path 模板、Header/Query 条件、优先级 |
| 安全 | 认证方式、允许的 audience/scope、Body 上限、CORS 策略 |
| 流控 | 租户/应用/用户配额、并发上限、请求优先级 |
| 上游 | 集群 ID、协议、端口、发现来源、负载均衡算法 |
| 韧性 | 连接/响应/总超时、重试条件、熔断、降级 |
| 发布 | 稳定版本、候选版本、分流条件、镜像策略 |
| 观测 | 指标标签、日志采样、审计级别、敏感字段脱敏 |

不要用实例 IP 当路由身份，也不要把所有配置藏在一段无类型的脚本中。稳定 `routeId` 是指标、日志、配额、审计和发布的共同关联键。

## 2. 匹配顺序与冲突

![API 路由匹配决策](/architecture/gateway-route-matching.svg)

常见匹配维度从粗到细为 Host、Method、Path、Header/Query。匹配器必须产生唯一结果，否则配置应在发布前被拒绝。

### Path 精确度

`/orders/search` 应比 `/orders/{id}` 更精确，`/orders/{id}` 又比 `/orders/**` 更精确。如果只靠配置文件顺序，一次不相关排序就可能改变生产路由。优先级算法应当明确，并在 CI 阶段检测重叠。

### Method 不能忽略

`GET /orders/{id}` 和 `DELETE /orders/{id}` 可以有不同的身份、配额、超时和审计要求。只按 Path 管理会让高风险写操作继承读接口的宽松策略。

### Header 路由要可控

版本、灰度或合作方可使用 Header 路由，但必须区分外部可设 Header 与网关内部 Header。不能让用户通过伪造 `X-Canary: true` 访问未开放版本。

## 3. Path 重写的风险

网关可将外部 `/api/v1/orders/123` 重写为内部 `/orders/123`，但重写应保持语义简单。需要注意：

- 对 Path 参数先解码还是先匹配，必须与安全层一致，防止双重编码绕过。
- 保留原始 URI 用于审计，但不将其不受控地传给上游。
- 重写后的 Location Header、绝对 URL 和签名规则必须一致。
- 不在网关中做大量 JSON 字段重组；这属于 BFF/适配层。

## 4. 服务发现的四种来源

| 来源 | 优点 | 主要风险 |
|---|---|---|
| 静态地址 | 简单、可预期 | 扩缩容与故障切换需人工改配置 |
| DNS | 通用、与平台解耦 | TTL、负缓存、连接池不随 DNS 立即更新 |
| 注册中心 | 实例级发现与元数据丰富 | 控制面依赖、推送风暴、过期实例 |
| Kubernetes Service/EndpointSlice | 与集群生命周期集成 | readiness 传播延迟、大规模 Endpoint 更新 |

无论哪种来源，数据面都应有当前可用实例快照。发现系统短暂故障时，网关应继续使用最后有效快照，而不是清空全部上游。但快照也要有最大陈旧时间和告警，防止长期调用已下线地址。

## 5. 健康状态不能只看注册

上游可用性来自多个信号：

- **平台 readiness**：实例是否愿意接收新流量。
- **网关主动健康检查**：是否可连接并返回期望响应。
- **被动异常统计**：真实请求是否持续出现连接失败、重置或 5xx。
- **局部过载反馈**：上游是否明确返回 429/503/Retry-After。

主动检查能发现没有真实流量的实例故障，被动检查能发现特定路径和协议错误。两者都需要连续失败/成功阈值和最小驻留时间，避免在健康与不健康之间振荡。

## 6. 负载均衡算法如何选

| 算法 | 适用 | 陷阱 |
|---|---|---|
| Round Robin | 同规格实例、请求成本接近 | 不感知长请求与慢实例 |
| Weighted RR | 实例规格不同或版本分流 | 静态权重不代表实时容量 |
| Least Requests | 请求耗时差异大 | 只看数量，不看每个请求成本 |
| Consistent Hash | 稳定灰度、缓存亲和 | 热 Key 使单实例过热 |
| EWMA/Latency Aware | 快速避开变慢实例 | 需探索恢复实例，防止永久饿饿 |

算法的作用域要明确。如果网关每个实例都使用本地 Least Requests，它只知道自己发出的请求，不知道同一上游被其他网关实例施加的负载。这不一定错，但容量设计不能误以为它是全局最小负载。

## 7. 上游连接池

网关终止客户端连接后，会另建到上游的连接。上游连接池至少要管理：

- 每集群/实例的最大连接数和最大等待队列。
- HTTP/1.1 Keep-Alive 复用与 HTTP/2 每连接最大并发流。
- 连接最大生命、空闲超时、每连接最大请求数。
- DNS/发现更新后旧连接的排空。
- TLS session 复用、mTLS 证书轮换和 SNI。

连接池不足时，请求会在网关内排队，此时 Java 上游的 CPU 可能很低。所以必须监控 `pending requests`、获取连接耗时、连接复用率和每实例连接分布，而不只看上游响应时间。

## 8. 优雅上下线

### 上线

1. 实例启动，readiness 仍为失败。
2. 完成配置、连接和必要预热。
3. readiness 成功，发现系统推送实例。
4. 网关主动检查达到健康阈值。
5. 慢启动逐步提高流量，避免空缓存实例瞬间过载。

### 下线

1. readiness 转为失败，停止分配新请求。
2. 等待发现、网关快照和连接池状态传播。
3. 拒绝新长连接，对已有 HTTP/2/WebSocket 发送优雅关闭信号。
4. 在有界 drain timeout 内完成在途请求。
5. 超时后中断剩余请求，记录数量并下线。

如果容器的 `terminationGracePeriod` 小于网关摘流传播加排空时间，每次发布都可能出现短暂 502/503。

## 9. 路由上线检查

- 匹配规则是否与现有路由重叠？
- 未匹配 Method 返回 404 还是 405，是否符合契约？
- Path 重写、Query 保留和编码是否通过恶意用例测试？
- 发现快照为空、过期或部分实例失败时怎样响应？
- 连接池上限、队列上限和排队超时是多少？
- 上游扩容和缩容时，旧连接如何排空？
- 路由指标中能否区分匹配失败、无健康上游和连接池排队？
