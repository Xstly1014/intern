# 外部集成层：隔离第三方的不确定性

支付、短信、地图、物流、ERP、身份核验等第三方系统不受本团队控制。外部集成层用 Adapter/防腐层把供应商协议转换为内部稳定模型，并隔离其超时、限流、错误码、版本和安全风险。

## 1. 基本结构

```text
业务服务 → 内部端口 PaymentGateway
                    ↓
          WeChatPayAdapter / StripeAdapter
                    ↓
           签名、限流、超时、第三方 API

第三方回调 → 独立回调入口 → 验签/防重放 → Inbox → 业务处理
```

领域层只认识 `PaymentRequest`、`PaymentResult`，不认识供应商 SDK 的 DTO 和异常。切换供应商或升级版本时，变化局限在适配器。

## 2. 出站调用

- 连接、响应和总预算分别设超时；连接池按供应商隔离。
- 只重试明确可重试且幂等的操作，使用供应商幂等键与本地请求号。
- 按供应商/接口做限流、熔断和舱壁，避免一个渠道耗尽全局线程。
- 保存内部请求号、外部请求号、状态、必要响应摘要和审计信息。
- 错误分类为业务拒绝、参数错误、短暂技术失败和未知结果；“超时”不等于“对方没成功”。

对于支付等操作，超时后先查询状态或等待回调，不盲目再次扣款。未知状态进入对账和人工处置流程。

## 3. 入站回调

回调端点必须校验 TLS、签名、时间戳、nonce、事件 ID 和允许来源，原始 body 在验签前不能被重新序列化。快速持久化到 Inbox 后返回供应商要求的 ACK，再异步处理，防止处理过慢导致回调风暴。重复事件返回成功但不重复执行。

回调可能乱序，例如“退款成功”先于“支付成功”到达；业务状态机需按外部事件版本、发生时间和当前状态处理，而不是按 HTTP 到达顺序覆盖。

## 4. 数据映射与合规

统一内部金额、币种、国家码、时区、地址和状态语义。保存原始外部状态用于追查，但不能让它成为内部枚举的唯一含义。向第三方发送最少数据，记录处理目的和保留期；Secret 放密钥服务并轮换，日志脱敏。

## 5. 可替换性与灾备

多供应商不是简单写两个 Adapter：还要定义路由、健康评分、成本、配额、数据一致、回切和对账。短信可在失败时快速切换；支付渠道切换则涉及用户确认、订单状态和清算，不应自动无限尝试。

集成测试使用供应商 Sandbox 加契约测试，关键协议保留已脱敏样本；用故障注入验证超时、429、重复回调、乱序和签名轮换。生产指标按供应商分组：成功率、延迟、错误类型、限流、熔断、未知状态、回调延迟与对账差异。

## 6. 常见误区

- 供应商 SDK 散落在各业务服务，升级时全局修改。
- 把第三方返回 200 当作最终业务成功。
- 回调不验签、不幂等，或在 HTTP 请求内做完整长事务。
- 同时重试请求和等待回调，产生重复业务动作。
- 没有对账，永远无法收敛网络分区造成的未知状态。
