# 端到端落地与演进：从第一版到生产级系统

架构应从业务约束推导并按证据演进。最稳妥的路径通常是先做边界清楚的模块化单体，建立安全、观测、备份和自动交付，再根据真实瓶颈拆分，而不是一开始复制大厂拓扑。

## 1. 架构设计输入

在画组件图前收集：核心用户旅程、峰值与平均 QPS/TPS、读写比、数据增长、延迟目标、可用性 SLO、RTO/RPO、敏感数据、合规、预算、团队规模和交付期限。缺少这些数字，所谓“高并发高可用”无法验证。

容量可从简单模型开始：

```text
峰值 QPS = 峰值用户数 × 每用户峰值操作频率 × 安全系数
并发请求 ≈ QPS × 平均响应秒数（Little's Law）
日增数据 = 日请求量 × 写入比例 × 单记录含索引/副本大小
```

再通过压测校准，不用拍脑袋决定实例、连接池和分区数。

## 2. 推荐演进路线

### 阶段一：可上线的模块化单体

![第一阶段模块化单体生产架构](/architecture/modular-monolith.svg)

必须具备：HTTPS、身份权限、输入校验、数据库迁移、结构化日志、指标/Trace、备份恢复、自动构建部署、健康检查、优雅停机和关键业务告警。单体不等于低质量。

### 阶段二：增长与异步化

流量和功能增长后增加网关、缓存、MQ、搜索和任务平台。先异步化通知、索引、报表等旁路，再处理复杂核心流程。为消息建立 Outbox、幂等、重试、死信和积压看板。

### 阶段三：按价值拆服务

选择具有独立团队、发布、伸缩、数据或故障隔离价值的领域拆出。先定义 API/事件契约与数据所有权，再迁移数据和流量；通过绞杀者模式逐步替换，避免一次性重写。

### 阶段四：平台化与多地域

当服务和团队数量足够大，建设统一交付、安全、可观测和治理平台。只有明确的 SLO、合规或全球延迟需求才进入多地域写入，并为冲突、切换和运营复杂度付费。

## 3. 创建订单端到端时序

![创建订单的端到端同步与异步时序](/architecture/order-end-to-end.svg)

这里要明确：入口超时后同一幂等键可查询原订单；库存预占有超时释放；订单与 Outbox 同事务；消费者重复执行不会重复扣款；任何未知支付状态由查询/回调/对账收敛；所有步骤由 orderId、requestId 和 traceId 关联。

## 4. 故障设计表

| 故障 | 立即行为 | 恢复机制 | 不变量 |
|---|---|---|---|
| 网关过载 | 分级限流、拒绝低优先级 | 扩容、流量切换 | 高价值容量保留 |
| 库存超时 | 不无限等待，订单不误报成功 | 幂等重试或释放预占 | 不超卖/可解释 |
| DB 主库故障 | 快速失败或短队列，禁止重试风暴 | 主备切换、重连退避 | 已确认数据不丢超出 RPO |
| MQ 不可用 | Outbox 保留待发事件 | Broker 恢复后续传 | 业务与事件最终一致 |
| 消费失败 | 退避重试、死信隔离 | 重放、补偿、人工处理 | 不重复副作用 |
| 第三方超时 | 标记未知，不盲重试 | 查询、回调、对账 | 不重复支付/退款 |

## 5. 架构评审必须回答

### 边界与数据

- 谁拥有每份数据？谁能写？跨服务如何查询？
- 核心不变量在哪里强制？事务边界在哪里？
- API、事件和 Schema 如何兼容演进？

### 可靠性

- 每条依赖的超时、重试、熔断、舱壁和降级是什么？
- 请求/消息如何幂等？重复、乱序、积压怎样处理？
- 最坏部分失败时用户看到什么，怎样自动或人工修复？

### 安全与运维

- 身份、资源授权、租户隔离、Secret、脱敏和审计是否完整？
- SLI/SLO、仪表盘、告警、负责人和 Runbook 是什么？
- 发布、回滚、数据库迁移、备份恢复和容灾是否演练？

### 容量与成本

- 峰值模型和压测依据是什么？瓶颈先出现在哪里？
- 连接、线程、队列、分区、磁盘和带宽是否有上限与余量？
- 新组件带来的运维成本由谁承担，退出方案是什么？

## 6. 何时应该拆，何时不该拆

拆分的有效信号包括独立伸缩差异超过数倍、发布互相阻塞、故障爆炸半径不可接受、团队所有权稳定、数据边界清楚。无效理由包括“微服务更先进”“以后可能有亿级流量”“简历需要”。

合并也可以是正确演进：两个服务频繁同步调用、共享事务和团队，独立发布没有价值时，合并可降低网络与一致性成本。架构演进不是单向增加组件。

## 7. 最终原则

1. 先业务目标，后技术组件。
2. 先逻辑边界，后物理拆分。
3. 让数据所有权和失败语义显式化。
4. 默认网络会失败、消息会重复、人会误操作。
5. 可靠性、安全、观测和恢复从第一版就建设。
6. 用指标和演练验证架构，而不是用图的复杂度证明架构。
