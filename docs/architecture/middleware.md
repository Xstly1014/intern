# 异步与中间件层：解耦、削峰与系统协调

中间件提供跨业务复用的分布式能力，包括消息、任务调度、服务发现、配置、分布式协调和流量治理。它能降低特定耦合，但每引入一个中间件，就增加一个需要容量规划、升级、监控、备份和应急的生产系统。

## 1. 能力地图

| 能力 | 解决问题 | 常见产品 |
|---|---|---|
| 消息队列/事件流 | 异步、削峰、一对多、事件留存 | Kafka、RocketMQ、RabbitMQ |
| 任务调度 | 定时、分片、补跑、任务编排 | XXL-JOB、Quartz、K8s CronJob |
| 配置中心 | 动态配置、环境隔离、版本发布 | Nacos、Apollo、Spring Config |
| 服务注册发现 | 动态实例地址与健康状态 | Kubernetes Service、Nacos、Consul |
| 分布式协调 | 选主、租约、少量元数据一致性 | ZooKeeper、etcd |
| API/RPC 治理 | 超时、熔断、限流、服务路由 | Resilience4j、Sentinel、Service Mesh |

## 2. 消息模型与选择

RabbitMQ 适合灵活路由、工作队列和较低延迟；Kafka 适合高吞吐、按分区有序、保留并重复消费的事件流；RocketMQ 对业务消息、延迟和事务消息有丰富能力。选择要看投递模型、顺序、吞吐、延迟、保留、消费方式和团队运维经验，而非只比峰值 TPS。

事件包含唯一 ID、类型、发生时间、生产者、业务 Key、Schema 版本、Trace 上下文和载荷。分区键决定局部顺序与并行度；同一订单用 orderId 可保序，但热点大客户可能造成分区倾斜。

## 3. 可靠消息闭环

```text
业务事务：保存订单 + Outbox
                   ↓ Relay 重试发布
Broker：持久化 + 副本 + Producer Confirm
                   ↓ Consumer 拉取
消费者：幂等处理 + 业务提交 → ACK
                   └ 失败 → 退避重试 → 死信 → 人工/自动修复
```

“Exactly Once”通常只是某个技术边界内的保证。端到端仍应按至少一次设计：生产者可靠发布、Broker 正确持久化、消费者幂等、失败可重放。重试要指数退避并限制次数；永久性错误直接进入隔离队列，不能无限阻塞主队列。

## 4. 消息契约治理

事件是长期公共契约。新增可选字段通常兼容；删除、改类型、改语义会破坏消费者。采用 Schema Registry 或契约测试，消费者忽略未知字段，生产者提供迁移窗口。事件中避免携带敏感数据和巨大对象，传标识并按授权读取。

监控生产/消费速率、端到端延迟、Consumer Lag、最老消息年龄、重试和死信、分区倾斜、Broker 磁盘与副本状态。扩容消费者受分区/队列并行度上限约束。

## 5. 任务调度

任务必须可重入、幂等、可分片、可超时、可取消、可补跑。调度器负责“何时触发”，业务服务负责“做什么”；不要在调度平台脚本中堆业务规则。保存每次执行的参数、分片、开始结束、结果和错误，并防止同一业务周期重复成功。

短暂失败自动退避，长期失败告警；大批量任务使用游标/分片和速率限制，避免凌晨集中压垮数据库。涉及金钱或状态修复的补跑需审批和 dry-run。

## 6. 配置与服务发现

配置区分静态启动配置、动态业务开关和 Secret。动态变更有类型、范围、默认值、负责人、审计、灰度和回滚；应用收到非法配置应拒绝并保留上个有效值。Feature Flag 带到期时间，避免永久分支。

在 Kubernetes 内优先使用原生 Service/DNS，避免再叠加一套无必要的注册中心。服务发现故障时客户端应使用短期缓存，但要处理地址过期和摘流。

## 7. 分布式锁与协调

锁用于协调，不替代业务正确性。锁的持有者可能暂停到租约过期后继续写，因此对关键资源使用单调递增 fencing token，由资源端拒绝旧持有者。优先使用数据库约束、状态条件更新、消息串行化；不要用 `SETNX` 加一个过期时间就宣称强一致锁。

## 8. 常见误区

- 为“解耦”发送无所有者、无契约的消息，问题反而更难追踪。
- 消费成功前 ACK，或业务成功后 ACK 丢失却没有幂等。
- 重试没有退避和上限，引发下游恢复前的持续攻击。
- 把配置中心当数据库，频繁存大对象或强一致业务状态。
- 中间件集群上线后没有容量、升级、备份和故障演练负责人。
