# API 网关层：从公网请求到内部服务的治理边界

API 网关不只是一个反向代理，它是内部服务之前的**统一流量策略执行点**。客户端不应知道订单服务有多少实例、正在发布哪个版本或使用哪种 RPC 协议；内部服务也不应各自重复实现公网路由、通用验签、租户配额、灰度分流和访问日志。

但网关不是“越集中越好”。它位于几乎所有同步请求的必经之路，任何阻塞代码、错误路由、失控重试或配置全量发布，都会把局部故障放大成全站事故。因此网关的设计核心不是“功能多”，而是**数据面简洁、策略可解释、故障有边界、变更可回退**。

## 1. 网关在整体链路中的位置

![API 网关运行时请求链路](/architecture/gateway-runtime-path.svg)

一条动态 API 请求通常会经过：

1. DNS/GSLB 选择地域或边缘入口。
2. CDN、Anti-DDoS 和 WAF 处理缓存、攻击清洗和通用 Web 规则。
3. L4/L7 负载均衡器将流量送到某个可用的网关实例。
4. API 网关识别 API，执行身份初检、配额、路由、灰度和上游保护。
5. BFF/接入层完成终端适配、DTO 校验与粗粒度组装。
6. 业务服务执行资源级授权、领域规则和事务。

边缘 WAF、负载均衡、API 网关和 BFF 都能理解 HTTP，但它们的判断依据不同：WAF 根据攻击特征判断，LB 根据健康与连接负载调度，网关根据 API 与流量策略决策，BFF 根据终端场景组装。没有这个边界，同一条规则会散落在四层并产生冲突。

## 2. 请求在网关内的处理顺序

![API 网关请求处理管线](/architecture/gateway-filter-pipeline.svg)

不同产品使用 Filter、Plugin、Middleware 或 Policy 表示处理节点，但生产管线通常遵循如下顺序：

1. **连接与协议检查**：限制 TLS/HTTP 版本、Header 数量与字节、URI 长度、Body 大小和上传速率。应尽早拒绝明显无效请求，不让它消耗验签和路由资源。
2. **信任边界清洗**：删除外部伪造的 `X-User-Id`、`X-Tenant-Id`、`X-Forwarded-*` 等内部 Header，再由受信任代理重建。
3. **路由匹配**：通过 Host、Method、Path、Header 和 API 版本找到唯一路由。未知 API 直接 404/405，不应交给默认后端“猜”。
4. **请求上下文**：验证或重建 `traceparent`，生成请求 ID，标记路由 ID、入口地域和发布版本。
5. **认证初检**：验证 Token/API Key/mTLS 身份，确认签名、发行方、受众、时间窗口和撤销状态。
6. **粗粒度访问策略**：检查该客户端或 scope 是否允许访问路由；资源归属和业务状态仍由业务服务决定。
7. **配额、限流与并发保护**：按路由、租户、应用、用户和来源组合计数，为关键流量保留容量。
8. **流量选择**：根据地域、版本、灰度分组、实例健康和熔断状态选择上游集群。
9. **上游调用**：从连接池取连接，应用连接与响应超时，只在允许的错误和总预算内重试。
10. **响应处理**：清理 Hop-by-hop Header，添加安全和配额 Header，保留业务错误语义，不把所有错误改成 HTTP 200。
11. **遥测与计费**：记录路由、主体、上游、尝试次数、上下游状态码、各阶段耗时和策略命中，严格脱敏。

顺序不是装饰性细节。如果先调用外部鉴权再限制 Body，攻击者可用超大请求拖垮鉴权系统；如果在路由匹配前就使用路由级限流键，就无法稳定归类；如果访问日志没有上游尝试次数，则无法识别重试放大。

## 3. 网关的责任边界

| 能力 | 网关负责 | 网关不负责 |
|---|---|---|
| 路由 | API 到上游集群的映射、版本和灰度 | 根据订单状态选择业务流程 |
| 身份 | 凭证基本合法性、身份声明的可信传递 | “用户能否修改这张订单”的最终授权 |
| 流控 | 全局、租户、应用、用户、路由配额 | 库存数量、促销资格等业务限制 |
| 协议 | TLS/HTTP、CORS、gRPC/HTTP 桥接、Header 治理 | 频繁变化的业务 DTO 组装 |
| 可靠性 | 超时、有界重试、熔断、过载保护 | 业务补偿、分布式事务 |
| 观测 | 访问日志、路由指标、Trace 传播 | 业务成功的最终定义 |

一个可操作的判断方法是：

- 规则是否跨业务通用？
- 是否只依赖请求元数据、本地策略和短期计数状态？
- 该规则失败时，是否能定义统一、稳定的技术错误语义？
- 规则变更是否不需要与某个领域数据 Schema 一起发布？

多数答案为“是”才适合放在网关。一旦需要读取订单库、判断商品类别或编排多个领域操作，应移到 BFF 或业务服务。

## 4. 逻辑网关与物理部署

### 单集群共享网关

所有公网 API 共用一个网关集群。优点是标准统一、资源利用率高；风险是爆炸半径大，某个路由的大 Body、慢流或插件异常可影响全部业务。适合规模较小且已有严格路由隔离的系统。

### 按信任域拆分

将公网用户 API、合作方 Open API、管理端 API 和内部 East-West API 分成不同网关或至少不同数据面。它们的身份方式、流量模型、容错和发布节奏本就不同，强行共用会导致复杂条件规则。

### 按地域或 Cell 拆分

每个地域/Cell 有独立数据面，配置由全局或地域控制面发布。一个 Cell 的流量、连接池和故障不影响其他 Cell，但要管理配置版本一致性、地域例外和跨地域切流。

### 集中式与 Sidecar/Service Mesh

公网 North-South API 通常仍需要集中入口网关。Service Mesh 擅长内部 East-West 流量的 mTLS、服务路由和遥测。两者可以共存，但不要在网关和 Sidecar 同时配置三次重试和各自的熔断窗口。

## 5. 网关与 Ingress、BFF、Service Mesh 的差异

| 组件 | 主要关心 | 典型配置所有者 |
|---|---|---|
| 云 LB / Ingress | 将流量安全送入集群，TLS、Host/Path 基础路由 | 基础设施/平台团队 |
| API 网关 | API 产品、消费者身份、配额、版本、流量发布 | API 平台 + 服务所有者 |
| BFF | 终端体验、数据裁剪、粗粒度组装 | Web/App 接入团队 |
| Service Mesh | 内部服务间连接、mTLS、路由、重试和可观测 | 平台 + 服务团队 |

Kubernetes Ingress 是资源模型与入口能力，不自动等于完整 API 网关。Gateway API 能表达更丰富的路由与角色分工，但配额、开发者应用、API 产品、计费和凭证生命周期仍需要额外能力。

## 6. 技术选型不只看吞吐

| 方案 | 适用情况 | 需重点验证 |
|---|---|---|
| Spring Cloud Gateway | Java/Spring 团队、需定制 Filter 和动态路由 | Reactor 阻塞、GC、插件质量、配置发布 |
| Apache APISIX / Kong | 需成熟插件、高性能数据面和 API 管理 | 控制面高可用、插件隔离、团队运维能力 |
| Envoy / Envoy Gateway | Kubernetes/Service Mesh 生态、多协议、精细流量治理 | xDS 控制面、配置规模、过载保护 |
| 云 API Gateway | 希望降低运维、与云 IAM/无服务整合 | 成本曲线、限额、可移植性、私网回源 |

选型压测必须使用真实请求特征：长短连接比例、HTTP/2 并发流、JWT 签名算法、Header 数量、Body 分布、访问日志量、TLS 新建连接和插件组合。只用一个 Keep-Alive 连接压空响应，得到的 QPS 不能代表生产容量。

## 8. 最小上线基线

一个能转发请求的代理还不是可上线的 API 网关。最少应确认：

- 每条路由有唯一所有者、上游、超时、Body 上限、身份策略和配额。
- 外部身份 Header 会被删除，网关到上游使用受信任网络或 mTLS。
- 连接超时、响应超时、总预算和重试次数有明确上限。
- 配置发布有 Schema 验证、影响分析、灰度、审计和一键回滚。
- 能按 route、upstream、status、region 查看流量、错误、延迟、限流和熔断。
- 实例跨故障域部署，支持 readiness、优雅摘流和有界排空。
- 已压测正常容量、上游变慢、无健康上游、计数存储故障和配置面故障。
