# 客户端与边缘层总览：从用户设备到 Java 网关

客户端与边缘层不是一台 Nginx，也不是“在应用前面加一个 CDN”。它是一条跨越用户设备、公共互联网、运营商网络、全球边缘节点和源站入口的完整传输与防护链路。

这一层的目标可以浓缩为一句话：**在不信任网络和不稳定终端的条件下，把合法请求安全、快速、可控地送到正确的 Java 系统入口，并把响应尽可能高效地送回用户。**

本章不再试图用一页讲完所有组件，而是拆成九个专题逐层下钻。

## 2. 完整请求路径

![客户端到 Java 服务的完整边缘请求路径](/architecture/edge-request-path.svg)

请求并不一定经过图中所有组件。同一个云产品也可能同时承担 DDoS 清洗、CDN、WAF 和 L7 负载均衡。图中的“层”表示职责和信任边界，不要求一层对应一套独立产品。

## 3. 正向路径和反向路径

架构图经常只画请求从左到右，却忽略响应从右到左。实际上两个方向关注点不同：

| 方向 | 主要控制点 |
|---|---|
| 请求进入 | DNS、握手、身份线索、大小限制、限速、WAF、路由、超时 |
| 响应返回 | 压缩、缓存头、内容类型、安全 Header、分块/流式、错误缓存、连接复用 |

例如 Java 服务返回了 `Cache-Control: public, max-age=86400`，CDN 可能把它缓存给所有用户；返回错误的 `Content-Type` 可能让浏览器执行本应下载的内容；响应压缩配置不当会浪费 CPU 或暴露敏感信息。因此边缘层不是只管理“入口流量”。

## 4. 这一层拥有和不拥有的职责

### 应该拥有

- 域名、证书、公开入口和源站暴露策略。
- 静态内容分发、公开响应缓存和回源规则。
- DDoS、通用 WAF、Bot、连接和请求级过载保护。
- L4/L7 负载均衡、健康检查、跨地域与跨可用区流量调度。
- HTTP/TLS 协议策略、请求大小、连接时长和 Header 清洗。
- 边缘访问日志、网络指标、合成探测和故障切流机制。

### 不应该拥有

- “订单是否允许退款”“用户是否满足活动资格”等核心业务规则。
- 依赖多张业务表的资源级授权。
- 跨领域长流程编排和数据库事务。
- 为掩盖后端性能问题而无限缓存本应强一致的动态数据。
- 只能由某个供应商黑盒规则解释、业务团队完全无法追踪的关键决策。

## 5. 五个关键边界

### 5.1 信任边界

公网请求中的所有 Header、IP、Host、证书信息和身份声明默认不可信。每经过一个可信代理，都要明确哪些字段被删除、重写或追加。尤其不能直接相信客户端传来的 `X-Forwarded-For`、`X-User-Id`、`X-Tenant-Id`。

### 5.2 缓存边界

边缘缓存只保存权威数据的副本。必须能说清缓存键、TTL、失效方式、陈旧窗口、错误响应是否缓存，以及个性化响应如何避免串用户。

### 5.3 超时边界

超时从外向内逐层缩短，给外层留下处理和返回错误的时间。例如：

![从客户端到业务依赖逐层递减的超时预算](/architecture/timeout-budget.svg)

这只是示意值。下载、上传、流式响应和普通 JSON API 应使用不同预算。

### 5.4 容量边界

每一层都有不同的饱和资源：客户端是连接和电量，CDN 是带宽与回源，WAF 是检查吞吐，LB 是并发连接和新建连接速率，Java 服务是线程、CPU、堆和下游连接。容量规划不能只看 QPS。

### 5.5 所有权边界

每个域名、证书、WAF 规则、CDN 分发、LB 和回源地址都要有负责人、变更记录、监控和应急手册。没有所有者的“公共入口”最终会成为高爆炸半径遗留系统。

## 7. 动态请求示例：创建订单

1. App 从本地安全存储读取访问令牌并生成幂等键。
2. DNS/GSLB 选择最近且健康的边缘 PoP。
3. 客户端复用已有 TLS 连接，提交压缩后的 JSON 请求。
4. Anti-DDoS 检查网络流量，Bot 系统评估设备和行为。
5. WAF 校验协议和通用攻击特征，但不决定订单业务资格。
6. CDN 识别该 POST 不可缓存，把请求送到区域源站。
7. L7 LB 选择健康网关实例，覆盖不可信转发 Header。
8. 网关执行 Token 初检、接口限流和路由，再进入 BFF/业务服务。
9. 响应沿原连接返回；客户端根据业务结果决定展示或查询原幂等结果。

## 8. 静态内容示例：加载商品图片

1. HTML 引用带内容哈希的 URL：`/assets/product.a83f1.webp`。
2. 浏览器缓存若仍新鲜，完全不发网络请求。
3. 浏览器未命中时请求 CDN；CDN 节点命中则就近返回。
4. CDN 未命中时请求对象存储或静态源站，并进行请求合并。
5. 响应带长 TTL、`immutable`、正确 MIME 和跨域策略。
6. CDN 缓存副本，后续用户不再回源。

这种“URL 随内容变化”的模式比发布后全网 purge 更可靠，也更容易回滚。

## 9. 本章统一设计原则

1. **默认不信任客户端和公网。** 信任必须由受控代理和密码学凭证建立。
2. **尽量在靠近用户的位置结束无价值流量。** 但误杀必须可观察、可回滚。
3. **缓存公开、可复用、允许陈旧的内容。** 不用缓存替代业务一致性。
4. **所有队列、连接、Body、Header、超时和重试都有上限。**
5. **故障切换必须演练。** 配置了备用地址不等于能够在事故中切换。
6. **端到端衡量用户体验。** 源站健康不能证明所有地域用户都能访问。
7. **边缘配置也是代码。** 版本化、评审、灰度、测试和回滚。
