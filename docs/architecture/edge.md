# 客户端与边缘层：流量进入系统的第一站

边缘层位于用户和应用机房之间。它不理解“订单能否退款”，只关心如何把合法流量低延迟地送到健康入口，并尽量在靠近用户的位置挡住攻击、缓存静态内容、吸收突发流量。

## 1. 典型链路

```text
终端 → 递归 DNS → 权威 DNS / GSLB → CDN / Anti-DDoS / WAF
     → 公网 LB → API Gateway 集群
```

| 组件 | 职责 | 关键设计 |
|---|---|---|
| DNS/GSLB | 域名解析、地域和运营商调度、故障切流 | TTL、健康检查、DNS 污染与缓存 |
| CDN | 静态资源与可缓存响应就近分发 | Cache-Control、回源、刷新、版本化 URL |
| Anti-DDoS | 清洗大流量网络攻击 | 清洗阈值、源站隐藏、弹性带宽 |
| WAF | 阻断 SQL 注入、XSS、恶意 Bot 等应用攻击 | 规则误杀、学习模式、例外范围 |
| L4 LB | 基于 IP/端口分发 TCP/UDP | 连接数、源地址保持、跨区流量 |
| L7 LB | 基于 Host/Path/Header 分发 HTTP | TLS、HTTP/2/3、健康检查、超时 |

## 2. 这一层具体负责什么

### 域名与证书

按环境和信任边界规划域名，如 `api.example.com`、`admin.example.com`、`internal.example.com`。公网管理端不应只是换一个 Path；它通常需要独立域名、访问控制和审计。证书应自动签发、轮换并监控到期时间，私钥放在受控的密钥服务或负载均衡器中。

### 缓存与加速

带内容哈希的 JS、CSS、图片可设置长缓存；HTML 和用户相关 API 要谨慎。响应同时满足“公开、不同用户相同、允许陈旧”才适合 CDN 缓存。使用 `ETag`、`Last-Modified`、`Cache-Control` 明确语义，发布新资源用新 URL，避免全网强制刷新。

### 入口保护

限制请求体、Header 数量、URL 长度、连接速率和空闲时间；上传采用客户端直传对象存储的临时凭证，避免大文件穿过 Java 服务。WAF 规则先观察再阻断，高风险路径单独配置，且保留规则命中日志和申诉机制。

### 负载均衡与健康检查

存活检查只证明进程活着，就绪检查才说明实例能接流量。实例下线应先摘除流量，再等待在途请求结束。无状态 HTTP 服务优先避免会话粘滞；确有长连接时，要设计连接排空、重连退避和扩缩容影响。

## 3. 信任边界与真实 IP

`X-Forwarded-For` 可以被公网客户端伪造。只有受信代理才可以追加或重写转发头，应用应从可信代理链解析客户端 IP。边缘向内传递的用户、租户等身份头必须先删除外部同名头，再由可信组件写入；内部链路最好使用 mTLS 或签名防止伪造。

## 4. 失败、容量和观测

| 风险 | 防护与恢复 | 重点指标 |
|---|---|---|
| 单地域故障 | GSLB 切流、多地域预热、定期演练 | 健康探测、切换耗时 |
| 源站过载 | CDN 缓存、入口限速、连接排队 | 回源率、活跃连接、拒绝数 |
| WAF 误杀 | 灰度规则、按规则回滚、白名单带过期时间 | 命中率、误报率、状态码 |
| 证书过期 | 自动续期、双证书轮换、提前告警 | 剩余有效期、握手失败 |
| 跨区流量过大 | 就近路由、拓扑感知、容量预留 | 区域流量、延迟、带宽成本 |

边缘层的核心 SLI 包括 DNS 成功率与解析时延、TLS 握手错误、CDN 命中率与回源带宽、WAF 拦截量、LB 活跃连接、入口 4xx/5xx 和各地域 P50/P95/P99。

## 5. Java 团队的交界面

Java 应用需要正确处理代理协议、上传大小、连接超时和优雅停机，但不应在 Controller 内重复实现 WAF 或 CDN。Spring Boot 的 `/actuator/health/liveness` 与 `/readiness` 应区分；Tomcat/Netty 的连接、线程与请求体限制要和外层一致；应用返回的缓存头、CORS 和安全头要经过端到端验证。

## 6. 常见误区

- 把 CDN 当成数据一致的缓存数据库，忽略节点间失效延迟。
- 健康检查只访问 `/`，即使线程池耗尽仍持续接流量。
- 信任客户端传来的真实 IP 或身份 Header。
- 所有流量都跨可用区转发，得到高可用却付出额外延迟和成本。
- 只配置防护设备，不定义攻击期间的降级页面、沟通和恢复流程。
