# 工作负载身份、服务间信任与委托

微服务之间的网络位置不能证明身份。Pod、虚拟机、Serverless 函数、批任务和消息消费者都应有独立、短期、可验证的工作负载身份，并且每个下游仍执行自己的授权。

## 1. 服务请求的双重身份

![工作负载身份与服务间信任链](/architecture/security-workload-identity.svg)

服务 B 接到请求时通常要区分：

- **直接调用方**：哪个 workload 建立了连接，可由 mTLS/SPIFFE、云 IAM 或签名请求证明。
- **原始用户**：业务动作代表谁，来自受约束委托 Token。
- **调用链**：经过哪些服务，仅用于审计与策略条件，不能让任意上游伪造。

只传播用户 Token 会看不出哪个服务实际调用；只验证服务证书又会丢失用户资源边界。

## 2. 身份签发与轮换

每个 workload 使用专属 Service Account，平台根据部署身份签发数分钟/数小时有效证书或 Token。私钥不离开工作负载或代理；自动续期、旧证书重叠和过期告警必须在生产演练。

禁止所有服务共享一个 Kubernetes ServiceAccount、数据库账号或永久 Access Key。共享身份使最小权限、撤销和审计全部失效。

## 3. mTLS 的能力与边界

mTLS 同时提供链路加密和双方身份，但它只证明“持有该证书的工作负载”。授权仍需判断该服务能否调用具体 API、租户和动作。证书要验证信任域、SAN、用途、有效期和撤销/轮换，不按任意 CN 字符串授权。

Service Mesh 可自动发证和加密，但应用层仍需要用户委托与资源授权。Sidecar/代理策略和应用策略要避免互相假定对方已执行。

## 4. On-behalf-of 委托

![服务身份与用户委托的双主体模型](/architecture/security-delegation.svg)

委托 Token 应缩小 audience、Scope、资源、租户和有效期；下游不能把它当成可继续无限转发的用户原始 Token。管理员代理操作同时保留 `actor`、`subject`、原因、工单、认证强度和允许动作。

高风险场景使用 Token Exchange/受控委托服务，使每一跳获得面向目标服务的新 Token。不要由服务随意复制外部 Access Token 到日志、队列或几十个下游。

## 5. 异步消息与批任务

消息脱离原 HTTP 会话后，消费者身份来自当前 workload；消息中的用户/租户是业务上下文，不是对消费者的认证。消息必须有可信生产来源、Schema、完整性保护、重放/幂等策略和保留期限。

延迟任务不能长期携带即将过期的用户 Access Token。应保存受控业务授权事实或在执行时重新获取服务凭证并按当前策略校验。Dead Letter Queue 同样包含敏感上下文，要限制访问和保留。

## 6. 出站访问和第三方凭证

- 按服务限制可访问域名、IP、端口与协议，阻断云元数据和内网管理面。
- 第三方 API Key 按环境/服务隔离，通过 Secret Manager 注入并轮换。
- 回调/Webhook 校验签名、时间戳、nonce 和原始 Body，防止重放。
- 出站代理记录目标与结果但不记录凭证；TLS 验证不能因排障永久关闭。

## 7. 故障策略

身份签发端短暂故障时，已有短期证书可继续到期；续期在到期前抖动重试。授权或证书验证不确定时默认拒绝，不能降级为匿名全通。提前监控证书剩余有效期、签发失败和时钟偏差，避免全站同时过期。

## 8. 上线检查

- 每个 workload 是否有唯一身份和最小 API/数据权限？
- mTLS 是否验证 SAN/信任域，而不是“只要有证书就通过”？
- 下游能否同时识别直接调用服务和被代表用户？
- 委托是否限制 audience、Scope、租户、资源和传播深度？
- 消息/任务是否不依赖过期用户 Token，并能抵御伪造与重放？
- 证书轮换、签发故障和时钟异常是否演练过？
