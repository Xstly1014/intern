# 多租户隔离、数据安全与隐私生命周期

多租户安全不是给每张表补一个 `tenant_id`。租户边界要贯穿身份、查询、唯一约束、缓存、消息、搜索、对象存储、分析、备份、导出和运维工具；任何遗漏都可能形成跨租户泄露。

## 1. 隔离模型选择

![多租户隔离强度与成本](/architecture/security-tenant-isolation.svg)

| 模型 | 隔离 | 适用 | 主要代价 |
|---|---|---|---|
| 共享库共享表 | 逻辑 | 大量中小租户 | 每条路径必须带 tenant，爆炸半径大 |
| 共享实例独立 Schema | 中等 | 数量可控、合规有区分 | 迁移、连接与 Schema 管理 |
| 独立数据库 | 强 | 大客户、数据驻留 | 成本、连接池、版本编排 |
| 独立集群/账户 | 最强 | 高监管/高价值租户 | 运维与容量利用率 |

模型可按租户分层，但路由映射必须来自可信目录，不能由客户端传数据库名。

## 2. TenantContext 的来源与传播

tenant ID 来自经过认证的成员关系/会话，BFF 请求 Body 中的 tenant 只能作为“请求切换目标”，服务端再次验证成员关系。后台任务、消息和异步线程显式携带租户上下文；上下文缺失直接拒绝，不能默认落到公共租户。

管理员跨租户支持要使用专门代理流程：审批、限时、原因、工单、强 MFA、醒目标识和实时审计，不使用普通查询参数偷偷切换。

## 3. 数据访问防线

- Repository API 强制 tenant 参数或使用不可绕过的行级安全策略。
- 主键查询仍加 tenant 条件，防止可猜 ID 造成 IDOR。
- 唯一索引通常为 `(tenant_id, business_key)`，按真实全局唯一语义例外。
- Join、临时表、批处理、软删除恢复和迁移脚本同样限制租户。
- 数据库账户最小权限；管理连接与应用连接分离。

RLS 可提供额外防线，但 Session 变量/连接池复用必须正确清理，迁移和超级用户可能绕过，不能因此取消应用测试。

## 4. 非数据库边界

缓存 Key、锁、幂等 Key、限流桶、搜索文档、对象存储 Prefix、消息 Partition/Topic、指标维度和导出目录都需租户命名空间。缓存内容还要包含主体/权限变体，避免同租户内越权。

消息消费者从可信 envelope 获得 tenant，并验证生产者是否可代表该租户。DLQ、重放工具和数据修复脚本是高风险跨租户入口。

## 5. 数据生命周期

![敏感数据从采集到删除的安全生命周期](/architecture/security-data-lifecycle.svg)

1. **分类与最少采集**：公开、内部、敏感、受监管；没有明确用途就不收集。
2. **传输与存储**：TLS；磁盘/对象存储加密；高敏字段可信封加密或 Tokenization。
3. **使用**：按目的和最小字段授权，批量/导出更严格。
4. **共享**：第三方处理者、地域、用途、保留和删除责任有合同与技术限制。
5. **保留**：按业务/法规设置 TTL，不能“以后可能有用”永久保存。
6. **删除**：覆盖主库、索引、缓存、派生数据；备份按保留期自然过期并防恢复后复活。

## 6. 密钥与密码

密码使用 Argon2id、bcrypt 或 scrypt 等慢哈希，每条独立盐，参数可升级；不使用可逆加密或通用 SHA。应用层字段加密使用 DEK 加密数据、KMS 管理 KEK，密文保存 key version，轮换时支持渐进重加密。

密钥和数据不能存同一权限域。KMS 操作、解密量和失败要监控，高敏明文只在最短内存范围出现。

## 7. 日志、测试与分析数据

- 日志和 Trace 默认不采集 Body、Token、Cookie、证件、卡号和密码。
- 脱敏是字段级白名单，不靠正则事后碰运气。
- 非生产环境使用合成/不可逆脱敏数据，访问权限不因“测试”放宽。
- 分析平台使用目的限定、列权限、行过滤和小样本防重识别。
- 支持工单查询数据时记录操作者、理由、字段和结果数量。

## 8. 上线检查

- tenant 是否来自可信身份关系，缺失/冲突时默认拒绝？
- 主键、列表、Join、唯一索引和批处理是否都包含租户维度？
- 缓存、锁、搜索、对象、消息、导出和备份是否保持隔离？
- 数据是否有分类、用途、保留、删除和责任所有者？
- 高敏字段加密是否支持 key version、轮换和最小解密权限？
- 恢复旧备份后，已删除用户和撤销权限是否不会永久复活？
