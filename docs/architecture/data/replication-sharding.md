# 复制、读写分离、故障转移与分片

复制提高读取能力和恢复选项，但异步副本天然陈旧；分片扩展写入/容量，却把 Join、唯一约束、事务、迁移和运维复杂度推给应用。两者都必须从业务一致性需求出发。

## 1. 复制链路

![主库提交、复制日志与副本可见性](/architecture/data-replication-lag.svg)

主库提交后写 WAL/binlog，副本接收并重放。commit 成功只保证主库状态，不保证任意副本已可见。复制延迟由网络、重放能力、长事务、大 DDL 和热点写入影响。

## 2. 写后读一致性

![写后读在异步副本上的一致性策略](/architecture/data-read-after-write.svg)

方案按需求选择：关键路径读主；在短会话窗口粘主；写响应返回 LSN/GTID/version，副本达到位点后再读；或 UI 显示处理中并由事件更新。不能统一把所有 GET 路由副本后再责怪“偶发数据消失”。

授权、幂等结果、状态机下一步和金额等当前决策通常读主；列表、报表和可容忍陈旧内容可读副本。

## 3. 故障转移

故障检测、选主、提升副本、DNS/代理切换和应用重连都有时间。异步复制可能丢失尚未复制的已确认事务，RPO 不一定为 0。防止旧主恢复后双主写入，需要 fencing/隔离和明确拓扑控制面。

连接池在切换时可能产生重连风暴，使用退避/jitter、合理 DNS/连接寿命和容量预留。每季度演练而不是只信云控制台 SLA。

## 4. 分片时机

先证明单库瓶颈：数据/索引超容量、写吞吐、维护窗口、IO 或租户隔离确实不可解决。读压力优先索引、缓存、读副本；历史数据可归档/分区；不要因预测可能增长就过早分片。

## 5. 分片键

![分片键、路由与热点分布](/architecture/data-shard-routing.svg)

好分片键覆盖主访问路径、基数足够、分布均匀、稳定不变，并允许请求单分片完成。tenant ID 常适合 B2B，但超级租户会热点；order ID 均匀却可能不支持按用户查询。可使用层级路由、虚拟分片或大租户专属分片。

无分片键查询必须限制为管理/离线 fan-out，设置并发、超时、结果上限，不能让普通 API 扫全分片。

## 6. 全局能力变化

- 全局唯一 ID 在应用/专用服务生成；全局业务唯一需目录/归属分片或异步检测，不能靠各分片局部 UNIQUE。
- 跨分片事务尽量通过业务流程和幂等最终一致，避免分布式锁/2PC 成默认。
- 跨分片排序分页需要每分片 Top-K 合并和稳定游标，成本显著。
- Join 通过共置、投影或数据平台；不要在应用内无界嵌套查询。

## 7. 扩容与再均衡

使用逻辑/虚拟分片减少路由变更。迁移流程：复制历史 → 持续同步增量 → 校验 → 双读/影子读 → 切唯一写主 → 观察 → 清旧。任何时刻明确写入权威，避免无协议双写。

路由配置版本化并随请求/数据记录可追踪；迁移任务限速，不能抢占在线流量。

## 8. 上线检查

- 每类查询是否明确读主/副本及允许的最大陈旧？
- 写后读是否用粘主、位点/version 或处理中契约解决？
- 故障转移是否验证数据 RPO、旧主 fencing 和连接重建？
- 分片键是否覆盖主查询、避免热点并支持租户隔离？
- 全局唯一、分页、Join、事务和无 Key 查询是否有明确方案？
- 再均衡是否指定唯一写主、增量同步、校验、限速和回滚？
