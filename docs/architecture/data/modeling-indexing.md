# 关系建模、约束、索引与查询计划

关系数据库设计的重点是让权威事实可约束、可查询、可演进。索引不是“慢了就加”，而是为明确访问路径建立有写入和存储成本的数据结构。

## 1. 表与键设计

- 主键稳定、不可变；业务编号通常另设唯一键，避免业务规则变化影响引用。
- ID 方案权衡排序、索引局部性、跨节点生成和信息泄露；不迷信某一种全局 ID。
- tenant 表的主键查询和唯一约束包含租户维度，防跨租户与错误全局唯一。
- 金额用定点 decimal + currency，不用浮点；时间保存 Instant/UTC 与必要业务时区。
- 可空性表达真实三态；不要用空串、0、1970 时间冒充缺失。
- JSON 列适合演进较快的附属属性，不应逃避核心字段约束和查询设计。

## 2. 约束是最后防线

NOT NULL、CHECK、UNIQUE、外键（适合聚合内部）和条件更新把并发正确性下沉为原子保证。应用层先检查用于友好错误，数据库约束决定最终胜负，并映射为稳定业务冲突。

跨服务数据库不建外键；用事件、对账和状态机维护引用生命周期。

## 3. 复合索引

![复合索引匹配过滤与排序的方式](/architecture/data-composite-index.svg)

索引列顺序依据等值过滤、范围、排序和选择性综合设计。例如 `WHERE tenant_id=? AND status=? AND created_at<? ORDER BY created_at DESC LIMIT 50` 可考虑 `(tenant_id,status,created_at DESC,id)`。最左前缀、范围后的列利用、覆盖索引和回表需通过执行计划验证。

每个索引增加写放大、缓存占用和迁移时间。重复/包含索引定期清理，但先核对生产查询与约束用途。

## 4. 执行计划

![SQL 从条件到执行计划与实际行数](/architecture/data-query-plan.svg)

查看 estimated vs actual rows、访问类型、扫描行数、过滤比例、回表、排序/临时表、Join 顺序、锁等待与 IO。估算偏差可能来自统计信息陈旧、数据倾斜和相关列；不能只看到“用了索引”就结束。

在生产数据量级或脱敏副本验证。小测试表会让优化器选择完全不同计划。

## 5. 分页

浅页可 offset；深页 `OFFSET 100000` 仍需扫描/丢弃大量行且并发插入会漂移。游标分页使用稳定唯一排序，如 `(created_at,id)`，下一页条件与排序完全一致。游标签名/编码，包含过滤版本，不能只传一个可篡改时间。

分页契约定义快照一致性、重复/遗漏容忍和最大页大小。导出走异步任务/对象存储，不把全量分页塞进在线请求。

## 6. Join、反范式与大字段

同一所有权数据库内 Join 是正常能力，不必为“微服务”拒绝关系查询。跨上下文不做跨库事务 Join；建立投影或 API。

反范式用于已证明的读路径，记录来源与更新机制。大文本/BLOB 与高频核心行拆分，避免缓存和扫描放大；真正大文件放对象存储，数据库保存元数据与状态。

## 7. 慢查询治理

按总消耗（频次 × 单次成本）和 P99 排序，不只盯最慢一条。为 API 建查询预算：最大行数、扫描量、返回字节、statement timeout。临时加索引前判断是否是 N+1、错误分页、统计信息或锁问题。

## 8. 上线检查

- 表中 null、金额、时间、枚举和业务 ID 语义是否明确？
- 核心不变量是否有数据库约束而非仅应用先查？
- 每个关键查询是否有匹配过滤/排序的索引和真实执行计划？
- 索引写放大、空间和在线创建时间是否纳入容量？
- 深页是否使用稳定游标，导出是否脱离在线事务？
- 慢查询是否按总资源消耗、扫描、锁和计划偏差治理？
