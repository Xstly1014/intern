# 缓存、搜索、对象存储与派生数据

派生存储优化访问模式，但不拥有原始业务事实。设计时必须同时处理陈旧、重复、乱序、删除、权限变化、重建和依赖故障，而不是只画“数据库同步 Redis/ES”的箭头。

## 1. Cache-Aside

![Cache-Aside 读写、失效与竞态](/architecture/data-cache-aside.svg)

读：查缓存，未命中回权威库，按 TTL 写缓存。写：事务提交权威库，再删除/失效缓存；通常删除而非直接双写值。数据库提交与缓存失效不是原子操作，需接受短暂陈旧，或通过 Outbox/CDC 重试失效。

并发“旧读回填覆盖新写失效”可用短 TTL、版本化 Value/Key、延迟二次删除或事件版本判断。关键强一致决策直接读权威库。

## 2. 缓存风险控制

- Key 包含环境、Schema version、tenant、业务 ID 和权限变体。
- TTL 加 jitter 防同时过期；空值短缓存/入口校验防穿透。
- 热 Key 用请求合并 singleflight、本地两级缓存、预热或分片。
- 大 Value、无界 Key 和高频序列化会制造内存/网络放大。
- Redis 故障时限制回源并发，避免缓存雪崩压垮数据库。
- 监控命中率之外，还要看 load latency、eviction、hot key、回源率和数据年龄。

缓存故障不能降级为跨用户复用数据；权限和 tenant 安全优先于可用性。

## 3. 搜索索引

![权威数据库到搜索索引的版本化同步](/architecture/data-search-sync.svg)

使用 Outbox/CDC 生成索引文档，携带 entity ID、tenant、source version 和 Schema version。消费者只接受更高版本，抵御重复/乱序；删除使用 tombstone。索引别名支持新旧版本并行构建和原子切换。

搜索结果是候选集合：高风险读取可回源验证当前权限/状态。全量重建从一致快照 + 增量日志衔接，避免扫描期间丢变更。

## 4. 对象存储

![文件上传、扫描与授权下载流程](/architecture/data-object-lifecycle.svg)

服务生成随机对象 Key 和短时签名直传；客户端上传到隔离区；异步检测真实类型、病毒和大小；通过后更新元数据状态并移动/标记可用。下载前服务校验资源权限，返回短时签名 URL。

Bucket 默认私有，开启版本/生命周期、服务端加密和访问日志。数据库元数据与对象可能出现孤儿，定期对账清理；删除请求覆盖对象版本和 CDN 缓存。

## 5. 分析与只读投影

OLTP 变更通过 CDC/事件进入数仓或 ClickHouse，查询与生产主库资源隔离。投影记录 watermarks、失败分区和重建进度。报表的时区、币种、迟到事件、维度历史和数据修订必须有语义定义。

个人数据删除/保留也传播到分析和导出；“分析用途”不是无限复制敏感数据的理由。

## 6. 缓存是否值得

先优化查询与索引。缓存适合读多写少、允许一定陈旧、Key 稳定且 Value 可控的数据。低命中、强个性化、高写频或权限变体多时，缓存整体响应可能成本大于收益。

任何缓存上线前做容量估算：唯一 Key 数 × Value/元数据大小 × 副本 × 峰值/碎片余量。

## 7. 重建与回切

派生系统必须能从权威数据重建，并在重建期间双写/消费增量。验证文档数、版本 watermark、抽样内容和查询结果后通过别名/路由切换；保留旧版本回滚窗口。不能只能“删库重新跑，希望不漏”。

## 8. 上线检查

- 每个派生副本是否声明权威来源、允许陈旧、同步与全量重建？
- Cache-Aside 是否处理旧读回填、失效失败和回源雪崩？
- 缓存 Key 是否完整隔离 tenant、权限、locale 和 Schema 版本？
- 搜索同步是否用 source version 处理重复、乱序和删除？
- 对象是否隔离扫描、默认私有、下载重新授权并有孤儿对账？
- 删除/权限变更是否传播到缓存、搜索、分析、对象和 CDN？
