# 事务、MVCC、隔离级别与锁

事务不是给方法加 `@Transactional` 就完成。必须明确原子边界、隔离异常、锁范围、失败结果和重试条件，并避免长事务耗尽连接、阻塞清理和放大死锁。

## 1. ACID 与业务边界

本地事务覆盖必须共同成功/失败的数据变化，通常是一个聚合、幂等记录、Outbox 和必要审计。远程调用、Broker 确认和文件处理不在其中。跨服务一致性由 Saga/TCC/对账处理。

## 2. MVCC 直觉

![MVCC 快照、版本与可见性](/architecture/data-mvcc-visibility.svg)

MVCC 通过行版本/Undo 让读者看到符合快照的版本，减少读写互阻；写写冲突、唯一约束和部分范围操作仍需锁。长事务持有旧快照会阻止旧版本清理，导致 Undo/膨胀和复制压力。

不同数据库、不同隔离级别的快照时机和锁规则不同，必须以目标 MySQL/PostgreSQL 版本验证。

## 3. 隔离异常

![隔离级别与并发异常示意](/architecture/data-isolation-anomalies.svg)

| 异常 | 示例 | 常见控制 |
|---|---|---|
| 脏读 | 读到对方未提交值 | Read Committed 以上 |
| 不可重复读 | 同事务两次读到不同已提交值 | Repeatable Read/显式锁/版本 |
| 幻读 | 范围内新增/删除行 | 范围锁、Serializable 或约束重构 |
| 丢失更新 | 两方基于旧值覆盖 | 乐观版本、条件更新、锁 |
| 写偏差 | 两行各自合法但组合不变量破坏 | Serializable、聚合/约束重构、锁共同资源 |

隔离名称不能替代业务分析。先写并发交错，再选择约束、条件更新或隔离策略。

## 4. 乐观锁与悲观锁

乐观锁适合冲突低：读取 version，更新 `WHERE version=?`，0 行映射冲突/重读。悲观锁适合高冲突短事务：`SELECT ... FOR UPDATE`，固定加锁顺序、范围和超时。

锁内不得远程调用。批量锁按稳定顺序获取，减少死锁；死锁是数据库主动终止一个事务的恢复机制，应用只在幂等和预算内重试整个事务。

## 5. 条件更新和原子操作

库存扣减使用 `UPDATE ... SET available=available-? WHERE available>=?`，受影响行数决定成功。计数器、状态转换和租约也可用 Compare-And-Set。它通常比“先读→Java 判断→写”更可靠且锁范围小。

## 6. Spring 事务陷阱

- 代理自调用可能绕过 `@Transactional`。
- checked/自定义异常回滚规则需明确，不能捕获后静默提交。
- `REQUIRES_NEW` 额外占连接，外层大量并发可能把池耗尽。
- `readOnly=true` 不是安全只读保证，数据库账户/路由仍需控制。
- 异步线程不自动继承事务；不要把 Entity 带到另一个线程修改。
- 事务提交成功后响应断开意味着客户端未知，需幂等查询结果。

## 7. 死锁与长事务治理

采集死锁图、参与 SQL、锁对象和业务用例，不只自动重试。统一访问顺序、缩小扫描/事务、补索引和拆批是根治方法。监控 oldest transaction、lock wait、dead tuples/undo、连接使用时长。

后台迁移、报表和手工会话同样会制造长事务，要设置超时和 kill/playbook。

## 8. 上线检查

- 事务是否只覆盖必须原子的数据，且不包含远程/大计算？
- 每个核心不变量是否分析过并发交错和选用的原子机制？
- 乐观冲突、死锁和 statement timeout 是否映射为正确业务结果？
- 锁是否按固定顺序、命中索引、范围可控并有等待超时？
- 是否监控长事务对 MVCC 清理、复制和连接池的影响？
- Spring 传播、自调用、异常回滚和异步边界是否有集成测试？
