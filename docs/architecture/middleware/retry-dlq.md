# 重试、指数退避、延迟消息与死信治理

重试只适合预期会自行恢复的瞬时故障。格式错误、权限拒绝、业务不允许和不兼容 Schema 不会因多试几次变好；错误分类错误会让 Broker 变成持续攻击下游的放大器。

## 1. 失败分类

![消息失败分类与处理决策](/architecture/middleware-failure-routing.svg)

| 类别 | 示例 | 处理 |
|---|---|---|
| 瞬时 | 连接重置、短限流、临时主从切换 | 有界指数退避重试 |
| 业务等待 | 依赖事实尚未到、窗口未开启 | 明确延迟/状态等待，不忙重试 |
| 永久 | Schema/格式坏、权限拒绝、资源非法 | 直接隔离/DLQ |
| 未知结果 | 外部调用 timeout | 查状态或同幂等键重试 |
| 系统性 | 代码 Bug、配置错误、下游全挂 | 暂停消费/熔断，避免每条重试 |

## 2. 退避与预算

![指数退避、抖动与重试上限](/architecture/middleware-retry-timeline.svg)

延迟近似 `min(base × 2^attempt, maxDelay) + jitter`，同时限制最大次数、总年龄和业务过期时间。消息已经过期就进入明确终态，不再消耗资源。

立即内存重试 1～2 次只适合极短瞬时抖动；更长等待释放 Consumer 资源，使用重试 Topic、延迟队列或调度表。注意重试 Topic 会改变原分区顺序。

## 3. DLQ 不是垃圾桶

![DLQ 从隔离、修复到安全重放](/architecture/middleware-dlq-lifecycle.svg)

DLQ 保存原 eventId、来源、失败阶段、异常分类、尝试次数、首次/最后时间、Schema 和受控 Payload 引用。按错误码、生产者、版本和年龄告警；有 owner、处理 SLA 和容量/保留。

处理流程：诊断 → 修代码/配置/数据 → dry-run → 选择批次 → 限速重放 → 观察业务效果 → 关闭事件。重放不生成新 eventId，否则绕过去重。

## 4. Poison Pill 与分区阻塞

单条坏消息反复失败可阻塞分区。经过少量确定性尝试后隔离，记录 offset/key；若严格顺序不可越过，则暂停该 Partition 并升级人工处理。选择必须写入业务 SLO，不在现场临时决定。

反序列化失败可能发生在 Listener 之前，框架错误处理器也必须能提取原始记录并转 DLQ。

## 5. 重试风暴

当下游全挂，生产流量 + 多轮重试会成倍增长。使用 Consumer 并发限制、Retry Budget、断路/暂停、全局限流和恢复后渐进放量。不要让每个实例独立判断后同时冲击恢复中的下游。

## 6. 延迟消息与定时语义

延迟队列适合秒/分钟级业务触发，但不保证精确到毫秒。定义 not-before、过期、时钟来源、重复触发和取消语义。长周期任务更适合持久调度表/调度平台，可查询、修改和补跑。

订单超时关闭仍要在执行时检查当前状态；延迟消息只是触发器，不是“订单一定还未支付”的事实。

## 7. 安全与隐私

DLQ 和重试存储会延长 Payload 保留并扩大访问人员，按原数据等级加密、脱敏和权限控制。修复工具使用生产受审计身份，禁止把消息下载到个人电脑编辑后随意发回。

## 8. 上线检查

- 每个错误是否分瞬时、永久、未知和系统性，并有不同动作？
- 重试是否有指数退避、jitter、次数、总年龄和业务过期上限？
- DLQ 是否有 owner、SLA、容量、告警、诊断和限速重放工具？
- Poison Pill 是否不会无限阻塞主分区或无限循环？
- 下游全挂时是否能暂停/限流，恢复后是否渐进追赶？
- DLQ/重试中的敏感数据保留与访问是否受控？
